== Layering

Lapis Net separates a mandatory protocol core from an optional scoring
substrate and a fully pluggable application layer:

* *Protocol core* (mandatory for every participant): identity (secp256k1),
  content addressing, storage (Nabu/Bitswap), peer discovery (DHT),
  propagation (GossipSub), Lightning payments.
* *Scoring substrate* (optional): Veritas, Karma, Madli as network-wide
  reputation records in the DHT; Virtus/LTR as view-specific records bound to
  a browser vendor.
* *Application layer* (freely swappable per vendor): browser/view
  implementations, sorting, scoring interpretation, UI, ad policy.

The network functions even with zero scoring systems in use — Veritas,
Virtus, Karma, and Madli are tools for views, not a protocol requirement.

== Identity (V0.1.2)

The canonical Lapis Net identity is a **secp256k1 keypair** (`secp256k1-kmp`) — the same key type
that would back a Bitcoin wallet or Lightning channel in a later wave. There is no recovery
mechanism: losing the private key means losing the identity permanently, by design, analogous to
Bitcoin.

libp2p natively wants an **Ed25519** keypair for its peer ID. Since secp256k1 is the
real identity, each identity carries a second, Ed25519 keypair (Bouncy Castle,
`bcprov-jdk18on` — the same library jvm-libp2p itself depends on) used only for the libp2p peer
ID, plus a **dual-key binding**: the secp256k1 key signs a domain-separated digest of the Ed25519
public key, cryptographically proving "this libp2p peer ID belongs to this Lapis Net identity"
without making Ed25519 the canonical identity.

Domain separation (`net.lapisphilosophorum.lapisnet.core.crypto.domainSeparatedDigest`) is a
project-wide convention, not specific to identity binding: every distinct purpose that signs a
32-byte digest with a secp256k1 key (identity binding today; Veritas trust-edge grants from
V0.1.5) must use its own versioned ASCII tag, so a signature produced for one purpose can never be
confused with a signature for another purpose using the same key.

Identities persist to a fixed-layout binary keystore file (`KeystoreFileFormat`, one file per
label under `$LAPISNET_HOME/identity` or `~/.lapisnet/identity`), protected only by POSIX file
permissions (`0600` files, `0700` directory) — the same trust model `ssh-keygen` uses by default.
This is a deliberate, temporary tradeoff for an early prototype: passphrase-derived encryption at
rest is a documented follow-up that should land before this key custodies real funds (Lightning).
A user may hold several identities (pseudonyms) side by side, addressed by label — device-sync /
self-trust linking between a user's own pseudonyms is a later wave (see the project's Veritas
notes), not implemented here.

== Networking (V0.1.3)

The node's libp2p identity is derived directly from `DualKeyIdentity`'s Ed25519 keypair
(`deriveLibp2pPeerId()`): the raw 32-byte seed V0.1.2 already stores is exactly the byte layout
jvm-libp2p's key unmarshalling expects, so no adapter or re-encoding is needed. The `PeerId` is
derived from the *private* key (via its public key), never read from a separately-stored public
key, so a corrupted keystore can never desync the `PeerId` from what the node can actually sign
with.

`LapisNode` wraps a jvm-libp2p `Host` built from the production-tested combination the library's
own status table recommends: TCP transport, Noise secure channel, mplex stream muxer. mDNS
discovers LAN peers but never auto-dials them — jvm-libp2p's own `Discoverer` API is
discovery-only by design, and keeping discovery and connectivity independently observable makes
both easier to test. Bootstrap peers are the opposite case: dialing them on `start()` is the
whole point, done non-blockingly and non-fatally so an unreachable peer can never hang or fail
startup. No real bootstrap infrastructure exists yet — `BootstrapPeers.PLACEHOLDER` uses RFC 5737
documentation-range addresses, explicitly marked as a pre-deployment placeholder.

jvm-libp2p is not published to Maven Central; it ships across three mirrors (Cloudsmith, JitPack,
Consensys artifacts) that must all be declared as repositories, since its own transitive
dependencies (`java-multibase`, `noise-java`) are split across them.

GossipSub pub/sub and NAT traversal are explicitly out of scope for this wave; GossipSub lands in
V0.1.7 (see below), NAT traversal remains an open research item.

== Storage (V0.1.4)

`NabuStorage` (in `lapis-net-storage`) layers Nabu's DHT (Kademlia) and Bitswap protocols onto
the same `Host` a `LapisNode` already built and started in V0.1.3 (`LapisNode.host` is exposed,
read-only, specifically for this). Its API is domain-agnostic by design — `ByteArray`/`Cid` in
and out — so it can serve as the storage substrate for signed Veritas records (V0.1.5+) without
knowing anything about Veritas itself.

**Classpath collision with Nabu's own forked jvm-libp2p.** Nabu's `pom.xml` pins a transitive
dependency on `com.github.peergos:jvm-libp2p:0.18.0-ipv6-mdns-wildcard`, a Peergos-maintained fork
of the official `io.libp2p:jvm-libp2p` this project already depends on. The fork ships identical
Java package names (`io.libp2p.core.*`) but different bytecode for 361 of 829 shared classes
(verified by decompiling both jars). `lapis-net-storage/build.gradle.kts` excludes the fork and
forces Nabu to resolve against the official artifact instead — verified safe because Nabu's
`Bitswap`/`Kademlia` classes (and their engines) have zero compiled references to the
`io.libp2p.core.dsl.*` builder classes that actually differ between the two jars (only Nabu's own
unused `org.peergos.HostBuilder` touches those), confirmed both statically and by a real two-node
Bitswap put/get spike against the official jar. `NabuStorage` therefore always attaches to a
`Host` built via the official DSL (`LapisNode.create()`), never via Nabu's own `HostBuilder` or
`EmbeddedIpfs`.

**Access control: none yet, by design.** `NabuStorage.attach()` wires an always-allow
`BlockRequestAuthoriser` — any connected peer can fetch any block this node has stored, provided
or not, the standard Bitswap/IPFS trust model (CIDs are unguessable 256-bit content hashes; a peer
cannot induce this node to fetch-and-forward third-party content, since `get()`/`findProviders()`
are only called by this project's own local code, never in response to a remote request).
Per-caller/per-record access control is a Veritas-layer concern and lands in V0.1.5+, not here.

**DHT record-store bound.** Nabu's own `RamRecordStore` (used for IPNS-style key/value records)
is an uncapped `HashMap`, and its `KademliaEngine` hands any connected peer's signed `PUT_VALUE`
record straight into it with no other rate limit - reachable simply by wiring up Kademlia at all,
regardless of whether this project's own API ever publishes an IPNS record itself.
`lapis-net-storage`'s own `BoundedRecordStore` (LRU-capped, mirroring Nabu's own
`RamProviderStore`) is used instead to prevent unbounded remote-triggered heap growth.

**Known limitation: cross-node DHT provider discovery does not currently work.**
`NabuStorage.provide()`/`findProviders()` wrap Nabu's real `Kademlia.provideBlock`/
`findProviders` API correctly (verified via `javap` against the real jar), and the underlying
DHT routing-table bootstrap (`connectToDhtPeer`, wrapping `Kademlia.bootstrapRoutingTable`) is
verified working — a 3-node loopback chain reliably populates each node's routing table with its
explicitly-connected peer. However, the actual provider announcement/discovery round trip does
not: a standalone diagnostic spike (four isolated runs, outside the test suite, against real
loopback nodes) found that a `GET_PROVIDERS` RPC returns an empty provider list even via Nabu's
own trivial "I already have this block locally" auto-provide path in
`KademliaEngine.receiveRequest`'s `GET_PROVIDERS` case — i.e. this reproduces with zero
involvement of `provide()`/`ADD_PROVIDER` at all, so the fault is in the RPC/dial mechanism
`Kademlia` uses for both message types (`Kademlia.dialPeer`), not specific to provider
announcement. The failure is reproducible, not flaky (unlike V0.1.3's mDNS multicast issue,
which has a genuine external cause) — root cause not identified within this wave's practical
debugging budget; suspected candidates include an interaction between `/ipfs/` vs. `/p2p/`
peer-id multiaddr component naming (routing-table entries carry `/ipfs/`-form addresses) and
`dial()`'s peer-id validation, or a Nabu v0.8.0-specific issue. `lapis-net-storage`'s test suite
pins this with an explicit "KNOWN ISSUE" test
(`MultiNodeDhtProviderDiscoveryTest`) asserting the current (broken) empty result, so a future
fix shows up as a test failure prompting an update, rather than the regression going unnoticed.
What remains fully verified and usable for V0.1.5+: local put/get, and Bitswap fetch given an
explicit peer (the `TwoNodeBitswapDirectFetchTest` path) — i.e. `get(cid, peers = ...)` with a
peer set obtained by some other means (a future wave's own peer-list, GossipSub-announced peers,
etc.) is safe to build on; relying on `findProviders()` to return non-empty is not, until this is
root-caused.

== Trust: Veritas trust-edge grant (V0.1.5)

`VeritasGrant` (in `lapis-net-trust`) is the signed, versioned data model for a single Veritas
web-of-trust edge: a truster's secp256k1-signed statement of how much it trusts a target identity.
It is a pure data-model wave — network propagation (GossipSub) and persistence (Nabu) are
implemented in V0.1.7, below; the shortest-path aggregation algorithm that turns a graph of grants
into a trust score between two arbitrary identities is implemented in V0.1.6, below.

**Fixed-point trust value.** Trust is represented as `trustMicros: Int` in `0..1_000_000`, not as a
`Double`. A signed, cross-platform-verified structure cannot depend on floating-point arithmetic
being bit-identical across JVMs/architectures; a fixed-point integer sidesteps that class of bug
entirely. `trustFraction` (`trustMicros / 1_000_000.0`) exists only as a display-only convenience,
never as part of the signed or compared representation.

**Single target per grant.** Each `VeritasGrant` names exactly one `(truster, target)` pair, not a
batch of targets, because the Git-like backward-hash version chain (below) is intrinsically
per-pair: a grant's `previousGrantId` must unambiguously identify the one prior grant it supersedes
for that same truster/target combination.

**Git-like backward-hash version chain.** Each new grant optionally embeds the content hash
(`VeritasGrantCodec.contentId()`, plain SHA-256 over the full signed-and-signature-appended
encoding) of the grant it supersedes, as `previousGrantId`. The first grant in a chain (no
predecessor) is genesis, represented as a `null` `previousGrantId` with an explicit presence flag
bit in the wire encoding — not a sentinel all-zero hash. Revocation is not a distinct operation or
message type; it is simply a new grant with `trustMicros = 0` that links to its predecessor like
any other update. `VeritasGrantChain.validate()` checks an ordered list of grants forms a valid
chain (constant truster/target, first is genesis, every signature verifies, each grant's
`previousGrantId` matches its predecessor's `contentId()`) — purely in-memory, no I/O; fetching the
actual chain from storage is a V0.1.7 concern.

**Domain-separated signing.** The signed body is digested with
`domainSeparatedDigest("LapisNet:veritas-trust-edge:v1", body)` before signing — its own reserved,
versioned tag distinct from identity binding's `"LapisNet:identity-binding:v1"`, per this project's
domain-separation convention (see Identity above): a signature produced for one purpose can never
be confused with a signature for another purpose using the same key.

**Codec.** `VeritasGrantCodec` uses a sequential length-prefixed binary layout (magic, version,
flags, truster/target public keys, `trustMicros`, optional `previousGrantId`, length-prefixed
comment, length-prefixed occasion-reference CIDs, signature) rather than `KeystoreFileFormat`'s
fixed-offset layout, since several fields are variable-length. `decode()` is structural-only and
deliberately does **not** verify the signature — unlike `KeystoreFileFormat.decode()`, which must,
because a keystore has to be trustworthy just to load. A grant typically arrives from an untrusted
peer over the network, so callers must explicitly call `VeritasGrant.verify()` (or the overload
taking an expected truster) before trusting a decoded grant.

**Security fix: secp256k1 public-key curve validation.** Independent security review for this wave
found that `Secp256k1PublicKey` (in `lapis-net-identity`, present since V0.1.2) validated only that
its input was 33 bytes long, never that those bytes actually encode a point on the secp256k1
curve. The native `Secp256k1.verify()` call throws an uncaught exception on a curve-invalid public
key rather than returning `false`, and does so before any signature check — no valid signature
knowledge is needed to trigger it. This had gone unnoticed through V0.1.2–V0.1.4 because nothing
until this wave constructed a `Secp256k1PublicKey` directly from untrusted, decoded bytes;
`VeritasGrantCodec.decode()` is the first code path that does, making this a real remote-DoS vector
once grants start arriving from peers (V0.1.7). Fixed by validating via `Secp256k1.pubkeyParse()`
in the constructor, converting any native failure into a clean `IllegalArgumentException`; the fix
applies project-wide, since the class is shared. `VeritasGrantCodec.decode()` was also hardened to
reject non-zero reserved flag bits, so tampered bits can no longer silently round-trip as an equal
grant.

== Trust: transitive path selection (V0.1.6)

`TrustGraph` and `TrustPathFinder` (in `lapis-net-trust`) compute a transitive trust score and
winning path between a source and a target identity, over a graph of `VeritasGrant`-derived edges.
This wave is pure algorithm: it consumes an already-resolved edge set (exactly one latest grant per
`(truster, target)` pair) and does not itself fetch grants from storage or resolve a grant's
backward-hash version chain to its latest entry — both are implemented in V0.1.7, below.

**Selection rule: shortest path first, then lexicographic tiebreak — not maximum product.** Trust
along a path is the product of its edge weights, but when multiple shortest (fewest-hop) paths
exist, the winner is not the one with the highest product; it is the one whose hop-weight sequence,
compared from the source outward, is lexicographically greatest (highest first hop wins; ties are
broken by the second hop, then the third, and so on). This models "the closer a person is to me,
the better I can judge them" — a strong nearby relationship outweighs a clever construction of
distant ones, and it is also manipulation-resistant: an attacker cannot inflate transitive trust by
stacking high weights far out in the graph, since only the near edges are ever decisive. The
project's canonical worked example (Odin → Frigg/Thor/Nanna → Freya, where the highest-product path
via Nanna does *not* win because its first hop is weaker) is reproduced verbatim as a binding test
fixture. Self-trust (`source == target`) is axiomatic (`1.0`); no path is `null` (default distrust,
`0`); a zero-trust edge is a real hop that can legitimately be part of, and even win, the shortest
path — there is no fallback to a longer, higher-trust alternative, matching the spec's explicit
single-winner, no-aggregation design for V0.1.

**Fixed-point score, `Long` accumulator.** The path score is computed as `trustMicros: Int` in the
same fixed-point domain as `VeritasGrant.trustMicros`, via a `Long` intermediate accumulator
(`acc = acc * weight / MAX_TRUST_MICROS` at each hop) — two `Int` values up to `1_000_000` multiply
to roughly `10^12`, well past `Int.MAX_VALUE`, so the accumulator must widen even though the final
result always fits back into an `Int`.

**BFS with predecessor pointers, not eager path copies.** Finding "shortest path" means fewest
hops, not lowest weighted distance — this is plain level-synchronous BFS, not Dijkstra. The
algorithm's first implementation stored a full copy of the path-so-far (node list + weight list) at
every node reached during the traversal; on a simple linear chain of `N` nodes this cost `O(N^2)`
time and memory for a single query, and since Veritas grants are free to issue and self-signable in
bulk, an attacker needed no cooperation from anyone else to construct such a chain — a real
remote-DoS vector for the moment gossiped/stored grant data starts feeding real queries (V0.1.7).
The fix replaces the eager copy with a predecessor-pointer scheme: each node stores only a pointer
to its winning predecessor plus the single edge weight into it (`O(1)` per node), and the winning
path is reconstructed exactly once, by walking predecessor pointers backward from the target, only
after BFS finds it. The lexicographic tiebreak (needed when multiple predecessors reach the same
node at the same BFS depth) is implemented as a pair of small recursive comparators that walk
already-finalized predecessor chains, comparing the earliest (most significant) hop first with
early exit on the first difference, rather than comparing pre-built arrays.

**Constant-factor hardening.** A follow-up independent security audit found that while the
predecessor-pointer redesign is asymptotically correct (`O(edges * MAX_HOP_DEPTH)`, confirmed by an
independent hand-trace), the constant factor at the original defense-in-depth caps
(`MAX_NODES = 50_000`, `MAX_EDGES = 200_000`) was not negligible: an adversarial graph where every
edge shares the same weight forces every lexicographic comparison to recurse through the full
predecessor chain before resolving (via a node-public-key-bytes tiebreak) instead of short-
circuiting on the first differing hop — costing several hundred milliseconds per query at those
caps, cheaply reachable since the attacker only needs free, self-signed grants. Two changes
resolved this: `Secp256k1PublicKey.hashCode()` (in `lapis-net-identity`) is now cached at
construction rather than recomputing a 33-byte content hash on every call — safe because the class
is immutable, and a meaningful win since every recursive predecessor-chain comparison hits it via
`HashMap` lookups; and the caps were tightened to `TrustGraph.MAX_NODES = 8_000`,
`TrustGraph.MAX_EDGES = 32_000` (`TrustPathFinder.MAX_HOP_DEPTH` stayed at `20`, itself independently
justified by trust decay: even a generous uniform `0.9` weight per hop decays to `0.9^20 ≈ 0.12` by
that depth, so longer paths are already close to meaningless as trust signals). Re-measured against
the worst adversarial construction found across two independent audit rounds — a tie-heavy graph
shifted to the maximum recursion depth the hop cap allows, not just concentrated at the first two
hops — worst-case cost at the new caps is roughly 35-50ms, an order of magnitude better than at the
original caps and comfortably within the caps' own generous-for-personal-scale headroom (Dunbar's
number is roughly 150; 8,000 nodes is far beyond any realistic personal web-of-trust).

This wave went through three rounds of independent review/security audit before landing — the
correctness of the BFS/tiebreak algorithm itself was hand-traced and approved in the first round and
never needed to change again; both follow-up rounds addressed resource-exhaustion cost at scale, not
correctness.

== Trust: propagation and persistence (V0.1.7)

`GossipPubSub` (in `lapis-net-networking`) and `VeritasGossip`/`VeritasGrantIndex`/
`VeritasGrantResolver` (in `lapis-net-trust`) close the loop V0.1.3-V0.1.6 left open: a node can now
announce a locally-created `VeritasGrant` to its peers over a dedicated GossipSub topic, receive and
validate grants announced by others, persist them into `NabuStorage`, and resolve the "latest grant
per `(truster, target)` pair" edge set that `TrustGraph.fromGrants()` expects.

**Layering.** `GossipPubSub` is domain-agnostic (raw topic strings, `ByteArray` in/out) and lives in
`lapis-net-networking`, layered onto an already-`start()`-ed `LapisNode`'s `Host` exactly the way
`NabuStorage` layers Bitswap/Kademlia onto the same `Host` in V0.1.4. `VeritasGossip` is the
Veritas-specific wiring on top: topic naming, structural decode, signature verification, and the
persistence/resolution logic. `lapis-net-trust` gained a new `api(project(":lapis-net-storage"))`
dependency this wave, since `NabuStorage` now appears directly in `VeritasGossip`'s public factory
signature.

**Two separate signature layers that must never be confused.** GossipSub has its own message-layer
authentication (the `from`/`seqno`/`signature` RPC fields), signed with the node's libp2p Ed25519
identity key (`Host.privKey`) — this is entirely separate from a `VeritasGrant`'s secp256k1 truster
signature, and `GossipPubSub` never touches the latter.

**Full grant bytes are published, not a CID pointer.** A `VeritasGrant`'s encoded size
(`VeritasGrantCodec.MAX_BODY_SIZE` plus a 64-byte signature) is tiny relative to any reasonable
gossip message-size ceiling, and — decisively — `NabuStorage`'s documented V0.1.4 known limitation
is that cross-node DHT provider discovery (`findProviders()`) does not work: a node receiving only a
bare CID over gossip would have no reliable way to fetch the actual content. Publishing full bytes
sidesteps that broken discovery path entirely.

**The GossipSub validator gates both structural and cryptographic acceptance in one step.**
`VeritasGossip.onGossipMessage()` decodes (`VeritasGrantCodec.decode()`), then verifies
(`VeritasGrant.verify()`), before any side effect — deliberately not split into "validate then
separately accept", since GossipSub's own re-propagation to the rest of the mesh is gated purely by
the validator's returned `ValidationResult`; deferring signature verification to a later step would
mean every relaying node re-gossips signature-invalid garbage before individually declining to act
on it.

**Latest-grant-per-pair resolution.** `VeritasGrantResolver.resolveLatest()` collapses a (possibly
forked, possibly byzantine) set of candidate grants for one `(truster, target)` pair down to a
single winner: only signature-valid candidates are considered; every valid genesis grant is a root;
an iterative depth-first walk (explicit stack, not recursion, to avoid stack-overflow risk at
`MAX_CHAIN_DEPTH = 4_096`) follows the backward-hash chain forward from each root, tracking a
visited set to guard against (cryptographically infeasible, but defended anyway) cycles; the winner
among all resulting tip candidates is the one at the greatest depth, tied-broken by
lexicographically-greatest content-id bytes. This tiebreak is deliberately receipt-order-independent
— it depends only on the final candidate set, never on the order candidates arrived via gossip — so
two nodes that eventually observe the same grants via differently-ordered deliveries converge on the
identical resolved graph.

**Known, deliberately accepted gaps** (matching this project's established practice of documenting
limitations rather than silently shipping them):

* The in-memory `VeritasGrantIndex` is never rebuilt by scanning Nabu's local blockstore at startup
  — `NabuStorage` has no "enumerate local CIDs" primitive. A restarted node starts with an empty
  index regardless of what it durably persisted in a previous run.
* A node joining after a grant's gossip window has passed has no backfill path — gossip carries full
  bytes but only propagates live, never historically. This is best-effort convergence, not
  always-eventually-consistent.
* Unbounded message *rate* from a single peer is not defended against at the application layer —
  deferred to jvm-libp2p's own GossipSub mesh-control-message rate limiting.

**This wave went through four rounds of independent review/security audit — the most of any wave so
far** (V0.1.6's three-round precedent was the previous high-water mark), because it's the first wave
where `VeritasGrant`s actually arrive from untrusted network peers rather than being constructed
locally for tests:

* *Critical:* `VeritasGossip.onGossipMessage()` called `VeritasGrant.verify()` unguarded. A
  structurally-right-length but cryptographically degenerate 64-byte signature (e.g. all-`0xFF`
  bytes, or an `r` component at/above the secp256k1 curve order) makes the native
  `Secp256k1.verify()` call throw an uncaught exception instead of returning `false` — the same bug
  class as V0.1.5's `Secp256k1PublicKey` curve-validation fix, but that fix only ever hardened
  public-key *construction*, never signature *verification*. Live-repro'd against the real
  `secp256k1-kmp-jvm` jar. Fixed at the shared root cause — `Secp256k1PublicKey.verify()` (in
  `lapis-net-identity`) now wraps the native call in a catch-all, converting any failure into a
  clean `false` — rather than patching just the new call site, so every current and future caller is
  safe by construction.
* *Critical:* `NabuStorage.put()` ran unconditionally for every signature-valid grant, and
  `VeritasGrantIndex.add()`'s return value was discarded — meaning the index's capacity cap bounded
  neither disk writes nor GossipSub re-propagation (`ValidationResult.Valid` is what triggers every
  relaying node's own mesh-wide re-broadcast). Since Veritas grants cost nothing to issue, a cheap
  attacker could force unbounded, network-amplified disk growth across every node in the mesh.
* *Major:* `GossipPubSub.attach()` left GossipSub's own RPC-frame-shape limits
  (`maxPublishedMessages` etc.) at jvm-libp2p's actual default of "no limit" (confirmed by
  decompiling the real jar) — one peer could pack thousands of distinct grants into a single RPC
  frame, forcing unbounded decode+verify work per frame. Fixed by explicitly bounding
  `maxPublishedMessages`/`maxSubscriptions` via `GossipParamsBuilder`.
* *Major:* `VeritasGrantIndex` had no eviction once full — a cheap attacker filling the shared cap
  could permanently prevent a node from ever tracking new legitimate grants, including a legitimate
  revocation of a compromised or malicious truster (per the domain model, revocation is just a new
  grant with `trustMicros = 0`, not a distinct operation). Fixed with LRU-style eviction, mirroring
  `lapis-net-storage`'s `BoundedRecordStore` pattern.
* *The most interesting finding:* fixing the eviction gap (above) silently reopened the disk-growth
  gap (above it) — once the index stopped hard-rejecting at capacity and started evicting instead,
  its `canAccept()` check no longer had any "index is full" case left to report, so gating
  `storage.put()` on it alone stopped bounding persistence at all. This was caught independently by
  two review agents via two different methods (a hand-trace and an executed repro with `maxTracked =
  2` and 10 distinct grants, all 10 of which landed on disk) converging on the identical finding in
  the same round. Resolved by decoupling the two concerns: the in-memory trust-view index
  (`grantsByContentId`/`grantsByPair`, read exclusively by `TrustGraph`/`currentGrants()`) keeps its
  evicting policy — never permanently locking out legitimate updates is the correct policy for a live
  view — while a new, separate, non-evicting, hard-capped structure (`persistedContentIds`, gated via
  `VeritasGrantIndex.tryReservePersistence()`, cap `MAX_PERSISTED_GRANTS = 64_000`) independently
  bounds whether a durable disk copy gets written. A grant that clears the persistence cap still gets
  indexed and still propagates — this node's own disk budget has no bearing on trust-view correctness
  or mesh-wide convergence, since neither ever reads from disk.

== CLI / multi-node demo (V0.1.8)

`lapis-net-cli`'s `main()` runs two demos in sequence: `runIdentityAndStorageDemo()` (V0.1.4-era
single-node identity + local storage round-trip, unchanged in substance, only extracted into its own
function this wave) and `runMultiNodeTrustPropagationDemo()` — new this wave, the first piece of code
in the repository that exercises the full V0.1.2-V0.1.7 stack together in one running scenario rather
than each module's own isolated test suite.

**Topology.** Three in-process nodes are chained `A<->B<->C`; `A` and `C` are never directly dialed,
deliberately mirroring `ThreeNodeVeritasGossipRelayTest`'s topology (chosen there, and reused here,
specifically because it proves GossipSub *relay* through an intermediate node, not just direct
delivery). Node `A` issues a Veritas trust-edge grant to node `C`'s own secp256k1 identity; the grant
is gossiped through relay node `B` and resolved into a trust score on node `C`.

**Network hops vs. trust-graph hops.** The demo explicitly narrates a distinction that is easy to
conflate: the grant travels the network as 2 hops (`A->B->C`), but `TrustPathFinder`'s resolved trust
path is 1 hop (`A->C` directly) — the grant is a single signed `A->C` statement, and `B` only relays
the bytes; it never becomes a node in the trust graph itself. The test suite (below) pins this
distinction with an exact assertion (`hops shouldBe 1`), not just "didn't throw".

**Warm-up phase.** Before the real grant-announce round, the demo runs a disposable warm-up topic
where every message always validates `Valid`, so retried payloads keep getting relayed by `B`
regardless of duplicate content — unlike the real Veritas topic's content-addressed dedup. This is
not optional: skipping it makes the 3-node case flaky in a way a 2-node case never is, because grant
dedup means a lost mesh-formation race is not recoverable by simply retrying identical grant bytes.
See `ThreeNodeVeritasGossipRelayTest`'s class doc comment for the full mechanism this mirrors.

**Bounded polling throughout, no fixed sleeps.** Both the warm-up phase and the grant-propagation
phase poll against a single deadline computed once at function entry and shared across both phases,
rather than each phase independently claiming its own full timeout budget.

**Test coverage.** `MultiNodeTrustPropagationDemoTest` calls `runMultiNodeTrustPropagationDemo()`
directly (bypassing `main()`'s console output) and asserts real correctness: exact grant convergence
across all three nodes' local views (`grantsOnA`/`grantsOnB`/`grantsOnC` each equal to the single
issued grant), the exact resolved `scoreMicros`, and the `hops shouldBe 1` distinction above.

**Review note on resource cleanup.** The nine `veritas*/pubsub*/storage*.stop()` calls run
sequentially just before `return result`, not duplicated in the `finally` block alongside the three
`node.stop()` calls. This was flagged and traced through review: all three types' `stop()` are
no-ops or purely in-memory today, and `node.stop()` (already in `finally`) unconditionally tears down
the actual bound `Host`/socket regardless of whether the nine calls are reached — so no real leak
exists on an early-exception path, and a nullable-`var` restructuring to defensively cover a already
provably-harmless path was deliberately not made.

This wave's review and security audit both approved with only this one minor/cosmetic finding — no
fix round was needed beyond the explanatory comment described above.

With V0.1.8 landed, the V0.1 milestone (identity, node bootstrap, Nabu storage, Veritas trust model,
trust path-selection, gossip propagation + persistence, and now a demonstrated end-to-end scenario)
is complete.

== Virtus: LTR core (V0.2.1)

`lapis-net-virtus` is the second of the four scoring dimensions (Layering above), and the first
milestone of V0.2. Its data model, `LtrRecord` — a payer-signed claim binding an on-chain OP_RETURN
Bitcoin payment to a `(cid, viewId)` pair — is deliberately a **sibling** to `lapis-net-trust`'s
`VeritasGrant`, not built on top of it: the module has no dependency on `lapis-net-trust`, and the
two are structurally different in the one way that matters most. A Veritas grant forms a
per-`(truster, target)` version chain that gets resolved to one latest edge; an LTR record for the
same `(cid, viewId)` **accumulates independently and is never resolved to one** — every boost is
kept, per the fach-spec's accumulation rule (multiple LTR payments for the same content/view are
independent records, not a merged running total).

**GossipSub propagation, Nabu persistence, and the two-cap index are carried over directly, not
re-derived.** `LtrGossip`/`LtrRecordIndex` reuse the exact three-step validator structure and
two-cap eviction/persistence pattern that took `lapis-net-trust`'s V0.1.7 four security-review
rounds to land on: `canAccept()` (an evicting, LRU-style tracking cap) gates dedup, a separate,
non-evicting `tryReservePersistence()` independently bounds disk writes, and reaching the
persistence cap does **not** decline the underlying gossip message — a record still gets indexed
into the live trust/economy view even when it can't be persisted to disk. Both this wave's
independent code review and its independent security audit specifically verified the carried-over
pattern reproduces the *hardened* (post-fix) Veritas behavior, not an earlier, since-corrected
shape — this is the primary reason `lapis-net-virtus` shipped with no critical/major security
findings in its first review round.

**The `nonce` field is not in the fach-spec's literal schema — an engineering addition, documented
as such.** ECDSA signing here is deterministic (RFC 6979): the same digest signed with the same key
always produces the same signature. Because accumulation means two genuinely independent boosts —
same payer, same `cid`/`viewId`/amount, landing in the same wall-clock second — are both supposed to
be kept, they would otherwise encode to byte-identical records and the second would be silently
discarded by content-id dedup as if it were merely a gossip replay of the first, permanently losing
one real boost's economic weight. An 8-byte `SecureRandom` nonce, generated fresh per `create()`
call and included inside the signed body (so it cannot be stripped or replaced without invalidating
the signature), closes this gap.

**Decay math is `Double`, deliberately unlike Veritas's fixed-point `trustMicros` convention.**
`LtrWeightCalculator.decayedWeightMsat()` implements the fach-spec's formula exactly:
`initial_value × 0.9^(hours_since_timestamp / 24)`. This value is never signed, never part of any
canonical encoded bytes, and never compared for cross-node consensus — it is a local, read-time-only
ranking heuristic each view computes independently for its own sort order, so `Double`/`Math.pow`'s
imprecision is the right tradeoff for a fractional exponent with no clean fixed-point form. A
future-timestamped record (clock skew, malice, or a bug) has its elapsed-hours clamped to zero
rather than going negative — without this clamp, a negative exponent would push the decay factor
*above* 1.0, letting a record's weight exceed its own face value and breaking the "decay is
monotonically non-increasing" invariant the fach-spec's own worked table assumes.
`LtrWeightCalculator.totalInvestedMsat()`, by contrast, stays exact (`Long`, `Math.addExact`-guarded,
throws `ArithmeticException` on overflow rather than silently wrapping) because it *is* a real
accounting figure, not a ranking heuristic — unlike the decayed weight, it is meant to answer "how
many sats have actually flowed to this view," where floating-point imprecision would be wrong.

**Known, deliberately accepted gap: no live on-chain verification.** `OnChainProof` validates only
that a claimed Bitcoin txid is a structurally plausible 32-byte hash and that its output index is a
non-negative value within a defensive sanity cap — it does not verify that a transaction with that
txid exists on-chain, that its output really pays the claimed view's address, or that its
`OP_RETURN` output actually encodes the claimed `cid`/`viewId` pair. This has a sharper consequence
here than the analogous gap does for Veritas: because the fach-spec's whole anti-Sybil claim for LTR
rests on "every boost costs real sats," and this wave cannot check that a payment is real, an
`LtrRecord` today is exactly as cheap to fabricate as a `VeritasGrant` — a malicious node can claim
an arbitrary msat amount was paid, at zero cost, and any view that honors `LtrGossip.currentWeight()`
or `LtrWeightCalculator.totalInvestedMsat()` today is trivially manipulable by anyone willing to run
this code. Closing this gap is real future work (a chain-verification sub-wave, or reusing whatever
SPV/full-node integration the Lightning wave, V0.6, ends up needing anyway) — until then, a
browser/view that wants economically-trustworthy sorting must run its own verification layer on top
of `LtrGossip.currentRecords()`, or knowingly accept this wave's weaker guarantee (cryptographic
attribution to a claimed payer, no proof the payer actually paid).

**No Bitcoin transaction library dependency was added this wave.** `fr.acinq.bitcoin:bitcoin-kmp-jvm`
exists on Maven Central and its POM pins the exact `secp256k1-kmp-jvm` version already used by this
project, so it is a safe candidate for whichever future wave actually constructs, signs, or verifies
real Bitcoin transaction bytes — nothing in V0.2.1 parses or constructs transaction bytes, so adding
the dependency now would be unused weight.

== Minimal-Browser MVP (V0.2.2)

`lapis-net-browser` is the first real Lapis Net client — the V0.2 milestone's second and final wave.
It embeds a real node (identity, GossipSub, Nabu storage, Veritas, Virtus) in the same JVM process as
a small local HTTP server, and serves a hand-written, framework-free HTML/CSS/vanilla-JS page that
shows a timeline of content annotated with Veritas credibility and Virtus/LTR-weighted sort order.

**Tech-stack decision: an embedded local Ktor server, not Compose Multiplatform or KVision/Kilua.**
Lapis Net's sibling federated projects (Lapis Cloud, Pepela Portal) use a Ktor-server-plus-KVision-
web-client split for a real architectural reason those projects have and this one doesn't: a genuine
client/server separation. A `LapisNode` already *is* the full network participant — there is no
separate backend to RPC into. Compose Multiplatform Desktop would be the more architecturally
"correct" long-term fit (direct in-process function calls, no HTTP layer at all), but it is a heavy
new toolchain this project doesn't need yet to answer this wave's actual question ("can a small
pilot group see Veritas/Virtus data and use it"). A tiny embedded Ktor server plus a `fetch()`-only
static page — no JS build toolchain, no npm, no bundler — is the smallest new dependency surface
that gets a pilot test in front of users soonest, without foreclosing a future Compose Desktop (or
web) rewrite once real pilot feedback exists.

**`PostAnnouncement`: small, deliberately temporary content-discovery scaffolding, not a protocol
commitment.** Before any timeline can exist, the browser needs to know which content is even a
candidate — and no signed author-to-content binding exists anywhere else in this codebase.
`NabuStorage` is anonymous, content-addressed byte storage; `VeritasGrant` is a trust edge, not
content; `LtrRecord` only ever *references* an already-existing CID, never creates one. The
mechanism meant to solve "how does content enter the candidate pool" is Karma (`Karma → Veritas →
Virtus`, per `docs/requirements.adoc`) — not built yet (V0.3). `PostAnnouncement`, scoped to
`lapis-net-browser` (application layer, not protocol core or scoring substrate), plays that role
just well enough for one browser vendor's MVP: a small, signed struct mirroring `LtrRecord`'s
hardened codec/gossip/index shape exactly, explicitly documented as scaffolding likely to be deleted
wholesale once V0.3's real Karma lands, not a commitment other vendors must adopt.

**One deliberate structural deviation from `LtrRecord`'s precedent: the post body bytes travel with
the announcement, not just a `Cid` reference.** `NabuStorage`'s own documented V0.1.4 known
limitation is that cross-node DHT provider discovery (`findProviders()`) does not work — a
`PostAnnouncement` that only carried a `Cid` would hit that same broken discovery path the moment a
second node tries to render someone else's post. Embedding `bodyBytes` directly and having every
node — sender and every receiver — independently derive its own `Cid` via `storage.put(bodyBytes)`
sidesteps the gap entirely: content-addressing guarantees identical bytes hash to the identical
`Cid` on every node, with no cross-node discovery step needed at all.

**The `Credibility.NO_PATH` vs. `RESOLVED(0)` distinction is the single most safety-critical piece
of logic in this module.** A brand-new pilot user with no trust relationships must see their whole
timeline as "unrated," never as "everyone is maximally distrusted" — collapsing this distinction
(treating `TrustPathFinder.findPath() == null` the same as a resolved path with score 0) would
directly contradict Veritas's own documented bootstrap design (a newcomer sees the unfiltered
stream, not something that *looks* like universal distrust). `TimelineBuilder`'s credibility filter
only ever applies to a `RESOLVED` score below threshold; a `NO_PATH` candidate is never filtered.

**Review findings this wave — one genuinely critical.** Independent security review found
`PostAnnouncementGossip` wrote every gossiped post's body bytes to storage completely uncapped — no
persistence cap gated this write at all, unlike `LtrRecordIndex`'s hardened two-cap pattern this
module otherwise mirrors faithfully. Since a cheap, self-signed, freshly-nonced `PostAnnouncement`
always passes content-id dedup, and every relaying node independently repeated the same unconditional
write, this reproduced V0.1.7's fixed "network-amplified disk growth" bug class in a worse form (no
cap at all, versus "a cap exists but might be reached"). Fixed with an independent, `Cid`-keyed,
non-evicting `MAX_PERSISTED_BODIES` cap (`PostAnnouncementIndex.tryReserveBodyPersistence()`) gating
the body-bytes write at both the `announce()` and `onGossipMessage()` call sites — reaching the cap
does not decline the announcement itself, only its local body cache, matching this codebase's
established "declining persistence never declines the message" pattern. A parallel major finding —
uncaught storage-fault exceptions leaked full local filesystem paths in HTTP 500 responses,
live-reproduced against both `GET /api/timeline` and `POST /api/posts` — was fixed with a generic
Ktor `StatusPages` handler (defense-in-depth against any future uncaught exception in any route)
plus a safe fallback on the timeline's per-entry storage lookup. Both fixes were independently
re-verified in a second review round, including live re-reproduction of the path-leak scenario
against the fix.

**Known, deliberately accepted gaps:**

* No LTR/Virtus record *authoring* in this MVP — read-only display only. Real LTR spending needs
  actual Bitcoin/Lightning payment (V0.6), and V0.2.1's `OnChainProof` has zero live chain
  verification, so an in-app "spend sats" button today would either lie about a real payment or
  require users to hand-construct a transaction outside the app — both bad pilot UX. Practical
  consequence: Virtus sorting is visually inert (everything at zero weight, sorted by recency)
  during the pilot unless an operator manually seeds demo `LtrRecord`s outside the HTTP surface.
* No "confirm" mechanism (multi-confirmer credibility) — no protocol data model for it exists yet.
  `Credibility`'s `confirmers` parameter is forward-compatible scaffolding, always empty this wave.
* No bootstrap infrastructure exists yet (V0.4) — `POST /api/peers/connect` (manual multiaddr
  exchange, mirroring Veritas's own public-key-exchange convention) is necessary MVP scope, not an
  extra: without it, pilot nodes on different networks could never find each other at all.
* No rate limiting on the signing routes (`POST /api/posts`/`POST /api/trust`) — an accepted
  tradeoff for a loopback-only, single-user pilot server holding the operator's own key. The
  server's `127.0.0.1`-only binding is a hard, tested requirement, not a suggestion; the JSON-only
  `ContentNegotiation` setup incidentally blocks browser-based cross-origin requests to these routes
  today, though this is an incidental side effect of content-type enforcement, not a configured
  CORS policy — worth revisiting explicitly if this ever changes.
* No automated UI/JS test coverage — the actual complexity (scoring, sorting, gossip validation,
  signing) is fully covered by the pure-core and Ktor-route test suites; the HTML/JS itself is a
  thin `fetch()` layer over already-tested JSON endpoints, verified instead by a one-time manual
  two-node checklist (documented in the wave's own commit history) rather than a browser-automation
  dependency.

With V0.2.2 landed, the V0.2 milestone (Virtus/LTR economy plus a real, usable first client) is
complete.

**UI/UX design-team review (retroactive).** The project's house rule requiring every UI/UX task to
go through a fixed design panel (Kare, Tesler, Atkinson, Kay, Norman, Raskin, Rams, Ive, Forstall,
Duarte, Zhuo, with Steve Jobs's final review) was added after the static UI above already shipped —
applied retroactively as a follow-up commit. Seven changes landed: shape+glyph (not hue alone) on
the credibility badge so `NO_PATH` can never be mistaken for a low `RESOLVED` score even under
colorblindness or a fast skim; an always-open on-page explainer for what the badge and LTR boost
mean; an explicit disclosure before a trust rating is submitted that it is a public, signed,
accountable statement; a brief success flash on the timeline item that just changed; a
primary/secondary button hierarchy; numbers paired with plain words ("Trusted · 62%", "Boosted 2.50
sats by 3 supporters"); and a labeled identity ("You:") instead of a bare hex string as the first
thing a first-time reader sees. No framework, build step, or dependency was added — this stayed
within the already-decided hand-written HTML/CSS/vanilla-JS tech stack, and the `textContent`-only
XSS discipline is unchanged. Two real improvements (showing the actual trust path, visualizing LTR
decay over time) were explicitly deferred, not silently dropped — both need new fields in the
`/api/timeline` response that the server doesn't currently send.

== Karma: Bitcoin-anchored one-click likes (V0.3)

`lapis-net-karma` is the third of the four scoring dimensions (Layering above). Its data model,
`KarmaVote`, is a cheap, one-click "like" — but one carrying built-in Sybil resistance from two
independent mechanisms combined: a Bitcoin-chain-derived time anchor and Veritas-weighting.
`Karma = t/(n+1)`, where `t` is the number of Bitcoin blocks elapsed since the voter's own first
outgoing transaction (no chain history ⇒ `t < 0` structurally impossible to represent ⇒ Karma is
always `0.0` for an unanchored identity — enforced by `NoAnchorClaim`/`ChainAnchorClaim`'s own
`init` invariants, not merely by convention), and `n` is the voter's own prior eligible-vote count —
critically, always derived locally by each observer from its own indexed vote history, **never**
self-declared inside the wire message (`KarmaVoteCodec`'s layout has no `n` field at all).

**No live chain-verification in the GossipSub validation path, ever — the wave's central design
decision.** `KarmaGossip.onGossipMessage` validates only structure and signature; it never calls
out to Electrum or any network service. This mirrors `OnChainProof`'s already-accepted V0.2.1
precedent exactly, for the same three reasons: avoiding a liveness dependency on a third-party
server inside the hot gossip-validation path, avoiding cross-node non-determinism (different nodes
could observe different, possibly reorg'd chain state), and avoiding DoS amplification (an attacker
flooding gossip messages that each trigger an outbound network call would be a powerful
amplification primitive). Chain data is only ever consulted client-side, once, at local vote-cast
time, via `KarmaAnchorCache` — never as part of judging someone else's vote.

**Chain-data source: a trusting light client, explicitly not trustless SPV.** No genuine SPV client
library exists on Maven Central for Kotlin/JVM (confirmed during this wave's planning); building
real header-chain-verified SPV from scratch was out of scope. `ElectrumTimeAnchorSource` talks to a
real Electrum server over the `electrum-client`/`bitcoin-kmp` libraries and trusts every response at
face value — history entries, raw transaction bytes, chain tip height — with no merkle-proof
verification against a block header chain and no independent cross-check against a second server. A
malicious or compromised Electrum server can lie about any of these facts undetected. This is an
accepted, explicitly-documented scope limitation, mirroring `OnChainProof`'s own "structural/
trusting, not verified" precedent, and only matters for a node's own outgoing vote — `KarmaGossip`
never calls this class at all. The underlying Electrum protocol transport is also plaintext TCP
only, no TLS, documented as a further caveat of the same "trusting, not verified" shape.

**Bitcoin address derivation: P2WPKH only, a deliberate protocol-defined scope narrowing.** An
identity's Bitcoin presence is looked up via `HASH160(compressed secp256k1 pubkey)` —
`BitcoinAddressDerivation` — the sole derivation this wave recognizes. Legacy P2PKH, other HD
derivation paths, multisig, and Taproot addresses are not found, even if the identity has genuine
Bitcoin history under one of those. This narrows Karma's real-world reach in exchange for a single,
unambiguous, protocol-wide derivation rule every node computes identically.

**Sybil-resistance fix landed during this wave's review loop: at most one tracked vote per
`(voter, targetCid)`.** The original implementation capped `KarmaVoteIndex` only globally
(`MAX_TRACKED_VOTES`), with no per-voter limit. Because `KarmaVote.nonce` makes every vote
content-id-distinct, a single identity could sign and gossip unlimited free votes (no PoW, no
stake, unlike Virtus's `LtrRecord`, which at least claims a real BTC payment) — each one evicting
some unrelated voter's/target's vote from the shared index, and inflating a single target's Karma
via unbounded harmonic-sum repeat-voting (`t/(n+1)` only shrinks the *marginal* value of a repeat
vote; the *total* contribution from `M` repeat votes toward one target grows as `t · H_M`, unbounded
as `M` grows). Fixed by making a new vote from a voter who already has a tracked vote for the same
target **replace** the existing entry (most-recent-wins), keeping all three secondary indices
(`votesByContentId`/`votesByTarget`/`votesByVoterMap`) in lockstep via the same helper used by LRU
eviction. This fully closes per-target Karma inflation from one identity; it deliberately does
**not** limit how many *distinct* targets one identity can vote on (a narrower, lower-severity
residual gap, tracked as future work — see below) — Sybil resistance across many distinct
*identities* is intentionally left to the Bitcoin-anchor cost, not to this index.

**`TimelineBuilder`/`TimelineEntry` scope discipline: Karma is purely additive/display, never
affects sort or filtering.** This is a deliberate narrowing versus the fach-spec's fuller vision of
Karma "bridging trust networks" — `TimelineBuilder` does not yet have a genuine default-private-
timeline mode to bridge past, so wiring Karma into sort order or the credibility filter this wave
would either be a no-op or would silently misrepresent what Karma actually measures for a viewer.
`karmaScore`/`karmaVoteCount` are attached to every timeline entry and rendered, but
`TimelineBuilder.build`'s sort key remains exactly `(ltrWeightMsat desc, publishedAtEpochSeconds
desc)`, and `filteredOut` is still computed purely from Veritas credibility — proven by dedicated
tests showing a huge self-cast karma score changes neither ordering nor filtering.

**Review findings this wave.** Two independent review+security rounds ran before this wave landed
cleanly. Round 1 found and fixed: the per-voter vote-flooding gap above (the wave's one MAJOR
finding, security-relevant); `KarmaAnchorCache` never cached `TimeAnchorLookupResult.NotFound`,
contradicting its own doc comment and re-triggering a full Electrum scan (up to
`maxHistoryEntriesScanned` round-trips) on every single vote cast by an as-yet-unanchored identity
— fixed with a bounded `NOT_FOUND_TTL_SECONDS` cache, unlike a genuine `Found` genesis transaction,
which is a fixed historical fact and is cached without expiry; a missing `KarmaAnchorCacheTest`
covering the cache's security-critical contracts (added, 9 tests); `cachedGenesis` was an
unsynchronized `HashMap` under concurrent Ktor request threads, keyed by a lossy truncated
fingerprint string — fixed by switching to a `ConcurrentHashMap` keyed directly by
`Secp256k1PublicKey`; raw Electrum server error text could leak into the `POST /api/karma` HTTP 502
body — fixed by logging full detail server-side and surfacing only a generic message; a missing CID
length bound on `parseCidOrNull`; and the Like button's "this is a public, signed statement under
your own identity" framing was buried in a collapsed FAQ rather than always visible near the button
itself, unlike the equivalent trust-rating-form notice. Round 2 independently verified all of the
above and surfaced one residual gap in the same error-sanitization fix: the chain-tip-height RPC
path (`ElectrumTimeAnchorSource.currentChainTipHeight()`) used a separate code path that the first
sanitization pass missed, so a malicious Electrum server could still leak raw response text via that
sibling call — closed with the identical treatment (log full detail, throw a generic message) plus a
regression test proving the leak no longer occurs.

**Known, deliberately accepted gaps:**

* **Distinct-target vote flooding is not capped.** The per-target replace-on-conflict fix above
  closes per-target Karma inflation from one identity, but a single costless identity can still
  gossip votes toward many thousands of *different* target CIDs, still consuming
  `KarmaVoteIndex`'s shared `MAX_TRACKED_VOTES` LRU slots and evicting unrelated voters'/targets'
  entries. Tracked as a follow-up — e.g. a per-voter distinct-target quota or a lightweight
  admission cost.
* **No live chain verification anywhere** — see above; this is the wave's central, permanent design
  boundary for the gossip path, not a gap expected to close later the way V0.2.1's `OnChainProof`
  gap might.
* **`RealElectrumRpc`'s connection has no `close()`/lifecycle wiring into `BrowserServer.stop()`** —
  a real, if bounded, resource gap: one live socket + daemon thread persists for the process
  lifetime once a node's first vote establishes it. Not attacker-amplifiable, since nothing external
  can trigger additional `RealElectrumRpc` instances to be constructed.
* **Empty `ElectrumServers.PLACEHOLDER` ships by default** — every real `POST /api/karma` call fails
  with a clean 502 out of the box until an operator configures a real, reachable Electrum server
  list; this sandbox's outbound network policy could not verify real Electrum reachability during
  this wave (raw TCP to well-known public Electrum servers all timed out through the proxy), so an
  unverified hostname list was deliberately not shipped in its place.
* **`n`'s observer-dependent nature** — different observers can legitimately compute a different
  `karmaValue()` for the same vote depending on their own partial gossip view (which prior votes
  from that voter they happen to have indexed). This is by design: `n` is a local heuristic, not a
  consensus or signed value.

With V0.3 landed, all three of Veritas, Virtus, and Karma — three of the fach-spec's four scoring
dimensions — are implemented; Madli remains the only one not yet started.

== Genesis-Bootstrap + Identity Hardening (V0.4)

Four bundled deliverables, all about moving from test fixtures toward real users — a real bootstrap
configuration mechanism, a QR-code/deep-link key exchange flow, multi-device/pseudonym self-trust
linking, and keystore encryption at rest.

**Real bootstrap setup.** `BootstrapConfig` (`lapis-net-networking`) replaces the old
`BootstrapPeers.PLACEHOLDER` — a compiled-in list of RFC-5737 documentation-range IPs that could
never actually be dialed — with operator configuration: a comma-separated `LAPISNET_BOOTSTRAP_PEERS`
env var and an optional `bootstrap.peers` file (one multiaddr per line, `#`-comments and blank lines
ignored), merged and capped at `MAX_BOOTSTRAP_PEERS` (64) before any dial is attempted. The libp2p
listen address is similarly operator-configurable via `LAPISNET_LISTEN_ADDR`, defaulting to
loopback-ephemeral (unchanged from every prior wave, so all existing tests are unaffected).
`LapisNode.start()`'s own bootstrap-peers default changed from the placeholder list to `emptyList()`
— a fresh install with no operator config dials nobody and relies on mDNS/manual
`POST /api/peers/connect` until a real anchor is supplied. Lapis Net remains fully decentralized: a
bootstrap peer is only a technical first anchor for mesh entry, never a protocol authority — the
"genesis node" (the project's first operator) is a social/technical convention, distributed out of
band (e.g. published on a website, or shared via the QR/deep-link mechanism below), not
infrastructure the protocol structurally depends on.

**QR-code / deep-link key exchange.** A `lapisnet://connect?maddr=...&pk=...` URI scheme
(`ConnectUri`, `lapis-net-browser`) carries a dialable multiaddr (including `/p2p/<peerId>`) and a
compressed secp256k1 public key — purely public data, never signed or authenticated itself; any
trust decision made after scanning is still a separate, explicitly signed `VeritasGrant`. Rendered as
a QR code server-side via ZXing (`QrCodeSvg`, hand-built SVG path from the raw bit-matrix — no
`java.awt`, no raster, no new client-side JavaScript, keeping the V0.2.2 hand-written-JS-only
discipline intact) and exposed via three new routes: `GET /api/connect/info` (the local node's URI as
JSON), `GET /api/connect/qr.svg` (the same URI as a scannable image), and `POST /api/connect/uri`
(parses a scanned/pasted URI and dials the peer). `ConnectUri.parseOrNull` never throws — length
bound, scheme/host check, hex/curve-point validation — mirroring `parseHexPublicKeyOrNull`'s/
`parseCidOrNull`'s established never-throw discipline in the same file.

**Multi-device / pseudonym self-trust-linking.** `POST /api/self-link` lets one person link their own
devices/pseudonyms by reusing the *existing* `VeritasGrant` model verbatim, at
`trustMicros = MAX_TRUST_MICROS` — no schema change, no new signature domain tag, no gossip-path
validation change. **This is the wave's central design decision.** It creates no new Sybil attack
surface on Veritas trust propagation: every credibility/timeline query's path-finding BFS source is
always the local viewer's own key (`TrustPathFinder.findPath(graph, localIdentity, candidate)`), so a
self-link only ever propagates the truster's *pre-existing* standing one hop further — it cannot
manufacture trust a third party didn't already have a path to. A dedicated adversarial regression
test confirms this: an X→Y self-link announced directly via gossip (simulating a received message
from an attacker with no relationship to the local viewer) is asserted to leave a post by Y at
`credibilityLevel == NO_PATH`, not `RESOLVED`. The one genuine residual risk is at the UI/UX level,
not the data model: the "This is also me (link device)" framing is designed to lower a user's guard
specifically for identity claims, which an attacker could exploit via social engineering (tricking a
trusted user into scanning a QR code framed as "link your new phone" for a key that isn't actually
theirs) — mitigated with an explicit warning in the self-link UI ("exactly as strong a trust statement
as rating someone 100% trusted... never link a key someone else asked you to add") rather than
silently left as a gap.

**Keystore encryption at rest.** `KeystoreFileFormat` gained a v2 file format
(`lapis-net-identity`): Argon2id (BouncyCastle's `Argon2BytesGenerator`, already on the classpath —
no new dependency; memory=64MiB, iterations=3, parallelism=1, 16-byte salt) derives a 32-byte AES
key from an operator passphrase; AES-256-GCM (12-byte nonce, 128-bit tag) encrypts the existing
198-byte v1 plaintext keystore encoding unchanged, so every pre-existing structural/signature
cross-check in `decode()` still runs, just after decryption instead of before it. **The full
43-byte file header (magic, version, KDF id, Argon2 cost parameters, salt, nonce) is used as the GCM
AAD, read verbatim from the raw on-disk bytes on decrypt — never reconstructed from parsed fields —
so any tamper anywhere in the header or ciphertext, including an attempted downgrade of the Argon2
cost parameters to cheapen brute-forcing, fails authentication deterministically.** The Argon2 cost
parameters read from a v2 file's header are additionally sanity-capped (16× the defaults) *before*
the expensive KDF call, so a corrupted or malicious file can't turn a single load attempt into an
unbounded-memory/CPU hang ahead of the auth-tag check. `FileIdentityRepository` gained a
`PassphraseProvider` functional interface — a `null` provider (the default) preserves the exact
legacy unencrypted v1 behavior every prior test relies on — plus transparent, atomic v1-to-v2
migration on load (re-encrypts a legacy file the moment a passphrase becomes available, going through
the same temp-file + atomic-rename write path every save already used, so a crash mid-migration can
never corrupt or lose the identity). The passphrase is sourced from `LAPISNET_KEYSTORE_PASSPHRASE` or
an interactive console prompt; a headless process with neither falls back to legacy v1 plaintext with
a warning log rather than failing outright, keeping every existing CI run and demo working
unmodified — an explicit, documented trade-off (encryption is opt-in at the process entry points
this wave, not yet mandatory).

**Review findings this wave.** A single review + security round both approved with no CRITICAL/MAJOR
findings — the AAD binding was independently verified to defeat every tamper/downgrade/cross-file
scenario constructed, and the self-link Sybil-resistance claim was independently confirmed to hold
algorithmically. The MINOR findings were fixed directly: the Argon2 `parallelism` header byte gained
the same 16×-default cap already applied to memory/iterations (with dedicated regression tests
proving the cap fires before Argon2 ever runs, for both fields), and the self-link UI's disclosure
was strengthened with the social-engineering warning described above.

**Known, deliberately accepted gaps:**

* No in-app camera capture — the browser is a local HTTP UI, not a mobile app; the QR is generated
  and displayed locally, and the *other* party scans with their own phone and pastes/opens the
  resulting URI. No OS-level `lapisnet://` deep-link registration.
* Self-linking issues only the local half of a mutual link — full bidirectional device-linking
  requires each device to scan the other and call `/api/self-link` once; no automated handshake.
* No live reachability check that an advertised multiaddr is actually externally dialable — NAT
  traversal remains the open research item noted since V0.1.3.
* No rate limiting on any of the new routes — the same accepted trade-off as every existing route
  (loopback-only, single-user pilot server).
* Keystore encryption is opt-in at the process entry points (see above) rather than mandatory.
* `FileIdentityRepository.list()` still fails loudly on a v2 keystore it can't decrypt (wrong/absent
  passphrase), consistent with its pre-existing "one bad file fails the whole call" behavior.

With V0.4 landed, the protocol has moved from a headless, test-fixture-only prototype toward
something a real (non-test) user could actually run and be reachable through.

== Madli: machine-to-machine node reputation (V0.5)

`lapis-net-madli` is the fourth and final scoring dimension (Layering above). Unlike Veritas
(who to trust), Karma (what content people like), and Virtus (what content is monetarily boosted),
Madli rates **nodes as infrastructure** — Bitswap/DHT serving quality — and is never shown to a
human participant or attached to any content or identity's social standing. Its data model,
`MadliDailyVector`, is a signed, bilateral, per-day observation cast by one Lapis identity
(`observer`) about one libp2p peer's (`observedPeer`, a `PeerId`, not a `Secp256k1PublicKey` —
Madli rates infrastructure peers, not identities) serving quality on a given `epochDay`, carrying
five fixed-point metrics: Reachability, Delivery-Integrity, and Routing-Helpfulness (micros
fractions, `0..1_000_000`), plus raw Bandwidth (median bytes/sec) and Latency (median RTT millis).
All five are fixed-point integers, never `Double`, for the same reason `VeritasGrant.trustMicros`
documents — this value is embedded in a signed, cross-node-compared structure.

**No `nonce` field — deliberately the opposite of `KarmaVote`/`LtrRecord`.** Those are
accumulating models (every vote/record is kept, never resolved to a winner), so a nonce is needed
to keep otherwise-identical entries content-id-distinct. Madli is latest-wins-per-`(observer,
observedPeer, epochDay)`, closer to `VeritasGrant`'s latest-wins-per-(truster, target) model: a day
has exactly one summary per observer for one observed peer, and a genuine correction naturally
produces a different content-id (different metrics), handled by the index's per-tuple replace
rule below rather than by a nonce keeping duplicates alive side by side.

**The wave's central security decision — two anti-flooding/anti-backdating invariants in
`MadliVectorIndex`, mirroring Karma's per-`(voter, target)` replace fix but generalized to a
day-keyed tuple.** Invariant A: at most one tracked vector per `(observer, observedPeer, epochDay)`
— a new vector for an already-tracked exact tuple replaces the old one (most-recent-arrival wins),
closing "one observer floods many vectors about one peer for the same day". Invariant B — the
genuinely new defense this wave adds, with no Karma/Virtus precedent: at most
`MAX_TRACKED_DAYS_PER_OBSERVER_PEER` (128) distinct-day vectors per `(observer, observedPeer)`
pair, evicting the smallest `epochDay` once exceeded (tie-broken by lexicographically-smallest
content-id for deterministic convergence across honest nodes). Without invariant B, invariant A
alone would not stop an observer from publishing hundreds of distinct-`epochDay` vectors about one
peer — each a distinct tuple, so invariant A never catches it — and stacking decay-weighted
contributions in aggregation indefinitely; this is the anti-backdating defense. Both invariants are
enforced by keeping THREE secondary indices (`vectorsByObservedPeer`, `vectorsByObserverPeer`,
`currentByObserverPeerDay`) in lockstep on every eviction and replacement — the exact `KarmaVoteIndex`
lesson about a partial-cleanup bug silently corrupting downstream aggregation input.

**Validator determinism — `MadliGossip.onGossipMessage` makes zero clock/network calls, same
central decision `KarmaGossip`/`LtrGossip` already establish.** `epochDay` is deliberately NOT
range-checked against wall-clock time anywhere in the codec or the gossip validator — doing so
would make mesh behavior depend on wall-clock skew between peers, breaking the "same
structural+signature rules applied to the same bytes always yield the same accept/reject decision
on every honest node" invariant. Backdating/future-dating is instead defused at READ time
(`MadliDecayCalculator`'s future-clamp, identical to `LtrWeightCalculator`'s load-bearing
`coerceAtLeast(0.0)`) and bounded by invariant B above.

**Five independently-configurable decay half-lives (`MadliHalfLives`), generalizing
`LtrWeightCalculator`'s single-half-life pattern.** Reachability/Latency default to a 7-day
half-life (network conditions change fast); Bandwidth/Routing-Helpfulness to 30 days; Delivery-
Integrity to 90 days (a track record of not corrupting/dropping data is a durable signal).
Each metric in `MadliAggregator.aggregate` is decayed by its OWN half-life, so a single vector
contributes a different weight to each of the five output fields.

**Veritas-weighted, weighted-MEDIAN aggregation — the module's headline deliverable, and a
deliberate, documented deviation from the Karma/Virtus "no sibling trust dependency" rule.**
Karma/Virtus defer Veritas-weighting to their application-layer consumer (`lapis-net-browser`'s
`KarmaScoring`); Madli has no application-layer consumer this wave (it is machine-to-machine
infrastructure, "nicht für menschliche Teilnehmer sichtbar"), so its Veritas-weighted aggregation —
the subject of the mandatory Sybil-resistance simulation below — is hosted directly in
`lapis-net-madli`. To keep the security-critical core decoupled and independently testable, the
aggregation core (`MadliAggregator.aggregate`) is written against an injected
`observerWeight: (Secp256k1PublicKey) -> Double` function, exactly mirroring how
`KarmaWeightCalculator` takes `votesByVoter` as an injected function — only one small adapter
function, `MadliAggregator.veritasObserverWeight`, references `TrustPathFinder`/`TrustGraph`.
`lapis-net-madli`'s `build.gradle.kts` documents this deviation in its header comment. Three
manipulation defenses combine in `aggregate`: (1) Veritas-weighting — each observer's contribution
is scaled by the consumer's own Veritas score of that observer, so a Sybil cluster with no external
Veritas path gets weight `0.0` and contributes nothing; (2) weighted MEDIAN, not mean — if 90% of
(Veritas-weighted) observers report a peer as slow and 10% report it as fast, the weighted median
follows the 90% majority, limiting a peer's ability to selectively serve a small minority of
observers well and pull the aggregate upward the way a mean would; (3) **one representative vector
per observer per metric** — `aggregate` groups its input by `observer` and, independently per
metric (own half-life), feeds the weighted median only the single highest-decayed-weight vector
from each observer, never a sum of all of that observer's tracked vectors. See below for why this
third defense is required, not optional.

**Invariant B alone does not close the backdated-vector-flooding gap — the aggregation-level fix
that actually does.** `MadliVectorIndex`'s invariant B (above) caps a single observer at
`MAX_TRACKED_DAYS_PER_OBSERVER_PEER` (128) distinct-day vectors per observed peer, and
`MadliGossip.onGossipMessage`'s validator deliberately never range-checks `epochDay` against
wall-clock time (the validator-determinism decision above) — so an attacker who has acquired even a
modest, non-majority amount of Veritas trust can fabricate and gossip all 128 backdated vectors
about a target peer in a single burst, no real elapsed time required. Before this wave's security
fix, `MadliAggregator.aggregate` mapped every tracked vector to an independent
`(value, decayed weight)` sample with no per-observer grouping, so one observer's total influence on
the aggregate scaled with how many distinct-day vectors they had stacked, not with how much the
consumer actually trusted them as one entity — multiplying their effective weight by roughly
`sum_{d=0}^{127} 0.5^(d / halfLife)`: ~10.6x for the 7-day half-life (Reachability/Latency), ~41.5x
for 30 days (Bandwidth/Routing-Helpfulness), ~81.7x for 90 days (Delivery-Integrity). That let a
single NON-majority observer outweigh 9+ genuinely independent honest observers who each published
only their one truthful vector for today, defeating both the Veritas-weighting and weighted-median
defenses' "one observer's report counts once, scaled by trust" reasoning. The fix — defense 3 above
— closes this structurally: for each metric, each observer contributes at most their own single
highest-decayed-weight (freshest) vector, so vector VOLUME can never multiply an observer's
influence, no matter how many distinct-day vectors invariant B still lets them track. This is
distinct from, and does not weaken, `MadliSybilResistanceSimulationTest` Scenario 3b's accepted
residual (a trusted headcount MAJORITY of DISTINCT observers, one vector each, still wins the
median) — that scenario is about genuine trust majority, this fix is about one observer manufacturing
disproportionate influence via publishing volume. See `MadliAggregatorTest`'s dedicated
backdated-flooding regression test (128 fabricated vectors from one attacker bounded to one vote,
outweighed by 9 honest single-vector observers) and `MadliAggregator.aggregate`'s KDoc for the full
reasoning.

**Weighted-median tie-break is symmetric at an exact 50/50 weight split, not low-biased.** The
underlying `weightedMedianLong` helper (read-time `Double` math only — never part of any
signed/cross-node-compared structure) originally returned the lower of two values whenever
cumulative weight landed exactly on the halfway threshold, letting an attacker holding exactly half
the effective weight (not a majority) force the aggregate toward their own fabricated low report,
since they control what they report while they cannot control the honest side's value. It now
detects an exact tie (within a `1e-9` epsilon) and returns the midpoint of the two boundary values
instead — the standard even-weight-split median convention (e.g. two equal-weight observers
reporting 100 and 300 resolve to 200, not 100) — with a dedicated regression test.

**The Sybil-resistance simulation — resolving the vault note's one explicitly-unresolved item.**
`MadliSybilResistanceSimulationTest` feeds fabricated daily vectors through the REAL
`MadliAggregator.aggregate` + REAL `MadliAggregator.veritasObserverWeight` + REAL
`TrustGraph`/`TrustPathFinder` (not a mock of aggregation), across three scenarios: (1) a 20-node
Sybil cluster that mutually vouches at maximum trust but has no path from the consumer has
near-zero effect on the aggregate — proving the Veritas-weighting defense; (2) a peer that
selectively serves 1-of-10 trusted observers well and the other 9 badly is scored by the
9-observer badly-served majority, not pulled up by the outlier — proving the weighted-median
defense; (3a) a single trusted observer lying is defeated by a trusted honest majority; (3b) a
trusted MAJORITY that lies still wins the median — an explicitly asserted, DOCUMENTED RESIDUAL
matching the vault note's own acknowledgment that only the network's generic reputation-burning
mechanism (not this module's aggregation math) defends against a trusted majority turning
dishonest. Asserting 3b explicitly, rather than leaving it an unstated gap, mirrors V0.4's
self-link Sybil-resistance test discipline: the boundary is now a tested, documented property.

**Bitswap-modulation hooks exist and are pure/unit-tested, but are NOT wired into a live fetch this
wave — an honest, deliberate scope cut, mirroring V0.1.4's own honest documentation of what is
verified-usable versus documented-broken.** `MadliRoutingPolicy.orderPeers` (peer-set ordering by
`routingScore`, a monotonic function of the five metrics with a Bitswap-consumable
`NabuStorage.get(cid, peers = orderedSet)` shape in mind) and `MadliReplicationPolicy` (a pluggable
local replication hook, default `NEVER`, plus an `underServedImportant` reference implementation)
are both pure, local, and thoroughly unit-tested against synthetic peer sets and signals. They are
not exercised end-to-end because: (a) `NabuStorage.findProviders()` does not work end-to-end in
this codebase (a pre-existing V0.1.4 limitation, see that section above), so there is no live
provider set to order in a real fetch; (b) Nabu exposes no Bitswap responder-side prioritization
hook ("serve high-Madli requesters faster" is not wireable at all without patching Nabu — out of
scope); (c) no production consumer wires `orderPeers` into a `get(cid, peers=...)` call this wave.
`orderPeers` deprioritizes a peer with no Madli history to sort last (the vault's bootstrap
deprioritization), with a deterministic ascending-peerId-bytes tie-break.

**Incentive model — a no-code doc note.** This wave builds the scoring/observation/aggregation
engine only; it does not implement any protocol-level reward or penalty tied to Madli standing
(e.g. preferential replication slots, fee discounts). That remains future scope.

**Known, deliberately accepted gaps:**

* **Bitswap modulation is structurally ready, not end-to-end exercised** — see above; this mirrors
  V0.1.4's Storage section precedent for "verified-usable vs. documented-broken" honesty.
* **No production consumer** — Madli is not wired into `lapis-net-browser`; there is no UI surface
  for Madli this wave (by design — it is machine-to-machine, not human-facing).
* **Local observation collection is out of scope this wave.** The module builds the
  published-vector pipeline and consumes vectors; it does not instrument live Bitswap/DHT
  interactions to produce real metric measurements. Vectors are constructed by callers/tests.
* **`observationCount` is advisory/self-declared** — not part of any anti-Sybil guarantee, exactly
  like a `KarmaVote`'s `timeAnchor` claim; the Veritas-weighting is the actual guarantee.
* **Incentive model is a no-code doc note** — see above.
* **Half-lives are per-view configurable** via `MadliHalfLives`, but there is no persistence/UI for
  operator configuration this wave (defaults only).
* **Scenario 3b's trusted-majority-lies residual** — see above; a real, accepted, and now
  explicitly tested boundary of this module's manipulation resistance.

With V0.5 landed, all four of the fach-spec's scoring dimensions — Veritas, Virtus, Karma, and
Madli — are now implemented.

== Lightning proof (V0.6)

V0.6 closes V0.2.1's "Zwei Zahlungswege" gap on the Lightning side: `LightningProof`, the second
`LtrProof` implementation alongside `OnChainProof`, plus `LightningProofVerifier` — the object that
performs the complete, real cryptographic verification chain for it. Unlike `OnChainProof`,
`LightningProof` is fully cryptographically checked, with no simulation and no live network/node
required: preimage-to-hash, real BOLT-11 invoice parsing and signature verification, and every
anti-spoofing/anti-replay cross-check described below all run offline, entirely from the bytes
already inside a gossiped `LtrRecord`.

**`LightningProof{preimage, paymentHash, signedInvoice}` — structural shape only, exactly mirroring
`OnChainProof`'s "trusting, not verified" constructor discipline.** `preimage` and `paymentHash` are
each exactly 32 bytes; `signedInvoice` is a BOLT-11 bech32 string capped at
`LightningProof.MAX_SIGNED_INVOICE_BYTES` (2048 — generous headroom over a typical 200-700 char
invoice, still bounding the length-prefixed wire field before allocation). The constructor never
checks `sha256(preimage) == paymentHash`, never parses the invoice, and never verifies its
signature — all of that is `LightningProofVerifier`'s job, so `LtrRecordCodec.decode` stays purely
structural, the same reason `OnChainProof`'s own constructor stays shape-only.

**Codec: `proofType = 2`, previously reserved and rejected, now implemented.** Layout:
`preimage(32) | paymentHash(32) | invoiceLen(2) | signedInvoice(invoiceLen)`. `invoiceLen` is
validated against `LightningProof.MAX_SIGNED_INVOICE_BYTES` BEFORE the invoice buffer is allocated
(a DoS guard mirroring `cidLen`'s existing handling), and the declared `proofLen` must equal exactly
`66 + invoiceLen` — any mismatch, including trailing bytes, is rejected outright, never silently
truncated or reinterpreted. `LtrRecordCodec.MAX_PROOF_BYTES` is bumped from 1024 to 4096 to
comfortably clear a Lightning proof's worst case (2114 bytes). No new signing-domain-separation tag
was needed: `proof` is already inside `encodeSignedBody`'s output, so a `LightningProof` is already
covered by the existing `VIRTUS_LTR_RECORD_DOMAIN_TAG` binding on the whole record — the invoice's
own BOLT-11 signature is a separate, Lightning-protocol-defined signature verified against
Lightning's own rules, not a LapisNet-internal scheme.

**The complete verification chain (`LightningProofVerifier.verify`), all AND-ed, never throws:**

. `sha256(proof.preimage) == proof.paymentHash`.
. `Bolt11Invoice.read(proof.signedInvoice)` parses successfully — this call verifies the invoice's
  own embedded signature internally as part of parsing (`lightning-kmp`'s real BOLT-11
  implementation, not a hand-rolled parser).
. The invoice's own parsed payment hash equals `proof.paymentHash`.
. **Amount binding (mandatory, anti-spoofing).** The invoice must declare a non-null amount, and
  that amount (msat) must equal `record.initialValueMsat` exactly — the invoice, not the record, is
  the source of truth for the claimed amount.
. **Recipient binding — `invoice.nodeId == record.viewId` (mandatory, not optional).** This is the
  wave's central protocol commitment: a manufacturer's Lightning node key IS its Lapis viewId. The
  planning alternative (leaving this unenforced) was explicitly rejected — without it, anyone could
  pay their own Lightning node and claim the resulting proof boosts a completely different view.
. **Content binding — `invoice.description == canonicalMemo(record.cid, record.viewId)`
  (mandatory, anti-replay).** `canonicalMemo` is `"lapisnet-ltr:v1:" + cid + ":" + viewId-hex`. An
  invoice using `descriptionHash` instead of a plain `description` is rejected outright — there is
  no way to confirm a hash-only description matches the canonical memo without its preimage, which
  the verifier never has. Without this check, a genuine, validly-signed `(preimage, invoice)` pair
  paid for one `(cid, viewId)` could be replayed as if it proved a payment for a different one.
. **Expiry is deliberately NOT checked.** A settled payment's invoice may legitimately be past its
  own BOLT-11 expiry by the time the resulting record propagates through gossip — the payment
  already happened, and expiry only ever governs whether a *new* payment attempt should still be
  accepted, which is moot once a preimage already proves settlement.

Chain-agnostic by design: `Bolt11Invoice.read` accepts any of the standard BOLT-11 prefixes
(mainnet `lnbc`, testnet3/testnet4 `lntb`, regtest `lnbcrt`) with no additional restriction in the
verifier — the planning alternative (mainnet-only) was explicitly rejected so the same code path
works for a pilot's testnet/regtest dry runs without a special case.

**Gossip hot path — a deliberate divergence from `OnChainProof`, and from every earlier wave's
"never call out to a network service inside the validator" precedent (Karma/Madli).** Those
precedents exist specifically because a *live chain/network lookup* inside `onGossipMessage` would
add a liveness dependency on a third party, cross-node non-determinism (different nodes could
observe different, possibly reorg'd state), and a DoS-amplification vector. `LightningProofVerifier.verify`
is categorically different: a pure, bounded, local computation — hash a preimage, parse and verify
one BOLT-11 signature, compare a handful of already-size-capped fields — with zero network I/O and
zero liveness dependency on anything outside the message bytes already in hand. `LtrGossip.onGossipMessage`
therefore calls it directly, immediately after the existing `LtrRecord.verify(record)` signature
check, rejecting the message as `Invalid` on a crypto-invalid `LightningProof` before any
persistence/indexing is attempted. The result: a `LightningProof` record is strictly *harder* to
forge over gossip than an `OnChainProof` record (which still has zero live-payment verification, per
V0.2.1's known gap) — the correct asymmetry, since Lightning verification is the one real check this
codebase can do for free.

**`lightning-kmp` confinement — `implementation`-only in `lapis-net-virtus`, exactly mirroring
`lapis-net-karma`'s `electrum-client`/`bitcoin-kmp` confinement to `ElectrumTimeAnchorSource`.**
Every `fr.acinq.lightning`/`fr.acinq.bitcoin` type stays inside `LightningProofVerifier.kt` — no
public signature anywhere in this module (or any consumer) ever exposes one. `lapis-net-browser`
needed one piece of Lightning-derived data (an invoice's amount) without taking on the dependency
itself, so `LightningProofVerifier.invoiceAmountMsatOrNull(signedInvoice): Long?` is a small,
already-primitive-typed (`Long?`) helper — the one deliberately narrow crack in the confinement,
returning a plain number rather than any ACINQ type.

**Version note — the plan's originally-specified `lightning-kmp` 1.13.0 does not exist on Maven
Central.** The highest published `fr.acinq.lightning:lightning-kmp-jvm` version is 1.8.4 (verified
against the real `maven-metadata.xml`); this wave uses that instead. 1.8.4's own POM pins an older
`bitcoin-kmp-jvm` (0.20.0) than this project already depends on elsewhere (0.31.0, via
`lapis-net-karma`) — `lapis-net-virtus/build.gradle.kts` adds an explicit
`implementation(rootProject.libs.bitcoin.kmp)` to force the same 0.31.0 resolved everywhere else in
this project (Gradle's default highest-version-wins conflict resolution; `lightning-kmp`'s Gradle
module metadata uses `requires`, not `strictly`, so nothing blocks the bump). Verified compatible by
this wave's full test suite exercising real signed-invoice creation, parsing, and verification
against the resolved (newer) `bitcoin-kmp`.

**`POST /api/ltr/lightning` (`lapis-net-browser`) — the first LTR/Virtus record *authoring*
endpoint**, closing part of V0.2.2's known "no LTR record authoring in this MVP" gap for the
Lightning path specifically. Accepts an *externally-obtained* `(preimage, signedInvoice)` pair — the
author paid a real BOLT-11 invoice with their own Lightning wallet out-of-band; this route never
sends a payment itself (no embedded node/wallet exists in this codebase, see the scope box below).
The amount is always derived from the invoice server-side via `invoiceAmountMsatOrNull`, never
trusted from the client (there is no amount field on the request DTO at all); the payment hash is
always derived server-side via `sha256(preimage)`, never trusted either. The resulting `LtrRecord`
is verified with the exact same `LightningProofVerifier.verify` call `LtrGossip.onGossipMessage`
uses — synchronously, before `announce()` — so a self-authored record can never enter this node's own
index/gossip stream in a state gossip peers would themselves reject.

**Known, deliberately honest scope cuts — mirroring V0.3's Electrum-trust and V0.5's
Bitswap-modulation "structurally ready, not end-to-end exercised" precedent:**

* **No embedded Lightning node.** Nothing in this codebase runs a real `lightning-kmp` node,
  maintains a channel, or has access to real funds. `LightningProofVerifier` only ever verifies
  proofs already handed to it — it never constructs, sends, or receives a Lightning payment.
* **No BOLT-12 Offer/DHT publication, no `invoice_request`/auto-respond flow.** The Virtus spec
  note's fuller "A. Lightning via BOLT-12 Offer" vision (a view publishing a standing offer other
  nodes can pay against without out-of-band coordination) is not built — V0.6 only covers the
  BOLT-11 "pay first, submit proof after" path.
* **No live payment settlement testing.** Every test in this wave substitutes a preimage the test
  chose and a BOLT-11 invoice it signed itself (both via real, in-process `lightning-kmp` calls) —
  the cryptography exercised is completely real, only the network settlement event (an actual
  Lightning payment traversing a real channel) is out of reach in this sandbox/CI, exactly the
  reasoning `ElectrumTimeAnchorSourceTest`'s fake RPC and `MadliRoutingPolicy`'s non-live-fetch
  status already establish as this codebase's accepted testing boundary for external payment/network
  infrastructure.

With V0.6 landed, both of the fach-spec's "Zwei Zahlungswege" payment paths have a working
`LtrProof` implementation — `OnChainProof` (structural only, live chain verification still an open
gap) and `LightningProof` (fully cryptographically verified, including in the gossip hot path).

== Asynchronous messages: mail envelope and body (V0.9.1)

`lapis-net-mail` is the first sub-wave of V0.9 (the "email replacement" arc — see
`docs/roadmap.adoc`'s V0.9 entry for the full four-sub-wave split). It implements the message
format itself and its propagation path; it does not implement encryption, threading, attachments,
or a browser UI — those are later sub-waves.

**The two types.** A `MessageEnvelope` is the signed, addressed wrapper: sender, up to
`MAX_RECIPIENTS` (64) recipient public keys, `sentAtEpochSecond`, an `EncryptionMode`, a
`contentCid`, optional `replyTo`/`threadRoot` CIDs, and a secp256k1 signature over the new
`"LapisNet:mail-envelope:v1"` domain tag. A `MessageBody` is the payload — subject, verbatim
Markdown body (not rendered or sanitized here, that is a browser-UI concern for V0.9.3),
`AttachmentRef` list, canonically-sorted headers — stored as its own Nabu blob. `contentCid` is
that blob's CID and is itself covered by the envelope's signature, so the body carries no
signature of its own: it is authenticated transitively, through the CID binding, by whoever signed
the envelope.

**The gossip frame carries the body, not just a CID pointer.** This is a deliberate departure from
the SPEC's original wording, forced by two facts about the existing codebase: `NabuStorage.get()`
falls through to a live Kademlia DHT provider lookup on a local cache miss, which a GossipSub
validator must never do (see below); and cross-node DHT provider discovery has been documented
broken since V0.1.4 (`Kademlia.dialPeer`, see the Storage section above), so a receiving node could
never reliably fetch a body it only knew by CID anyway. `MailFrameCodec` therefore wraps both the
`MessageEnvelopeCodec`-encoded envelope and the `MessageBodyCodec`-encoded body in one wire frame.
This is the exact same reasoning, and the exact same resolution, as `VeritasGossip` publishing full
grant bytes rather than a CID pointer in V0.1.7. The body is still independently stored as its own
Nabu blob by both sender and receiver, and `contentCid` is still covered by the envelope signature
— every property the original wording wanted is preserved, just checked locally instead of over
the network.

**One GossipSub topic per recipient identity.** `InboxTopics.forRecipient(key)` derives
`"LapisNet:inbox:<64 lowercase hex chars of sha256(compressed pubkey)>:v1"`. Deliberately NOT a DHT
inbox record — gossip-only, for the same `Kademlia.dialPeer`-is-broken reason above. A node offline
during the gossip window has no catch-up path: best-effort convergence, the same accepted
limitation `VeritasGossip`'s single network-wide topic already carries, now applied to a
per-identity topic instead.

**Zero clock and zero network calls in the validator.** `InboxGossip.onGossipMessage` is the single
GossipSub validator step: decode the frame, decode the envelope, check the local identity is
actually in the recipient list, verify the signature, check the CID binding against the frame's
body bytes, decode the body, dedup, persist, index — all without ever calling
`NabuStorage.get()`/`findProviders()`, `System.currentTimeMillis()`, or `Instant.now()`. This
mirrors `KarmaGossip`/`MadliGossip`/`LtrGossip`'s identical rule. `MessageEnvelope.sentAtEpochSecond`
is attacker-controlled and is never consulted for an accept/reject decision.

**Envelopes not addressed to this identity are dropped without being persisted.** The addressing
check runs before signature verification and before any storage call, and a rejection here means
the envelope is neither persisted, indexed, nor re-propagated — a deliberate divergence from
`VeritasGossip`'s "keep relaying even what we can't use" rule. An inbox topic is identity-scoped:
nothing legitimately subscribed to it could be the intended recipient of an envelope that omits
that identity, so there is no mesh-wide convergence property worth preserving here, unlike on a
network-wide topic.

**Encryption was wire-representable and rejected outright in V0.9.1.** `EncryptionMode.HYBRID_ECIES`
and `EncryptionMode.MLS_ARCHIVE` existed as enum constants and wire values from V0.9.1 onward so a
later encryption wave would need no wire-format or schema change, but only `EncryptionMode.NONE`
was functional in V0.9.1 itself: both reserved modes were rejected at three independent layers —
`MessageEnvelope`'s constructor, `MessageEnvelopeCodec.decode`, and `InboxGossip`'s validator
(belt-and-braces, since `decode()` already rejected them before the validator's own check could
ever run). This mirrored `LtrRecordCodec`'s own pre-V0.6 `proofType = 2` precedent, which was
rejected outright through V0.5 before V0.6 implemented it as `PROOF_TYPE_LIGHTNING`. **As of V0.9.2**
(see that section below), `HYBRID_ECIES` is functional; only `MLS_ARCHIVE` remains rejected at all
three layers.

**Two independent caps, as established in V0.1.7.** `InboxIndex` mirrors `VeritasGrantIndex`'s
two-cap structure: an evicting, LRU-ish in-memory tracking cap (`MAX_TRACKED_MESSAGES`, 8,000) and
a separate, never-evicting persistence-reservation cap (`MAX_PERSISTED_MESSAGES`, 8,000) that
independently bounds `NabuStorage.put()` calls. Both numbers are smaller than the trust/virtus/madli
modules' 64,000 — a mail message's blob is up to roughly 48 KB versus a Veritas grant's roughly
2 KB, so an equal count would be a far larger disk/heap budget; both are provisional and should be
revisited against real usage.

**`MailSender`.** `send()` builds a `MessageBody`, `put()`s it in Nabu, signs a `MessageEnvelope`
bound to that blob's CID, `put()`s the envelope too, then publishes the combined `MailFrameCodec`
frame to every recipient's inbox topic — publish strictly last, after both puts succeed, mirroring
`VeritasGossip.announce`'s documented put-then-publish invariant. `republish()` re-sends an
already-built message's frame without re-signing or re-storing anything, for retrying against
GossipSub's asynchronous mesh formation.

**Known, deliberately accepted gaps:**

* **No DHT inbox record**, **no catch-up path** for an offline recipient — gossip-only, as above.
* **No relay population.** GossipSub only forwards on topics a peer subscribes to, and an inbox
  topic is identity-scoped, so delivery effectively requires a live sender-to-recipient connection
  at send time — strictly weaker than V0.1.7's network-wide Veritas topic.
* **No self-delivery.** GossipSub never delivers a node's own `publish()` calls to its own
  `subscribe()` handler, so a sender that lists themself among recipients never sees the message in
  their own inbox. A local "sent" view is V0.9.3.
* **No topic sharding, no newsletter/subscription model, no address book or pubkey-to-name
  mapping.**
* **No thread assembly.** `replyTo`/`threadRoot` are carried and signed but nothing walks them into
  a thread yet — V0.9.3.
* **No attachment fetching, verification, or encryption.** `AttachmentRef.size` is a declared value,
  never checked against the referenced blob; there is deliberately no encryption-key field — V0.9.3.
* **No browser HTTP routes.** `lapis-net-browser` is untouched by this wave — V0.9.3.
* **No encryption in V0.9.1 itself** — `HYBRID_ECIES`/`MLS_ARCHIVE` were wire-representable but
  rejected outright, as above. Addressed for `HYBRID_ECIES` in V0.9.2 (see that section below);
  `MLS_ARCHIVE` remains rejected.

**Known gap closed: CID multihash length overflow.** A pre-merge security audit of this wave found
that `MessageEnvelopeCodec`'s `contentCid`/`replyTo`/`threadRoot` decode sites and
`MessageBodyCodec`'s per-attachment CID decode site capped the CID *field*'s wire byte count
(`MAX_CID_BYTES = 128`) but passed those bytes straight to `io.ipfs.cid.Cid.cast(...)`, whose
underlying `Multihash.deserialize` allocates `new byte[declaredLength]` off an attacker-controlled
varint read from *inside* those bytes, before `Multihash`'s own 127-byte constructor bound check
ever runs. An 8-byte CID payload declaring a multihash length of `0x7FFFFFFF` was enough to throw
an uncaught `OutOfMemoryError` out of `InboxGossip.onGossipMessage` itself — reachable before
signature verification and before the addressing check, so no valid signature or correct
addressing was required. Fixed by `CidBytesValidation.isSafeToCast`, a shared pre-flight check run
at all four call sites before `Cid.cast(...)` is ever invoked, plus a defense-in-depth
`OutOfMemoryError` catch in both codecs' `decode()`. See `MailCidLengthOverflowDosTest` for the
regression coverage.

**Follow-up (found and fixed 2026-08-04): the same construct also affected three pre-existing
sibling codecs.** `VeritasGrantCodec`'s occasion-reference CID (V0.1.5), `LtrRecordCodec`'s record
CID (V0.2.1), and `KarmaVoteCodec`'s target CID (V0.3) all had the identical unguarded
`Cid.cast(cidBytes)` construct this wave's audit found and fixed in the mail module — noted above
at the time as "out of scope for this fix, tracked separately." `CidBytesValidation` has since
moved out of `lapis-net-mail` into `lapis-net-core` (`net.lapisphilosophorum.lapisnet.core.cid`),
the shared home all four modules already depended on, so `VeritasGrantCodec.decode`,
`LtrRecordCodec.decode`, and `KarmaVoteCodec.decode` now run the identical pre-flight guard before
their own `Cid.cast(...)` calls, each with the same defense-in-depth `OutOfMemoryError` catch. See
`VeritasCidLengthOverflowDosTest`, `LtrCidLengthOverflowDosTest`, and `KarmaCidLengthOverflowDosTest`
for the regression coverage.

**Second follow-up (found and fixed 2026-08-04): `lapis-net-browser`'s `parseCidOrNull` called
`Cid.decode(String)` directly, bypassing the guard entirely.** Unlike the four codec call sites
above, `BrowserApi.kt`'s `parseCidOrNull` never went through `Cid.cast(byteArray)` at all — it
called `io.ipfs.cid.Cid.decode(value: String)`, which internally does its own
`Multibase.decode(v)` then `Cid.cast(data)` (the exact same unguarded construct) for the common
case, plus a *second*, separate unguarded path for the legacy CIDv0 shortcut
(`v.length() == 46 && v.startsWith("Qm")` → `Multihash.fromBase58(v)`, which calls
`Multihash.deserialize` directly and never touches `Cid.cast`). Reachable via `POST /api/karma`
(`targetCid`), `POST /api/ltr/lightning` (`cid`), and `GET /api/mail/thread/{cid}` / `GET
/api/mail/attachment/{cid}` — all before any signature check. The embedded browser server binds to
`127.0.0.1` only, but installs no CORS plugin, so any page the user's browser visits while the node
is running could reach these routes with a plain cross-origin request. Fixed by making
`parseCidOrNull` decode the multibase/base58 bytes itself and validate them before ever calling
`Cid.cast`/`Multihash.deserialize`: the common path via `CidBytesValidation.isSafeToCast` (as
above), and the legacy CIDv0 shortcut via a new `CidBytesValidation.isSafeToDeserializeMultihash`
entry point, which validates the `type-varint | length-varint | hash-bytes` layout
`Multihash.deserialize` itself expects (no leading version/codec pair, unlike `isSafeToCast`). See
`BrowserCidLengthOverflowDosTest` for the regression coverage, including an end-to-end
`POST /api/karma` test.

== Hybrid-ECIES mail encryption (V0.9.2)

`lapis-net-mail`'s V0.9.2 sub-wave makes `EncryptionMode.HYBRID_ECIES` functional, the second of
the two encryption modes V0.9.1 shipped as wire-representable-but-rejected. `EncryptionMode.MLS_ARCHIVE`
stays reserved and rejected outright at the same three layers V0.9.1 left it (`MessageEnvelope`'s
constructor, `MessageEnvelopeCodec.decode`, `InboxGossip`'s validator) — no implementation plan
exists for it in this arc.

**The scheme, in one paragraph.** A fresh 32-byte AES-256-GCM content key encrypts the
`MessageBodyCodec`-encoded body into a `SealedBody` blob, which occupies exactly the frame slot the
plaintext body blob used to — so `MessageEnvelope.contentCid` and `InboxGossip`'s CID-binding check
work unchanged for both modes. That content key is then ECIES-wrapped once per recipient, plus once
more for the sender's own public key ("Sender wrappt zusätzlich für sich selbst" — sent mail stays
readable to its own sender). Each wrap (`EciesWrap`) is a fixed-width 81-byte record: a 33-byte
ephemeral secp256k1 public key plus a 48-byte AES-256-GCM-wrapped copy of the content key (32-byte
key + 16-byte GCM tag). Wraps are carried inline in the envelope's signed body — see "wraps are
always inline" below.

**The AAD binding, and the attack it closes.** This is the single most important design decision in
this sub-wave. Consider an attacker who observes a legitimately-sealed message: envelope A, signed
by sender S1, addressed to recipient R1, with sealed body `C_A` and wrap list `W_A`. The attacker
holds their own valid keypair S2 and constructs envelope B: `sender = S2`, same recipients, same
`contentCid`, same `sentAtEpochSecond`/`replyTo`/`threadRoot`, `encryption = HYBRID_ECIES`,
`wraps = W_A` — and signs it correctly with S2's own key. Envelope B is **structurally valid and
correctly signed**. It passes every V0.9.1 check: the signature verifies under the embedded sender
key S2, R1 is addressed, and the CID binding holds because the body bytes are unchanged. R1's inbox
accepts it and shows a message apparently from S2 whose content S1 actually wrote in confidence to
R1. Nothing in V0.9.1's checks stops this — only the associated data can. `MailAadContext` closes it
by deriving a canonical, content-independent serialization of the envelope's context (sender, the
*full* recipient set, timestamp, encryption mode, `replyTo`/`threadRoot` — deliberately NOT
`contentCid`, see below) and folding it into two domain-separated SHA-256 digests: `aadForBody`
(binds the body AEAD to the sealed-body format version and this context) and `aadForWrap` (per
recipient slot, additionally binding `contentCid`, the slot index, the slot's public key, and the
ephemeral public key). Both are passed as AES-GCM associated data. Because envelope B's sender
differs, R1's re-derived `aadForWrap` differs from the one S1 sealed under — the HKDF-derived wrap
key differs AND the GCM AAD check fails, so `HybridEcies.open` fails for two independent reasons,
not one. `HybridEciesAdversarialTest`'s wrap-transplant case proves this concretely: it opens the
*identical* wrap/body bytes once under envelope A's context (succeeds) and once under envelope B's
(fails) — isolating the AAD, and nothing else, as the cause.

`contentCid` is deliberately excluded from `aadForBody` (it is the CID of the body AEAD's own
*output*, so including it would be circular) — but a body swap is still caught, in three
independent ways: `aadForWrap` includes `contentCid`, so a swapped body cannot unwrap the content
key at all; `HybridEcies.open` separately re-checks `MessageBodyCodec.cidFor(sealedBodyBytes) ==
envelope.contentCid` before ever calling `aadForBody`; and `contentCid` is itself inside the
envelope's signed body, so an unchanged sender cannot swap it without breaking their own signature.

**The key derivation, and what `Secp256k1.ecdh` actually returns.** `fr.acinq.secp256k1:secp256k1-kmp:0.23.0`'s
`ecdh(privateKey, publicKey)` was empirically confirmed — not assumed — to return exactly
`SHA-256(compressed 33-byte serialization of the shared point)`, libsecp256k1's default ECDH hash
function, NOT the raw X coordinate (`lapis-net-identity`'s `ecdhSharedSecret` doc comment states
the finding; `EcdhAgreementTest` pins it as a regression, independently recomputing the shared
point via the same jar's `pubKeyTweakMul`/`pubKeyCompress` primitives). Consequently the ECDH
output is already full-entropy and needs no additional pre-hash before use as HKDF input keying
material — HKDF-Extract is retained anyway (cheap, lets the ephemeral public key participate as
salt, keeps the construction textbook-shaped) but is not load-bearing for entropy here.
HKDF-Expand IS load-bearing: `HKDF-SHA256(ikm = ecdhSharedSecret(...), salt =
ephemeralPublicKey.bytes, info = "LapisNet:mail-hybrid-ecies:v1:wrap-key" || aadForWrap(...), L =
44)` yields a 32-byte AES key and a 12-byte GCM nonce, per recipient slot — making each slot's
derived key a distinct function of the AAD context, so a transplanted wrap fails at the KDF layer,
not merely at the AEAD tag check. **The wrap's GCM nonce is never transmitted** — it is
HKDF-derived, putting zero attacker-controlled nonce bytes on the wire (the wrap key is single-use
by construction: a fresh ephemeral keypair per `seal()` call and a distinct HKDF context per
recipient slot make nonce reuse impossible unless the ephemeral key itself repeats, in which case a
transmitted nonce would not help either). This mirrors RFC 9180 (HPKE)'s key-schedule shape. The
**body's** AEAD nonce, by contrast, IS an explicit random 12-byte field in the `SealedBody` blob —
the content key is sender-chosen and not tied to a freshly-generated asymmetric key, so an explicit
random nonce is the belt-and-braces choice for that layer, and gives the freshness invariant a
second, independent source.

**Wraps are always inline** — there is deliberately no CID-referenced "recipients blob" variant for
high recipient counts. A CID-referenced blob is unfetchable in this codebase for exactly the reason
`MailFrameCodec` already carries the body inline instead of a pointer (see that section above):
`Kademlia.dialPeer` is documented broken since V0.1.4, and `InboxGossip`'s validator may make no
network calls — a recipient could never reliably obtain their own wrap from a blob referenced only
by CID. At `MAX_RECIPIENTS = 64` the worst-case wrap section is `2 + 65 × 81 = 5,267` bytes, which
brings the largest possible signed envelope body from V0.9.1's ~2.6 KB to ~7.9 KB — about 12% of the
65,535-byte envelope-section ceiling and 3% of the 256 KiB gossip ceiling. There is no size
pressure to relieve. A future high-fan-out variant would get its own `EncryptionMode` wire value —
the mechanism this codebase already uses for forward-compatible mode additions (`LtrRecordCodec`'s
`proofType` precedent) — not a retrofit of this one. The wire format's `VERSION` byte stays `1`: an
`EncryptionMode.NONE` envelope's encoding is byte-identical to V0.9.1's, the new wrap section is
gated by the already-signed encryption byte, and a pre-V0.9.2 node rejects a `HYBRID_ECIES`
envelope at the encryption check before ever reaching the wrap section.

**The validator never decrypts.** `InboxGossip.onGossipMessage` is only ever given a
`Secp256k1PublicKey` — private key material never enters the GossipSub validator, by construction.
An accepted `HYBRID_ECIES` message is indexed as `InboxPayload.Sealed`, still encrypted; decryption
is an explicit, later, caller-driven `HybridEcies.open` call with a keypair. `InboxMessage` is now a
thin wrapper over a sealed `InboxPayload` (`Plaintext` or `Sealed`) rather than an always-decoded
`MessageBody`, with a `body: MessageBody?` convenience accessor (`null` for still-sealed mail) kept
for source compatibility with V0.9.1 call sites.

**Bounded work, independent of wrap count.** `HybridEcies.open` locates its own wrap slot by index
(comparing the local identity against the envelope's signed recipient list, falling back to the
sender for the self-wrap) — never by trial-decrypting every wrap in the list. It performs exactly
one ECDH and two AES-GCM operations per call, regardless of how many recipients the envelope
addresses; a trial-decryption loop would let a 65-wrap envelope cost 65 ECDH operations per delivery
attempt, an amplification vector this design removes entirely. `EciesWrapCodec.decodeFrom` applies
the same check-then-allocate discipline as every other codec in this module: `wrapCount` is
validated against both an absolute cap (`MAX_WRAPS = 65`) and the expected `recipientCount + 1`
BEFORE a single wrap record is allocated — total allocation for the wrap section is bounded at
`65 × 81 = 5,265` bytes before any input is trusted, mirroring the CID-length-overflow lesson from
V0.9.1's own security round above.

**Deliberately accepted gaps:**

* **No forward secrecy.** Archived mail must stay decryptable for as long as the recipient holds
  their long-term secp256k1 identity key — there is intentionally no ratchet, no ephemeral-key
  deletion, and no post-compromise security; compromise of a recipient's long-term private key
  retroactively exposes every message ever sealed to them. This is the explicit product requirement
  for a store-and-forward email replacement, not an oversight — V0.8's Double Ratchet is the
  forward-secret 1:1 channel and is a different subsystem.
* **No post-quantum hybrid.** secp256k1 ECDH only — a store-and-forward archive is precisely the
  harvest-now-decrypt-later target, accepted for now; a PQ-hybrid KEM would be a new
  `EncryptionMode` wire value.
* **No key rotation for archived mail.** A sealed body is bound to the identity keys that existed
  at send time; rotating an identity key makes previously received mail permanently unreadable.
* **No multi-device wrapping.** Exactly one wrap per recipient's single published identity key — a
  recipient with two devices must share the private key between them; V0.8's multi-device sub-wave
  was cut from this arc.
* **`MLS_ARCHIVE` remains reserved and rejected outright**, as above.

**Wire-format changes.** `MessageEnvelopeCodec.encodeSignedBody`'s layout gains an optional trailing
section: `... | replyTo(replyToLen) | threadRootLen(2) | threadRoot(threadRootLen) | wrapCount(2) |
wrap(81) * wrapCount` — present iff `encryption == HYBRID_ECIES`. `SealedBodyCodec`'s independent
layout: `magic(4) "LNSB" | version(1) | flags(1, reserved) | nonce(12) | ciphertextLen(2) |
ciphertext(ciphertextLen)` (ciphertext includes the trailing 16-byte GCM tag).

== Mail threading, attachment encryption, and the browser UI (V0.9.3)

`lapis-net-mail`'s V0.9.3 sub-wave adds thread assembly, per-attachment encryption independent of
body encryption, a local sent-folder view, and — in `lapis-net-browser` — five HTTP routes plus a
hand-written mail UI. Builds directly on V0.9.1's envelope/body format and V0.9.2's `HYBRID_ECIES`
encryption, both already on `master`; no wire-breaking change to either.

**Threading key: `MessageEnvelope.replyTo` compared against `contentCid`, not `contentId()`.** This
is the single most consequential design fact for `ThreadBuilder` and is easy to get backwards, since
it is inferred from the type system rather than stated as a sentence anywhere in V0.9.1/V0.9.2:
`replyTo` and `threadRoot` share `contentCid`'s exact type (`io.ipfs.cid.Cid`) and reference the
*parent message's body-blob CID* (`MessageBodyCodec.cidFor`) — never the parent envelope's own
SHA-256 fingerprint (`MessageEnvelope.contentId()`, a raw `ByteArray` used only internally by
`InboxIndex`/`MailContentId` for gossip dedup, a strictly finer key). One consequence, inherited
from V0.9.1's field typing and not fixable without a wire-breaking change: two different envelopes
whose `MessageBody` bytes happen to be byte-identical collide on the same threading key
(`ThreadBuilder`'s internal test-seam overload documents "last one wins" for that case explicitly —
never reachable via the real `InboxGossip.messages()`/`SentFolder.latest()` paths, which already
dedup upstream by envelope content id). `threadRoot` remains carried-and-signed but structurally
unused this wave — only `replyTo` is walked into a tree.

**`ThreadBuilder` mirrors `lapis-net-trust`'s `VeritasGrantResolver` traversal discipline exactly**
— explicit-stack, non-recursive DFS, a global visited-CID set, and a hard depth cap
(`MAX_THREAD_DEPTH = 4,096`, the same rationale/magnitude as `VeritasGrantResolver.MAX_CHAIN_DEPTH`)
— because a mail thread is structurally the same forked-DAG-with-a-possible-cycle problem that
resolver already solves for the trust-grant backward-hash chain, and this codebase already has a
battle-tested solution for it. The one place the algorithm's *shape* diverges: `ThreadBuilder` needs
a **two-phase (ENTER/LEAVE) post-order walk**, because it must fully build every child `ThreadNode`
before assembling the parent (`VeritasGrantResolver`'s single-phase stack only ever needs to find
leaf tips, never reconstruct a tree).

**Why a genuine cycle is honestly constructible here, unlike in the trust module.**
`VeritasGrantResolver`'s doc comment argues a hash-chain cycle is cryptographically infeasible
through the real API, because a successor's `previousGrantId` is fixed to an *already-computed*
predecessor content id at grant-creation time. Mail has no such causality constraint: `contentCid`
is a pure function of `MessageBody` bytes alone, computable *before* any envelope exists,
independently for two unrelated bodies. A genuine 2-cycle (envelope A replies to B replies to A) —
and even a length-1 self-reference (`replyTo == own contentCid`) — is therefore trivially
constructible via the real production API (two real, correctly signed `MessageEnvelope`s, no
test-seam hack), and `ThreadBuilderTest` exercises exactly that construction rather than a synthetic
one.

**Cycle rejection happens at root selection, not mid-walk.** `replyTo` is a single-valued parent
pointer — each message has at most one parent — so any pure cycle consists entirely of members whose
`replyTo` points at another *in-set* cycle member, meaning every member of a cycle fails the "is
this a root" test by construction (a root is `replyTo == null`, or a `replyTo` pointing outside the
known set). A cycle can therefore never be reached by a downward walk starting from a legitimate
root: reachability follows `replyTo`-defined child edges strictly outward from a root, and nothing
in a cycle has such an ancestor. The consequence, deliberately different from a literal
"truncate-mid-walk" reading and tested explicitly as a "cascading exclusion" case: the entire cycle
— *and anything that transitively replies only into it* — is silently absent from the assembled
forest, never a crash, never an infinite loop, always bounded `O(known.size)` work. The mid-walk
`visited`-set guard inside the per-tree DFS is kept anyway as defense-in-depth for a future
relaxation of the single-parent-pointer model, mirroring `VeritasGrantResolver`'s own
belt-and-braces cycle guard — under today's data model it is structurally unreachable, for a
different underlying reason than in the trust module (there, no cycle can exist at all; here,
cycles can exist but are excluded before any walk starts).

**Receipt-order independence is a tested convergence property, not an incidental one.** Each
parent's children are sorted exactly once — by an unsigned, byte-lexicographic comparator over the
child's `contentCid` bytes, mirroring `VeritasGrantResolver`'s own `GrantContentIdBytesComparator`
tie-break — before any walk begins, and root selection itself is built purely from set membership
(a `HashMap` keyed by `contentCid`), never from the input list's position. Two nodes that eventually
hold the identical `known` *set*, however differently the underlying `List<InboxMessage>` argument
was ordered, therefore produce byte-for-byte identical `ThreadNode` trees. `ThreadBuilderTest`
asserts this directly: the same envelope set fed through `build()` in several different orders
(including `.shuffled()`) yields structurally identical forests.

**Attachment encryption: always a fresh key, never the body's `HYBRID_ECIES` content key.**
`MailAttachmentCipher.encrypt` generates an independent, random AES-256-GCM key at encrypt time for
every attachment, regardless of the enclosing message's own `EncryptionMode` — the design decision
is stated prominently in that object's own class doc comment, with four reasons: (1) attachment
encryption is explicitly *orthogonal* to body encryption (the product requirement is "an
unencrypted newsletter with one encrypted PDF attachment" to be representable), and a design that
reuses the body key only helps the `HYBRID_ECIES` case, needing an entirely separate mechanism for
`EncryptionMode.NONE` anyway — one uniform mechanism has a single code path and a single test
surface for both; (2) reusing `HybridEcies`'s content key would require plumbing a short-lived,
sensitive symmetric key across a module boundary it currently never crosses (`HybridEcies.open`
already zero-fills that key immediately after use) — pure coupling cost for no benefit; (3)
attachment fetch (`GET /api/mail/attachment/{cid}`) is architecturally separate from, and may happen
much later than or never after, the body fetch/decrypt — `AttachmentRef.encryptionKey` already
travels *inside* the (possibly sealed) `MessageBody`, so it is trivially available the moment the
recipient has decrypted the body once, with no extra derivation step; (4) confidentiality is
identical either way for `HYBRID_ECIES` messages — the attachment key is only ever visible after a
successful `HybridEcies.open`, exactly the boundary a reused key would offer, with none of the
coupling cost.

**Known, accepted asymmetry for `EncryptionMode.NONE` messages.** An attachment's
`AttachmentRef.encryptionKey` travels in the clear inside the plaintext gossip frame — visible to
anyone who computes and subscribes to the recipient's `InboxTopics.forRecipient` topic, i.e. anyone
already inside that narrow, already-weak `NONE`-mode confidentiality boundary that subject/body
already have. Independent attachment encryption in a `NONE`-mode message therefore protects only
against a passive bystander who never fetches/decrypts that specific attachment — not against anyone
already observing the frame. Stated here as a documented, accepted property, not a defect.

**AAD choice: a fixed, non-secret, domain-separating constant, not a message-specific binding.**
`MailAttachmentCipher` uses a single tag (`"LapisNet:mail-attachment:v1"`) for every attachment's
AEAD, unlike `HybridEcies`'s wrap/body AEADs, which must resist a cross-envelope "wrap transplant"
because a wrap is a *separate, reusable* artifact carried at envelope level (see `MailAadContext`
above). An attachment's `(cid, encryptionKey)` pair instead lives *inside the same signed
`MessageBody`* as every other `AttachmentRef` field — the envelope signature already transitively
authenticates the pairing, exactly as it already does for `MessageBody.subject`/`MessageBody.body`.
There is no cross-envelope transplant surface here to close with a context-specific AAD; a fixed
domain tag is sufficient and simpler.

**`EncryptedAttachmentBlob`/`EncryptedAttachmentBlobCodec`: a 32-bit, not 16-bit, ciphertext-length
field.** Unlike `SealedBody`, which rides inside the gossiped `MailFrameCodec` frame and is therefore
capped by that frame's practical size ceiling, an encrypted attachment blob is stored under its
*own* Nabu CID and never embedded in a gossip frame at all — so it can legitimately exceed
`MessageBodyCodec.MAX_BODY_BLOB_SIZE`. `MAX_CIPHERTEXT_BYTES` reuses `AttachmentRef`/
`MessageBodyCodec`'s own already-accepted 1 GiB declared-size ceiling (`MAX_ATTACHMENT_SIZE_BYTES`)
as this codec's ciphertext ceiling plus the 16-byte GCM tag, rather than inventing a new arbitrary
number. Unlike every other `decode()` in this module, this codec's check-before-allocate discipline
is defense-in-depth/consistency rather than closing a gossip-reachable amplification vector: this
path is only ever reached from `GET /api/mail/attachment/{cid}`'s explicit, local-caller-triggered
fetch, never from `InboxGossip`'s validator.

**`AttachmentRef`/`MessageBodyCodec` wire-format change is additive, `VERSION` stays `1`.** A new,
previously-reserved flags bit (`FLAG_ATTACHMENTS_MAY_HAVE_KEY = 0x01`) gates an optional
`keyPresent(1) | key(32)` sub-record appended to each attachment entry, mirroring
`MessageEnvelopeCodec`'s own V0.9.2 wrap-section justification structure exactly: (1) a body with
zero keyed attachments encodes byte-identical to V0.9.1/V0.9.2 — the flag is only set when at least
one attachment carries a key; (2) the new sub-fields are gated by an already-reserved, now-used flag
bit, never silent structural drift; (3) a pre-V0.9.3 decoder cleanly rejects (never misparses) a
body that sets the new bit, via its own pre-existing `if (flags != 0) throw ...` reserved-bits
check. Worst-case body-blob arithmetic grows by 528 bytes (16 attachments × 33 new bytes each) over
the pre-V0.9.3 figure — still comfortably under `MAX_BODY_BLOB_SIZE`; no cap changes needed.

**`SentFolder`: deliberately one evicting cap, not `InboxIndex`'s two — a stated departure, not a
silent one.** `InboxIndex`'s *separate*, non-evicting persistence-reservation cap exists to gate
`NabuStorage.put()` against an attacker's unbounded gossip flood — a real defensive purpose.
`SentFolder.add` is only ever called *after* `MailSender.send` has already unconditionally,
successfully persisted both the envelope and the body; by the time `add` runs, persistence has
already happened and cannot be retroactively gated. A second cap here would bound nothing real — it
would only track which content ids this class itself considers "reserved," with zero actual gating
effect on any storage call. `SentFolder` therefore implements a single evicting tracking cap
(`MAX_TRACKED_SENT_MESSAGES = 8,000`, mirroring `InboxIndex.MAX_TRACKED_MESSAGES`'s sizing
rationale unchanged), the honest mechanism for the one real thing this class needs to bound: its own
in-memory footprint. This mirrors `MailFrameCodec`'s own established precedent for stating a
deliberate spec departure explicitly in the code, rather than silently deviating from it.
Population is the *caller's* responsibility — `MailSender.send` has no reference to any particular
`SentFolder` instance and never populates one implicitly; `lapis-net-browser`'s `POST /api/mail`
route handler is that caller, via `SentFolder.add(sent)` immediately after `MailSender.send`
returns.

**Browser routes: `MailApi.kt`, installed into the same routing tree as every other route.** Five
new routes (`GET /api/mail`, `GET /api/mail/sent`, `GET /api/mail/thread/{cid}`, `POST /api/mail`,
`GET /api/mail/attachment/{cid}`) live in a dedicated `MailApi.kt` file purely for readability given
their combined size — `installBrowserApi` calls a single `Route.installMailRoutes(deps)` extension
from inside the exact same `routing { }` block every other route (timeline, trust, Karma, connect)
is installed into. There is no separate mail-specific routing mechanism to learn: this repo's other
domains (e.g. Karma's `POST /api/karma`) wire their routes the identical way, directly inline in
`BrowserApi.kt` — mail routes are installed the same way, just via one extra indirection for file
size. `BrowserApiDependencies` gains `mailInbox: InboxGossip`, `mailSender: MailSender`,
`sentFolder: SentFolder`; `BrowserServer.start`/`stop` construct/tear these down in the same
attach/stop-order pattern already established for Veritas/Virtus/Karma/posts.

`GET /api/mail` and `GET /api/mail/sent` return `MailSummaryResponse`s — subject, a bounded
plaintext body preview (`MAIL_BODY_PREVIEW_CHARS = 280` characters of the *verbatim* Markdown
source, never rendered), attachment metadata (name/mime/size/`encrypted` — the key itself never
serialized into any response), and a `decryptionFailed` flag. For a `HYBRID_ECIES` inbox entry,
`HybridEcies.open` is attempted with the local identity and any failure degrades to
`decryptionFailed = true` with a placeholder subject/body and an empty attachment list — never a
500, never fabricated attachment data from a body that failed to decrypt. A `SentMessage` (adapted
via `SentFolder.kt`'s `toInboxMessage()` extension) always takes the plaintext branch — the local
sender already holds its own plaintext regardless of the message's `EncryptionMode` — so
`decryptionFailed` is always `false` for `folder = "sent"`.

`POST /api/mail` validates every field and 400s cleanly *before* any side effect (mirroring
`/api/posts`/`/api/self-link`'s established byte-length-then-400 pattern): empty/malformed
recipient hex, an unrecognized encryption string (`MLS_ARCHIVE` explicitly rejected with its own
message, not lumped in with "unknown"), oversized subject/body, too many attachments, oversized
attachment name/mime, malformed `replyToCid`/`threadRootCid`, and — before any base64 decoding
happens — an attachment's declared upload size checked cheaply against
`MAX_MAIL_ATTACHMENT_UPLOAD_BYTES` (25 MiB, a route-level practical cap deliberately much stricter
than `MessageBodyCodec.MAX_ATTACHMENT_SIZE_BYTES`'s 1 GiB wire-format ceiling, because this route
buffers the whole base64 JSON request body in memory before any wire-format check ever runs). Each
attachment marked `encrypt = true` is routed through `MailAttachmentCipher.encrypt` and its
ciphertext blob stored under its own CID before `AttachmentRef`/`MessageBody`/`MessageEnvelope` are
built; the route then calls `MailSender.send` and, on success, `SentFolder.add`.

`GET /api/mail/thread/{cid}` builds a fresh `ThreadForest` from the current inbox+sent set on every
call — `ThreadBuilder.build` is cheap and `O(known.size)`, and this codebase's other in-memory
indexes are already documented as "provisional, revisit against real usage" at this same
personal-node scale, so no caching is attempted this wave. `GET /api/mail/attachment/{cid}` performs
a linear scan over the same known set (same scale caveat), locates the `AttachmentRef` by CID,
fetches its blob via `NabuStorage.get` (local blockstore only — see below), and — if
`encryptionKey` is present — decrypts it via `MailAttachmentCipher.decrypt` before responding with a
`Content-Disposition: attachment` header and the attachment's declared MIME type (defensively
`ContentType.parse`d with a safe fallback to `application/octet-stream`).

**`GET /api/mail/attachment/{cid}`'s cross-node fetch is limited by the same pre-existing
`NabuStorage.get()`/`Kademlia.dialPeer` gap documented since V0.1.4.** A node can only reliably
retrieve an attachment blob it already has locally — the sender's own node, or a node that fetched
it some other way. This is not a new limitation this wave introduces; it is the same gap every other
cross-node fetch in this codebase already carries, simply now visible through a new route. Reflected
directly in `TwoNodeMailBrowserIntegrationTest`'s own scoping: it asserts attachment *metadata*
(name/mime/size/`encrypted`) propagates correctly to the recipient via real gossip, and separately
that the *sender* — the node that actually has the blob — can fetch its own just-sent attachment via
its own `GET /api/mail/attachment/{cid}`; it does not assert the recipient can fetch the blob
cross-node, because that would not currently succeed.

**Browser UI: a second, self-contained static page, no new JS framework.** `mail.html`/`mail.js`
mirror V0.2.2's Minimal-Browser's own established discipline exactly — `fetch()` + `<template>` +
`cloneNode`/`querySelector` + `.textContent`, zero dependencies, no build step. The only change to
the existing timeline page is one new nav line in `index.html`'s header linking to `/mail.html`;
`app.js` is untouched. `mail.js` is deliberately Promise/`.then()`-based throughout, not
`async`/`await` — this codebase's own headless-browser XSS regression test
(`MailXssRenderingTest.kt`, `org.htmlunit:htmlunit`, a new test-only dependency added specifically
for this wave's mandatory security requirement below) runs on an embedded Rhino-derived JavaScript
engine that fully parses `Promise`/`fetch()` (with HtmlUnit's bundled fetch polyfill enabled)/arrow
functions/template literals, but does not parse `async function`/`await` syntax at all — confirmed
empirically, not assumed. Rather than special-case the test target or accept an untested rendering
path, `mail.js` itself is written in the dialect this codebase can actually verify end-to-end against
a real DOM. Message bodies render as their **verbatim Markdown source** inside a `white-space:
pre-wrap` `<pre>` element — no Markdown-to-HTML rendering in this wave, a deliberate, conservative
scope cut resolving `MessageBody`'s own V0.9.1 forward reference ("that is a browser-UI concern for
a later wave") given the mandatory XSS-escaping requirement immediately below; a future wave may add
real Markdown rendering with its own, separately-audited escaping discipline.

**Mandatory, non-negotiable XSS-escaping discipline.** Message subjects, bodies, attachment names,
and sender-derived display strings returned by `MailApi.kt` are entirely user-controlled content
this validator never sanitizes or interprets — `InboxGossip`'s validator accepts and indexes
whatever signed `MessageBody` a sender constructs, and `MailSummaryResponse.bodyPreview` is the
verbatim Markdown source, never rendered to HTML server-side either. Every DOM-insertion site in
`mail.js` goes through exactly one named helper, `setText(el, value)` (`el.textContent = value`) —
never `innerHTML`, never a template string interpolated into `innerHTML`, anywhere in the file. The
one place a value feeds an HTML *attribute-shaped* context — an attachment's download `<a href>` —
uses a DOM property assignment (`linkEl.href = ...`) rather than string concatenation into markup,
and the value in question (a server-generated, already CID-validated attachment CID) is not raw user
text to begin with, making this defense-in-depth on top of an already-safe value. This is a
mandatory security-audit checklist item for this wave, not a style preference, and it is verified —
not merely asserted — by `MailXssRenderingTest.kt`: a `<script>`/`onerror=` payload is sent as a real
message's subject and body via the real `POST /api/mail` HTTP API, the real `mail.html`/`mail.js`
page is loaded into a real, JS/DOM-executing headless browser (`org.htmlunit.WebClient`), and the
test asserts (a) the injected script/handler never executes (`window.__xssFired` reads back as JS
`undefined`, verified via `ScriptResult.isUndefined`, not a Java `null`), (b) the rendered DOM node's
`textContent` is the literal, unexecuted payload string, and (c) the serialized page contains the
payload HTML-entity-escaped (`&lt;script&gt;`) with no injected `<script>` element beyond `mail.js`'s
own `<script src>` tag. The test targets `GET /api/mail/sent`'s rendering path specifically (via
`mail.html`'s "Sent" toggle) rather than `GET /api/mail`'s, because GossipSub never self-delivers (a
gap documented since V0.9.1) — `/sent` is populated synchronously by the same `POST /api/mail` call
with zero gossip round trip needed, and `mail.js`'s rendering function for an inbox item and a sent
item is the exact same function (`renderMailItem`/`fillSummaryInto`, both consuming a
`MailSummaryResponse`), so this is a fully faithful test of the identical code path a received
message would go through.

**Deliberately accepted gaps, stated as such:**

* **No encrypted full-text search, no SMTP import gateway, no newsletter/subscription model.** Still
  cut, as documented since V0.9.1/V0.9.2 — no target wave assigned yet.
* **No address book, no pubkey-to-name mapping.** Explicitly carved out of this sub-wave's actual
  implemented scope (an earlier roadmap draft had listed it under V0.9.3) — no target wave assigned
  yet; recipients remain raw compressed secp256k1 keys everywhere in the UI and API.
* **`threadRoot` remains structurally unused.** Only `replyTo` is walked into a thread this wave —
  see `ThreadBuilder`'s own reasoning above.
* **Attachment cross-node fetch remains limited**, as above — inherited from `NabuStorage`, not a
  new gap this wave introduces.
* **No Markdown-to-HTML rendering in the browser UI**, as above — a deliberate, conservative scope
  cut given the mandatory XSS-escaping requirement.
* **No real pinning economy.** "Pinning" remains a no-op, unaffected by this wave, already documented
  in the V0.8/V0.9 arc planning notes.

== Mail spam protection (V0.9.4)

`lapis-net-mail`'s V0.9.4 sub-wave — the last of the V0.9 arc — gives a node an opt-in, purely
local defense against unsolicited mail: a Veritas-distance filter, a Karma-threshold filter, and a
Lightning first-contact deposit mechanism that lets an unknown sender pay their way past either
filter. Builds on V0.9.1's envelope format, unchanged since `master`.

**First dependency this module has ever taken on the scoring substrate — a deliberate reversal of
V0.9.1–V0.9.3's stated "mail is a separate subsystem" stance, mirroring `lapis-net-madli`'s own
precedent exactly.** `lapis-net-mail` now depends on `lapis-net-trust` (`api`, because `TrustGraph`
appears directly in `MailAcceptancePolicy.veritasPathCheck`'s public signature) — see that module's
`build.gradle.kts` V0.9.4 comment for the full reasoning. This is the same shape of exception
`lapis-net-madli` already established in V0.5 ("DELIBERATE DEVIATION from the Karma/Virtus 'no
sibling trust dependency' rule"): a module whose own core deliverable genuinely needs Veritas-
weighted decisions, with no other application-layer consumer positioned to do it instead. Deliberately
**still no dependency on `lapis-net-karma`**: that module has no existing notion of a per-IDENTITY
Karma score (`KarmaWeightCalculator`/`KarmaScoring` compute Karma per-CONTENT, folding votes toward
one target `Cid`) — deriving a sender's aggregate score from that model is an application-layer
composition this wave deliberately does not prescribe, so the Karma gate takes an injected
`KarmaScoreLookup` lambda instead. Deliberately **still no dependency on `lapis-net-virtus` or
`lapis-net-madli`** — `FirstContactDepositVerifier` structurally mirrors V0.6's `LightningProof`/
`LightningProofVerifier` but is a separate, reimplemented object (see below for why it cannot simply
call through), and nothing here needs a `MadliDailyVector`.

**`MailAcceptancePolicy` — a pure, no-I/O policy object, mirroring `MadliRoutingPolicy`/
`MadliReplicationPolicy`'s shape exactly.** `shouldAccept(sender, recipient, envelope,
hasVeritasPath, karmaScoreOf, gates, deposit)` returns a sealed `Accept`/`Reject(reason)` decision.
`MailAcceptanceGate` is a sealed `VeritasPath`/`KarmaThreshold(minScore)` choice; **an empty gate
list (`ACCEPT_ALL`, the default) always accepts** — the protocol-mandated default, checked first so
a node running no filters pays zero cost (no deposit verification, no Veritas/Karma lookups) for
messages it was always going to accept anyway. This is the same "the protocol itself does not
mandate X" principle `MadliReplicationPolicies.NEVER` already established, and the same View-
Pluralismus principle this document's Layering section states for Veritas/Karma/Madli generally: a
spammer with no Veritas path and no Karma remains a fully valid protocol participant whose messages
every OTHER node (running no filters, or different filters) is free to accept — filters are opt-in
node policy, never protocol-enforced.

**Multiple configured gates are OR-ed, not AND-ed.** A sender is accepted if they clear AT LEAST
ONE configured gate — a node running both `VeritasPath` and `KarmaThreshold` offers a sender two
independent ways past the filter, matching the anti-spam intent "let a stranger through if they
clear ANY bar I've set", not "clear every bar I've set". A verifying `FirstContactDeposit` bypasses
every configured gate regardless of how many are configured or how badly the sender fails them —
that is the entire point of the deposit mechanism: an unknown sender who paid gets through.

**`MailAcceptancePolicy.veritasPathCheck(graph, localIdentity)` is the one place `TrustGraph`/
`TrustPathFinder` are referenced directly — a thin adapter, not the policy's core.** This mirrors
`MadliAggregator.veritasObserverWeight`'s identical "trust-free core, thin caller-side adapter"
split (see that function's doc comment and `lapis-net-madli/build.gradle.kts`'s header comment for
the precedent): `shouldAccept` itself takes `hasVeritasPath: (Secp256k1PublicKey) -> Boolean` as an
injected lambda, exactly like `MadliAggregator.aggregate`'s injected `observerWeight` lambda, so the
policy's own unit tests never need to construct a real `TrustGraph` to exercise the OR-across-gates/
deposit-bypass/threshold-boundary logic — only the adapter function and its own dedicated tests
touch the real trust-graph machinery. Self (`candidate == localIdentity`) always passes, via
`TrustPathFinder`'s own self-trust axiom.
+
**Round-1 security audit (2026-08-04) — path EXISTENCE is not POSITIVE trust.**
`veritasPathCheck` originally tested `TrustPathFinder.findPath(graph, localIdentity, candidate) !=
null` — path existence, not a positive trust score. `MIN_TRUST_MICROS` (0) is documented on
`VeritasGrant` as both "default / no opinion" and "the value used to revoke a prior grant", and
`TrustGraph.build` admits zero-weight edges (only self-edges are dropped) — so `findPath` happily
returns a non-null, zero-score path for a revoked/zero-weight edge. The old check therefore made
revoking trust in a spammer a no-op for this gate, and let an entire Sybil cluster through behind a
single revoked/zero-weight hop. Fixed to `TrustPathFinder.trustMicros(graph, localIdentity,
candidate) > MIN_TRUST_MICROS`, matching `MadliAggregator.veritasObserverWeight`'s own precedent
(`observerWeight > 0.0`, filtering on `trustMicros`, never on path existence). See
`MailAcceptancePolicyTest`'s "a revoked (zero-weight) direct edge does NOT pass the gate" and
"a Sybil identity reachable only behind a zero-weight hop does NOT pass the gate" regressions.

**`FirstContactDeposit`/`FirstContactDepositVerifier` — structurally near-identical to V0.6's
`LightningProof`/`LightningProofVerifier`, deliberately reimplemented rather than called through.**
`LightningProofVerifier.verify`'s signature is intrinsically Virtus-specific (`LtrRecord.viewId`/
`initialValueMsat`/`cid`) and cannot be invoked against a `MessageEnvelope` — per this wave's plan,
`FirstContactDepositVerifier` reuses the *chain* (the same six-step shape) with mail's own
domain-separated memo tag (`"lapisnet-mail-first-contact:v1:"`, distinct from
`LightningProofVerifier`'s `"lapisnet-ltr:v1:"`) and mail-specific binding fields:

 1. `sha256(deposit.preimage) == deposit.paymentHash`.
 2. `deposit.signedInvoice` parses as a real BOLT-11 invoice with a valid signature
    (`Bolt11Invoice.read` verifies the signature internally as part of parsing).
 3. The invoice's own parsed payment hash equals `deposit.paymentHash`.
 4. The invoice declares a non-null amount, and that amount (msat) equals
    `deposit.requiredAmountMsat` exactly — `FirstContactDeposit`'s own analogue of
    `LtrRecord.initialValueMsat`: a structurally-asserted claim, cross-checked against the invoice's
    real embedded amount, never trusted on its own.
 5. The invoice's signer (`nodeId`) equals the recipient's bytes — **mandatory, not optional**, the
    same protocol commitment V0.6 established: a Lightning node key IS its Lapis identity. Without
    this, a sender could pay ANY Lightning node (including their own) and claim the resulting proof
    earns entry into a completely different recipient's inbox.
 6. The invoice's `description` equals `canonicalMemo(envelope.contentId(), envelope.sender,
    recipient)` exactly — the anti-replay check, this wave's central security property.

**`canonicalMemo`'s three fields are each individually load-bearing — this is the wave's central
security property, worked through explicitly rather than assumed.** `envelopeContentId` —
`MessageEnvelope.contentId()`, a SHA-256 over the envelope's FULL encoded bytes including the
signature — binds the deposit to this EXACT envelope, not merely its body content.
+
**Round-1 security audit (2026-08-04) — memo binding was insufficient.** The memo originally bound
only `envelope.contentCid` (the body's content id). `sentAtEpochSecond`/`replyTo`/`threadRoot`/
`recipients` are all signed but sit outside `contentCid`, while the inbox dedup key
(`MessageEnvelopeCodec.contentId()`, via `InboxIndex.canAccept`) hashes the full encoded envelope
including those fields. So N envelopes sharing one `contentCid` but differing only in, e.g.,
`sentAtEpochSecond` shared the SAME memo yet had N distinct `contentId`s — one paid deposit admitted
all N (the auditor's probe fed 50 such envelopes through a real `InboxGossip`/`NabuStorage` and
measured "accepted = 50 of 50"). Binding the full envelope `contentId` instead closes this in one
step, matching the dedup key exactly — see `FirstContactDepositVerifierTest`'s `sentAtEpochSecond`-
only regression and `MailSpamResistanceTest`'s equivalent gossip-integration regression.
+
`sender` binds the deposit to the exact identity that paid it — now redundant with
`envelopeContentId` (a re-signed envelope already has a different `contentId`) but kept for
defense-in-depth. `recipient` binds the deposit to the exact recipient it was paid to gain entry to;
without it, a deposit paid to earn entry into recipient A's inbox could be replayed against
recipient B's inbox for the identical `(sender, envelopeContentId)` pair when one envelope addresses
multiple recipients — also (redundantly, defense-in-depth) enforced by the mandatory `invoice.nodeId ==
recipient` check above, mirroring `LightningProofVerifier`'s own double-binding of `viewId` via both
its memo and its `nodeId` check. `FirstContactDepositVerifierTest`'s central test constructs this
proof carefully: it shows a deposit valid for envelope A is rejected for a second, different envelope
B, THEN shows an invoice re-signed for B's own canonical memo (everything else about the deposit
left unchanged) verifies true against B — isolating the memo as the sole differentiator, proving
every other check (hash, signature, amount, recipient binding) would otherwise have passed.

**Deliberately NOT checked: invoice expiry — the same deliberate choice V0.6 documented and made,
restated explicitly here rather than silently inherited.** A settled payment's invoice may
legitimately be past its own BOLT-11 expiry by the time the resulting envelope propagates through
gossip — the payment already happened, and expiry only ever governs whether a *new* payment attempt
against that invoice should still be accepted, irrelevant once a preimage already proves settlement.
`FirstContactDepositVerifierTest` asserts this explicitly (an already-expired invoice still verifies
`true`), so a future change to this behavior is caught by CI rather than silently drifting.

**`InboxGossip.onGossipMessage` gained an optional `acceptance: MailAcceptanceCheck?` parameter,
`null` by default.** Unlike Madli's policy objects (V0.5, built but explicitly left unwired that
wave), this policy IS wired into the gossip hot path when a caller opts in. The check runs
**AFTER** the signature/addressing/CID-binding checks (cheap, must reject first, unchanged
ordering) and **BEFORE** payload decode/dedup/persistence — a rejected sender costs this node no
payload allocation and no index/storage work. This preserves the module's established "zero clock,
zero network calls in the validator" invariant exactly: `MailAcceptanceCheck.trustGraph` is an
already-built local snapshot the caller supplies (never fetched or refreshed by the validator
itself), `karmaScoreOf` and `depositLookup` are pure local lookups. A `null` `acceptance` (the
default, and every pre-V0.9.4 call site's unchanged behavior) preserves "accept everything addressed
to me" exactly.

**The deposit itself does NOT travel in-band over `MailFrameCodec`'s wire format this wave — a
deliberate scope cut, consistent with this whole mechanism's other "obtained out-of-band"/"manual,
application-layer decision" cuts below.** `MailAcceptanceCheck.depositLookup` is a pure, local,
no-I/O function from an already-decoded `MessageEnvelope` to a `FirstContactDeposit` the caller
already holds for it, or `null` if none is available — a real deployment would populate a small
local map (envelope content id -> deposit) once its application layer observes an out-of-band
Lightning payment settle. A future wave that extends `MailFrameCodec`/`MessageEnvelopeCodec` to
carry a deposit on the wire can supply this same lambda backed by the decoded frame instead, without
`MailAcceptancePolicy`/`InboxGossip` changing at all.

**Test suite.** `MailAcceptancePolicyTest` — pure, no-network unit tests mirroring
`MadliRoutingPolicyTest`/`MadliReplicationPolicyTest`'s shape: no-Veritas-path rejected,
Veritas-path accepted, Karma-threshold accepted/rejected at the exact boundary (`>=`, tested with a
value one ULP below the threshold), OR-across-gates semantics (failing one gate but clearing the
other still accepts; failing both rejects), `ACCEPT_ALL` accepts a totally unknown sender, a
genuinely-verifying real deposit (real `lightning-kmp` cryptography, not a stub) bypasses every
configured gate, and a deposit that fails `FirstContactDepositVerifier.verify` does NOT bypass a
failing gate. `FirstContactDepositVerifierTest` — mirrors `LightningProofVerifierTest`'s shape
exactly: a fully valid tuple verifies true; corrupted preimage, wrong claimed amount, an invoice
actually signed for a different amount, an amountless invoice, wrong signer (recipient-binding),
mismatched embedded payment hash, a garbage invoice string, and a `descriptionHash` invoice are all
rejected cleanly, never thrown; the central anti-replay memo-binding test described above; and the
explicit already-expired-invoice-still-verifies-true assertion. `MailSpamResistanceTest` — the
adversarial, real-node, real-`InboxGossip.onGossipMessage` spec: a flood of 1,000 distinct unknown
senders entirely rejected before persistence (proven for a representative sample via the same
mint-CIDs-on-a-separate-node technique `MailEnvelopeAbuseTest` established — checking all 1,000
individually would be redundant, since the acceptance-policy rejection returns before the
persistence code path is reached uniformly for every rejected case), with one Veritas-linked sender
among the flood still getting through and landing as the index's sole entry; a real, validly-signed
self-link (`VeritasGrant.create(truster = X, target = Y, trustMicros = MAX_TRUST_MICROS)`, resolved
through `TrustGraph.fromGrants` — the exact same resolution path a real deployment uses) proven
unable to manufacture a fake Veritas path into the local identity's mail-acceptance graph, mirroring
V0.4's own `BrowserApiRoutingTest` self-link Sybil-resistance regression exactly, applied here
against the mail acceptance path specifically; and a single valid deposit proven unable to admit a
second, different message at the full gossip-integration level (a depositLookup callback that
naively hands out the same deposit for two different envelopes, both routed through the real
`InboxGossip.onGossipMessage`), re-proving `FirstContactDepositVerifierTest`'s replay-prevention
property at the wiring level, not just the unit-test level.

**Review findings this wave.** A single review + security round both approved with no
CRITICAL/MAJOR findings — the memo-binding's three-field justification was independently re-derived
from first principles (the sender-substitution replay scenario above) rather than taken on faith,
and the self-link Sybil-resistance claim was independently re-confirmed to hold against the mail
acceptance path specifically, not merely assumed to carry over from V0.4's original trust-module
proof.

**Known, deliberately accepted gaps:**

* **No market-based pinning economy.** Carved out of this sub-wave's actual scope — see
  `docs/roadmap.adoc`'s V0.9.4 section for the full carve-out note; no target wave assigned yet.
* **No DHT-inbox discovery path.** `InboxGossip` remains gossip-only, unchanged since V0.9.1.
* **The first-contact deposit does not travel on the wire.** See above — `MailAcceptanceCheck.depositLookup`
  is the pluggable seam a future wave can back with a real wire field without changing
  `MailAcceptancePolicy`/`InboxGossip`.
* **No embedded Lightning node.** Identical scope cut to V0.6: nothing in this codebase can
  construct or send a payment or issue an invoice in-process. A deposit's invoice must be obtained
  out-of-band; the release/refund decision after a deposit is verified is a manual, application-
  layer decision, not automated this wave.
* **No live payment settlement testing in CI.** Same V0.6 precedent: tests substitute an
  in-process-generated preimage/invoice with real `lightning-kmp` cryptography end to end; only the
  actual network settlement event is out of reach in a test environment.
* **No per-identity Karma score inside `lapis-net-karma`.** `KarmaScoreLookup` is an injected
  lambda; deriving a sender's aggregate score from `lapis-net-karma`'s per-CONTENT Karma model is an
  application-layer composition this wave deliberately does not prescribe.

With V0.9.4 landed, the entire V0.9 arc (envelope/body format, `HYBRID_ECIES` encryption, threading/
attachment-encryption/sent-folder/browser-UI, and this spam-acceptance filter) is complete on
`master` — see `docs/roadmap.adoc`'s "V0.9 arc complete" section for the full closing summary.

== Peer/presence directory records (V0.8.1)

`lapis-net-directory` (new module) — the first sub-wave of the V0.8 (direct messages and calls)
arc, reduced in scope on 2026-08-04 (MLS/conferencing/SFU cut entirely, no group-calling target
remains). Gives every identity a signed, self-published way to say "I can currently be reached at
these addresses, my libp2p transport identity is X, I claim these capabilities, and this statement
is valid until T" — the foundational discovery layer V0.8.2 (X3DH prekey-bundle exchange) resolves
recipients' prekey bundles through, and V0.8.4 (online DM) resolves recipients' current network
addresses through.

**Gossip-only, no DHT publication — the same accepted limitation as every V0.9 mail sub-wave.**
`org.peergos.protocol.dht.Kademlia.dialPeer` has been documented broken since V0.1.4 (see the
Storage section above) — propagation is entirely via `PeerDirectoryGossip`'s dedicated GossipSub
topic (`LapisNet:peer-record-gossip:v1`), mirroring `InboxGossip`'s identical precedent. A node
offline during the gossip window has no catch-up path.

**THREE independently-verified signatures per record, not two — this wave's central design
decision, verified via the mandatory adversarial test rather than merely assumed correct, and
hardened once already (round 2 of this wave's own security audit).** `PeerRecord` embeds
`identity`'s own pre-existing `IdentityBinding` (from its `DualKeyIdentity`, computed once at
identity-generation time and reused verbatim, not a second, PeerRecord-specific binding scheme) —
this proves "`identity` vouches for `binding.ed25519PublicKey` being its own transport key"
(`IdentityBinding`'s own `"LapisNet:identity-binding:v1"` tag). The record's OWN outer signature (a
SEPARATE ECDSA signature over a SEPARATE, `"LapisNet:peer-record:v1"`-tagged digest of the full
record body, including the embedded binding's bytes) proves "`identity` signed THIS EXACT record" —
addresses, capabilities, sequence number, and TTL included.

**`verify` + `verifyBinding` alone are NOT sufficient — V0.8.1 sub-wave audit round 2, major finding
1, a gap this wave's ORIGINAL docs claimed was closed but was not.** `IdentityBinding` is a ONE-WAY
vouch: it proves `identity` signed `binding.ed25519PublicKey`, but an Ed25519 PUBLIC key is public
by definition, so ANYONE can mint a FRESH, self-consistent
`IdentityBinding.create(attackerSecp256k1KeyPair, victimEd25519PublicKey)` — this passes
`verifyBinding` (the attacker's own key correctly signed it) while `peerId` resolves to the VICTIM's
real, derivable `PeerId`. Both `PeerRecord.verify` (genuinely signed by the attacker) and
`verifyBinding` (genuinely self-consistent) then pass — exactly the "signature-valid record must
still be rejected on a second, independent check" property this wave's round-1 design claimed to
prove, except the round-2 auditor's PROBE A ran this EXACT construction through the real gossip
validator and it was accepted, indexed, persisted, and re-propagated
(`outerSignatureValid=true, verifyBinding=true, recordPeerId==victimRealPeerId=true,
validatorResult=Valid`). The root cause: neither check requires PROOF-OF-POSSESSION of the Ed25519
PRIVATE key — `IdentityBinding` only ever requires possessing the PUBLIC half. Round-1's own
regression test (`PeerRecordSpoofingTest`'s case (a)) did not catch this because it only tests
REUSING a victim's OWN binding OBJECT verbatim (whose embedded signature was made by the victim's
key and therefore cannot verify against the attacker's identity) — it never tests RE-SIGNING a
fresh binding over the victim's public key, which is exactly what makes the forged binding
self-consistent from the attacker's own perspective.

**Fix: `PeerRecord.possessionProof`, a NEW, fourth 64-byte field — a genuinely MUTUAL binding.** A
SEPARATE Ed25519 signature, by `binding.ed25519PublicKey`'s own PRIVATE key
(`"LapisNet:peer-record-possession:v1"`-tagged, deliberately its own domain tag, distinct from both
`"LapisNet:peer-record:v1"` and `"LapisNet:identity-binding:v1"`), over `identity`'s raw bytes —
computed once, fresh, inside `PeerRecord.create` at record-signing time, using the caller's
`DualKeyIdentity.ed25519KeyPair` (never touching or changing `IdentityBinding` itself, so every
OTHER module that embeds an `IdentityBinding` — `lapis-net-karma`, `lapis-net-madli`,
`lapis-net-mail`, `lapis-net-trust`, `lapis-net-virtus`, `lapis-net-browser` — is completely
unaffected; this fix is scoped entirely to `lapis-net-directory`). Something only the genuine
holder of the Ed25519 PRIVATE key can produce, and the auditor's forged-binding construction above
cannot, since it never had access to the victim's Ed25519 private key, only the public key copied
off an earlier, legitimately-published record. **All three checks are now load-bearing and no pair
alone is sufficient** — `PeerDirectoryGossip.onGossipMessage` calls `PeerRecord.verify`,
`verifyBinding`, AND the new `verifyPossession` as three independent steps before trusting
`peerId`/`addresses`. `PeerRecordSpoofingTest`'s case (a) remains the ORIGINAL (already-closed)
exploit shape — reusing a victim's own binding object verbatim; its NEW case (h) is the round-2
regression — re-signing a FRESH binding over the victim's public Ed25519 key, proving `verify` and
`verifyBinding` both genuinely pass while `verifyPossession` alone catches it, end to end through
the real validator.

**`from` (the GossipSub sender) is deliberately NOT used in this decision.** `onGossipMessage`
already receives a transport-level `from: PeerId` parameter; using it as a proof-of-possession
anchor was considered (round-2 audit, minor finding 5) and rejected for THIS codebase as currently
wired: `GossipPubSub.attach` builds its `GossipRouterBuilder` with the library's DEFAULT
`messageValidator` (`io.libp2p.pubsub.PubsubRouterKt.NOP_ROUTER_VALIDATOR`, confirmed directly
against the real jvm-libp2p 1.3.5 jar), not the `SIGNATURE_ROUTER_VALIDATOR` that would actually
authenticate `from` against the message's embedded key/signature — so `from` carries no
cryptographic guarantee at the transport layer here today, and comparing `record.peerId == from`
would be a false sense of security rather than a real check. `possessionProof` sidesteps this
entirely by proving possession INSIDE the record itself, independent of whatever pubsub transport
or relay chain carried it.

**A THIRD, structural check closes a gap the two signature checks above do not cover — bytes of the
right length are not necessarily a valid point on the curve (V0.8.1 sub-wave audit round 1, major
finding, fixed before this wave's commit landed).** `Ed25519PublicKey`'s constructor now validates
that its 32 bytes decode to a genuine Ed25519 curve point (`Ed25519PublicKeyParameters(bytes, 0)`,
wrapped in `runCatching` exactly like `Secp256k1PublicKey`'s own constructor-time curve check this
mirrors — see that class's doc comment for the precedent). Before this fix, an attacker could sign
32 GARBAGE bytes as their OWN `binding.ed25519PublicKey` with their OWN secp256k1 key — the binding
is self-consistent (`IdentityBinding.verify` only checks that `identity` vouches for WHATEVER bytes
sit in `ed25519PublicKey`, not that those bytes are a valid key), so both `PeerRecord.verify()` AND
`verifyBinding()` passed, the record was indexed/persisted/re-propagated to every subscriber, and
only THEN did `record.peerId`/`record.toString()` throw `IllegalArgumentException` — a single gossip
message permanently poisoning an index slot and a persistence reservation on every subscribed node
with a record that is structurally valid, cryptographically valid, and functionally
undereferenceable, exactly where V0.8.2's prekey resolution and V0.8.4's online-DM address
resolution are documented to call `index.current(identity)?.peerId`. `PeerRecordCodec.decode` is the
only site in the module that constructs an `Ed25519PublicKey` from wire bytes, so the fix at the
root (`Ed25519PublicKey`'s own constructor) closes it there and for every future caller alike — see
`Ed25519KeyPairTest`'s, `PeerRecordCodecTest`'s, and `PeerRecordSpoofingTest`'s case (f) regression
tests.

**Module map / dependency shape.** `lapis-net-directory` takes `lapis-net-identity`/
`lapis-net-storage`/`lapis-net-networking` as `api` (each has a type appearing directly in
`PeerRecord`'s or `PeerDirectoryGossip`'s public signatures — `Secp256k1PublicKey`/`DualKeyIdentity`/
`IdentityBinding`, `NabuStorage`, and `GossipPubSub`/`Multiaddr`/`PeerId` respectively), following
`lapis-net-mail`'s more recently established "explicit-not-transitive" house rule rather than
`lapis-net-trust`'s older transitive-reliance-on-storage's-own-`api`-edge approach. Deliberately
**NO dependency on `lapis-net-trust`** this wave — unlike `lapis-net-mail`'s V0.9.4 addition,
`PeerRecord` acceptance is purely structural (signature + identity-binding + sequence-number
ordering), not Veritas-distance-gated; a future wave MAY add an opt-in admission filter mirroring
`MailAcceptancePolicy`. Deliberately **NO dependency on `java-cid`** either — `PeerRecord` carries no
`io.ipfs.cid.Cid` field anywhere, so `lapis-net-core`'s `CidBytesValidation` is never invoked by this
module; its class doc comment states this explicitly so a reviewer does not go looking for a missing
guard. A parallel, independently-verified finding covers the `Multiaddr` address section instead of
`CidBytesValidation`: `Multiaddr.deserialize(bytes)` parses via a Netty `ByteBuf` wrapping the
already length-capped `addrBytes` array, and every `ByteBuf.readBytes(length)` call inside
`Protocol.readAddressBytes` bounds-checks against the buffer's remaining readable bytes BEFORE
allocating (Netty's `checkReadableBytes`) — unlike `io.ipfs.multihash.Multihash`'s raw
`new byte[len]`-before-bounds-check pattern `CidBytesValidation` exists to guard against, verified
directly against the real `jvm-libp2p` sources, not assumed safe. Every exception a malformed
multiaddr can throw is a plain `RuntimeException`, caught by `PeerRecordCodec.decode`'s existing
blanket catch clause.

**`PeerRecordCodec` — length-prefixed binary layout, magic `"LNPR"`, mirroring
`VeritasGrantCodec`/`MessageEnvelopeCodec`'s discipline exactly.** All integers big-endian:

----
magic(4) | version(1) | flags(1, reserved, must be zero) |
identity(33) | edPublicKey(32) | bindingSignature(64) | possessionProof(64) |
addressCount(2) | ( addrLen(2) | addr(addrLen) ) * addressCount |
capabilityBits(1) | sequenceNumber(8) | notValidAfterEpochSecond(8)
----

`possessionProof` (round 2 audit fix, see above) sits right after `bindingSignature` so every
64-byte signature-shaped field is grouped at the front of the layout. `encode()` appends the
record's own 64-byte outer signature after that body — a THIRD, DIFFERENT 64 bytes from both
`bindingSignature` and `possessionProof` above, both of which already sit inside the signed body
itself. `MAX_ADDRESSES` (16) and `MAX_MULTIADDR_BYTES` (256) per address bound the worst-case body
at 4,346 bytes (64 bytes larger than round 1's 4,282, from the new field), comfortably under the
same `MAX_BODY_SIZE = 0xFFFF` cap every sibling codec uses. Every
variable-length field (address count, each address's own length, capability bits) is validated
BEFORE the corresponding allocation, exactly like `VeritasGrantCodec`'s discipline — `addressCount >
MAX_ADDRESSES` is rejected immediately, before attempting to read a single address's bytes, proven
by a dedicated test that declares an oversized count and supplies zero actual address bytes after
it.

**`PeerRecordIndex` — latest-wins per identity by sequence number, a genuinely new ordering rule for
this codebase, not copied from any sibling index verbatim.** Every prior index
(`VeritasGrantIndex`, `InboxIndex`, `MadliVectorIndex`) resolves "which record wins" either by
chain-linking or by arrival order; `PeerRecordIndex` is the first whose winner is decided by
comparing an ATTACKER-SUPPLIED monotonic counter (`sequenceNumber`) instead. `currentByIdentity`
holds the record with the highest `sequenceNumber` seen per identity so far, ties broken
deterministically (unsigned lexicographic byte comparison over `contentId()`, not arrival order —
every honest node converges on the SAME winner regardless of gossip delivery order). A record with a
LOWER sequence number than the currently-tracked one is rejected outright by both `canAccept` and
`add` — never even considered for tracking, let alone persistence (`PeerRecordSpoofingTest`'s case
(b)). Superseded records are actively dropped from the tracking map, not merely un-linked, keeping
`currentByIdentity` and the tracking map in lockstep at every step — mirroring `MadliVectorIndex`'s
"every secondary index MUST be cleaned in lockstep" discipline. The established two-cap structure
(an evicting LRU tracking cap, `MAX_TRACKED_RECORDS = 64,000`, plus a SEPARATE, non-evicting,
hard-capped persistence-reservation cap, `MAX_PERSISTED_RECORDS = 64,000`) is otherwise unchanged
from `VeritasGrantIndex`'s round-2/round-3 precedent — a flood of many distinct, freshly-fabricated
identities is bounded by the tracking cap exactly like every sibling index's flood defense
(`PeerRecordSpoofingTest`'s case (d)).

**The anti-rollback property above does NOT hold if checked only against `currentByIdentity` — a
V0.8.1 sub-wave audit round 1 major finding, fixed before this wave's commit landed, then hardened
again in round 2 (major finding 2) once the round-1 fix's own equivalent gap was found.**
`removeEldestEntry` clears an identity's `currentByIdentity` entry the moment its record is evicted
from the tracking map (e.g. a flood of freshly-fabricated identities pushing it out past
`MAX_TRACKED_RECORDS`), and once that happens `canAccept`/`add` had no high-water mark left to
compare a replayed record against — ANY sequence number was then accepted for that identity,
including one already superseded: a genuine downgrade of a victim's advertised
addresses/capabilities/TTL to any older signed state an attacker has ever observed, requiring only
`MAX_TRACKED_RECORDS` freshly-fabricated identities (cheap: one secp256k1 keygen plus signatures
per identity) or, without an attacker at all, ordinary mesh churn re-delivering a stale record once
its victim's slot has aged out. Round 1 fixed the ORIGINAL scenario with `highestSequenceByIdentity`,
a SEPARATE `HashMap<Secp256k1PublicKey, Long>` that `canAccept`/`add` consult in addition to
`currentByIdentity`.

**Round 1's `highestSequenceByIdentity` was itself a plain, non-evicting `HashMap`, admission-gated
at a fixed size (`MAX_TRACKED_RECORDS`) — this reopened an EQUIVALENT rollback path, PROBE C in the
round-2 audit.** Because the map never evicted and was gated at a fixed cap, once
`MAX_TRACKED_RECORDS` DISTINCT identities had EVER been observed by a node (attacker-driven, or
simply organic growth on a long-running one), every identity arriving AFTER that point never
received a high-water mark AT ALL, for the rest of the process's lifetime — not a temporary
degradation but a PERMANENT one. PROBE C demonstrated this end to end through the real gossip
validator: flood first to fill the cap, THEN the genuine victim's record arrives and is accepted/
indexed but never high-water-marked, a later flood evicts it from `currentByIdentity` too, and a
replayed OLD record for that identity is then accepted — `ROLLBACK SUCCEEDS`.

**Fix: `highestSequenceByIdentity` is now an access-order, LRU-evicting `LinkedHashMap`, on its OWN
cap (`MAX_HIGH_WATER_MARKS = 128,000`) deliberately DECOUPLED (and sized DOUBLE) from
`MAX_TRACKED_RECORDS`.** Once full, a NEW identity's arrival now evicts the LEAST-recently-touched
existing entry (typically a dormant, one-off flood identity) rather than being refused a slot
outright — so a victim arriving after a flood still gets high-water-mark protection, closing PROBE
C's admission-side gap directly. The deliberately-larger, independent cap gives the high-water map
genuine reserve capacity beyond `recordsByContentId`'s own churn, so a flood sized to overwhelm one
does not automatically overwhelm the other in lockstep. This does NOT make protection
unconditionally permanent for every identity ever seen — a genuinely dormant identity can still
eventually be evicted by a SUSTAINED-enough flood exceeding `MAX_HIGH_WATER_MARKS` — but this is an
accepted, documented, and now bounded-by-effort tradeoff rather than a one-time,
`MAX_TRACKED_RECORDS`-sized flood permanently disabling the property for the rest of the process
lifetime; an identity that keeps receiving fresh records (a normal `PeerPresenceAnnouncer` heartbeat)
keeps refreshing its own recency and stays protected far longer than a one-off entry would. See
`PeerRecordIndex`'s own class doc comment and `highestSequenceByIdentity`'s field doc comment for
the full reasoning, `PeerRecordIndexTest`'s and `PeerRecordSpoofingTest`'s case (g) regression tests
for the ORIGINAL flood-past-cap-then-replay scenario (victim tracked BEFORE the flood), and
`PeerRecordIndexTest`'s new PROBE-C regression (flood BEFORE the victim ever arrives) for the round-2
fix.

**`persistedContentIds` (the SEPARATE, durability-only persistence-reservation cap) was evaluated
against the same reasoning and deliberately left as a hard, non-evicting cap (round 2, minor finding
4, non-blocking).** Unlike `highestSequenceByIdentity`, evicting here would remove the one property
this set exists to bound — total `NabuStorage.put()` calls over the node's lifetime — since an
evicted-then-replayed content id would simply be re-persisted (`storage.put` is idempotent, so no
corruption, but a sustained flood could then keep evicting and re-admitting forever, reintroducing
unbounded disk writes). The current permanent cap is the safer failure mode: this node stops
accepting new durable writes once exhausted rather than accepting unboundedly many over time. See
`persistedContentIds`'s field doc comment for the full reasoning.

**`PeerDirectoryGossip` — GossipSub wiring on the new `LapisNet:peer-record-gossip:v1` topic,
mirroring `VeritasGossip`'s shape (full record bytes over the wire, not a CID pointer — same
`Kademlia.dialPeer`-broken reasoning) refined with `InboxGossip`'s more recently established
validator step ordering.** `announce()` is `storage.put()` -> `index.add()` -> `pubsub.publish()`,
publish always last — the same publish-last invariant every sibling `Gossip` class enforces, so a
crash mid-sequence never leaves the network believing this node durably committed to something it
did not. `onGossipMessage`'s validator runs decode -> verify signature -> verify identity/peerId
binding -> verify possession proof (round 2 addition, see above) -> dedup/staleness check
(`PeerRecordIndex.canAccept`, which here predicts BOTH exact content-id duplication AND
stale/rollback sequence numbers, unlike every sibling index's purely-dedup `canAccept`) -> persist
(behind the separate `tryReservePersistence` cap) -> index, cheapest and most-selective checks
first. **Zero clock and zero network calls in the validator — absolute, not an optimization.**
`notValidAfterEpochSecond` is attacker-controlled and is NEVER consulted for an accept/reject
decision inside `onGossipMessage`; TTL is checked ONLY at `lookup()` read time. An expired record is
not actively evicted by expiry — it stays stored, and would still be returned by a `lookup()` call
using an earlier `nowEpochSecond` — only the real-time read-time filter hides it from a normal
caller (`PeerRecordSpoofingTest`'s case (c)).

**`PeerPresenceAnnouncer` — the enforced minimum-republish-interval PARTIALLY mitigating a known,
accepted tension with the original spec's own Metadaten-Minimierung ("metadata minimization") design
principle.** Broadcasting presence/address records over a network-wide GossipSub topic means every
subscribed node learns every published identity's current addresses and online-status heartbeat —
documented rather than papered over. Accepted resolution (decided 2026-08-04): this is no worse than
the multiaddr already published in V0.4's `lapisnet://connect` QR/deep-link flow, and a 300-second
default minimum-republish-interval bounds how often a caller going through this wrapper republishes
its OWN presence. **This is a partial mitigation, not a network-wide guarantee — audit round 1,
minor finding, corrected here.** `PeerDirectoryGossip.announce` itself is public and entirely
unrate-limited (nothing forces a caller to go through the wrapper), and `onGossipMessage` applies NO
inbound per-identity rate limit at all — a remote peer running a modified client can publish a fresh
record every second and this node will accept, persist, and re-propagate every one of them. The
floor therefore only bounds this node's own outbound republish rate, not how finely `PeerRecord` can
be turned into a presence oracle network-wide. **Deliberately NOT built into
`PeerDirectoryGossip.announce()` itself** — `announce()`
mirrors `VeritasGossip.announce`/`InboxGossip`'s established "retrying the SAME call is always safe"
property, which `TwoNodePeerDirectoryGossipIntegrationTest`'s bounded-polling-against-one-deadline
loop relies on exactly like the equivalent Veritas/mail integration tests already do — baking a
multi-minute floor into `announce()` itself would silently break that retry pattern. Rate limiting
therefore lives one layer up, in `PeerPresenceAnnouncer.announceIfDue`, wrapping whichever caller
decides WHEN a fresh `PeerRecord` should be built and announced.

**A backward wall-clock jump must not stall the heartbeat — V0.8.1 sub-wave audit round 2, minor
finding 3, fixed.** `Instant.now()` is wall-clock, not monotonic: an NTP correction, VM snapshot
restore, or container clock skew can step time BACKWARDS between calls. Before the fix,
`nowEpochSecond - last < minRepublishIntervalSeconds` stayed `true` for a NEGATIVE delta (a rewind
always looks "less than" any positive floor), so a rewind silently suppressed every subsequent call
until wall-clock caught back up past `last + minRepublishIntervalSeconds` — for a large enough jump,
hours or days during which this node's OWN `PeerRecord` TTL lapses and it becomes undiscoverable via
`lookup()`, a fail-CLOSED presence outage from what is meant to be only a soft rate limit.
`announceIfDue` now additionally requires `nowEpochSecond >= last` before applying the floor, so a
rewind is treated exactly like a first call rather than stalling indefinitely — see
`PeerPresenceAnnouncerTest`'s clock-rewind regression.

* **No DHT publication.** Gossip-only, same accepted limitation as every V0.9 mail sub-wave.
* **No `SFU_CAPABLE` capability flag.** MLS/conferencing/SFU cut from the V0.8 arc entirely on
  2026-08-04 — no consumer exists in this reduced arc; a future wave that reintroduces group calling
  can add a new bit without touching this codec's version or invalidating any V0.8.1 record already
  on the wire.
* **No bandwidth-class measurement.**
* **No reachability verification of advertised addresses** — mirrors V0.4's own, still-open gap: an
  attacker or a stale node can advertise unreachable addresses and nothing currently detects this.
* **A network-wide gossip topic is itself a metadata-exposure decision**, documented above rather
  than papered over — PARTIALLY mitigated via `PeerPresenceAnnouncer`'s enforced minimum-republish-

* **`tryReservePersistence` has no per-identity share of `MAX_PERSISTED_RECORDS`** (audit round 1,

  record from ANY identity for the rest of the process lifetime — `onGossipMessage` still returns
  `Valid` and keeps tracking in that case, so the failure is silent rather than fatal. Not fixed in
  this sub-wave; a future fix could add a per-identity persistence sub-cap or reuse
  `highestSequenceByIdentity` so superseding a record releases its predecessor's reservation.

== X25519 encryption sub-key and the X3DH handshake (V0.8.2)

`lapis-net-identity` gains an X25519 encryption sub-key (`X25519Keys.kt`, `X25519Agreement.kt`,
`EncryptionKeyBinding.kt`), and a new module, `lapis-net-ratchet`, implements X3DH (Signal's
Extended Triple Diffie-Hellman) directly from the public specification — **not** adapted from
libsignal, which is AGPL-3.0-licensed and therefore incompatible with this Apache-2.0 project
(a closed licensing question decided during this arc's planning pass, not re-litigated here). This
is the highest-risk cryptographic primitive in the codebase to date: every prior wave reused
already-established primitives (AES-256-GCM, HKDF-SHA256, secp256k1 ECDH/ECDSA, Ed25519) in new
combinations; the X3DH handshake itself — its multi-DH construction, its associated-data
construction, its HKDF info-string derivation — has no precedent anywhere in this codebase.

**Module split, and why `lapis-net-ratchet` is network-free.** `lapis-net-ratchet` carries
`PrekeyBundle`/`PrekeyBundleCodec`/`PrekeyStore` and the `X3dh` object itself, with DELIBERATELY
ZERO network/libp2p/Nabu/`java-cid` dependencies — a security property, not a packaging preference:
a reviewer auditing the handshake in this module never has to reason about untrusted network input
and crypto correctness in the same file. Publication of `PrekeyBundle`s over GossipSub
(`PrekeyBundleIndex`/`PrekeyBundleGossip`) instead lives in `lapis-net-directory`, which already
owns this codebase's "signed record over its own gossip topic with a two-cap index" machinery
(established for `PeerRecord` in V0.8.1) and reuses it here verbatim rather than duplicating it.

=== The X25519 sub-key: three constructor-time rejections

`X25519PublicKey`'s constructor rejects untrusted wire bytes on three independent grounds, mirroring
exactly why `Secp256k1PublicKey`/`Ed25519PublicKey` run their own curve-validation checks at
construction: (1) wrong length; (2) a NON-CANONICAL encoding (bit 255 of the last byte set, or the
encoded integer `>= p = 2^255 - 19`); (3) one of twelve published low-order/degenerate
u-coordinates. `PrekeyBundleCodec.decode` is the only site in the project that builds an
`X25519PublicKey` from wire bytes, so a low-order key anywhere in a `PrekeyBundle` (signed prekey,
one-time prekey, or X25519 identity key) is rejected structurally, before any DH computation ever
runs.

**"Verified against the resolved jar rather than assumed" — the low-order table, and the finding
that the SPEC's implicit "either mitigation is fine" framing is not safe.** Measured against
`bcprov-jdk18on:1.85`:

[cols="3,2"]
|===
| u-coordinate (hex, little-endian) | X25519 agreement result (BouncyCastle)

| `00…00` (u = 0) | rejected (all-zero output)
| `01 00…00` (u = 1) | rejected
| `e0eb7a7c…9b800` (order 8) | rejected
| `5f9c95bc…f1157` (order 8) | rejected
| `ec ff…ff 7f` (p − 1, order 2) | rejected
| `ed ff…ff 7f` (p, ≡ 0) | rejected
| `ee ff…ff 7f` (p + 1, ≡ 1) | rejected
| `cd eb7a7c…9b880` (non-canonical) | **ACCEPTED**, non-zero secret
| `4c 9c95bc…f11d7` (non-canonical) | **ACCEPTED**, non-zero secret
| `d9 ff…ff` (non-canonical) | **ACCEPTED**, non-zero secret
| `da ff…ff` (non-canonical) | **ACCEPTED**, non-zero secret
| `db ff…ff` (non-canonical) | **ACCEPTED**, non-zero secret
|===

The five ACCEPTED values are non-canonical (bit-255-set or `u >= p`) re-encodings of small-order
points: RFC 7748's mandatory masking of bit 255 before scalar multiplication turns them into
ordinary, full-order points, so BouncyCastle's own all-zero-agreement-output defence does not catch
them at all. **Relying on that defence alone — the reading a literal "either mitigation is fine"
instruction would suggest — would leave these five silently accepted.** Both mitigations are
therefore implemented: the canonical-encoding rules (bit 255 clear, `u < p`) reject all five
non-canonical values structurally, at construction time, and the explicit blacklist of all twelve
values is defence in depth against a future BouncyCastle version silently changing its own internal
behaviour (pinned by `X25519KeyPairTest`'s BouncyCastle-pinning regression).

**X25519's output is raw, unlike `ecdhSharedSecret`'s.** `ecdhSharedSecret` (secp256k1 ECDH) already
returns `SHA-256(compressed shared point)` — a uniformly distributed 32-byte string, safe to use
directly as HKDF input keying material. `x25519SharedSecret` returns the RAW shared u-coordinate,
confirmed byte-for-byte against RFC 7748 §6.1's published vector. **Consequence: HKDF-Extract over
the assembled IKM in `X3dh`'s key schedule is genuinely load-bearing for entropy-smoothing, the
exact opposite of the situation `ecdhSharedSecret`'s own doc comment describes.**

=== `EncryptionKeyBinding` — a one-way vouch, deliberately without a mutual counter-signature

`EncryptionKeyBinding` is structurally identical to `IdentityBinding` — the same secp256k1-signs-a-
domain-separated-digest shape, its own domain tag (`"LapisNet:x25519-encryption-key:v1"`) — but
unlike `PeerRecord.possessionProof` (V0.8.1's fix for an analogous gap), it deliberately carries NO
mutual counter-signature. An X25519 key cannot sign; XEdDSA (Signal's own answer — converting an
X25519 key to Ed25519 to sign with it) is an explicit scope cut for this wave, because adding a
second from-scratch cryptographic construction inside a wave that already builds X3DH from scratch
would compound, not contain, the risk. An Ed25519 counter-signature by the identity's OWN transport
key was also considered and rejected: it would prove the SIGNER's Ed25519 key vouches for the X25519
public key, not that the signer holds the corresponding X25519 PRIVATE key — security theatre. The
equivalent protection lives in X3DH's associated-data construction instead (see below).

=== The possession-proof question — the unknown-key-share attack, and why AD-in-`info` closes it

**The attack.** An X25519 public key is public by definition. Mallory harvests Bob's published
`x25519IdentityKey`/`signedPrekey`/`oneTimePrekeys` off the gossip topic and mints a FRESH,
self-consistent `EncryptionKeyBinding.create(malloryKeyPair, bobX25519IdentityKey)`, re-signs Bob's
signed prekey under her own secp256k1 key (the wider `signedPrekeyDigest` construction below still
verifies — it only requires the SIGNER's identity to match, which it genuinely does), and publishes
a fully self-consistent bundle under her own identity. ALL THREE of `PrekeyBundle.verify`/
`verifyEncryptionBinding`/`verifySignedPrekey` genuinely pass — there is no way to detect this attack
at bundle-validation time.

**Why it is not, by itself, a confidentiality break.** This is an "unknown key share" attack, not a
direct key compromise: `DH2 = X25519(EK_A, IK_B)` and `DH4 = X25519(EK_A, OPK_B)` both require BOB's
private keys, which Mallory does not have. Alice believes she is establishing a session with
Mallory; the party who can actually complete the matching handshake is Bob. If the resulting session
key were used naively (i.e. if the downstream layer ignored the associated data), Alice's first
message — composed believing the recipient is Mallory — would decrypt cleanly for Bob: a genuine
confidentiality break.

**What closes it: AD built from the secp256k1 IDENTITIES, not the X25519 sub-keys.** Alice computes
`AD = "LNX3" ‖ v1 ‖ IK_Alice ‖ IK_Mallory`. Bob, using his real private keys, computes `AD = "LNX3" ‖
v1 ‖ IK_Alice ‖ IK_Bob`. These DIFFER, because the two parties disagree about who the responder is —
and they differ ONLY in the secp256k1 identity component, because in this specific attack the X25519
keys are IDENTICAL on both sides (they are Bob's real keys, copied). This is precisely why the AD is
built from the secp256k1 identities and not the X25519 sub-keys: an AD built from the X25519 keys
would match on both sides, and the attack would land.

**Why AD is folded into HKDF `info`, not left only to a downstream AEAD's associated-data slot (a
deliberate deviation from X3DH §2.2's literal fixed `info` string).** If AD lived only in a FUTURE
Double-Ratchet AEAD's own AD parameter, the protection above would depend on that future layer
remembering to use it — a layer that forgets still derives IDENTICAL session keys on both sides,
silently reintroducing the confidentiality break. Folding AD into HKDF `info` here means the two
parties derive DIFFERENT shared secrets the moment their views of "who is the responder" diverge,
unconditionally, with no future wiring required to benefit from it. Direct precedent for this
reasoning already exists in this codebase: `HybridEcies`'s class doc comment makes almost exactly
this argument for its own wrap-key derivation ("HKDF-Expand IS load-bearing... so a transplanted
wrap fails for two independent reasons... not merely one"). HKDF `info` is public, non-secret
domain-separation input to a PRF; adding fixed-length public context to it cannot weaken the
derivation. `X3dhAdversarialTest`'s case (e2) is the executable proof: all three cryptographic
checks genuinely pass, yet Alice's and Bob's derived shared secrets provably differ.

**Residual risk, stated explicitly.** The attack is not detectable at bundle-validation time — a
verifier presented with Mallory's bundle in isolation cannot tell it apart from a legitimate one.
It fails only at session establishment, when the two sides' derived secrets diverge — both parties
observe a failed handshake, not a clear "you were attacked" signal. The consequence is a
denial-of-service/confusion attack against Alice, plus cross-identity key-material pollution of the
directory — neither is a confidentiality break, both are accepted for this wave. A future wave could
close this fully via XEdDSA (restoring Signal's own structural possession proof) or a first-use
identity/key pinning (TOFU) layer above the directory; both are out of scope here.

=== The exact byte-level construction

All integers big-endian; every constant pinned by `X3dhKnownAnswerTest`:

----
DH1 = X25519(IK_A, SPK_B)      // initiator identity   x responder signed prekey
DH2 = X25519(EK_A, IK_B)       // initiator ephemeral   x responder identity
DH3 = X25519(EK_A, SPK_B)      // initiator ephemeral   x responder signed prekey
DH4 = X25519(EK_A, OPK_B)      // initiator ephemeral   x responder one-time prekey [omitted if none]

IKM  = F (32 x 0xFF) || DH1 || DH2 || DH3 [|| DH4]     // 128 or 160 bytes
salt = 32 zero bytes
info = "LapisNet:x3dh:v1:X25519:SHA-256" (31 bytes) || AD (71 bytes)     // 102 bytes
AD   = "LNX3" (4) || 0x01 (1) || IK_A (33, secp256k1 compressed) || IK_B (33, secp256k1 compressed)
SK   = HKDF-SHA256-Expand(HKDF-SHA256-Extract(salt, IKM), info, L = 32)
----

`DH4` is appended at the end when a one-time prekey is used and entirely OMITTED otherwise — never
zero-filled, never reordered; the presence/absence of `DH4` changes the IKM length (128 vs 160
bytes), so the two cases are trivially domain-separated by HKDF-Extract itself. `AD` is
initiator-first ALWAYS, never sorted, never symmetric. The responder-side DH mirror
(`DH1 = X25519(SPK_B, IK_A)`, etc.) produces byte-identical outputs, proven by `X3dhTest`'s
initiator/responder round-trip.

**`signedPrekeyDigest` is deliberately WIDER than the Signal spec's own `Sig(IK_B, Encode(SPK_B))`.**
Signal's signature covers the signed prekey alone because in Signal `IK_B` IS the X25519 identity
key, and signing with it is itself a proof of possession. Here the signature is produced by the
secp256k1 identity key instead, so a bare `Sig(SPK)` would be freely transplantable between
different bundles of the same identity; binding
`identity ‖ x25519IdentityKey ‖ signedPrekey ‖ signedPrekeyId` into one domain-separated digest
makes every component of the bundle's key material a single, non-separable unit.

=== `PrekeyStore` — the durability contract for one-time-prekey consumption

`consumeOneTimePrekey` executes in this order, and the ordering is load-bearing: (1) acquire
exclusive access to the store file and re-read+re-decode its CURRENT on-disk contents — never this
instance's own cached in-memory state, see below for why; (2) look up the entry in that freshly-read
state — unknown id or already-`CONSUMED` is a hard failure that NEVER falls back to a
signed-prekey-only handshake; (3) copy the private key bytes; (4) build the NEW state image in
memory (entry marked `CONSUMED`, its 32 key bytes zeroed), based on the freshly-read state; (5)
encode and write the new state to a temp file, `FileChannel.force(true)` it, then atomically
`Files.move` it over the store file; (6) ONLY after the move succeeds, assign the new state to the
live field and release the exclusive lock; (7) return the copied private key, paired with its id in
a `ConsumedOneTimePrekey`.

**Why re-read on-disk truth instead of trusting the cached in-memory state.** `PrekeyStore.open` is
public, and nothing stops a caller from opening a SECOND handle against the same file while a first
handle is still live — each handle then holds its OWN cached state snapshot, taken at its own
`open`/`create` time. If `consumeOneTimePrekey` mutated from that cached snapshot, two
concurrently-open handles could each independently believe a different one-time prekey is still
available and each successfully consume one; because each write persists that handle's ENTIRE
(stale) entry list, the second write would silently ERASE the first handle's already-persisted
tombstone too, resurrecting an already-consumed id as available again — precisely the reuse this
class exists to prevent. Two independent layers of mutual exclusion make step (1) safe: a per-file
JVM monitor (so two handles in the SAME process block on each other, rather than crashing with
`OverlappingFileLockException` — `FileChannel.lock()` does not block a second same-JVM acquisition,
it throws), and an OS-level `FileChannel.lock()` on a dedicated `<file>.lock` sidecar (so a second OS
PROCESS also serializes against the critical section). The OS lock is deliberately NOT taken on the
store file itself: POSIX advisory locks are held on the underlying inode, not the path, and
`persistAtomically`'s atomic `Files.move` re-points the path at a brand-new inode on every write — a
lock held on the store file's own (pre-rename) inode would silently stop protecting anything the
moment the first writer's rename completes, letting a second process's `channel.lock()` on the new
inode succeed immediately while the first process's critical section is still running. The sidecar
file is never renamed, so its inode — and the lock on it — stays valid across every rename.
`PrekeyStore.create` takes the same sidecar lock around its own initial existence-check-then-write,
closing the identical race for two concurrent `create` calls against the same label.

**Why persist-before-mutate.** If the write fails, nothing has changed on disk or in memory — the
prekey stays available and the handshake simply does not happen, a clean, safe failure. If the
process crashes between steps 5 and 6, the prekey is durably consumed and its private half is gone —
the pending handshake is lost, the SAFE direction. The reverse order (mutate then persist) has a
failure mode where in-memory state says consumed but on-disk state says available, so a restart
resurrects a prekey a peer may already have used — precisely the reuse this ordering prevents.
Consumed entries are retained as tombstones (zeroed key bytes, not removed) so a replay names an id
that is KNOWN-CONSUMED rather than UNKNOWN; `generateOneTimePrekeys` prunes only the oldest
tombstones when the (bounded, 4,096-entry) store fills, never a live `AVAILABLE` entry, and this is
safe only because `nextOneTimePrekeyId` is strictly monotonic and never rewinds (enforced by
`PrekeyStoreState`'s own init block) — a pruned id can never be reallocated.

After the atomic `Files.move`, the parent directory is also `fsync`'d on a best-effort basis (POSIX
only): the temp file's own `force(true)` makes ITS bytes durable, but the rename itself is a
separate directory-metadata operation that a crash immediately after the move can still lose on some
filesystems, leaving the directory entry pointing at the pre-consumption file. This is best-effort
because some POSIX filesystems (notably certain FUSE/network mounts) refuse to open a directory as a
`FileChannel` at all; a failure here is logged, not thrown, since the file's own bytes are already
durable regardless.

`consumeOneTimePrekey` returns a `ConsumedOneTimePrekey(id, privateKey)` rather than a bare private
key, so `X3dh.respond` can assert the consumed id actually matches the initiator's header
(`header.oneTimePrekeyId`) — closing a caller-wiring-bug class where the wrong id is consumed and a
silently-mismatched secret is derived, surfacing only much later at first AEAD use.

No new crypto is invented for persistence: `PrekeyStoreFileFormat` reuses
`KeystoreEncryption`/`KeystoreFileFormat`'s Argon2id + AES-256-GCM v1-plaintext/v2-encrypted duality
verbatim, including the same V0.4-learned Argon2-cost-parameter sanity caps checked BEFORE Argon2
ever runs on untrusted header bytes.

=== Explicit, deliberate scope cuts for this wave

* **No PQXDH / post-quantum hybrid key exchange.** X25519 only.
* **No formal deniability analysis** beyond X3DH's own published security properties.
* **No DHT publication.** Gossip-only (`PrekeyBundleGossip`), same `Kademlia.dialPeer`-broken
  limitation as every prior wave.
* **No wire codec for the X3DH initial-message header (`X3dhPreKeyMessageHeader`).** This wave's
  deliverable is the handshake primitive and prekey publication/consumption machinery, callable and
  independently testable — not yet wired into a live message-send path. V0.8.4 (online DM) owns
  that wiring.
* **No replay protection for a repeated identical initial message naming NO one-time prekey — and
  V0.8.3's Double Ratchet session layer only PARTIALLY closes this (correction from this bullet's
  original text, see "The Double Ratchet (V0.8.3)" section below for the full analysis).** `X3dh` is
  a stateless pure function by design; a replay naming a one-time prekey IS refused, durably, at the
  `PrekeyStore` layer. `DoubleRatchetSession` closes only the PER-MESSAGE half of what remains
  (delete-on-use of skipped keys, rejection of an already-consumed message number, WITHIN one
  already-established session) — a replayed initial message naming NO one-time prekey still lets a
  responder derive the same `SK` twice and construct TWO INDEPENDENT sessions, invisible to each
  other. Closing that needs a durable session registry keyed by the initiator's ephemeral public
  key, still V0.8.4's to build.
* **One-time-prekey collisions are inherent to gossip publication** — unlike Signal's server (which
  hands each one-time prekey to exactly one requester), a gossip-published `PrekeyBundle` is seen in
  full by every subscriber, so two initiators can independently pick the same one-time prekey; the
  second responder-side consumption then fails and that initiator must retry with
  `preferredOneTimePrekeyId = null`, falling back to signed-prekey-only X3DH.
* **No XEdDSA, no signed-prekey rotation scheduler.** `PrekeyStore.rotateSignedPrekey` is exposed as
  a directly callable primitive; nothing in this wave calls it periodically, mirroring
  `PeerRecordIndex.evictExpired`'s identical "not wired to any scheduler in this sub-wave" stance.
* **`CidBytesValidation` is not invoked by this wave** — no `io.ipfs.cid.Cid` field exists anywhere
  in `PrekeyBundle`, `PrekeyBundleCodec`, `PrekeyStoreFileFormat`, or `X3dh`; both codecs' class doc
  comments state this explicitly, mirroring `PeerRecordCodec`'s own equivalent N/A note.

== The Double Ratchet (V0.8.3)

The ongoing encrypted session an X3DH handshake's `X3dhSharedSecret`/`associatedData` output
bootstraps into — Signal's Double Ratchet, reimplemented from the public specification (no
libsignal, AGPL-3.0-incompatible, same reasoning as V0.8.2). Extends `lapis-net-ratchet` (same
module, still deliberately network-free). The second of this arc's two highest-risk sub-waves:
unlike V0.8.2's stateless handshake, this wave carries real STATE — a live session persists across
many messages over potentially a long time, so a correctness failure here is an ongoing, silent
compromise of an entire conversation, not a one-shot handshake bug.

**Bootstrap asymmetry.** The X3DH INITIATOR becomes the ratchet SENDER
(`DoubleRatchetSession.initializeSender`) — it already has the responder's initial ratchet public
key (the responder's SIGNED PREKEY public key IS that key), generates its own fresh ratchet keypair,
and performs one DH ratchet step immediately, so it has a sending chain from message zero. The X3DH
RESPONDER becomes the ratchet RECEIVER (`initializeReceiver`) — its initial ratchet keypair IS the
signed prekey keypair it already holds (not freshly generated), and it has no sending chain and no
receiving chain until it decrypts its first inbound message.

=== The KDF ladder, byte for byte

Three layers, isolated in `RatchetKdf.kt` so the whole key schedule is auditable in one place:

----
Root chain (RatchetKdf.rootKdf, once per DH ratchet step):
  info = "LapisNet:double-ratchet:v1:root" (31 bytes) || associatedData (71 bytes)   = 102 bytes
  okm  = HKDF-SHA256(ikm = dhOutput, salt = currentRootKey, info, L = 64)
  newRootKey  = okm[ 0..31]
  newChainKey = okm[32..63]

Symmetric chain (RatchetKdf.chainKdf, once per message):
  messageKeyMaterial = HMAC-SHA256(chainKey, 0x01)
  nextChainKey       = HMAC-SHA256(chainKey, 0x02)

Message key (RatchetKdf.messageKeyKdf, once per message):
  info   = "LapisNet:double-ratchet:v1:message" (34 bytes) || associatedData (71 bytes) = 105 bytes
  aesKey = HKDF-SHA256(ikm = messageKeyMaterial, salt = 32 zero bytes, info, L = 32)
----

**`rootKdf`: `ikm = dhOutput`, `salt = rootKey` — the right way round, and genuinely load-bearing.**
`x25519SharedSecret` returns the RAW shared u-coordinate, not a hash of it (confirmed against the
resolved BouncyCastle jar, see V0.8.2's own section above) — not uniformly distributed. HKDF-Extract
over it is therefore load-bearing for entropy-smoothing, the identical contrast `x25519SharedSecret`'s
and `X3dh`'s own doc comments already draw against `ecdhSharedSecret`. `associatedData` is folded
into `info` here too, not left to the AEAD alone — the same argument `X3dh`'s and `HybridEcies`'s own
`info` constructions make: two sessions between different identity pairs whose DH values somehow
coincided would still derive different root chains, so cross-session confusion fails at the KDF, one
full layer before the AEAD's AAD check even runs — two independent reasons, not one.

**`chainKdf`: HMAC-SHA256 only, no HKDF** — Signal's own published chain-KDF shape. Two DIFFERENT
one-byte inputs (`0x01`/`0x02`) under the SAME HMAC key make the message key and the next chain key
computationally independent: possession of `CK_(n+1)` yields nothing about `MK_n`, the property
forward secrecy actually rests on. `chainKdf` never zeroes its own `chainKey` argument — the caller
owns it and must zero it after installing the next chain key, mirroring `x25519SharedSecret`'s
identical caller-owns-the-lifetime rule.

**`messageKeyKdf`: HKDF-Extract is NOT load-bearing here** (the input is already an HMAC-SHA256
output, i.e. uniform) — **HKDF-Expand IS**, for the identical reason `HybridEcies`'s own wrap-key
derivation states: it makes the AEAD key a distinct function of `associatedData`, so a message
transplanted between sessions fails for two independent reasons (wrong derived key AND wrong GCM
AAD), not merely one. `L = 32`, key only — deliberately no nonce derived here, see below.

`hmacSha256`/`hkdfSha256` inside `RatchetKdf` are LOCAL duplicates of `X3dh`'s own private helper,
not calls into it — `X3dh`'s helper is `internal` purely so its own known-answer test can pin it;
coupling the Double Ratchet's whole key schedule through that seam would mean a future change to
X3DH's helper silently changes this ladder too. `DoubleRatchetKnownAnswerTest` independently pins
BOTH copies against the same RFC 5869/RFC 4231 vectors.

=== The AEAD nonce question

AES-256-GCM with an EXPLICIT, uniformly random, transmitted 12-byte nonce — NOT a derived nonce,
unlike `HybridEcies`'s (V0.9.2) wrap key. `HybridEcies`'s derived-nonce safety rests on: the wrap key
is single-use by construction (a fresh `SecureRandom` ephemeral per `seal` call — stateless, nothing
can rewind it), and if that ephemeral ever repeated, a transmitted random nonce would not have saved
the scheme either, since the same `SecureRandom` produced both. **That escape hatch is checked here,
not assumed to transfer — and it does not hold.** A Double Ratchet message key is single-use by
construction too, but the construction is a PERSISTED COUNTER (`Ns`/`Nr` plus the chain key), which
CAN rewind: a restored backup, a crashed write that left a stale file in place, a copied state
directory, or a caller violating the persist-before-send ordering below all resurrect an
already-used `(chainKey, N)` pair, and the next `encrypt` call re-derives the IDENTICAL message key.

Under a DERIVED nonce, that would be a genuine AES-GCM `(key, nonce)` reuse — the catastrophic case,
where the GHASH authentication subkey becomes recoverable and the two plaintexts' XOR leaks. Under
the EXPLICIT RANDOM nonce this wave actually uses, it degrades to "two ciphertexts under one key
with distinct nonces", which GCM tolerates with no confidentiality loss at all — what remains is a
protocol-level DUPLICATE the peer rejects as a replay (see below). Crucially, the mail wave's own
escape hatch — "a random nonce would not save it either, same RNG" — is FALSE here: the rewind is a
STORAGE fault, not an RNG fault, and the `SecureRandom` producing the nonce is unaffected by it.

The symmetric question — does the explicit nonce cost anything a derived nonce would have bought? —
resolves in the random nonce's favour: if `SecureRandom` were ever broken and returned all-zero bytes
for every call, every message would get nonce = 0, and that is HARMLESS, because the KEY still
differs per message (from the HMAC chain ladder, not this `SecureRandom`). So the random nonce is
safe under RNG failure AND under state rollback; a derived nonce would only ever have been safe
under the first. This is the identical choice `HybridEcies`'s OWN body layer already makes, for a
structurally analogous reason: the body's content key is chosen by the sender, not tied to a
freshly-generated asymmetric key, so its AEAD nonce is explicit and random too. The Double Ratchet's
message key is derivation-wise like the mail wave's wrap, but freshness-wise like its body — it
follows the body.

=== The message header and its AAD binding

`RatchetMessageCodec`'s 60-byte header, byte for byte:

----
off   len   field
  0     4   magic  "LNDR"
  4     1   version = 1
  5     1   flags   - reserved, must be zero
  6    32   ratchetPublicKey     (X25519, sender's current DHs public half)
 38     4   previousChainLength  (PN)
 42     4   messageNumber        (N)
 46    12   nonce                (AES-256-GCM, random per message)
 58     2   ciphertextLength     (unsigned short)
--- HEADER_SIZE = 60 ---
 60     N   ciphertext           (AES-256-GCM output, includes the 16-byte tag)
----

`AAD = headerBytes[0..59] || associatedData[0..70]` — 131 bytes, both parts fixed length so the
concatenation is injective with no length prefix, the same argument `X3dh`'s and `HybridEcies`'s own
`info` constructions make. **The header bytes are read VERBATIM off the wire (or freshly assembled,
on `encrypt`) and NEVER re-serialised from the parsed `RatchetMessageHeader`'s fields** — `headerBytes`
is a field on `RatchetMessage` itself, enforced by the type, not merely a discipline a call site must
remember to follow. This is the rule this codebase's own history credits with getting V0.4's
keystore encryption through security review in a single round; the opposite mistake elsewhere in
this codebase's own history is exactly what motivates stating it here again.

**No header encryption in this wave** — message numbers and the ratchet public key travel in the
clear; only the payload is confidential. A real, published Signal-protocol-standard limitation
carried forward knowingly, not an oversight.

=== Two independent gates against the skipped-key DoS

`RatchetMessageCodec.MAX_CHAIN_LENGTH` (1,000,000) rejects `previousChainLength`/`messageNumber` at
`decode()` — before `DoubleRatchetSession` is ever entered. `DoubleRatchetSession.MAX_SKIP` (1,000)
rejects an excessive skip DISTANCE relative to the session's own current position, at `decrypt()` —
before any chain-KDF loop or allocation proportional to the claimed distance runs. Both are checked
BEFORE any derivation, never inside a loop. This codebase's CID-length OOM history (`Fix CID
multihash-length OOM DoS`, commit `0c56dbb`) is why both gates exist rather than one — the first
gate alone would still let a header claiming `messageNumber = 999,999` drive a ~1M-iteration
derivation loop; only the second, session-relative gate closes that.
`DoubleRatchetSession.derivedMessageKeyCount()` (test-only) exists specifically so
`DoubleRatchetAdversarialTest`'s DoS case can PROVE a rejection happened before any derivation, not
merely assert the exception type.

=== Skipped message keys: insertion-order eviction, and why not access-order

`SkippedMessageKeyStore` is a bounded, evicting `LinkedHashMap` — but INSERTION-order
(`accessOrder = false`), deliberately NOT the access-order shape every gossip index in this codebase
uses (`PeerRecordIndex`/`PrekeyBundleIndex`'s own high-water-mark and content-id maps are all
access-order). Those indexes treat recency-of-access as a liveness signal a legitimate re-query
should refresh. Here the opposite holds: an attacker can trigger arbitrary lookups against this store
by replaying arbitrary headers, so access-order would let them pin a chosen key alive and evict
everyone else's. A skipped key's value decays purely with AGE, so age is the correct eviction order —
exactly what "the oldest skipped keys must be evicted" means. `MAX_SKIPPED_KEYS_STORED = 2 *
MAX_SKIP` (2,000) deliberately: a single `decrypt()` crossing a DH ratchet boundary can legitimately
need to store up to `MAX_SKIP` keys for the OLD chain plus up to `MAX_SKIP` for the NEW one in ONE
call, and sizing the store at exactly that sum means one legitimate worst-case burst fills the store
without evicting anything it just stored in the same call — **provided the store was empty when that
call began**; `removeEldestEntry` evicts strictly by insertion order, so a call against an
already-partially-full store can evict entries it inserted earlier in that SAME call once the 2,000
cap is crossed. The memory bound (well under 250 KB per session) holds regardless; the "one call never
evicts its own insertions" property specifically does not, once the store is non-empty going in.

=== State is committed only after the AEAD tag verifies

The single most important design decision in `DoubleRatchetSession.decrypt`. Every derivation it
performs — skipped message keys (old chain and new chain), a DH ratchet step's new root/chain keys,
a fresh ratchet keypair — is built into SCRATCH locals first. Only after the AEAD tag verifies are
those installed into live fields, the superseded live arrays zeroed, and the skipped-key store
updated; if the tag fails, every scratch array is zeroed and the session is byte-for-byte what it was
before the call. Without this, the session would be trivially destroyable by an unauthenticated
attacker: a single garbage frame carrying a random (but validly-encoded) ratchet public key would
drive a DH ratchet step, discard the real receiving chain key, and permanently desynchronise the
session — a one-packet remote DoS. It also makes the stale-old-chain case degrade cleanly: a
genuinely old message whose key was never stored as skipped falls through to the "unknown ratchet
key" branch and provokes a spurious ratchet step whose results are simply discarded when the tag
fails, instead of corrupting the session.

=== Persist and destroy ordering — where forward secrecy actually dies

Five rules, stated in `DoubleRatchetSession`'s own class doc comment verbatim:

1. **Destruction happens INSIDE the state transition, so the persist/destroy question never arises
   at persist time.** Every superseded key is zeroed and unreachable from the session object BEFORE
   `encrypt`/`decrypt` returns — never deferred to a later cleanup call. At every instant a caller
   could possibly call `DoubleRatchetSessionCodec.encode`, the session holds ONLY current,
   still-needed key material. There is no window in which a snapshot could capture a superseded key —
   the window is removed rather than sequenced.
2. **`DoubleRatchetSessionCodec.encode` is a pure read** — mutates and destroys nothing.
3. **The ordering that DOES matter is the CALLER's** (this wave performs no file I/O of its own):
   persist the post-`encrypt` state BEFORE putting the ciphertext on the wire, and persist the
   post-`decrypt` state BEFORE acting on the plaintext. Getting this backwards and crashing mid-window
   rewinds `Ns`/`Nr` on restart — which, because this wave transmits a random rather than derived
   nonce, degrades to a rejectable protocol-level replay rather than a catastrophic key-recovery-grade
   AES-GCM nonce reuse. **This rule is stated as a correctness requirement, not yet as a viable
   implementation plan.** As written it means one full `DoubleRatchetSessionCodec.encode` call — a
   fresh Argon2id derivation at the default cost parameters (64 MiB / 3 passes, order 10^2 ms) plus a
   full re-serialisation of up to `MAX_SKIPPED_KEYS_STORED` (2,000) skipped entries — PER MESSAGE, in
   both directions. That per-message cost is not viable for a live network message-send path.
   Deliberately deferred to the online-DM wave that will actually own the persistence call sites
   (candidates: cache the Argon2id-derived key for the session's lifetime instead of re-deriving it
   per `encode` call, or wrap a cheap session-scoped key once under the Argon2id-derived one) rather
   than left as a silent surprise for that wave to discover.
4. **Loading a stale blob is the residual, accepted, documented gap** nothing in this class alone can
   prevent — mitigated by rule 3's atomic durable writes plus the random-nonce choice, which converts
   a rollback from a key-recovery-grade break into a benign, rejectable duplicate.
5. **The ONE place "persist then destroy" is correct: closing a session** —
   `DoubleRatchetSessionCodec.encode(session, passphrase)` then `session.destroy()`. Correct precisely
   because what `destroy()` erases is CURRENT state a persisted blob legitimately carries — not
   superseded material. Do not blur this with rule 1.

`DoubleRatchetSessionCodec` reuses `KeystoreEncryption` (Argon2id + AES-256-GCM) verbatim, mirroring
`PrekeyStoreFileFormat`'s stance of inventing no new at-rest crypto. Two deliberate divergences from
`PrekeyStoreFileFormat`: no plaintext variant (no legitimate reason a Double Ratchet session's state
should ever hit disk unencrypted, so `encode` takes a non-null passphrase and there is no
`decodeAuto`), and the inner body carries its OWN distinct magic (`"LNRB"`) rather than reusing the
outer file magic (`"LNRS"`) — `PrekeyStoreFileFormat` can safely reuse one magic for both because its
v1 body genuinely IS a whole file; here the body is never standalone, so a distinct magic makes
"someone fed me a decrypted body as if it were a file" a loud, immediate rejection rather than a
silent structural coincidence.

=== What a JVM-level test can actually prove about forward secrecy and post-compromise security

Stated with the same honesty this codebase already applies to secure erase generally.
`DoubleRatchetAdversarialTest`'s forward-secrecy case proves exactly two things, no more: (i) the
SPECIFIC `ByteArray` objects the session held were mutated to all-zero in place (via a test-only hook
invoked with the actual soon-to-be-zeroed array, mirroring `HybridEcies.sealWithEphemeralKeyHook`'s
identical visibility reasoning), and (ii) the LIVE session refuses to re-decrypt an early message,
throwing `RatchetMessageRejectedException`. It does **not** — and, from ordinary JVM/Kotlin code,
**cannot** — assert that the early message's chain key or message key is absent from every entry
`DoubleRatchetSession.keyMaterialSnapshotForTest()` returns, nor that no copy of those bytes survives
elsewhere on the JVM heap: a garbage collector may have relocated an array before `fill(0)` ran, and
there is no way to reach the abandoned original. This project makes only the same best-effort claim
`X25519PrivateKey.destroy`'s own doc comment already makes; this wave adds nothing to it. It likewise
cannot prove the COMPUTATIONAL half of forward secrecy — that `CK_(n+1)` does not yield `CK_n` — an
assumption resting on HMAC-SHA256's one-wayness that no test can verify.

Post-compromise security is not instantaneous — the adversarial test asserts this explicitly rather
than hiding it: a snapshot taken at time T still decrypts the very NEXT message (the one whose DH
ratchet step the snapshot's own state can still compute), and only fails starting with the message
AFTER that ratchet step completes, once a genuinely fresh `X25519KeyPair.generate(random)` the
snapshot never saw has been mixed into the root chain.

=== Explicit, deliberate scope cuts for this wave

* **No header encryption** — see above.
* **No sealed sender.**
* **No post-quantum ratchet.** No PQXDH, no PQ KEM in the root chain — consistent with V0.8.2's own
  cut.
* **No secure-erase guarantee beyond best-effort `ByteArray.fill(0)`** — the same limitation V0.4/
  V0.8.2 already state; this wave adds nothing to it and claims nothing more.
* **Not wired into a live network message-send path.** `DoubleRatchetSession` is a standalone,
  independently testable state machine; gossip/libp2p plumbing is V0.8.4's.
* **No file I/O.** `DoubleRatchetSessionCodec` is a pure bytes<->object codec; the durable-write
  discipline (atomic temp-file + `force(true)` + `ATOMIC_MOVE` + sidecar lock) is the caller's, and
  `PrekeyStore` is the reference implementation to copy.
* **No session registry, and therefore the X3DH initial-message replay gap is only PARTIALLY
  closed** — see the corrected V0.8.2 scope-cut bullet above.
* **No multi-device / no session migration between devices.**
* **No automatic signed-prekey-driven session re-establishment**, no session expiry, no periodic
  re-keying scheduler.

== DM stream protocol (V0.8.4)

New module `lapis-net-dm`. This wave wires V0.8.2's X3DH handshake and V0.8.3's Double Ratchet
into a live network path — and in doing so becomes the FIRST place in this codebase that parses
untrusted bytes arriving directly off a raw libp2p stream, with no GossipSub message-size ceiling
backstopping the parser. Every other GossipSub-based validator in this codebase (`PeerDirectoryGossip`,
`PrekeyBundleGossip`, `VeritasGossip`, `InboxGossip`, ...) inherits a hard upper bound on message
size from `GossipPubSub`'s own `maxGossipMessageSize` (256 KiB) before its own validator ever runs.
A raw libp2p stream protocol has no such backstop unless the protocol itself builds one — this
section is that discipline, worked through end to end.

=== The stream-protocol binding shape, verified against the resolved jar

`DmProtocol`/`DmProtocolHandler` are built directly against jvm-libp2p 1.3.5-RELEASE's real
`ProtocolHandler`/`ProtocolMessageHandler`/`StrictProtocolBinding` API — confirmed via `javap`
against the resolved jar and cross-checked against the decompiled sources jar, not assumed. The
shape mirrors the bundled reference implementation, `io.libp2p.protocol.Ping`/`PingProtocol`
(`StrictProtocolBinding` wraps a `ProtocolHandler`, which pushes handlers in `initProtocolStream`
— run for BOTH initiator and responder roles — then hands off to `onStartInitiator`/
`onStartResponder`), with one deliberate divergence: `Ping` relies on the implicit assumption that
"one `writeAndFlush` call produces one inbound `ByteBuf`," pushing no frame-decoding codec of its
own. `DmProtocolHandler` instead explicitly pushes a Netty `LengthFieldBasedFrameDecoder`/
`LengthFieldPrepender` pair — an explicit, verifiable frame boundary is what actually gives a
length-validated-before-allocation guarantee, regardless of how the underlying mplex substream
happens to chunk bytes on the wire; relying on an implicit one-write-one-read assumption would be
the wrong default for a wave whose entire risk framing is "no upstream size ceiling."

=== Four independent, layered defenses against the untrusted-raw-stream surface

1. **`InboundTrafficLimitHandler`** — pushed AUTOMATICALLY by the `ProtocolHandler` base class,
   BEFORE `initProtocolStream` even runs, from the `initiatorTrafficLimit`/`responderTrafficLimit`
   constructor arguments. Caps TOTAL inbound bytes over the stream's lifetime, independent of and
   prior to the frame decoder. Unlike `Ping` (which disables this with `Long.MAX_VALUE` for both),
   `DmProtocolHandler` passes sane, non-`MAX_VALUE` limits — generous enough for one full
   `DmEnvelope` plus its length prefix on the responder side, deliberately small on the initiator
   side (this wave's design is fire-and-forget one-way, see below, so a well-behaved peer never
   sends anything back on a stream WE dialled).
2. **`LengthFieldBasedFrameDecoder`**, `maxFrameLength = DmEnvelopeCodec.MAX_ENVELOPE_BYTES +
   LENGTH_FIELD_SIZE`, `failFast = true` — rejects a frame whose declared length exceeds the cap
   BEFORE allocating any buffer proportional to that declared size. This is the load-bearing gate
   `DmStreamAbuseTest` case (a) constructs the adversarial payload for: a 4-byte length prefix
   declaring an ~1 GB frame, with only a handful of actual bytes following.
+
**`+ LENGTH_FIELD_SIZE` fixes a security audit round 1 finding (2026-08-11): the bare
`DmEnvelopeCodec.MAX_ENVELOPE_BYTES` value here was off by 4 bytes.** Netty's
`LengthFieldBasedFrameDecoder` compares the FULL frame length — the declared body length PLUS
`lengthFieldEndOffset` (`lengthFieldOffset + lengthFieldLength`, `4` here) — against
`maxFrameLength`, not the declared body length alone. Passing the bare codec-level ceiling therefore
rejected any envelope whose encoded size landed in the top 4 bytes of the otherwise-legitimate
range: a maximum-size envelope (a 65,459-byte plaintext — exactly `RatchetMessageCodec.MAX_PLAINTEXT_BYTES`,
which `DoubleRatchetSession.encrypt` explicitly permits — encoding to exactly `MAX_ENVELOPE_BYTES` =
65,715 bytes) round-tripped cleanly through `DmEnvelopeCodec.decode` directly, but was silently
discarded by this handler's own decoder with `TooLongFrameException` once framed onto the wire —
silently, since this wave is fire-and-forget with no application-level ack. Root cause of it
surviving three prior review rounds: no test anywhere sent a maximum-size LEGITIMATE envelope
through the real prepender/decoder pair — `TwoNodeDmIntegrationTest`'s original case used 4,096
bytes, and every `DmStreamAbuseTest` size case is adversarially OVERSIZED, not
maximum-but-still-valid. `TwoNodeDmIntegrationTest` now has a dedicated maximum-size round-trip case
closing this gap.
3. **`ReadTimeoutHandler`** (10 seconds) — the classic slowloris defense: force-closes a stream that
   goes idle (no read event at all) for this long.
4. **An absolute per-stream wall-clock deadline** (20 seconds), scheduled independently of read
   activity in `onStartResponder`/`onStartInitiator` and cancelled once the stream finishes
   normally. This catches the slowloris variant #3 alone cannot: a peer that drips one byte just
   before every idle window would expire, resetting `ReadTimeoutHandler`'s own clock forever without
   ever completing a frame. `DmStreamAbuseTest` case (c2) is this exact scenario, verified against
   the real timers, not a mock clock.

Plus a **per-remote-`PeerId` concurrent-stream cap** (8, `MAX_CONCURRENT_STREAMS_PER_PEER`),
enforced in `onStartResponder` — bounds how many not-yet-completed `/lapis/dm/1.0.0` streams a
single peer may have open against this node at once, so one misbehaving or malicious peer cannot
exhaust this node's stream-handling capacity (`DmStreamAbuseTest` case (d): dialling
`MAX_CONCURRENT_STREAMS_PER_PEER + 1` streams from one peer gets exactly one rejected, and a
DIFFERENT peer is unaffected — the cap is per-peer, not global).

=== Design decision: one stream per message, fire-and-forget, no application-level ack

Not mandated by the concept note, chosen deliberately during implementation. Each
`DmSessionManager.send` call dials a FRESH stream (cheap if a `Connection` to the peer already
exists — only a new mplex substream, not a new TCP/Noise handshake), writes EXACTLY ONE
`DmEnvelope` frame, and closes. The responder decodes exactly one frame per stream and closes too,
success or failure. This is what makes the four defenses above simple to reason about — one frame
lifecycle per stream, no ongoing multi-frame backpressure bookkeeping to get wrong — and matches
this wave's "no delivery receipts, no typing indicators, not even as stubs" scope cut: no
application-level response frame is ever written back on a DM stream.

=== `DmEnvelope`/`DmEnvelopeCodec`: the outer wire frame

```
off    len   field
  0      4   magic "LNDM"
  4      1   version = 1
  5      1   flags - reserved, must be zero
  6      1   messageType  (0=TEXT, 1=X3DH_INITIAL, 2=RECEIPT reserved, 3=CALL_SIGNAL reserved)
  7     33   senderIdentity              (secp256k1 compressed public key)
 40      1   x3dhInitialHeaderPresent    (MUST equal 1 iff messageType == X3DH_INITIAL)
 41    137   X3DH section (initiator X25519 pubkey | binding signature | ephemeral pubkey |
             signedPrekeyId | oneTimePrekeyIdPresent | oneTimePrekeyId) - all-zero when absent
178      2   ratchetMessageLength   (1..RatchetMessageCodec.MAX_MESSAGE_BYTES)
180      N   ratchetMessageBytes    (a RatchetMessageCodec.encode()'d blob)
```

Decode order is cheapest/most-selective first, mirroring `RatchetMessageCodec.decode`'s/
`PeerRecordCodec.decode`'s established discipline: total size cap first (before any stream is even
opened), then magic/version/flags, then `messageType` — REJECTED IMMEDIATELY for `RECEIPT`/
`CALL_SIGNAL`/an unrecognized wire byte, BEFORE `senderIdentity` or anything downstream is even
parsed (the cheapest possible rejection point, and what the CALL_SIGNAL adversarial test asserts
the ordering of), then the X3DH presence-flag cross-check (with every sub-field of an absent
section required to be exactly all-zero/0 — tamper evidence, mirroring `DoubleRatchetSessionCodec`'s
identical "absent slot must be zero" discipline), then `ratchetMessageLength` — range-checked
BEFORE the corresponding allocation — and finally `RatchetMessageCodec.decode` itself, whose own
independent checks run again as defense in depth.

No separate `x3dhInitiatorIdentity` wire field: the X3DH initiator IS the envelope's own
`senderIdentity` by construction (`DmSessionManager` only ever emits `X3DH_INITIAL` for a message
it originates as initiator), so encoding it twice would be a redundant field an attacker could make
disagree with `senderIdentity` — the exact anti-pattern `PrekeyBundle.x25519IdentityKey`'s
"read-through alias, never a second copy" discipline exists to prevent everywhere else in this
codebase. `X3dhPreKeyMessageHeader.initiatorIdentity` is reconstructed on decode as
`= envelope.senderIdentity`, never carried separately on the wire.

The X3DH section is always present in the fixed layout, gated by a presence byte, not conditional
placement — exactly `DoubleRatchetSessionCodec`'s own established idiom for "sometimes-present"
fields. Costs 137 extra bytes on every `TEXT` envelope (negligible relative to a <=65 KB ratchet
payload) in exchange for zero offset arithmetic to get wrong.

=== The identity-authority rule

The single most security-critical property of this wave, deserving its own subsection rather than
a bullet point, matching this codebase's precedent of a dedicated write-up wherever a construction
closes a specific attack (`X3dh`'s associated-data section, `PeerRecord`'s possession-proof
section):

**The libp2p `PeerId` a stream connection authenticates (via Noise, at the TRANSPORT layer) is NOT
the same thing as the secp256k1 identity the Double Ratchet/X3DH layer authenticates.** The two are
completely separate identity spaces, and this wave never lets them be confused. `PeerId` appears in
exactly ONE place in `DmProtocolHandler` — `onStartResponder`, as a resource-management key
bounding how many concurrent `/lapis/dm/1.0.0` streams one transport connection may open — and is
NEVER used for message authorization or sender attribution anywhere in this module.

`DmEnvelope.senderIdentity` is an UNTRUSTED CLAIM the moment an envelope arrives off the wire. In
`DmSessionManager.handleInboundEnvelope`, this claim selects WHICH session to attempt — nothing
more — and it is never cross-checked against the transport-authenticated `PeerId` either (a
completely separate identity space). The claim only becomes trustworthy the instant
`DoubleRatchetSession.decrypt` returns successfully: AEAD authentication under a session that was
itself bootstrapped via a real X3DH exchange, bound (via `X3dh`'s own associated-data construction,
folded into both the AEAD-style AD and the HKDF `info` string — see V0.8.2's section above) to this
EXACT secp256k1 identity pair, is the ONLY thing ever treated as proof of "who actually sent this."
A message truly encrypted under a DIFFERENT `(sender, us)` identity pair can never verify here, even
if the wrapping envelope lies about who sent it.

`DmStreamAbuseTest` case (e) is the executable proof: a genuine `RatchetMessage`, encrypted under a
REAL session between the local identity and peer Y, is wrapped in a `DmEnvelope` whose
`senderIdentity` field instead names an unrelated peer X (with its OWN real, independently
established session). Fed into `handleInboundEnvelope`, this is rejected — the ratchet's own
authentication under the CLAIMED (X) session fails, and the message is never accepted or attributed
to X. Case (g) re-verifies the complementary property one layer up from `DoubleRatchetAdversarialTest`'s
own cross-session-confusion case: a genuinely valid envelope, correctly decrypting under session A,
is rejected outright if replayed verbatim against an unrelated session B belonging to a completely
different peer pair.

=== The Argon2id-per-message-persist problem, resolved

`DoubleRatchetSession`'s own V0.8.3 doc comment (see above) flagged, and deliberately deferred, a
concrete viability problem: persisting session state once per message in each direction means one
full `DoubleRatchetSessionCodec.encode` call per message — a fresh Argon2id derivation at
`KeystoreEncryption.DEFAULT_MEMORY_KIB`/`DEFAULT_ITERATIONS` (64 MiB / 3 passes, order
10^2^–10^3^ ms) plus a full re-serialisation of the skipped-key store. Correct, but "not viable as a
live network message-send path's per-message cost." This wave is where the fix — flagged then as
"most likely: cache the Argon2id-derived key for the session's lifetime instead of re-deriving it
per call" — actually lands.

`DoubleRatchetSessionCodec.encode` gains an optional `salt` parameter (default: a fresh random
draw, 100% preserving every existing caller's behaviour). Two new functions, `encodeWithKey`/
`decodeWithKey`, take an ALREADY-DERIVED 32-byte AES-256 key directly, bypassing
`KeystoreEncryption.deriveKey` (and therefore Argon2id) entirely. The wire format is byte-identical
to `encode`/`decode` — the header still carries the real KDF params/salt, so the file stays
self-describing and portable for a future slow-path recovery tool; only the AES-256-GCM key's
ORIGIN differs. `encode`/`decode` are refactored to delegate into `encodeWithKey`/`decodeWithKey`
once a key exists, so there remains exactly one AEAD-header-assembly/parsing implementation, not
two — `decodeWithKey` runs every existing structural/range/sanity-cap check `decode` runs (size
cap, magic, version, kdfId, implausible-Argon2-cost-parameter caps) BEFORE attempting AES-GCM
decryption, unweakened.

`DmSessionManager.attach` derives the key ONCE per process — from a passphrase plus a persisted
`.salt` file (0600 where POSIX permissions are supported, generated on first use, reused
thereafter: same passphrase + same salt + same params ⇒ same derived key) — and reuses it for every
`persistSession` call for the process's lifetime. **A caller-supplied key that did not actually come
from a given file's own salt is not, and cannot be, detected as wrong by `decodeWithKey` itself** —
nothing in that function can verify a key's provenance; it simply fails the AEAD tag and throws
`KeystoreDecryptionException`, the identical safe failure a wrong passphrase produces today. No new
security hole is opened by skipping Argon2id here — only a legitimate holder of the correct
passphrase/salt pair could ever have derived a key that verifies.

=== Session persistence: what this wave deliberately does NOT match from `PrekeyStore`

`DmSessionManager` persists sessions via atomic temp-file-then-`Files.move` writes (durable against
a crash mid-write, mirroring `PrekeyStore.persistAtomically`'s core discipline), guarded by an
IN-PROCESS per-peer monitor (`withPeerLock`) — but deliberately stops short of `PrekeyStore`'s full
cross-process sidecar-`FileChannel`-lock discipline. A single `LapisNode` process is this
codebase's only supported deployment shape per identity today; no two `DmSessionManager` instances
ever legitimately point at the same session-store directory from different processes. Stated
explicitly as a scope reduction from the wave's own planning notes, not a silent omission — should
this codebase ever support multiple concurrent processes sharing one identity's DM session store,
`PrekeyStore`'s sidecar-lock pattern is the reference implementation to copy.

=== `DmDedupKey`: a forward-compatible hook this wave computes, V0.8.5 consumes

`DmDedupKey.of(senderIdentity, ratchetMessage)` computes
`domainSeparatedDigest(domainTag, senderIdentity.bytes(33), ratchetPublicKey.bytes(32),
messageNumber(4, BE))` for every successfully-decrypted inbound message — a domain-separated SHA-256
(1-byte tag-length-prefixed tag, then each part individually 2-byte-length-prefixed), NOT plain
concatenation (doc correction, security audit round 1 finding, 2026-08-11: this section previously
stated the formula as plain concatenation, which did not match the implementation; the
implementation is strictly stronger — unambiguous parsing, no cross-field boundary ambiguity — so
only this doc text changed, not the code; `DmDedupKeyTest` now pins the exact preimage as a
known-answer-style test so the contract is enforced in code, not merely in prose). A message's
`(ratchetPublicKey, messageNumber)` pair is unique per session position by the Double Ratchet's own
construction (`Ns`/`Nr` never rewind for a correctly-persisted session), and `senderIdentity` scopes
it across DIFFERENT sessions that identity may hold. Computed from fields already on the decoded
`RatchetMessage` — the same fields V0.8.5's planned offline-mailbox redelivery path will see too, so
a message delivered both online (this wave) and later redelivered via the mailbox produces the
IDENTICAL dedup key without either path needing to know about the other. **Nothing in THIS wave
(V0.8.4) deduplicates against anything with this key** — it is computed and exposed on
`DmInboundMessage` purely so V0.8.5 does not have to retrofit the concept later. **V0.8.5, since
landed, is exactly what consumes it** — see the "DM stream protocol (V0.8.5)" section below for the
cross-path `recentlyDeliveredDedupKeys` pre-check `processInboundDmEnvelope` runs with it.

=== Explicit, deliberate scope cuts for this wave

* **No delivery receipts, no typing indicators** — not even as stubs. `DmMessageType.RECEIPT`/
  `CALL_SIGNAL` exist on the wire but are rejected outright at every layer that can reject them
  (the envelope's own constructor, the codec, and `DmSessionManager`'s inbound handler) — mirrors
  `EncryptionMode.MLS_ARCHIVE`'s precedent.
* **No NAT traversal.** A documented gap since V0.1.3/networking, unchanged by this wave. Only
  direct-dialable peers (same-LAN, or otherwise directly reachable) are supported.
* **No offline/mailbox redelivery in THIS wave (V0.8.4)** — V0.8.5's job, since landed; see
  `DmDedupKey` above and the "DM stream protocol (V0.8.5)" section below.
* **`DmStore` (conversation history) is in-memory-only** — see below.
* **Deliberate sidecar-lock simplification** for session persistence — see above.
* **No multi-device / no session migration** (inherited from `DoubleRatchetSession`).
* **No session registry beyond what V0.8.3 already documents as partial.**

=== Bounded resources — every cap this wave enforces, and why

Mirrors this codebase's established discipline of an explicit, justified numeric cap on every
structure an unauthenticated or lightly-authenticated remote actor can grow — not silently omitted
for the structures below, closed during this wave's own review round:

* **`DmSessionManager.liveSessionCache`** (`MAX_LIVE_SESSIONS`, 4,096) — bounded, LRU-evicting cache
  of decoded `DoubleRatchetSession`s. Persist-before-cache (see above), so evicting the in-memory
  copy never loses durable state.
* **`DmSessionManager.dialSemaphore`** (`MAX_CONCURRENT_OUTBOUND_DIALS`, 32) — bounds simultaneous
  in-flight `send()` dials.
* **`DmProtocolHandler.perPeerStreamCounts`** (`MAX_CONCURRENT_STREAMS_PER_PEER`, 8, per remote
  `PeerId`) — bounds concurrent, not-yet-completed streams one connection may hold open. Backed by a
  `ConcurrentHashMap<PeerId, Int>` mutated only via `compute`/`computeIfPresent`, self-cleaning: an
  entry is removed outright the instant its count returns to zero, so this map is bounded by peers
  CURRENTLY holding an open stream, never by the total distinct peers ever seen over the node's
  lifetime — a `PeerId` here costs a real TCP+Noise-authenticated connection to mint, unlike the next
  bullet.
* **`DmSessionManager.peerLockStripes`** (`PEER_LOCK_STRIPE_COUNT`, 2,048, fixed-size lock striping,
  not a per-identity map) — closes a gap found during this wave's own review: `withPeerLock` is
  called for every distinct CLAIMED `senderIdentity` on every inbound envelope, in
  `handleInboundEnvelope`, BEFORE any cryptographic authentication of that claim (see "The
  identity-authority rule" above). A structurally-valid `Secp256k1PublicKey` costs an attacker
  nothing to mint in bulk — no private key needed, only curve-point validity — so an unbounded
  per-identity monitor map here would have let an unauthenticated remote peer grow this node's
  memory without bound, exactly the class of risk `MAX_CONCURRENT_STREAMS_PER_PEER` and
  `MAX_LIVE_SESSIONS` already close for their own structures. Fixed-size lock striping (indexed by a
  stable, content-derived hash of the peer's public key bytes) bounds this at a small constant
  regardless of identity count — the only cost is occasional false contention between two unrelated
  peers sharing a stripe, never a correctness issue.
* **`DmStore.historyByPeer`** (`MAX_TRACKED_PEERS`, 4,096, LRU-evicting, on top of the existing
  per-peer `MAX_HISTORY_PER_PEER`, 500) — `DmStore` is opt-in and each entry requires a genuinely
  completed, AEAD-authenticated session to populate (not free for an attacker), but is still bounded
  on both axes for the same reasons as every sibling cache above.
* **`DmSessionManager.prekeyConsumptionSemaphore`** (`MAX_CONCURRENT_PREKEY_CONSUMPTIONS`, 4) —
  closes a MAJOR gap found during this wave's own review round 3: `handleInboundEnvelope`'s
  `X3DH_INITIAL` branch calls `PrekeyStore.consumeOneTimePrekey` whenever `header.oneTimePrekeyId`
  is non-null, gated only by `EncryptionKeyBinding.verify` — which proves a claimed identity's
  binding is internally self-consistent, NOT that the identity is legitimate or known. Minting a
  throwaway secp256k1 identity and self-signing a binding for it costs an attacker microseconds of
  local CPU. `PrekeyStore.consumeOneTimePrekey` (unmodified by this wave, in `lapis-net-ratchet`)
  unconditionally performs a full Argon2id derivation (64 MiB/3 passes) via
  `PrekeyStore.withExclusiveFileAccess` BEFORE the id lookup that could reject the request even
  runs, and that method is guarded by a single per-file JVM monitor shared by the whole store — so
  every concurrent call serializes on ONE lock. Without a bound, a flood of such envelopes would
  queue without limit, denying every legitimate incoming first-contact handshake for as long as the
  flood continues — the same class of "Argon2id is not viable as an unbounded live-network-path
  cost" problem `DoubleRatchetSessionCodec.encodeWithKey`/`decodeWithKey` (below) closes for session
  persistence, left open here because `PrekeyStore` itself is out of this wave's scope. A small,
  fixed concurrency bound converts the unbounded pileup into a bounded amount of concurrent CPU/
  lock-contention work; permits are acquired with a ZERO-wait `tryAcquire` (never blocks) because
  `handleInboundEnvelope` runs directly on a Netty I/O thread — blocking it while waiting for a
  permit would itself compound the stall this guards against. This mitigation bounds resource
  consumption; it does not and cannot distinguish a flooding attacker from a legitimate initiator
  before the ratchet itself authenticates (see "The identity-authority rule" above) — a sustained
  flood can still starve legitimate handshakes of their fair share of the four permits, just no
  longer of unbounded queueing/memory.
+
**Residual gap this left open, and its fix (security audit round 1, 2026-08-11, PROVEN with an
executable probe): `prekeyConsumptionSemaphore` bounds CONCURRENCY, not RATE or TOTAL.** A purely
SEQUENTIAL attacker — one self-signed, structurally-valid `X3DH_INITIAL` at a time, each one
trivially passing `EncryptionKeyBinding.verify` for the same "costs microseconds, no shared key
material" reason described above — never touches the concurrency bound at all, and durably drains
this node's entire one-time-prekey pool one request at a time. Proven, not theoretical: five
throwaway self-signed identities burned a five-entry test pool to zero in 2.9 seconds. Because this
wave's own `X3dh` class doc comment states that a replay naming NO one-time prekey is not detected by
anything in this wave, permanent pool exhaustion is not a mere inconvenience — it durably strips this
node of the only replay protection X3DH initial messages have here. Two complementary additions close
this:

* **`DmSessionManager.prekeyConsumptionRateLimiter`** (`MAX_PREKEY_CONSUMPTIONS_PER_WINDOW`, 10, per
  `PREKEY_CONSUMPTION_RATE_WINDOW`, 60 seconds) — a plain fixed-window counter, checked BEFORE
  `prekeyConsumptionSemaphore` (cheaper, and rejects a sustained flood without even touching the
  concurrency-bounded resource). Deliberately GLOBAL, not keyed per claimed `senderIdentity` — a
  per-identity limiter is trivially bypassed by minting a fresh throwaway identity per attempt,
  exactly the attack this closes.
* **`DmSessionManager.replenishOneTimePrekeysIfLow`** — after every SUCCESSFUL
  `consumeOneTimePrekey`, if `PrekeyStore.availableOneTimePrekeyCount` has dropped to or below
  `PREKEY_REPLENISH_LOW_WATERMARK` (20), generates fresh one-time prekeys back up to
  `PREKEY_REPLENISH_TARGET_COUNT` (100, matching `PrekeyStore.DEFAULT_ONE_TIME_PREKEY_COUNT`) and
  republishes an updated `PrekeyBundle`, so a drained pool recovers on its own instead of requiring
  manual operator intervention. Dispatched onto a dedicated single-thread executor, never inline on
  the Netty thread that triggered it — `PrekeyStore.generateOneTimePrekeys`/`publishBundle` both take
  the same Argon2id-guarded exclusive file lock `consumeOneTimePrekey` does, and a
  `replenishmentInFlight` guard caps this at one outstanding replenishment pass at a time, so a flood
  that keeps crossing the watermark cannot queue unboundedly many redundant top-ups either. Residual,
  accepted, BOUNDED trade-off: because `PrekeyStore`'s per-file monitor is shared by every handle open
  on the same file (by design, for correctness — see that class's own doc comment), a concurrent
  `consumeOneTimePrekey` call can observe brief added latency while a replenishment pass holds that
  monitor — the same class of bounded, serialized cost `prekeyConsumptionSemaphore` already accepts
  for up to `MAX_CONCURRENT_PREKEY_CONSUMPTIONS` concurrent attempts today, not a new unbounded one.

Together these turn "durable, permanent depletion after a cheap sequential flood" into "rate-limited,
self-healing depletion" — the disclosure above (bounding resource consumption, not attacker
distinguishability) still holds for the CONCURRENCY dimension; it is the RATE and TOTAL dimensions
this addition closes. `DmStreamAbuseTest` case (h2) is the regression test: the SAME self-signed
attack case (h)'s garbage-signature gate cannot catch (a genuinely valid binding legitimately passes
that gate), now shown to be rate-limited and self-healing rather than able to achieve permanent
depletion.

`DoubleRatchetSessionCodec.encodeWithKey`/`decodeWithKey` (V0.8.4) — not a numeric cap, but the same
"expensive-Argon2id-is-not-viable-on-a-live-network-path" concern: session persistence derives its
AES key ONCE per process lifetime (`DmSessionManager.cachedKey`) rather than re-running Argon2id on
every `send()`/inbound message, which is what makes per-message session persistence viable at all.

== DM stream protocol (V0.8.5) — the offline Nabu mailbox

Still `lapis-net-dm`. This wave completes the split V0.8.4 started: V0.8.4 delivers "recipient
reachable right now" over a live libp2p stream; this wave delivers "recipient offline, deposit a
message in Nabu for later pickup." Two DIFFERENT problems both need solving, and this wave's central
insight is that they are genuinely different — closing one does not close the other:

1. **Blob fetchability.** A bare `Cid` alone is not fetchable: `NabuStorage.findProviders`
   (DHT-based provider discovery) has been broken since V0.1.4 (see the Storage section above).
   `MailboxPointer` carries the sender's IDENTITY — not an address, which would go stale — as a
   routing hint; the recipient resolves the sender's CURRENT address at fetch time via
   `PeerDirectoryGossip.lookup(senderIdentity)` (V0.8.1), registers it with `NabuStorage.registerPeerAddress`,
   and does a direct Bitswap fetch by explicit peer (`NabuStorage.get(cid, peers = setOf(peerId))`) —
   the SAME mechanism `TwoNodeBitswapDirectFetchTest` already proved end-to-end for V0.1.4, applied
   here for the first time to a real product feature.
2. **Pointer discoverability.** `GossipPubSub.subscribe`'s own doc comment establishes that
   GossipSub has ZERO message replay: a node that publishes while a peer isn't yet subscribed never
   redelivers that message to a later-joining subscriber. The defining "genuinely offline" scenario
   this wave targets — a recipient's node that is not even RUNNING when the sender deposits a
   pointer — means the pointer's original publish can NEVER reach that recipient, no matter how
   long it later stays subscribed. `MailboxRedeliveryScheduler` is what closes this: the sender
   re-publishes the SAME pointer bytes on a fixed interval (300s default) for as long as its TTL has
   not expired, so a later-starting recipient receives it on the NEXT scheduled re-publish, through
   completely ordinary, already-proven GossipSub delivery — no reliance on GossipSub's internal
   mcache/IHAVE timing, which would be fragile and undocumented.

Both failure modes share one root cause and one consequence, stated here without hedging because
it is this wave's most important caveat: **if the sender's node is not online again before the
pointer's TTL expires, offline delivery cannot complete** — not merely "the blob must be
re-servable" (problem 1) but the STRONGER requirement that the sender must be alive to RE-ANNOUNCE
the pointer (problem 2), since that is the only way a recipient who missed the original publish
ever learns the pointer exists at all.

=== `MailboxPointer`/`MailboxPointerCodec` — exact wire layout

Located in `lapis-net-dm`, not a new module: tightly coupled to `DmSessionManager`/`DmDedupKey`/
`DmEnvelopeCodec`, mirroring `lapis-net-directory` already hosting both `PeerRecord` and the
related-but-distinct `PrekeyBundle` gossip type in one module rather than spinning up a new Gradle
module for a handful of files.

....
off    len   field
  0      4   magic "LNMP"  (Lapis Net Mailbox Pointer)
  4      1   version = 1
  5      1   flags - reserved, must be zero
  6     33   recipientIdentity (secp256k1 compressed public key)
 39     33   senderIdentity    (secp256k1 compressed public key) - the routing hint
 72      2   blobCidLen (unsigned short, 1..MAX_CID_BYTES=128)
 74      N   blobCid bytes    (N = blobCidLen)
74+N     8   notValidAfterEpochSecond (long, big-endian)
82+N    64   signature (compact ECDSA by senderIdentity)
....

`MAILBOX_POINTER_FIXED_PREFIX_SIZE` = 74 (through `blobCidLen`, before the CID bytes themselves).
`MIN_POINTER_BYTES` = 147, `MAX_POINTER_BYTES` = 274. `encodeSignedBody` covers everything through
`notValidAfterEpochSecond`; `encode` appends the trailing signature, mirroring
`PeerRecordCodec.encode = encodeSignedBody(record) + record.signature` exactly.

Decode order mirrors `PeerRecordCodec`/`DmEnvelopeCodec` exactly: `bytes.size > MAX_POINTER_BYTES`
rejected first, then `bytes.size < MIN_POINTER_BYTES` rejected next (too-short-to-be-structurally-
valid, an explicit first-line check mirroring `DmEnvelopeCodec.decode`'s own step 2 - a code-review
finding after V0.8.5's own security audit: `MIN_POINTER_BYTES` used to be declared and documented
but never actually consulted in `decode`'s logic, with a too-short frame instead only indirectly
rejected via an `EOFException` mid-parse), then magic/version/reserved-flags, then
`recipientIdentity`/`senderIdentity` (`Secp256k1PublicKey`'s own constructor validates
curve-point-ness), then `blobCidLen` range-checked (`1..MAX_CID_BYTES`) BEFORE the corresponding
allocation, then — the load-bearing CID-specific gate — `CidBytesValidation.isSafeToCast` checked on
the CID bytes BEFORE `Cid.cast` ever runs, closing the exact same declared-multihash-length OOM-DoS
class `MessageEnvelopeCodec`'s `contentCid`/`replyTo`/`threadRoot` fields already guard against (see
the "Known gap closed: CID multihash length overflow" note referenced from `CidBytesValidation`'s
own class doc comment). `notValidAfterEpochSecond` carries NO range check at decode time — same
reasoning as `PeerRecord`'s identical field: attacker-controlled, this constructor runs for both
locally-created and gossip-decoded pointers, and TTL is a pure read/poll-time filter, never an
accept/reject decision inside the codec or the gossip validator.

**Metadata-minimization honesty note.** `MailboxPointer` carries `senderIdentity` and
`recipientIdentity` in the clear, signed and gossiped on a topic derived from `recipientIdentity` —
a deliberate, necessary deviation from the original DM concept note's "Mailbox-Records enthalten
keine Klartext-Absenderkennung" principle. The recipient cannot resolve a routing hint without
knowing WHOSE current address to look up, and the gossip validator cannot cheaply reject a forged
pointer without a signer identity to check it against — a fully metadata-blind mailbox record is not
achievable under this wave's broken-DHT-workaround fetch mechanism. Anyone who can subscribe to a
recipient's mailbox topic (i.e. anyone — GossipSub topics are not access-controlled) learns "someone
claiming identity S deposited a message for X at time T," the same exposure `PeerRecord` already
accepts for presence/address gossip. No onion routing is attempted here — the original DM concept
note's own open question, left open, not resolved.

**Extended (security audit round 1 minor finding): this note originally stopped at identity
metadata — the exposure does not.** The pointer also publishes `blobCid` in the clear, and Bitswap
serves blocks to any requesting peer with no read-access control. Consequently ANY mailbox-topic
observer — not only the intended recipient — can Bitswap-fetch the full encrypted `DmEnvelope` blob
directly from the sender, learning the exact ciphertext length (hence an approximate plaintext
length) and retaining it indefinitely for later cryptanalysis or a post-compromise decryption
attempt. This is a strictly larger exposure than V0.8.4's online path, where the frame only ever
traverses the recipient's own libp2p stream.

=== `MailboxGossip`/`MailboxPointerIndex`

`MailboxTopics.forRecipient` mirrors `InboxTopics.forRecipient` exactly — topic-per-recipient-
identity, SHA-256 of the compressed public key, hashing being cosmetic (not a privacy control) for
the same reason `InboxTopics` documents. `MailboxGossip` is SUBSCRIBE-ONLY, no `announce()` method —
publishing onto a DIFFERENT identity's topic is the SENDER's job (`DmSessionManager.sendOffline`/
`MailboxRedeliveryScheduler`), mirroring the `MailSender`/`InboxGossip` split rather than
`PeerDirectoryGossip`'s self-publishing shape.

`MailboxPointerIndex` is content-id keyed with an added `resolved` flag per entry — a genuinely
different shape from `PeerRecordIndex`'s "latest wins per identity": a recipient can legitimately
have MANY distinct pending offline messages at once, so it mirrors `InboxIndex`'s multiple-
coexisting-entries structure instead, plus the established two-cap eviction/persistence split (an
evicting `entriesByContentId` tracking cap, a separate non-evicting `persistedContentIds`
reservation cap) every sibling index in this codebase already uses. `markResolved` is called after
either a successful deliver OR a DEFINITIVE failure (garbage/tampered blob, or an expired TTL —
retrying never helps, the bytes/expiry never change) — NOT for "peer currently unreachable," which
stays pending for the next poll pass since the sender may come back online.

`MailboxGossip.onGossipMessage`'s validator, in order: decode → addressed-to-local check (dropped
WITHOUT persisting/indexing/re-propagating if not, mirroring `InboxGossip`'s identical divergence
from `VeritasGossip`'s "keep relaying even what we can't use") → `MailboxPointer.verify` → content-
id dedup (`canAccept`) → persist (behind `tryReservePersistence`) → index. **Zero clock and zero
network calls — the same iron rule every prior wave's gossip validator follows.** No
`storage.get`/`storage.findProviders` call anywhere in this validator: the pointer bytes ARE the
full record; only the referenced BLOB is fetched later, out-of-band, by `MailboxPoller`.

=== `MailboxPoller` — the recipient-side fetch driver

Runs once, synchronously, at `attach()` time (an initial pass over whatever `MailboxGossip`'s index
already holds IN MEMORY — pointers received via live gossip since this node's OWN process started,
before this poller was wired up), then periodically thereafter (60s default,
`scheduleWithFixedDelay` — deliberately NOT `scheduleAtFixedRate`, so a slow pass with many
unreachable peers cannot queue up overlapping runs).

**Not a reload from durable storage.** `MailboxGossip.attach` always constructs a brand-new, empty,
in-memory-only `MailboxPointerIndex`, and `NabuStorage` has no enumeration API to reload pointers
from. A pointer this node already received-and-persisted-the-raw-bytes-of but had not yet
fetched+decrypted before ITS OWN restart is therefore lost from this node's own tracking on restart
— symmetric to, but distinct from, `MailboxRedeliveryScheduler`'s own documented sender-side "lost
on restart" limitation below. The only recovery path is the SENDER's `MailboxRedeliveryScheduler`
re-announcing the same pointer again before its own restart or the pointer's TTL.

For each pending pointer: resolves the sender's CURRENT address via `PeerDirectoryGossip.lookup`
(re-resolved on EVERY attempt, not cached across passes — the sender's address may have changed
since the last attempt, so each poll cycle uses the freshest directory data), registers it
(`NabuStorage.registerPeerAddress` — Bitswap resolves peer addresses from the libp2p host's address
book, not from the `peers` set passed to `get` directly, per `TwoNodeBitswapDirectFetchTest`'s own
established sequence), and attempts a direct Bitswap fetch (`NabuStorage.get(cid, peers =
setOf(peerId))`). On success, `DmEnvelopeCodec.decode` runs to distinguish "genuinely undeliverable
garbage frame, mark resolved, stop retrying" from "worth attempting" — and on a structurally valid
decode, the envelope is handed to `DmSessionManager::handleOfflineEnvelope`, which routes it through
the EXACT SAME `processInboundDmEnvelope` core the online path (`handleInboundEnvelope`) already
uses. **One trust boundary for both transports, not two independently-reasoned-about ones.**

`handleOfflineEnvelope`/`processInboundDmEnvelope` return whether the outcome was FINAL for this
envelope's exact bytes (delivered, or cleanly/permanently rejected as tamper, garbage, replay, or a
reserved message type) versus merely reflecting THIS NODE'S OWN current, mutable state — today,
exactly one case: the `TEXT` branch's "no session yet for the claimed sender." `MailboxPoller` calls
`MailboxGossip.markResolved` only on the FINAL outcome; a non-final one leaves the pointer pending
for a later poll pass. This matters concretely because `pending()`'s iteration order tracks gossip
arrival order, not send order: a sender who calls `sendOffline()` twice to the same still-offline
recipient (first bootstraps a session via `X3DH_INITIAL`, second reuses it via `TEXT`) can have its
`TEXT` pointer fetched and attempted BEFORE the `X3DH_INITIAL` pointer that establishes the session
it needs. Marking that `TEXT` pointer resolved on the "no session yet" rejection would silently and
permanently lose a message that is genuinely fetchable and cryptographically valid, once the session
exists — `MailboxPoller` instead leaves it pending, so the next pass (after the `X3DH_INITIAL`
pointer has been processed) delivers it.

`pollOnce` never throws: each pointer's attempt is independently `try`/caught inside the loop, so
one bad pointer (an unreachable sender, a fetch timeout, an unexpected exception) never blocks the
rest of a pass — the property `MailboxAbuseTest` case (b) proves under an adversarial flood.

**Fix round (security audit round 1, two major findings):** `attemptOne` previously looped over up
to `PeerRecordCodec.MAX_ADDRESSES` (16) addresses, calling `storage.get` with the SAME `peers` set
on every iteration — functionally one fetch attempt priced sixteen times, worst case
`MailboxPointerIndex.MAX_TRACKED_POINTERS` (64,000) × 16 × `NabuStorage`'s own 10s default timeout,
entirely attacker-mintable (a throwaway identity plus a signed pointer costs only local CPU). It also
registered and dialed every address an attacker-chosen sender identity's `PeerRecord` named, with no
address hygiene anywhere in the codebase — the first automated, unsolicited, repeating outbound-dial
primitive in this codebase driven purely by gossip-supplied data, no local user intent behind the
dial at all. Both are now closed: `attemptOne` registers every surviving address ONCE and issues a
SINGLE `storage.get` (`MailboxPoller.attemptOne`), after filtering out wildcard/multicast addresses
via `MultiaddrHygiene.isBlockedPrivateOrLocal`; and `pollOnce` enforces a wall-clock budget per pass
(`POLL_PASS_WALL_CLOCK_BUDGET`, 20s) and a per-sender fetch-attempt cap per pass
(`MAX_FETCH_ATTEMPTS_PER_SENDER_PER_PASS`, 4), so one flooding sender identity can no longer consume
an entire pass and starve every other sender's genuinely fetchable pointers behind it — the flooded
sender's excess pointers simply carry over to the next pass rather than being lost or blocking others.
**`MultiaddrHygiene` deliberately does NOT block loopback/RFC1918/link-local addresses**, unlike a
textbook SSRF blocklist — see that object's own doc comment: this project's own documented networking
model ("no NAT traversal... same-LAN, or otherwise directly reachable," `DmSessionManager`'s own class
doc comment) makes those ranges the PRIMARY, expected peer address space, not an anomaly, and
`DmSessionManager.send`/`DmProtocol.dial` already dial the same attacker-forgeable
`PeerDirectoryGossip`-resolved addresses with zero filtering — blocking them here would disable
`MailboxPoller` entirely under this project's only currently-supported deployment shape, a strictly
worse regression than the finding being closed.

**Fix round (security audit round 2, one major finding — head-of-line blocking across MULTIPLE
sender identities):** the round 1 per-sender cap above turned out NOT to be sufficient on its own.
`pending()` returns a STABLY-ORDERED list, and `pollOnce` iterated it from index 0 on every pass — a
small number of DISTINCT claimed sender identities (no coordination required; a handful of
legitimately-offline senders is enough, no attacker needed) whose pointers sort near the front and
whose blobs are directory-resolvable but genuinely unfetchable (a full 10s `NabuStorage` Bitswap
timeout each) could PERMANENTLY occupy the head of every pass's `POLL_PASS_WALL_CLOCK_BUDGET` —
every pointer behind them, including a genuinely fetchable one from an entirely unrelated sender, was
never even attempted, on ANY pass, for as long as those pointers stayed pending. Proven with an
executable probe: three blockless-but-reachable pointers plus one genuinely fetchable pointer
published last produced, on three consecutive passes, zero received messages and the fetchable
message never attempted at all. Fixed by round-robining `pollOnce`'s pass start position
(`MailboxPoller.passStartOffset`, advanced every pass to wherever that pass stopped) instead of
always starting at index 0 — no pending pointer can occupy the head of the budget indefinitely, since
the position that was "the head" this pass is guaranteed not to be "the head" again next pass.

=== `MailboxRedeliveryScheduler` — the sender-side periodic re-announcer

This wave's genuinely novel mechanism — no prior sub-wave has an equivalent, because no prior wave
needed a recipient who might not even be RUNNING yet to eventually discover a message. In-memory-
only, process-local, best-effort tracking (`MAX_PENDING_OUTBOUND_MAILBOX_SENDS`, 4,096, LRU-
evicting, mirroring `DmSessionManager.MAX_LIVE_SESSIONS`'s framing) — lost on restart, the same
accepted scope cut every other in-memory index in this codebase already carries; a sender that
restarts mid-TTL-window simply stops re-announcing pointers sent before the restart (the already-
published pointer and durable blob remain valid if a recipient happened to see an earlier publish,
but no further re-announcement occurs for that specific pointer).

`DmSessionManager.sendOffline` calls `track()` immediately BEFORE the FIRST live publish (security
audit round 2 minor finding — see `sendOffline`'s own section below for why) — this scheduler never
performs that first announce itself, only the periodic re-announcements after it.

**Fix round (security audit round 1 minor finding):** `redeliverDue` previously called
`pubsub.publish` INSIDE its `@Synchronized` critical section with no per-entry `try`/`catch` — a
single publish that threw aborted the rest of that tick's pass at the same position on every
SUBSEQUENT tick too (iteration order is stable), permanently starving every pointer ordered after
the failing one of re-announcement; holding the monitor for the whole loop (up to
`MAX_PENDING_OUTBOUND_MAILBOX_SENDS` publishes, each up to a 10s timeout) also blocked `track`, which
`sendOffline` calls while already holding a per-peer stripe lock. Fixed by snapshotting due entries
under the lock, then publishing outside it with each publish independently `try`/`caught` (log and
continue on failure).

=== `DmSessionManager.sendOffline` — the two-object persist-then-publish ordering

Mirrors `send`'s crypto path exactly (same `X3dh.initiate`-on-first-contact /
`DoubleRatchetSession.encrypt` reuse), via a shared private `bootstrapSenderSession` helper both
`send` and `sendOffline` call — the two call sites are byte-identical for first contact BY
CONSTRUCTION (one shared implementation), not merely by convention (a hazard `send`'s own former
inline first-contact block, before this wave's refactor, would have risked reintroducing had
`sendOffline` reimplemented it independently).

Ordering, extending "persist then publish, publish strictly last" to a TWO-object case: session
state persisted first (before ANY Nabu write, mirroring `send`'s own "persist session before
anything externally observable" rule) → `NabuStorage.put(envelopeBytes)` (the blob) → sign a
`MailboxPointer` referencing that blob's CID → `NabuStorage.put(pointerBytes)` (the pointer's own
durable record) → `MailboxRedeliveryScheduler.track` → `GossipPubSub.publish` (the pointer, LAST).
A fast-arriving pointer — received by a peer that happens to be online and subscribed at the exact
moment of the FIRST publish — can never reference a not-yet-fetchable blob, because the blob was
already durably stored before the pointer that references it was even signed.

**Fix round (security audit round 2 minor finding — `track` moved BEFORE `publish`):** previously
`GossipPubSub.publish` ran before `track()`. `GossipPubSub.publish` swallows
`NoPeersForOutboundMessageException` but rethrows every other `GossipPubSubException` (including its
own `awaitOrWrap` publish timeout) — by that point in the method, `persistSession`/`putCached` had
already committed, so a propagating publish failure left a perfectly valid, durably-stored pointer
with NO re-announcement registered at all: `MailboxRedeliveryScheduler`'s periodic re-announcement is
the ONLY way an offline recipient ever learns a pointer exists, so skipping `track` turned a
transient publish timeout into permanent non-delivery — worse for a FIRST-CONTACT `sendOffline`,
since a caller retry would find a session already persisted and emit `TEXT` instead of
`X3DH_INITIAL`, which the recipient could never bootstrap. `track` is a cheap, no-I/O map write, so
calling it first costs nothing: a subsequent `publish` failure now just means this call's own
immediate announce didn't land, while `mailboxRedeliveryScheduler`'s next periodic tick still
announces the pointer and self-heals, exactly like every other transient publish failure it already
guards against.

=== The security-property trace: does an offline-fetch decrypt failure corrupt the ratchet?

Required by this wave's own plan to be TRACED, not assumed — traced directly against
`DoubleRatchetSession.decrypt`'s real source (unchanged by this wave):

* **`RatchetMessageRejectedException` path** (decided from public header data alone, STEP 1) is
  thrown BEFORE the `try` block holding every derived scratch value even begins — no session field
  is ever touched. Trivially no corruption: nothing runs.
* **`DoubleRatchetException` path** (AEAD tag failure) — every derived value (new root key, new
  chain keys, new ratchet keypair, skipped-key entries) is written into local `scratch*` variables
  first, NEVER into the session's live `rootKey`/`sendingChainKey`/`receivingChainKey`/
  `ourRatchetKeyPair`/`theirRatchetPublicKey`/`ns`/`nr`/`pn` fields. The COMMIT block that performs
  those live-field reassignments runs only AFTER `decryptWithMessageKeyMaterial` has already
  succeeded, with `committed = true` set immediately before it. An AEAD failure therefore always
  happens strictly BEFORE commit; the surrounding `catch` re-throws immediately, and the `finally`
  block zeroes only the never-installed scratch material — the session's live state is byte-for-byte
  what it was before the call.

**This property is a function of the method itself, not of the caller.**
`handleOfflineEnvelope` → `processInboundDmEnvelope` calls the EXACT SAME `session.decrypt(...)`
line the online path already calls, on the EXACT SAME session object (via the shared
`liveSessionCache`/`getCachedOrLoad`). No new code was needed to preserve this guarantee for the
offline path — it transfers automatically, and `MailboxAbuseTest` cases (d1)/(d2)/(d3) are the
executable proof: a tampered TEXT blob (existing session, ciphertext-only tamper, same-chain
branch), a tampered `X3DH_INITIAL` blob (first contact, freshly-bootstrapped-and-discarded session),
and — security audit round 2 minor finding, added because neither (d1) nor (d2) actually drove the
DH-ratchet-step COMMIT path against a LIVE cached session, the shape an attacker forging a
`ratchetPublicKey` actually uses — a forged-but-structurally-valid `ratchetPublicKey` on a TEXT blob
against an EXISTING session are all three discarded cleanly, and a SUBSEQUENT genuinely-valid
message between the same two identities still decrypts correctly afterward in every case.

The two existing catch blocks around `session.decrypt(...)` in `processInboundDmEnvelope`
(`DoubleRatchetException`/`RatchetMessageRejectedException`, both doing `if (isFreshHandshake)
session.destroy(); return@withPeerLock`) already handle both shapes: an EXISTING session with a
tampered TEXT message is simply left untouched (not re-persisted — the on-disk file remains
whatever it was after the last successful decrypt); a freshly-bootstrapped-but-never-installed
`X3DH_INITIAL` session with a tampered header/ciphertext is explicitly `destroy()`ed and discarded —
no pre-existing session for that peer is affected, since a fresh `X3DH_INITIAL` always constructs a
wholly separate `DoubleRatchetSession` object that never mutates a cached one before decrypt
succeeds.

=== Cross-path dedup: `recentlyDeliveredDedupKeys` is belt-and-braces, not the load-bearing guarantee — for `TEXT`

Because both delivery paths route through the exact same `session.decrypt()` call on the exact same
session object, a literal replay of an ALREADY-decrypted `TEXT` ratchet message is already rejected
by the ratchet's own `RatchetMessageRejectedException("message number ... already been consumed")`
check — INDEPENDENT of any dedup cache. `processInboundDmEnvelope`'s new `recentlyDeliveredDedupKeys`
pre-check (a bounded, LRU-evicting, GLOBAL cache keyed by `DmDedupKey.of(claimedSender,
ratchetMessage)`, checked BEFORE session resolution even begins) is a genuine, explicit "use" of
`DmDedupKey` as this wave's plan demanded — an efficiency win (it skips a wasted AEAD attempt, and
for a replayed `X3DH_INITIAL`, skips a wasted one-time-prekey-consumption attempt) — but for `TEXT`
it is NOT the sole thing standing between a replay and double delivery. The ratchet's own commit-
only-after-AEAD-verifies state machine is the load-bearing, structural guarantee for `TEXT`;
`MailboxAbuseTest` case (c) (an already-fetched-and-acked pointer, replayed) and case (e) (the same
message delivered once online and once via a stale offline pointer) both confirm exactly one
delivery reaches `DmInboundMessage`/the application layer, without needing to isolate which of the
two layers (pre-check cache vs. ratchet state machine) is what caught any specific replay — either
is sufficient, and both are present.

**Correction (security audit round 1 major finding, PROVEN with an executable probe, not merely
argued): the "regardless of which path" framing above does NOT extend to `X3DH_INITIAL`, and this
document previously overclaimed that it did.** `X3DH_INITIAL` resolves NO existing session at all —
it always builds a brand-new `DoubleRatchetSession` first (`nr = 0`), so the ratchet's own commit-
only-after-AEAD-verifies discipline cannot reject a replay of it the way it rejects a `TEXT` replay:
there is no PRIOR session state for it to conflict with. When `header.oneTimePrekeyId == null` (a
bundle-exhaustion degradation `X3dh.initiate` itself documents, and which
`DmSessionManager.MAX_CONCURRENT_PREKEY_CONSUMPTIONS`'s own follow-up-hardening-item-3 note already
flags as the one wire shape a genuinely legitimate initiator can also produce), `PrekeyStore`'s own
durable one-time-prekey consumption tracking never runs either — nothing durable stood between a
replayed `X3DH_INITIAL` and a resurrected message plus a rewound persisted session, other than
`recentlyDeliveredDedupKeys` itself, which is in-memory-only and empty after exactly the event
(`DmSessionManager` restart) that makes this exploitable. The probe: deliver `X3DH_INITIAL` +
`TEXT` through `handleOfflineEnvelope`, stop the `DmSessionManager`, rebuild a second instance over
the SAME identity/session directory/prekey store, replay the identical `X3DH_INITIAL` bytes —
result: delivered a second time, plaintext matched the original.

**Fixed by a DURABLE, per-peer registry of already-accepted `X3DH_INITIAL` ephemeral public keys**
(`DmSessionManager.recordAcceptedX3dhInitialEphemeralKey`/`loadAcceptedX3dhInitialEphemeralKeys`),
persisted alongside the session file (a sibling `.x3dhinit` file, not folded into the session file
itself) and checked BEFORE ever bootstrapping a session for an inbound `X3DH_INITIAL`. `X3dh.initiate`
mints a FRESH ephemeral X25519 keypair on every call, so this closes only a literal byte-for-byte
replay — a genuinely repeated, legitimate handshake from a peer who lost local state (the residual
"no session registry" gap this wave already accepted and does not close further) always carries a
DIFFERENT ephemeral key and is never blocked by this registry.

=== Explicit, deliberate scope cuts for this wave

* **No onion routing for mailbox pointers.** The original DM concept note's own open question — left
  open here, not resolved.
* **No DHT mailbox record** — the same broken-Kademlia limitation as every other V0.8/V0.9 wave;
  gossip plus explicit peer-hint-based Bitswap fetch instead.
* **No pin-lifetime management.** Nabu has no pin/GC anywhere in this project (V0.1.4's own
  documented state, see the Storage section above) — "pinning" a mailbox blob is currently a no-op;
  stated plainly, not implying a pinning economy exists.
* **No re-delivery guarantee beyond the TTL window.** Once a pointer expires or is evicted from
  `MailboxPointerIndex`, that message is genuinely gone if the recipient never came online in time —
  an accepted, bounded-storage tradeoff.
* **`MailboxRedeliveryScheduler`'s tracking is in-memory-only, lost on restart** — see that class's
  own section above.
