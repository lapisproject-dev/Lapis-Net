== Running a node with the V0.9.x features

[source,bash]
----
# headless node behind a NAT: reserves relays, uses the DHT directory (no DM, no mail)
lapisnet node --reachability=private
# headless node that also serves as an onion relay (infrastructure only, nothing is anonymised)
lapisnet node --onion-relay=true
# EXPERIMENTAL (unreleased, wave V0.10.0-E): publish the directory entry only through onion circuits
lapisnet node --anonymity=on
# browser node: same switches as arguments, LAPISNET_* variables or $LAPISNET_HOME/browser.properties
lapisnet-browser --reachability=private --dm-veritas-gate=true
# mail gates (since v0.12.0, V0.9.17): off by default; mail from a sender who passes none of them is discarded
lapisnet-browser --mail-veritas-gate=true --mail-karma-min-score=2
----

Mail acceptance is wired in the browser node (since `v0.12.0`). Keys: `--mail-veritas-gate` (`LAPISNET_MAIL_VERITAS_GATE`, file key `mailAcceptance.veritasGate`), `--mail-karma-min-score` (`LAPISNET_MAIL_KARMA_MIN_SCORE`, `mailAcceptance.karmaMinScore`), `--mail-min-deposit-msat` (`LAPISNET_MAIL_MIN_DEPOSIT_MSAT`, `mailAcceptance.minDepositMsat`, no effect yet). All gates are off by default. Accepted contacts are always let through; blocked mail is discarded without reply and only counted in the status panel.

`--anonymity=on|off` (default `off`, `LAPISNET_ANONYMITY`, browser file key `anonymity`) is *experimental and incomplete*: with `on` the node publishes its directory entry only through onion circuits (persistent guards, diverse three-hop paths, a build rate limit) and switches hole punching off. With the browser node (unreleased wave V0.10.0-F1) direct messages are also carried through circuits, online and offline: only a recipient who is in anonymity mode as well can be reached, the answer to every other recipient is the same `recipient-not-reachable-anonymously` refusal (there is no fallback to a direct connection), attachments are not available, and a message is limited to about 5.4 KB; the recipient learns who the sender is. From unreleased wave V0.10.0-F2 *mail* is carried through circuits as well, with the same rule for recipients and the same absence of a fallback: a mail with attachments may be at most 1 MiB in total (at most 16 attachments) and is delivered only while you and the recipient are online at the same time (the node retries for 48 hours; the queue is lost on restart), a small mail without attachments (frame up to about 5.6 KB) is also delivered while the recipient is offline, and anything larger is refused with `mail-too-large-anonymous` (HTTP 413) before anything is sent. In this mode the node subscribes to no per-recipient inbox topic, leaves no DHT pointer for mail and never fetches an attachment from another node (an attachment that is not stored locally answers `attachments-unavailable-anonymous`). The headless CLI node has no direct messages, so for it nothing changes. From unreleased wave V0.10.0-G the *signals* of a call are carried through circuits as well (online only, through the same ratchet session, no reply route), but the *media* of a call can not be anonymised: it connects directly. Calls are therefore *off* in anonymity mode by default (the browser answers `409` with `CALL_MEDIA_DISABLED_IN_ANONYMITY_MODE`, and an incoming call from anyone is dropped without any reply). `--anonymity-allow-call-media=true|false` (default `false`, `LAPISNET_ANONYMITY_ALLOW_CALL_MEDIA`, browser file key `anonymityAllowCallMedia`, only valid together with `--anonymity=on`, restart required) allows calls: before every call you place or accept, the call page asks for a confirmation, and the call then reveals your IP address to the other party and to network observers (without the confirmation the browser answers `409` with `MEDIA_EXPOSURE_CONFIRMATION_REQUIRED`). With the option only public host candidates are offered; if neither side has a public address the call fails. Both ends must be in anonymity mode. It does *not* anonymise call media, and the node's IP address stays visible to every peer that connects to it; the start line, the CLI's stderr and the browser's status panel say so every time. The usual precedence applies (command line over environment over file over default); only the exact words `on` and `off` are accepted. The start is refused with `--hole-punching=auto` or `--hole-punching=on` (a missing hole-punching option resolves to `off`) and with `--onion-relay=true`. In the browser the connect QR code and connect info are disabled while the mode is on. With too few relays that are in different networks (for example on a loopback test network) the node reports `insufficient-relays` and publishes nothing; there is no fallback to publishing from the node itself. The refusal codes of the browser are `recipient-not-reachable-anonymously`, `anonymity-not-ready`, `rate-limited` (reserved), `message-too-large-anonymous` (HTTP 413) and `attachments-unavailable-anonymous` (HTTP 409); the call page adds `CALL_MEDIA_DISABLED_IN_ANONYMITY_MODE` and `MEDIA_EXPOSURE_CONFIRMATION_REQUIRED` (both HTTP 409); in the normal mode a failed send is answered with the fixed `dm-send-failed`. Details and limits: `docs/anonymity.adoc`, sections "Path selection and policy", "Direct messages over circuits", "Mail over circuits" and "Call signals over circuits".

An invalid option aborts the start. See `docs/release-notes/v0.11.0.adoc` and `docs/release-notes/v0.12.0.adoc` for all options, defaults and the metadata warning about the DHT fallback.

== Building and running from source

[source,bash]
----
./gradlew clean check   # compiles, runs tests, runs ktlint
./gradlew :lapis-net-cli:run
----

Requires JDK 25.

To run the reference node together with its minimal browser UI (main view, mail inbox, direct
messages):

[source,bash]
----
./gradlew :lapis-net-browser:run
----

It prints the local address to open in a browser and the identity fingerprint. For calls it also prints a link of the form `http://127.0.0.1:7878/call.html#t=<token>` (same device only: the token is regenerated on every start and must not be shared or logged; open the link from the console, a bare `/call.html` is refused). The HTTP port is
currently fixed at `7878` (there is no environment variable for it yet), so only one browser node can
run per machine; a second instance on the same machine fails with "address already in use" and would
also share the same identity and storage directory unless `LAPISNET_HOME` is changed. State lives under
`$LAPISNET_HOME` (default `~/.lapisnet`). Environment variables: `LAPISNET_KEYSTORE_PASSPHRASE` encrypts
the identity at rest (without it, and without an interactive console, the identity is stored
unencrypted with POSIX file permissions only and a warning is logged); `LAPISNET_LISTEN_ADDR` sets the
libp2p listen address (the default is loopback-only, so no other machine can reach the node until this
is set); `LAPISNET_BOOTSTRAP_PEERS` is a comma-separated list of peer multiaddrs, each including
`/p2p/<peerId>`, and entries in `$LAPISNET_HOME/bootstrap.peers` (one per line) are added to it.

There is no public network yet, and connecting two real nodes is still a manual step. Set
`LAPISNET_LISTEN_ADDR` to the machine's concrete LAN address, for example `/ip4/192.168.1.20/tcp/4001`.
The main page shows a connect link (`lapisnet://connect?maddr=...&pk=...`) and the same link as a QR
code; on the other node, paste that link into the "Paste a connect link" field of its main page, or
enter the plain multiaddr, including `/p2p/<peerId>`, in the connect field in the page header. The
peer ID is also logged at startup (`BrowserServer listening on ... (peer <peerId>)`). A wildcard such
as `/ip4/0.0.0.0/tcp/4001` makes the node listen on every interface, but the QR code and connect link
would then carry the wildcard, which another machine cannot dial; in that case type
`/ip4/<LAN-IP>/tcp/4001/p2p/<peerId>` into the header connect field by hand, taking the peer ID from
the log. Peers discovered through mDNS are only logged and
cached, never dialled automatically and not shown in the UI. If you only have one machine,
`./gradlew :lapis-net-cli:run` runs a multi-node trust-propagation demo inside a single process.
