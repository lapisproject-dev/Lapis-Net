= Lapis Net Roadmap

== V0.1 — Protocol core + Veritas

Target: first runnable prototype — network bootstrap plus Veritas (the first
of the four scoring dimensions), including GossipSub propagation of trust
edges between local nodes.

[cols="1,3"]
|===
| Wave | Content

| V0.1.1
| Gradle multi-module skeleton + CI/CD skeleton.

| V0.1.2
| Identity layer: secp256k1 keypair generation/persistence, dual-key binding to Ed25519 for the libp2p peer ID.

| V0.1.3
| P2P node bootstrap: jvm-libp2p setup, bootstrap peers, local mDNS discovery.

| V0.1.4
| Nabu integration: DHT + Bitswap for content storage (Veritas records as signed files).

| V0.1.5
| Veritas core: trust-edge data model, signing, Git-like versioning (backward hash to the previous grant).

| V0.1.6
| Veritas path algorithm: shortest paths, lexicographic ordering by next hop, product of edge weights.

| V0.1.7
| GossipSub propagation: distribute Veritas records over a dedicated topic and persist them in Nabu.

| V0.1.8
| Minimal CLI / test harness: demo with N local nodes, trust-edge issuance and propagation made visible.
|===

== V0.2 — Virtus + Minimal-Browser

Target: the second of four scoring dimensions — Virtus (the LTR/on-chain
economy) — plus a Minimal-Browser that makes Veritas and Virtus data
actually visible. The browser is deliberately placed here rather than as a
standalone later wave, so a real pilot test (PdV, Girchi) is possible as
soon as V0.2 lands, instead of only after every scoring dimension exists.

[cols="1,3"]
|===
| Wave | Content

| V0.2.1

+ Nabu persistence (mirroring the Veritas V0.1.5/V0.1.7 pattern), 10%/24h
decay math, accumulation (independent records per (cid, view) pair, never
merged). Structural-only `OnChainProof` — no live Bitcoin chain
verification yet (known, documented limitation).

| V0.2.2
| Minimal-Browser (MVP): a local, loopback-only Ktor HTTP server embedding
a real node, serving a framework-free HTML/JS timeline UI. Shows Veritas
credibility + Virtus/LTR-weighted sorting; a small, deliberately temporary
`PostAnnouncement` primitive fills the content-discovery gap Karma (V0.3)
will eventually close properly.

== V0.3 — Karma

Target: the third of four scoring dimensions — Karma, a cheap one-click
"like" with Bitcoin-chain-anchored, Veritas-weighted Sybil resistance —
wired into the Minimal-Browser as a persistently-visible Like button.

[cols="1,3"]
|===
| Wave | Content

| V0.3
| `lapis-net-karma`: `KarmaVote` data model (`Karma = t/(n+1)`, `t` =
blocks since the voter's own first outgoing Bitcoin transaction, `n` =
the voter's own prior eligible-vote count, always locally derived, never
self-declared); GossipSub propagation with zero live chain-verification
in the validation path (mirroring `OnChainProof`'s V0.2.1 precedent); a
client-side, trusting (not trustless-SPV) Electrum chain-data source used
only at local vote-cast time. Wired into `lapis-net-browser`: a new
`POST /api/karma` route and a Like button, with Karma kept purely
additive/display-only in `TimelineBuilder` (never affecting sort or
filtering).
|===

=== Progress

V0.3 is implemented (see `docs/architecture.adoc`'s "Karma: Bitcoin-

Target: move from test fixtures toward real users. Bundles four related

[cols="1,3"]

| Wave | Content

== V0.5 — Madli

Target: the fourth and final scoring dimension — Madli, a machine-to-machine
node-reputation system rating nodes as infrastructure (Bitswap/DHT serving
quality), never content or people, with Veritas-weighted, decay-weighted,
weighted-median aggregation resistant to Sybil clusters and selective
service.

[cols="1,3"]
|===
| Wave | Content

| V0.5
| `lapis-net-madli`: `MadliDailyVector` data model (five fixed-point
metrics — Reachability, Bandwidth, Latency, Delivery-Integrity,
Routing-Helpfulness — signed per `(observer, observedPeer, epochDay)`,
no `nonce`, latest-wins per tuple); `MadliVectorIndex` with two
anti-flooding/anti-backdating invariants (one tracked vector per exact
tuple; a capped number of distinct days per `(observer, observedPeer)`
pair); GossipSub propagation with zero clock/network calls in the
validation path (mirroring `KarmaGossip`/`LtrGossip`'s precedent);
`MadliDecayCalculator`'s five independently-configurable half-lives;
`MadliAggregator`'s Veritas-weighted weighted-median aggregation (a
deliberate, documented exception to the Karma/Virtus "no sibling trust
dependency" rule, since Madli has no application-layer consumer this
wave); `MadliRoutingPolicy`/`MadliReplicationPolicy` — pure,
unit-tested Bitswap-modulation hooks, structurally ready but not wired
into a live fetch this wave (honest scope cut, mirroring V0.1.4's own
provider-discovery limitation); and `MadliSybilResistanceSimulationTest`
— the mandatory adversarial harness resolving the vault note's one
explicitly-unresolved item, proving the Veritas-weighting and
weighted-median defenses hold against a real `TrustGraph`/
`TrustPathFinder`, and explicitly documenting the one accepted residual
(a trusted majority that lies still wins the median).
|===

== V0.6 — Lightning proof

Target: close V0.2.1's "Zwei Zahlungswege" gap on the Lightning side — a second, fully
cryptographically verified `LtrProof` implementation alongside `OnChainProof`, wired into the
gossip hot path, plus the first LTR record-authoring HTTP endpoint.

[cols="1,3"]
|===
| Wave | Content

| V0.6
| `lapis-net-virtus`: `LightningProof` data model (`preimage`, `paymentHash`, `signedInvoice` —
structural shape only, mirroring `OnChainProof`'s constructor discipline) and
`LightningProofVerifier`, the sole consumer of `lightning-kmp` in this module, performing the full
verification chain — `sha256(preimage) == paymentHash`, real BOLT-11 parsing + signature
verification via `Bolt11Invoice.read`, mandatory amount binding (`invoice.amount ==
record.initialValueMsat`), mandatory recipient binding (`invoice.nodeId == record.viewId` — a
Lightning node key IS its Lapis viewId, by protocol commitment), and mandatory content binding
(`invoice.description == canonicalMemo(cid, viewId)`, the anti-replay check) — deliberately never
checking invoice expiry. `LtrRecordCodec`'s `proofType = 2` (previously reserved, rejected outright)
is now implemented, with a DoS-guarded, length-validated-before-allocation invoice field.
`LtrGossip.onGossipMessage` calls `LightningProofVerifier.verify` directly in the gossip hot path —
a deliberate divergence from `OnChainProof`'s (and Karma/Madli's) "never call a network service
inside the validator" precedent, safe here because Lightning-proof verification is pure, bounded,
and local, with zero liveness dependency on anything outside the message bytes. `lapis-net-browser`:
`POST /api/ltr/lightning`, the first LTR record-authoring endpoint, accepting an
externally-obtained `(preimage, signedInvoice)` pair (the author paid a real invoice with their own
wallet out-of-band) and verifying it with the same crypto chain before announcing.
|===

=== Progress

V0.6 is implemented (see `docs/architecture.adoc`'s "Lightning proof (V0.6)" section). **The V0.6
milestone is complete**, with one honestly-scoped, deliberate gap carried forward as explicit future
work:

* **No embedded Lightning node.** Nothing in this codebase runs a real `lightning-kmp` node, holds a
  channel, or has access to real funds — `LightningProofVerifier` only ever verifies proofs already
  handed to it, never constructs or sends a payment.
* **No BOLT-12 Offer/DHT publication, no `invoice_request`/auto-respond flow.** V0.6 only covers the
  BOLT-11 "pay first, submit proof after" path from the Virtus spec note's "Zwei Zahlungswege"
  section; the fuller "A. Lightning via BOLT-12 Offer" vision (a view publishing a standing offer
  other nodes can pay against without out-of-band coordination) remains future work.
* **No live payment settlement testing.** Every test substitutes a preimage/invoice generated
  in-process with real `lightning-kmp` calls (fully real cryptography) — only the network settlement
  event itself (an actual Lightning payment over a real channel) is out of reach in this
  sandbox/CI, mirroring `ElectrumTimeAnchorSourceTest`'s and Madli's Bitswap-modulation precedent
  for external payment/network infrastructure. Real embedded-node send/receive testing is future
  work, likely alongside whichever wave eventually builds the embedded node itself.

=== V0.8.1 — Peer/presence directory records

Target: a signed, gossiped record binding an identity to its current network addresses and
transport-layer (libp2p) peer identity, with a monotonic per-identity sequence number and a
heartbeat TTL — the foundational discovery layer V0.8.2 (X3DH prekey bundles) and V0.8.4 (online DM
addressing) build on. New module `lapis-net-directory`.

[cols="1,3"]
|===
| Wave | Content

| V0.8.1
| `PeerRecord` — identity (secp256k1), a reused (not reinvented) `IdentityBinding` proof of the
libp2p transport key, a capped `Multiaddr` list, a `PeerCapability` bitmask (`DM`/`CALL`/`MAILBOX` —
deliberately no `SFU_CAPABLE`, no consumer in the reduced arc), a monotonic sequence number, a
`notValidAfterEpochSecond` heartbeat TTL, its own outer signature, AND (added in this sub-wave's
round-2 security-audit fix) `possessionProof` — a NEW Ed25519 counter-signature by the transport
key's OWN private key over the identity's bytes, making the identity<->transport-key binding
genuinely MUTUAL. THREE independently-verified signatures per record, not two, see
`docs/architecture.adoc`'s equivalent section for why `IdentityBinding` alone (a ONE-WAY vouch) left
a cross-binding/peerId-spoofing gap open. `PeerRecordCodec` — length-prefixed binary layout
mirroring `VeritasGrantCodec`/`MessageEnvelopeCodec`'s discipline exactly; carries no
`io.ipfs.cid.Cid` field at all, so `CidBytesValidation` is never invoked by this module.
`PeerRecordIndex` — latest-wins per identity by sequence number (a genuinely new ordering rule for
this codebase, not copied from any sibling index — see that class's doc comment), the established
two-cap eviction/persistence structure plus a THIRD, independently-sized, LRU-evicting anti-rollback
high-water-mark cap (`highestSequenceByIdentity`, hardened in round 2 after round 1's non-evicting
version reopened an equivalent rollback path). `PeerDirectoryGossip` — a new GossipSub topic
(`LapisNet:peer-record-gossip:v1`), gossip-only (no DHT publication — `Kademlia.dialPeer` documented
broken since V0.1.4, same accepted limitation as every V0.9 mail sub-wave). `PeerPresenceAnnouncer`
— the enforced minimum-republish-interval (300s default) PARTIALLY mitigating this record type's
metadata-exposure tension with the spec's own Metadaten-Minimierung principle (bounds only this
node's own outbound republish rate — `PeerDirectoryGossip.announce` is unrate-limited and
`onGossipMessage` applies no inbound rate limit, see `docs/architecture.adoc`) — deliberately a
caller-side wrapper, not built into `PeerDirectoryGossip.announce()` itself, and hardened in round 2
so a backward wall-clock jump cannot stall the heartbeat indefinitely.

Test suite: `PeerRecordTest`, `PeerRecordCodecTest` (round-trip, truncation, reserved-bits,
length-validated-before-allocation, malformed multiaddr bytes, sequence-number edge values, a
garbage non-curve-point ed25519 public key), `PeerRecordIndexTest` (latest-wins by sequence,
rollback rejection surviving tracking-cap eviction via a separate high-water mark, deterministic
tie-break, eviction, persistence-cap decoupling, and a round-2 regression proving a victim arriving
AFTER the high-water-mark cap first fills by a flood still gets rollback protection),
`PeerDirectoryGossipOnGossipMessageTest`, `TwoNodePeerDirectoryGossipIntegrationTest` (real two-node
loopback, address/peerId round-trip against the announcing node's own real
`LapisNode.listenAddresses()`/`peerId`), `PeerPresenceAnnouncerTest` (minimum-republish-interval
enforcement, boundary-inclusive timing, and a round-2 clock-rewind regression), and the mandatory
adversarial `PeerRecordSpoofingTest` — its central cases: (a) a record whose embedded
`IdentityBinding` OBJECT is reused verbatim from a victim does not actually verify against the
record's own signing identity (rejected by `verifyBinding`); (h) (round-2 regression) a record
embedding a FRESHLY RE-SIGNED `IdentityBinding` over the victim's public Ed25519 key passes BOTH
`verify` and `verifyBinding` genuinely and is only caught by the new `verifyPossession` — proving
this codebase's FIRST case where a signature-valid, binding-valid record must still be rejected on a
THIRD, independent cryptographic check.
|===

==== Progress

V0.8.1 is implemented (see `docs/architecture.adoc`'s "Peer/presence directory records (V0.8.1)"
section), including its round-2 security-audit hardening (mutual possession-proof binding,
LRU-evicting anti-rollback high-water mark, clock-rewind-safe presence announcer). Deliberate scope
cuts, stated as such in the code's own doc comments rather than silently omitted:

* **No DHT publication.** Gossip-only, same accepted limitation as every V0.9 mail sub-wave.
* **No `SFU_CAPABLE` capability flag.** MLS/conferencing/SFU cut from the V0.8 arc entirely on
  2026-08-04 — no consumer exists.
* **No bandwidth-class measurement.**
* **No reachability verification of advertised addresses** — mirrors V0.4's own, still-open gap: an
  attacker or a stale node can advertise unreachable addresses and nothing currently detects this.
* **A network-wide gossip topic is itself a metadata-exposure decision** — every subscriber learns
  every published identity's current addresses and online-status heartbeat. Accepted (2026-08-04):
  no worse than V0.4's own `lapisnet://connect` QR/deep-link multiaddr exposure, and
  `PeerPresenceAnnouncer`'s enforced minimum-republish-interval keeps this from being a fine-grained
  real-time presence oracle.
* **No opt-in Veritas-distance admission filter**, unlike `lapis-net-mail`'s V0.9.4 addition —
  `lapis-net-directory` takes no dependency on `lapis-net-trust` this wave; acceptance is purely
  structural (signature + identity-binding + sequence-number ordering). A future wave MAY add one,
  mirroring `MailAcceptancePolicy`.

=== V0.8.2 — X25519 encryption sub-key + X3DH handshake

Target: an X25519 encryption sub-key bound to each identity's secp256k1 key, and X3DH (Signal's
Extended Triple Diffie-Hellman), reimplemented from the public specification — not adapted from
libsignal, which is AGPL-3.0-licensed and therefore incompatible with this Apache-2.0 project. The
highest-risk primitive in this codebase to date: every prior wave reused already-established
primitives (AES-256-GCM, HKDF-SHA256, secp256k1 ECDH/ECDSA, Ed25519) in new combinations; X3DH
itself has no precedent anywhere in this codebase. New module `lapis-net-ratchet`.

[cols="1,3"]
|===
| Wave | Content

| V0.8.2
| `X25519Keys.kt` (`lapis-net-identity`) — `X25519PrivateKey`/`X25519PublicKey`/`X25519KeyPair`,
mirroring `Ed25519Keys.kt`'s defensive-copy/redaction discipline. `X25519PublicKey`'s constructor
rejects all twelve published low-order/non-canonical Curve25519 u-coordinates (seven canonical
small-order points AND five non-canonical bit-255-set re-encodings that BouncyCastle's own
all-zero-agreement check does NOT catch — verified against the resolved `bcprov-jdk18on:1.85` jar)
— so a low-order key is rejected structurally, before any DH ever runs. `X25519Agreement.kt` —
`x25519SharedSecret`, confirmed to return the RAW shared u-coordinate (not hashed, unlike
`ecdhSharedSecret`'s secp256k1 output), with a redundant explicit all-zero check as defence in
depth. `EncryptionKeyBinding.kt` — a secp256k1-identity → X25519-encryption-sub-key vouch,
structurally identical to `IdentityBinding` (own domain tag
`"LapisNet:x25519-encryption-key:v1"`), deliberately with NO mutual counter-signature (an X25519 key
cannot sign) — the equivalent protection lives in X3DH's associated-data construction instead (see
below).

`lapis-net-ratchet` (new module, deliberately ZERO network/libp2p/Nabu dependencies — a security
reviewer of the handshake never has to reason about untrusted network input and crypto correctness
in the same file): `PrekeyBundle`/`PrekeyBundleCodec` — identity, X25519 identity key (a
read-through alias into its `EncryptionKeyBinding`, never a second stored copy), a signed prekey
(signed by the secp256k1 identity key over `identity ‖ x25519IdentityKey ‖ signedPrekey ‖
signedPrekeyId` — deliberately WIDER than the Signal spec's own `Sig(IK_B, Encode(SPK_B))`, since a
bare `Sig(SPK)` would be transplantable between bundles of the same identity), and a capped
(≤100) one-time-prekey list. THREE independently-verified signatures per bundle, mirroring
`PeerRecord`'s three-signature design. `PrekeyStore`/`PrekeyStoreFileFormat` — local storage of the
PRIVATE halves, reusing `KeystoreEncryption`/`FileIdentityRepository`'s Argon2id/AES-256-GCM/atomic-
write pattern verbatim; `consumeOneTimePrekey` durably tombstones a consumed one-time prekey
(persist-before-mutate-before-return ordering, `FileChannel.force(true)` before the atomic move) so
a restart can never resurrect an already-used prekey. `X3dh.kt` — `initiate`/`respond` implementing
the actual multi-DH handshake: `DH1 = X25519(IK_A, SPK_B)`, `DH2 = X25519(EK_A, IK_B)`, `DH3 =
X25519(EK_A, SPK_B)`, `DH4 = X25519(EK_A, OPK_B)` if a one-time prekey was used;
`SK = HKDF-SHA256-Expand(HKDF-SHA256-Extract(32-zero-byte salt, 32×0xFF ‖ DH1 ‖ DH2 ‖ DH3 [‖ DH4]),
"LapisNet:x3dh:v1:X25519:SHA-256" ‖ AD, 32)`, where `AD = "LNX3" ‖ 0x01 ‖ IK_A ‖ IK_B` (the
secp256k1 IDENTITY keys, initiator-first, never the X25519 sub-keys — see below for why).
`PrekeyBundleIndex`/`PrekeyBundleGossip` (`lapis-net-directory`, Part B — this module is deliberately
network-free) — a dedicated GossipSub topic (`LapisNet:prekey-bundle-gossip:v1`), reusing
`PeerRecordIndex`/`PeerDirectoryGossip`'s established two-cap-index + gossip-validator machinery.

==== The possession-proof question, and why X3DH's associated data is the answer

Unlike `PeerRecord.possessionProof` (V0.8.1's Ed25519 counter-signature fix for an analogous gap),
no possession-proof field was added to `PrekeyBundle`. An X25519 key cannot sign, so anyone can mint
a FRESH, self-consistent `EncryptionKeyBinding` over a victim's PUBLIC X25519 identity key/signed
prekey/one-time prekeys and publish it, genuinely self-signed, under their OWN secp256k1 identity —
all three of `PrekeyBundle.verify`/`verifyEncryptionBinding`/`verifySignedPrekey` then pass. This is
an "unknown key share" attack, not a direct key compromise: the attacker cannot compute the DH terms
that need the victim's private keys, so only the victim — never the attacker — can complete the
matching handshake. What stops this from becoming a genuine confidentiality break is X3DH's
associated data: it is built from the secp256k1 IDENTITY keys (`AD = "LNX3" ‖ v1 ‖ IK_initiator ‖
IK_responder`), never the X25519 sub-keys, and folded into BOTH the associated data AND the HKDF
`info` string — so the initiator (who believes the attacker is the responder) and the real key
holder (who knows himself to be the responder) derive genuinely DIFFERENT shared secrets, even
though every DH term they each compute matches. See `docs/architecture.adoc`'s V0.8.2 section for
the full analysis.

==== Progress

V0.8.2 is implemented (see `docs/architecture.adoc`'s "X25519 encryption sub-key and the X3DH
handshake (V0.8.2)" section). Deliberate scope cuts, stated as such in the code's own doc comments:

* **No PQXDH / post-quantum hybrid key exchange.** X25519 only.
* **No formal deniability analysis** beyond X3DH's own published security properties.
* **No DHT publication.** Gossip-only (`PrekeyBundleGossip`), same `Kademlia.dialPeer`-broken
  limitation as every prior wave.
* **No wire codec for the X3DH initial-message header.** This wave's deliverable is the handshake
  primitive and prekey publication/consumption machinery, callable and independently testable — not
  yet wired into a live message-send path. V0.8.4 (online DM) owns that wiring.
* **No replay protection for a repeated identical initial message naming NO one-time prekey — and
  V0.8.3's Double Ratchet session layer only PARTIALLY closes this gap (correction from this
  section's original text, see V0.8.3's own section below for the full analysis).** `X3dh` is a
  stateless pure function by design; a replay naming a one-time prekey IS refused, at the
  `PrekeyStore` layer (durable, one-shot consumption). `DoubleRatchetSession` (V0.8.3) closes only
  the PER-MESSAGE half of the remaining gap (delete-on-use of skipped keys, rejection of an
  already-consumed message number) — a replayed initial message naming NO one-time prekey still lets
  a responder derive the same `SK` twice and construct TWO INDEPENDENT sessions, invisible to each
  other's state machine. Closing THAT needs a durable session registry keyed by the initiator's
  ephemeral public key, which remains V0.8.4's to build.
* **One-time-prekey collisions are inherent to gossip publication** (unlike Signal's server, which
  hands each prekey to exactly one requester) — mitigated by uniform-random selection and a
  documented retry-without-one-time-prekey fallback.
* **No XEdDSA, no signed-prekey rotation scheduler.** `PrekeyStore.rotateSignedPrekey` is exposed as
  a directly callable primitive; nothing in this wave calls it periodically.
* **`CidBytesValidation` is not invoked anywhere in this wave** — no `io.ipfs.cid.Cid` field exists
  in any new wire format, mirroring V0.8.1's own equivalent note.

=== V0.8.3 — Double Ratchet 1:1 sessions

Target: the ongoing encrypted session an X3DH handshake's `X3dhSharedSecret`/`associatedData` output
bootstraps into — Signal's Double Ratchet, reimplemented from the public specification for the same
licensing reason V0.8.2 states (no libsignal, AGPL-3.0-incompatible). The second of this arc's two
highest-risk sub-waves (alongside V0.8.2): this wave carries real STATE — a live session persists
across many messages over potentially a long time, so a correctness failure here (a forward-secrecy
leak, a post-compromise-security gap, a state-persistence bug that resurrects old keys) is an
ongoing, silent compromise of an entire conversation, not a one-shot handshake bug. Extends
`lapis-net-ratchet` (same module, still deliberately network-free).

secrecy (proving superseded key material is actually zeroed and unreachable, with an explicit
statement of what a JVM-level test can and cannot prove), (b) post-compromise security (a full
session snapshot decrypts the NEXT message but not the one AFTER the following DH ratchet step), (c)
skipped-key DoS (an `Int.MAX_VALUE` claim rejected before any derivation, `derivedMessageKeyCount`
provably unchanged), (d) out-of-order delivery and clean post-eviction failure, (e) replay rejection
in every shape, (f) single-bit tamper in ciphertext/header/AAD each independently and uniformly
causing `DoubleRatchetException`, (g) cross-session confusion, (h) truncated/oversized frames.

==== The nonce question, and why the mail wave's derived-nonce argument does not transfer

`HybridEcies`'s (V0.9.2) wrap-key AEAD nonce is DERIVED, not transmitted — safe because the wrap key
is single-use by construction (a fresh `SecureRandom` ephemeral per call), and if that ephemeral
ever repeated, a transmitted random nonce would not have saved the scheme either, since the same
`SecureRandom` produced both. **That escape hatch does not hold for the Double Ratchet.** A message
key here is single-use by construction too, but the construction is a PERSISTED COUNTER (`Ns`/`Nr`
plus the chain key), not a fresh random draw — and a persisted counter CAN rewind, via a restored
backup, a crashed write that left a stale file in place, or a caller violating the
persist-before-send ordering below. Under a DERIVED nonce, a rewound counter re-deriving an
already-used message key would be a genuine AES-GCM `(key, nonce)` reuse — the catastrophic case.
This wave therefore transmits an EXPLICIT, uniformly random 12-byte nonce per message instead: under
the same rewind, that degrades to "two ciphertexts under one key with distinct nonces" (which GCM
tolerates with no confidentiality loss), leaving only a protocol-level duplicate the peer rejects as
a replay. The random nonce is safe under a broken/mocked `SecureRandom` too (every message's KEY
still differs, since it comes from the HMAC chain ladder, not the nonce RNG) — so it is safe under
BOTH failure modes a derived nonce is normally chosen to survive, where the derived nonce would only
have been safe under one. See `DoubleRatchetSession`'s own class doc comment for the full argument.

==== State is committed only after the AEAD tag verifies

The single most important design decision in `DoubleRatchetSession.decrypt`: every derivation it
performs — skipped message keys, a DH ratchet step's new root/chain keys, a fresh ratchet keypair —
is built into scratch locals first; only after the AEAD tag verifies are those installed, the
superseded live arrays zeroed, and the skipped-key store updated. Without this, the session would be
trivially destroyable by an unauthenticated attacker: a single garbage frame carrying a random (but
validly-encoded) ratchet public key would drive a DH ratchet step, discard the real receiving chain
key, and permanently desynchronise the session — a one-packet remote DoS.

==== Progress

V0.8.3 is implemented (see `docs/architecture.adoc`'s "The Double Ratchet (V0.8.3)" section).
Deliberate scope cuts, stated as such in the code's own doc comments rather than silently omitted:

* **No header encryption.** Message numbers and the current ratchet public key travel in the clear;
  only the payload is confidential — a real, published Signal-protocol-standard limitation carried
  forward knowingly, not an oversight.
* **No sealed sender.**
* **No post-quantum ratchet.** No PQXDH, no PQ KEM in the root chain — consistent with V0.8.2's own
  cut.
* **No secure-erase guarantee beyond best-effort `ByteArray.fill(0)`** — the same limitation V0.4/
  V0.8.2 already state; this wave adds nothing to it and claims nothing more.
* **Not wired into a live network message-send path.** `DoubleRatchetSession` is a standalone,
  independently testable state machine; gossip/libp2p plumbing is V0.8.4's.
* **No file I/O.** `DoubleRatchetSessionCodec` is a pure bytes<->object codec; the durable-write
  discipline (atomic temp-file + `force(true)` + `ATOMIC_MOVE` + sidecar lock) is the caller's, and
  `PrekeyStore` is the reference implementation to copy.
* **No session registry, and therefore the X3DH initial-message replay gap is only PARTIALLY
  closed** — see the corrected V0.8.2 Progress bullet above.
* **No multi-device / no session migration between devices.**
* **No automatic signed-prekey-driven session re-establishment**, no session expiry, no periodic
  re-keying scheduler.

=== V0.8.4 — Online DM stream

different kind of risk than V0.8.2/V0.8.3: the cryptography is already built, reviewed, and

==== The identity-authority rule

The load-bearing security property of this entire wave, and the reason it gets its own
subsection rather than a bullet point: **the libp2p `PeerId` a stream connection authenticates
(via Noise, at the TRANSPORT layer) is NOT the same thing as the secp256k1 identity the Double
Ratchet/X3DH layer authenticates.** `PeerId` is used in exactly one place in this module —
`DmProtocolHandler.onStartResponder`, as a resource-management key bounding how many concurrent
`/lapis/dm/1.1.0` streams one transport connection may open — and NEVER for message authorization
or sender attribution. A connection from a given `PeerId` claiming to relay messages "from" some
`senderIdentity` in a `DmEnvelope` is not trusted on that claim alone: the message only counts as
genuinely from that identity once `DoubleRatchetSession.decrypt` succeeds under a session that was
itself bootstrapped, via a real X3DH exchange, with that identity's own prekey bundle. `X3dh`'s own
associated-data construction (folded into both the AEAD-style AD and the HKDF `info` string, see
V0.8.2's section above) is what makes this sound: a message genuinely encrypted under a DIFFERENT
`(sender, us)` identity pair can never verify here, even if the wrapping envelope lies about who
sent it. `DmSessionManager.handleInboundEnvelope`'s own doc comment states this rule at the exact
point the untrusted claim is read, and `DmStreamAbuseTest` case (e) constructs the concrete
confusion scenario (a genuine ciphertext from session Y, wrapped in an envelope claiming
`senderIdentity = X`) and proves the ratchet's own authentication — never the claimed field alone —
is what is trusted.

==== The Argon2id-per-message-persist problem, resolved

`DoubleRatchetSession`'s own V0.8.3 doc comment flagged that calling
`DoubleRatchetSessionCodec.encode`/`decode` once per message — each re-running Argon2id at
`KeystoreEncryption.DEFAULT_MEMORY_KIB`/`DEFAULT_ITERATIONS` (64 MiB / 3 passes, order
10^2^–10^3^ ms) — is "not viable as a live network message-send path's per-message cost," and
proposed the fix: "cache the Argon2id-derived key for the session's lifetime instead of re-deriving
it per call." This wave is where that fix lands. `DoubleRatchetSessionCodec` gains
`encode`'s optional `salt` parameter (defaults to a fresh random draw, preserving every existing
caller's behaviour unchanged) plus two new functions, `encodeWithKey`/`decodeWithKey`, that take an
ALREADY-DERIVED 32-byte AES key directly, bypassing `KeystoreEncryption.deriveKey` entirely. The
wire format is byte-identical to `encode`/`decode` — only the AES-256-GCM key's origin differs.
`DmSessionManager.attach` derives this key ONCE, from a passphrase plus a persisted `.salt` file
(0600 where POSIX permissions are supported), and reuses it for every session-persist call for the
lifetime of the process. A caller-supplied key that did not actually come from a given file's own
salt cannot be detected as wrong by `decodeWithKey` itself — it simply fails the AEAD tag and
throws `KeystoreDecryptionException`, the same safe failure a wrong passphrase produces today; no
new security hole, and every existing structural/range/sanity-cap check `decode` runs, still runs
here too, before AES-GCM decryption is ever attempted.

==== Explicit, deliberate scope cuts for this wave

* **No delivery receipts, no typing indicators** — not even as stubs. `DmMessageType.RECEIPT`
  exists on the wire but is rejected outright at every layer that can reject it (the envelope's own
  constructor, the codec, and `DmSessionManager`'s inbound handler) — mirrors
  `EncryptionMode.MLS_ARCHIVE`'s precedent exactly.
* **No NAT traversal.** This repo has no working NAT traversal — a documented gap since
  V0.1.3/networking, unchanged by this wave. This wave supports only DIRECT-DIALABLE peers
  (same-LAN, or otherwise directly reachable); a peer behind NAT without port forwarding simply
  cannot be reached.
* **No offline/mailbox redelivery in THIS wave** — V0.8.5's job, since implemented (see that
  section below). A forward-compatible dedup key (`DmDedupKey`,
  `SHA-256(domainTag || senderIdentity || ratchetPublicKey || messageNumber)`) is computed here in
  V0.8.4, from fields already on the decoded `RatchetMessage` that V0.8.5's mailbox path also sees,
  so a message delivered both online (this wave) and later redelivered via the mailbox produces the
  IDENTICAL dedup key without either path needing to know about the other — nothing in V0.8.4 itself
  deduplicates against anything with it; V0.8.5's `processInboundDmEnvelope` cross-path pre-check is
  what actually consumes it.
* **`DmStore` (conversation history) is in-memory-only.** An explicit, documented scope cut — this
  wave already carries the highest structural risk in the codebase to date (a new stream protocol,
  a new wire format, a new session state machine, the mandatory adversarial suite), and inventing a
  THIRD at-rest encryption scheme (after `KeystoreFileFormat`/`PrekeyStoreFileFormat` and
  `DoubleRatchetSessionCodec`) has no spare review budget here. Durable `DoubleRatchetSession`
  persistence — a DIFFERENT concern, what makes a restart resume rather than re-handshake — IS
  implemented, in `DmSessionManager`.
* **Deliberate simplification versus a full cross-process `PrekeyStore`-grade sidecar file lock**
  for session persistence: atomic temp-file-then-`Files.move` writes, guarded by an in-process
  per-peer monitor only, no OS-level `FileChannel` lock. A single `LapisNode` process is this
  codebase's only supported deployment shape per identity today.
* **No multi-device / no session migration** (inherited from `DoubleRatchetSession` itself).
* **No session registry beyond what V0.8.3 already documents as partial** — a second, legitimate
  `X3DH_INITIAL` from the same peer simply creates a new session, overwriting the persisted one.

=== V0.8.5 — Offline Nabu mailbox

Target: the offline-delivery path for 1:1 direct messages — completing the split V0.8.4 started:
V0.8.4 covers "recipient reachable right now" (a live libp2p stream), this wave covers "recipient
offline, deposit a message for later pickup." This wave's central mechanism is routing around the
broken DHT (`NabuStorage.findProviders`, broken since V0.1.4 — see the Storage section below) via a
peer-hint-based direct Bitswap fetch — AND, less obviously but just as load-bearing, that pointer
*discoverability itself* required inventing a new periodic-re-announcement mechanism, because
GossipSub has no message replay (`GossipPubSub.subscribe`'s own doc comment: a node that publishes
while a peer isn't yet subscribed never redelivers that message to a later-joining subscriber).
Both points are stated up front here, not buried, because together they are this wave's most
important caveat — see "The sender-must-remain-reachable caveat" below.

pass.

| V0.8.5
| `MailboxRedeliveryScheduler` — the sender-side periodic re-announcer, and this wave's genuinely
novel mechanism (no prior sub-wave has an equivalent). Re-publishes the SAME already-announced
pointer bytes on a fixed interval (300s default) for as long as its TTL has not expired, so a
recipient's node that starts up (or comes back online) LATER still receives the pointer on the next
scheduled re-publish, through completely ordinary GossipSub delivery — see the caveat subsection
below for why this is load-bearing, not an optimization.

| V0.8.5
| `DmSessionManager.sendOffline` — encrypts exactly as `send` does (same `X3dh.initiate`-on-first-
contact / `DoubleRatchetSession.encrypt` reuse, via a shared `bootstrapSenderSession` helper so the
two call sites are byte-identical for first contact by construction, not by convention), durably
stores the resulting `DmEnvelope` bytes in Nabu, THEN signs a `MailboxPointer` referencing that
blob's CID and hands it to `MailboxRedeliveryScheduler` (bounded, in-memory), THEN publishes the
pointer — "persist then publish, publish strictly last" so a fast-arriving pointer can never
reference a not-yet-fetchable blob. The pointer itself is not separately Nabu-persisted (a V0.8.5
hardening-pass finding, 2026-08-27, removed an earlier unread `nabuStorage.put` of the pointer bytes
- see `DmSessionManager.sendOffline`'s own doc comment). Also a new cross-path dedup pre-check in
`processInboundDmEnvelope` (a bounded, LRU-evicting, global `recentlyDeliveredDedupKeys` cache keyed
by `DmDedupKey`) — see below for why this is belt-and-braces, not the load-bearing guarantee.

|===

==== The sender-must-remain-reachable caveat

Stated plainly and prominently, per this wave's own most important limitation: **offline delivery
genuinely fails to complete if the sender never comes back online before the pointer's TTL
expires** — and this is a STRONGER requirement than "reachable enough to serve the eventual Bitswap
fetch." GossipSub has zero message replay: a pointer published while the recipient's node was not
yet running (the defining "genuinely offline" scenario `TwoNodeOfflineMailboxIntegrationTest`
covers) is never delivered to that later-starting subscriber by the ORIGINAL publish, no matter how
long the recipient stays subscribed afterward. The sender must be ALIVE FOR POINTER REDELIVERY
(`MailboxRedeliveryScheduler`'s periodic re-publish) — that is the ONLY way the pointer's existence
is ever discoverable by a recipient who missed the original publish, entirely separate from whether
the underlying blob would still have been fetchable via Bitswap once the recipient learns about it.
This is a real, inherent limitation of routing around the broken DHT with gossip alone — not a bug
to silently paper over, and it is documented here exactly as bluntly as `MailboxRedeliveryScheduler`
itself states it in code.

==== A necessary deviation from the original DM concept note's metadata-minimization principle

`MailboxPointer` carries `senderIdentity` and `recipientIdentity` in the clear, signed, and gossiped
on a topic derived from `recipientIdentity` — a deliberate, necessary deviation from "Mailbox-
Records enthalten keine Klartext-Absenderkennung" (mailbox records carry no plaintext sender
identification). The recipient cannot resolve a routing hint to fetch the blob without knowing WHOSE
current address to look up, and the gossip validator cannot cheaply reject a forged pointer without
a signer identity to check it against — a fully metadata-blind mailbox record is not achievable
under this wave's broken-DHT-workaround fetch mechanism. Anyone who can subscribe to a recipient's
mailbox topic (i.e. anyone — GossipSub topics are not access-controlled) learns "someone claiming
identity S deposited a message for X at time T," the same exposure `PeerRecord` already accepts for
presence/address gossip. This is stated explicitly rather than silently claiming more privacy than
the mechanism delivers.

==== Explicit, deliberate scope cuts for this wave

* **No onion routing for mailbox pointers.** The original DM concept note's own open question — left
  open here, not resolved.
* **No DHT mailbox record** — the same broken-Kademlia limitation as every other V0.8/V0.9 wave;
  gossip plus explicit peer-hint-based Bitswap fetch instead.
* **No pin-lifetime management.** Nabu has no pin/GC anywhere in this project (V0.1.4's own
  documented state, see the Storage section below) — "pinning" a mailbox blob is currently a no-op;
  this is stated plainly rather than implying a pinning economy exists.
* **No re-delivery guarantee beyond the TTL window.** Once a pointer expires or is evicted from
  `MailboxPointerIndex`, that message is genuinely gone if the recipient never came online in time —
  an accepted, bounded-storage tradeoff, not a bug.
* **The cross-path dedup registry (`recentlyDeliveredDedupKeys`) is belt-and-braces, not the load-
  bearing guarantee against double delivery — for `TEXT`.** `DoubleRatchetSession.decrypt`'s own
  commit-only-after-AEAD-verifies state machine already structurally rejects a literal replay of the
  same `TEXT` ratchet message (`RatchetMessageRejectedException`), regardless of which path (online
  or offline) re-delivers it, since both paths resolve the SAME session object for a given peer. The
  registry exists so a KNOWN duplicate is skipped WITHOUT even attempting a wasted AEAD decrypt or
  one-time-prekey-consumption attempt — an efficiency win, not the correctness property itself, for
  `TEXT`.
* **Correction (security audit round 1 major finding, PROVEN with an executable restart probe): the
  bullet above did NOT extend to `X3DH_INITIAL`, and earlier revisions of this document overclaimed
  that it did.** `X3DH_INITIAL` resolves no existing session at all, so the ratchet's own structural
  guarantee cannot apply to it; when the header names no one-time prekey, `PrekeyStore`'s own durable
  consumption tracking never runs either, leaving only the in-memory, restart-losable
  `recentlyDeliveredDedupKeys` between a replayed `X3DH_INITIAL` and a resurrected message plus a
  rewound persisted session. Closed by a DURABLE, per-peer registry of already-accepted
  `X3DH_INITIAL` ephemeral public keys (`DmSessionManager.recordAcceptedX3dhInitialEphemeralKey`),
  persisted alongside the session file and checked before ever bootstrapping a session — see
  `docs/architecture.adoc`'s "Cross-path dedup" section for the full trace.

==== Deliberate scope cuts

* **No `lapis-net-browser` wiring at all.** `DmAcceptanceCheck`, `DmAcceptedContacts`,
  `DmAttachmentFetcher.fetchAndDecrypt`, and `DmStore.peers()`/`lastEntryFor()` are complete,
  independently unit-tested building blocks with no production caller yet in this repo — a future
  browser UI (send button, attachment download route, an "Accept" action on a quarantined
  conversation) is their intended eventual caller. Every doc comment in `lapis-net-dm` that
  describes such a route describes an INTENDED future integration point, not an existing one — an
  earlier revision of several of these doc comments incorrectly cited a nonexistent `DmApi.kt` and
  specific nonexistent routes; corrected in this revision.
* **`DmStore`/`DmAcceptedContacts` persist nothing to disk** — the same explicit, deliberate scope
  cut V0.8.4's `DmStore` history already established, carried forward unchanged: a process restart
  forgets conversation history and every accept decision.
* **The offline pre-check (`shouldFetch`) can never see the in-band first-contact deposit.**
  `DmFirstContactDeposit`/`DmDepositBinding`'s binding needs the X3DH ephemeral public key, which
  only exists inside the `X3DH_INITIAL` header — unreadable until AFTER the very AEAD decrypt
  `shouldFetch` runs before. A stranger behind a gated node's offline mailbox can therefore only earn
  pre-check delivery by clearing a configured `AcceptanceGate`; the deposit only ever unlocks the
  post-AEAD `classifyDelivered` check. See docs/architecture.adoc's "two acceptance gates" section.
* **Unbounded attachment fetch, inherited from `NabuStorage`, not a new gap this wave introduces.**
  `NabuStorage.get`/Bitswap has no max-block-size parameter to bound the wire transfer by a
  declared size ahead of time — identical shape/limitation to `lapis-net-mail`'s existing attachment
  route. `DmAttachmentFetcher.fetchAndDecrypt` rejects an oversized blob before ever handing it to
  the codec, but cannot undo the memory already spent receiving it.

`lapis-net-core` (`implementation`, for the newly-extracted `FixedWindowRateLimiter` — see below).

**Wire/protocol**: `DmMessageType.CALL_SIGNAL` (reserved since V0.8.4) activated — no

==== Progress

V0.9.2 is implemented (see `docs/architecture.adoc`'s "Hybrid-ECIES mail encryption (V0.9.2)"
section). Deliberate scope cuts, stated as such in the code's own doc comments rather than
silently omitted:

* **No forward secrecy.** Archived mail must stay decryptable for as long as the recipient holds
  their long-term identity key — this is the explicit product requirement for a store-and-forward
  email replacement, not an oversight. V0.8's (separate) Double Ratchet is the forward-secret 1:1

* **No post-quantum hybrid.** secp256k1 ECDH only — a future PQ-hybrid KEM would be a new

* **No key rotation for archived mail.** A sealed body is bound to the identity keys that existed
  at send time; rotating an identity key makes previously received mail permanently unreadable.
* **No multi-device wrapping.** Exactly one wrap per recipient's single published identity key —
  V0.8's multi-device sub-wave was cut from this arc.
* **`MLS_ARCHIVE` still reserved and rejected outright** — no implementation plan exists for it in
  this arc.
* **Wraps are always inline**, never a CID-referenced blob — a blob would be unfetchable in this
  codebase for the same reason `MailFrameCodec` carries the body inline (see architecture doc).
* **The gossip validator never decrypts and never holds a private key** — a positive property
  carried forward from V0.9.1's design, not a limitation of this wave.

=== V0.9.3 — Threading, attachment encryption, sent folder, browser UI

Target: assemble `replyTo`-linked messages into a thread; make attachment encryption independent of
body encryption (so an unencrypted message can still carry an encrypted attachment, and vice versa);
give the local identity a record of its own sent mail; and expose all of it through
`lapis-net-browser`'s HTTP routes plus a hand-written, framework-free UI page. Builds directly on
V0.9.1's envelope/body format and V0.9.2's `HYBRID_ECIES` encryption, both already on `master`.

[cols="1,3"]
|===
| Wave | Content

| V0.9.3
| `ThreadBuilder` — assembles a `ThreadForest` from a flat `List<InboxMessage>`, threading on
`MessageEnvelope.replyTo` compared against every known envelope's `contentCid` (the parent
message's *body-blob* CID — not `MessageEnvelope.contentId()`, an unrelated SHA-256 fingerprint
used only for gossip dedup). Mirrors `lapis-net-trust`'s `VeritasGrantResolver` traversal
discipline exactly — explicit-stack, non-recursive, two-phase (ENTER/LEAVE) DFS, a global
visited-CID set, and a hard depth cap (`MAX_THREAD_DEPTH = 4096`) — because a mail thread is
structurally the same forked-DAG-with-a-possible-cycle problem `VeritasGrantResolver` already
solves for the trust-grant chain. Unlike that resolver's chain, a genuine cycle (`A` replies to `B`
replies to `A`, or a message replying to itself) is *honestly constructible* through the real
production API here (`contentCid` is a pure function of body bytes, computable independently for
two unrelated messages, with none of the grant chain's "successor fixes predecessor's already-
computed id" causality constraint) — `ThreadBuilder`'s own class doc comment states this contrast
explicitly. Cycle rejection happens at root selection, not mid-walk: every member of a cycle fails
the "is this a root" test by construction, so the whole cycle — and anything that replies only into
it — is silently absent from the assembled forest, never a crash or an infinite loop. Sibling order
is a deterministic, content-cid-byte-lexicographic sort applied once before any walk, which is what
makes the whole build receipt-order independent (two nodes that received the same message set in
different arrival orders build byte-identical thread structures — a tested, explicit convergence
property, not an incidental one). A reply whose parent is not locally known becomes its own
top-level root, never a synthesized placeholder node. `threadRoot` remains carried-and-signed but
structurally unused this wave — only `replyTo` is walked.

`MailAttachmentCipher` — per-attachment AES-256-GCM encryption, following the exact
length-validated-before-allocation/AEAD discipline already established by `HybridEcies`/
`SealedBodyCodec`. **Design decision: every encrypted attachment gets a fresh, independently
generated key at encrypt time — never the enclosing `HYBRID_ECIES` message's own body content
key**, regardless of the message's own `EncryptionMode` (full four-point justification in
`MailAttachmentCipher`'s class doc comment: orthogonality to body encryption, avoiding a new
cross-module key-plumbing coupling, attachment fetch being architecturally decoupled in time from
body fetch, and identical confidentiality either way for `HYBRID_ECIES` mail). AAD is a fixed,
non-secret, domain-separating constant (`"LapisNet:mail-attachment:v1"`) rather than a
message-specific binding — unlike `HybridEcies`'s wrap/body AEADs, an attachment's `(cid, key)` pair
lives inside the same signed `MessageBody` as every other `AttachmentRef` field, so the envelope
signature already transitively authenticates the pairing; there is no cross-envelope "wrap
transplant" surface here to close. Known, accepted asymmetry: for an `EncryptionMode.NONE` message,
an attachment's key travels in the clear inside the plaintext gossip frame — independent attachment
encryption there only protects a bystander who never observes the frame at all, not anyone who does.
`EncryptedAttachmentBlob`/`EncryptedAttachmentBlobCodec` — the ciphertext's own canonical encoding,
stored under its own Nabu CID (never embedded in the gossiped `MailFrameCodec` frame, so it uses a
32-bit, not 16-bit, ciphertext-length field — an attachment can legitimately exceed
`MessageBodyCodec`'s body-blob size ceiling). `AttachmentRef` gains an optional 32-byte
`encryptionKey` field; `MessageBodyCodec`'s wire format stays at `VERSION = 1` — the addition is
gated by a previously-reserved, now-used flags bit, so a body with no keyed attachments encodes
byte-identical to pre-V0.9.3 and a pre-V0.9.3 decoder cleanly rejects (never misparses) a body that
sets the new bit, mirroring `MessageEnvelopeCodec`'s identical V0.9.2 wrap-section justification.

`SentFolder` — a local-only, evicting-cap index of `SentMessage`s this identity has itself
authored via `MailSender.send`, closing V0.9.1/V0.9.2's documented "no self-delivery, no local sent
view" gap with local bookkeeping rather than a change to gossip's self-delivery behavior (which is
unchanged — GossipSub still never delivers a node's own publishes to itself). **Deliberately ONE
evicting cap, not `InboxIndex`'s two** — an explicit, documented departure from a literal reading of
"mirror `InboxIndex`'s two-cap structure," mirroring `MailFrameCodec`'s own precedent for stating
such a divergence rather than silently deviating: `InboxIndex`'s second, separate persistence-
reservation cap exists to gate `NabuStorage.put()` against an *attacker's* unbounded gossip flood,
but `SentFolder.add` only ever runs *after* `MailSender.send` has already unconditionally,
successfully persisted the envelope and body — by then there is nothing left to gate, so a second
cap here would bound nothing real. Population is the caller's responsibility (`MailSender.send` has
no reference to any particular `SentFolder`); `lapis-net-browser`'s `POST /api/mail` route handler
is that caller.

`lapis-net-browser`: five new routes wired into the same `installBrowserApi` routing tree every
other route uses (kept in a separate `MailApi.kt` file purely for readability given their combined
size, not a distinct routing mechanism — this repo's other domains, e.g. Karma, wire their routes
directly inline in `BrowserApi.kt`, and mail routes are installed identically, just via one extra
`Route.()` extension call). `GET /api/mail` / `GET /api/mail/sent` — inbox/sent listings as
`MailSummaryResponse`s (subject, a bounded plaintext body preview, attachment metadata, and a
`decryptionFailed` flag for a `HYBRID_ECIES` inbox entry this identity could not open). `POST
/api/mail` — compose+send, wired to `MailSender`/`HybridEcies`, with attachment bytes optionally
routed through `MailAttachmentCipher.encrypt` and stored under their own CID before the message
itself is built; every validation failure (bad recipient hex, an unrecognized or explicitly-
`MLS_ARCHIVE` encryption string, oversized subject/body/attachment fields, malformed base64,
malformed `replyToCid`/`threadRootCid`) 400s cleanly before any side effect. `GET
/api/mail/thread/{cid}` — the assembled thread for whichever tree contains `cid`, built fresh from
the current inbox+sent set on every call (`ThreadBuilder.build` is cheap, `O(known.size)`, and this
codebase's other in-memory indexes are already documented as "provisional, revisit against real
usage" at this same personal-node scale). `GET /api/mail/attachment/{cid}` — fetches (local
blockstore only — see below) and, if `encryptionKey` is present, decrypts an attachment blob.

Hand-written `mail.html`/`mail.js` — a second, self-contained static page (linked from the existing
timeline page's header via one new nav line, the only change to `index.html`/`app.js`), matching
V0.2.2's Minimal-Browser's own no-new-JS-framework discipline exactly: `fetch()` + `<template>` +
`cloneNode`/`querySelector` + `.textContent`, zero dependencies. **Every render path is
Promise/`.then()`-based, deliberately not `async`/`await`** — this codebase's own headless-browser
XSS regression test (`MailXssRenderingTest.kt`, `org.htmlunit:htmlunit`) runs on an embedded
Rhino-derived JS engine that fully supports `Promise`/`fetch()`/arrow functions/template literals
but does not parse `async function`/`await` syntax at all; rather than special-case the test target,
`mail.js` itself is written in the dialect the codebase can actually verify end-to-end. Bodies are
rendered as their **verbatim Markdown source**, not rendered to HTML — a deliberate V0.9.3 scope
cut resolving `MessageBody`'s own V0.9.1 forward reference ("that is a browser-UI concern for a
later wave") in the conservative direction, given the mandatory XSS-escaping requirement below; a
future wave may add real Markdown rendering with its own escaping discipline.

**Mandatory, non-negotiable XSS-escaping discipline** (security-audit checklist item, not a style
preference): message subjects/bodies/attachment names/sender-derived strings are entirely
user-controlled content this validator never sanitizes. Every DOM-insertion site in `mail.js` goes
through one named `setText(el, value)` helper (`el.textContent = value`), never `innerHTML` and
never a template string interpolated into `innerHTML` — the one place a value feeds an
attribute-shaped context (`<a href>` for an attachment download) uses a DOM property assignment on
an already CID-validated, server-generated value, never string concatenation into markup. Verified
by `MailXssRenderingTest.kt` against the real rendering function running inside a real, JS/DOM-
executing headless browser — not a description of intent: a `<script>`/`onerror=` payload in a sent
message's subject and body is asserted to never execute and to appear in the rendered DOM as inert,
HTML-entity-escaped text.

Test suite: `ThreadBuilderTest` (linear chain, forked replies, missing parent, a real honestly-
constructed cycle and self-reference — both asserted absent from the forest with bounded execution,
not a crash — depth cap, receipt-order independence via shuffled input, and the documented
`contentCid`-collision "last one wins" edge case); `MailAttachmentCipherTest`/
`MailAttachmentCipherAdversarialTest` (round trip, key/nonce freshness, wrong key, tampered
ciphertext/tag, truncated blob, the always-fresh-key-vs-`HYBRID_ECIES`-body-key design decision
tested explicitly); `EncryptedAttachmentBlobCodecTest` (round trip, bad magic, unsupported version,
reserved flags, truncated, oversized-declared-length rejected before allocation); `SentFolderTest`
(dedup by envelope content id, eviction, insertion order); `BrowserApiMailRoutingTest` (all five
routes including every documented error case); `TwoNodeMailBrowserIntegrationTest` (two real nodes,
one composes+sends via its own real `POST /api/mail`, the other receives via real GossipSub and
sees it via its own real `GET /api/mail` — the attachment assertion is scoped to node A fetching its
own just-sent attachment locally, see Progress below); `MailXssRenderingTest` (the real-browser XSS
proof described above).

=== V0.9.4 — Spam protection

Target: give `lapis-net-mail` an opt-in, node-local defense against unsolicited mail — a
Veritas-distance filter, a Karma-threshold filter, and a Lightning first-contact deposit mechanism
that lets an unknown sender pay their way past either filter. Builds on V0.9.1's envelope format
(already on `master`) and, for the first time in this module's history, on `lapis-net-trust`'s
`TrustGraph`/`TrustPathFinder` — a deliberate, documented reversal of V0.9.1–V0.9.3's "mail has no
dependency on the scoring substrate" stance (see `lapis-net-mail/build.gradle.kts`'s V0.9.4 comment
and `docs/architecture.adoc`'s Module map entry for the full justification, mirroring
`lapis-net-madli`'s own precedent exactly).

[cols="1,3"]
|===
| Wave | Content

| V0.9.4
| `MailAcceptancePolicy` — a pure, no-I/O policy object mirroring `lapis-net-madli`'s
`MadliRoutingPolicy`/`MadliReplicationPolicy` shape exactly: `shouldAccept(sender, recipient,
envelope, hasVeritasPath, karmaScoreOf, gates, deposit)` returns an `Accept`/`Reject(reason)`
decision. `MailAcceptanceGate` is a sealed `VeritasPath`/`KarmaThreshold(minScore)` choice; an empty
gate list (`ACCEPT_ALL`, the default) accepts every sender — the protocol-mandated default, filters
are opt-in node policy, never protocol-enforced, mirroring `MadliReplicationPolicies.NEVER`'s "the
protocol itself does not mandate X" precedent. Multiple configured gates are OR-ed (a sender needs
to clear only one), and a verifying `FirstContactDeposit` bypasses every gate regardless — the whole
point of the mechanism. `KarmaScoreLookup` is an injected `(Secp256k1PublicKey) -> Double` lambda,
not a `lapis-net-karma` dependency: that module has no existing notion of a per-IDENTITY Karma
score (Karma is computed per-CONTENT), so deriving one is left as an application-layer composition
this wave deliberately does not prescribe. `MailAcceptancePolicy.veritasPathCheck(graph,
localIdentity)` is the one place `TrustGraph`/`TrustPathFinder` are referenced directly — a thin
adapter mirroring `MadliAggregator.veritasObserverWeight`'s identical "trust-free core, thin
caller-side adapter" split.

`FirstContactDeposit`/`FirstContactDepositVerifier` — structurally near-identical to V0.6's
`LightningProof`/`LightningProofVerifier` (same six-step chain: preimage-to-hash, real BOLT-11
parse+signature via `Bolt11Invoice.read`, embedded-payment-hash consistency, mandatory amount
binding, mandatory recipient binding, mandatory anti-replay memo binding), reimplemented locally
rather than called through — `LightningProofVerifier.verify`'s signature is intrinsically
Virtus-specific (`LtrRecord.viewId`/`initialValueMsat`/`cid`) and cannot be invoked against a
`MessageEnvelope`. `canonicalMemo(envelopeContentId, sender, recipient)` binds all three fields —
every one load-bearing and individually justified in the class doc comment — into the invoice's
BOLT-11 `description`, the anti-replay property this wave's central security property depends on: a
deposit paid to earn one envelope past a recipient's filter cannot be replayed against a second,
different envelope. `envelopeContentId` is `MessageEnvelope.contentId()` — a SHA-256 over the
envelope's FULL encoded bytes (every signed field plus the signature), not just the body's
`contentCid` — fixed in a round-1 security audit (2026-08-04) after the original `contentCid`-only
binding was found to let one paid deposit admit an unbounded number of envelopes sharing a body but
differing in `sentAtEpochSecond`/`replyTo`/`threadRoot`/`recipients` (all signed, all outside
`contentCid`, all inside the inbox dedup key); see `docs/architecture.adoc`'s equivalent section for
the full writeup. Same deliberate, explicitly-restated choice as V0.6: invoice expiry is never
checked — a settled payment's invoice may legitimately be past its own BOLT-11 expiry by the time the
envelope propagates through gossip.

`InboxGossip.onGossipMessage` gained an optional `acceptance: MailAcceptanceCheck?` parameter
(`null` by default, preserving every prior wave's "accept everything addressed to me" behavior
exactly) — unlike Madli's policy objects (V0.5, built but left unwired that wave), this policy
actually runs in the gossip hot path when a caller opts in. The check runs AFTER the
signature/addressing/CID-binding checks (cheap, must reject first) and BEFORE payload
decode/dedup/persistence (a rejected sender costs this node no payload allocation and no
index/storage work), preserving this module's "zero clock, zero network calls in the validator"
invariant: `MailAcceptanceCheck.trustGraph` is an already-built local snapshot, `karmaScoreOf` and
`depositLookup` are pure local lookups the caller supplies. **The deposit itself does NOT travel
in-band over `MailFrameCodec`'s wire format this wave** — a deliberate scope cut, consistent with
this whole mechanism's "obtained out-of-band"/"manual, application-layer decision" cuts (see below):
`MailAcceptanceCheck.depositLookup` is a pure local lookup from an already-decoded envelope to a
deposit the caller already holds for it (e.g. populated once an out-of-band Lightning payment
settles), not a wire-carried field.

Test suite: `MailAcceptancePolicyTest` (no-Veritas-path rejected, Veritas-path accepted, Karma
threshold accepted/rejected at the exact boundary, OR-across-gates semantics, `ACCEPT_ALL` accepts
everyone, a genuinely-verifying real deposit bypasses every configured gate, a non-verifying deposit
does not); `FirstContactDepositVerifierTest` (valid proof accepted, wrong preimage/amount/recipient/
embedded-hash rejected, malformed invoice rejected cleanly, `descriptionHash` invoices rejected, an
already-expired invoice still accepted, and the central anti-replay test: a valid deposit's memo,
replayed against a second envelope with different content, is rejected — with an isolating
re-signed-for-B invoice proving every other check would otherwise have passed and only the memo
binding stops it); `MailSpamResistanceTest` (a flood of 1,000 distinct unknown senders entirely
rejected before persistence via the same mint-CIDs-on-a-separate-node technique
`MailEnvelopeAbuseTest` established, with one Veritas-linked sender among the flood still getting
through; a real, signed self-link (`VeritasGrant.create` resolved through `TrustGraph.fromGrants`,
mirroring V0.4's own Sybil-resistance regression exactly) proven unable to manufacture a fake path
into the local identity's mail-acceptance graph; a single valid deposit proven unable to admit a
second, different message at the full `InboxGossip.onGossipMessage` integration level, not just the
unit-test level).

  the personalized Karma of every CID a node believes that sender authored) is an application-layer
  composition this wave deliberately does not prescribe.

=== V0.9 arc complete

With V0.9.4 landed, the entire V0.9 arc (V0.9.1 envelope/body format, V0.9.2 `HYBRID_ECIES`
encryption, V0.9.3 threading/attachment-encryption/sent-folder/browser-UI, V0.9.4 spam protection)
is complete on `master`. `lapis-net-mail` now offers a signed, addressed, optionally-encrypted,
threaded, attachment-capable asynchronous message format with GossipSub-only delivery, a browser UI,
and an opt-in Veritas/Karma/Lightning-deposit spam-acceptance filter — the "e-mail replacement"

no DHT-inbox discovery path (still gossip-only since V0.9.1), no address book/pubkey-to-name mapping
(carved out of V0.9.3), no newsletter/subscription model, no encrypted full-text search, no SMTP
import gateway, no Markdown-to-HTML rendering in the browser UI (V0.9.3's deliberate XSS-conservative
choice), and no market-based pinning economy (carved out of V0.9.4, this section above). None of
these block the arc's own stated target; each remains a candidate for a future, separately-planned
wave outside the V0.9 arc.
