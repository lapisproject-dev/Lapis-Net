= Lapis Net Roadmap

== V0.1 — Protocol core + Veritas

Target: first runnable prototype — network bootstrap plus Veritas (the first
of the four scoring dimensions), including GossipSub propagation of trust
edges between local nodes.

[cols="1,3"]
|===
| Wave | Content

| V0.1.1
| Gradle multi-module skeleton + CI/CD skeleton.

| V0.1.2
| Identity layer: secp256k1 keypair generation/persistence, dual-key binding to Ed25519 for the libp2p peer ID.

| V0.1.3
| P2P node bootstrap: jvm-libp2p setup, bootstrap peers, local mDNS discovery.

| V0.1.4
| Nabu integration: DHT + Bitswap for content storage (Veritas records as signed files).

| V0.1.5
| Veritas core: trust-edge data model, signing, Git-like versioning (backward hash to the previous grant).

| V0.1.6
| Veritas path algorithm: shortest paths, lexicographic ordering by next hop, product of edge weights.

| V0.1.7
| GossipSub propagation: distribute Veritas records over a dedicated topic and persist them in Nabu.

| V0.1.8
| Minimal CLI / test harness: demo with N local nodes, trust-edge issuance and propagation made visible.
|===

=== Progress

V0.1.1 through V0.1.8 are implemented (see `docs/architecture.adoc` for
details). **The V0.1 milestone is complete.**

== V0.2 — Virtus + Minimal-Browser

Target: the second of four scoring dimensions — Virtus (the LTR/on-chain
economy) — plus a Minimal-Browser that makes Veritas and Virtus data
actually visible. The browser is deliberately placed here rather than as a
standalone later wave, so a real pilot test (PdV, Girchi) is possible as
soon as V0.2 lands, instead of only after every scoring dimension exists.

[cols="1,3"]
|===
| Wave | Content

| V0.2.1
| Virtus/LTR core (on-chain): `LtrRecord` data model, GossipSub propagation
+ Nabu persistence (mirroring the Veritas V0.1.5/V0.1.7 pattern), 10%/24h
decay math, accumulation (independent records per (cid, view) pair, never
merged). Structural-only `OnChainProof` — no live Bitcoin chain
verification yet (known, documented limitation).

| V0.2.2
| Minimal-Browser (MVP): a local, loopback-only Ktor HTTP server embedding
a real node, serving a framework-free HTML/JS timeline UI. Shows Veritas
credibility + Virtus/LTR-weighted sorting; a small, deliberately temporary
`PostAnnouncement` primitive fills the content-discovery gap Karma (V0.3)
will eventually close properly.
|===

=== Progress

V0.2.1 and V0.2.2 are implemented (see `docs/architecture.adoc`'s "Virtus:
LTR core (V0.2.1)" and "Minimal-Browser MVP (V0.2.2)" sections). **The V0.2
milestone is complete.**

== V0.3 — Karma

Target: the third of four scoring dimensions — Karma, a cheap one-click
"like" with Bitcoin-chain-anchored, Veritas-weighted Sybil resistance —
wired into the Minimal-Browser as a persistently-visible Like button.

[cols="1,3"]
|===
| Wave | Content

| V0.3
| `lapis-net-karma`: `KarmaVote` data model (`Karma = t/(n+1)`, `t` =
blocks since the voter's own first outgoing Bitcoin transaction, `n` =
the voter's own prior eligible-vote count, always locally derived, never
self-declared); GossipSub propagation with zero live chain-verification
in the validation path (mirroring `OnChainProof`'s V0.2.1 precedent); a
client-side, trusting (not trustless-SPV) Electrum chain-data source used
only at local vote-cast time. Wired into `lapis-net-browser`: a new
`POST /api/karma` route and a Like button, with Karma kept purely
additive/display-only in `TimelineBuilder` (never affecting sort or
filtering).
|===

=== Progress

V0.3 is implemented (see `docs/architecture.adoc`'s "Karma: Bitcoin-
anchored one-click likes (V0.3)" section). **The V0.3 milestone is
complete.** Three of the fach-spec's four scoring dimensions (Veritas,
Virtus, Karma) are now implemented; Madli remains the only one not yet
started.

== V0.4 — Genesis-Bootstrap + Identity Hardening

Target: move from test fixtures toward real users. Bundles four related
items that all circle the same theme: real bootstrap configuration, a
QR-code/deep-link key exchange flow, multi-device/pseudonym self-trust
linking, and keystore encryption at rest.

[cols="1,3"]
|===
| Wave | Content

| V0.4
| `BootstrapConfig` (`lapis-net-networking`): env-var + file-based
bootstrap-peer resolution and a configurable libp2p listen address,
replacing the old RFC-5737 placeholder list. `ConnectUri`/`QrCodeSvg`
(`lapis-net-browser`): a `lapisnet://connect` URI scheme plus a
server-side-rendered SVG QR code and three new HTTP routes so two real
users can connect without hand-copying multiaddrs. `POST
/api/self-link`: multi-device/pseudonym linking that reuses the
existing `VeritasGrant` model verbatim at maximum trust — no schema
change, no new Sybil attack surface. `KeystoreEncryption`/`KeystoreFileFormat`
v2 (`lapis-net-identity`): Argon2id + AES-256-GCM keystore encryption
at rest with the full file header bound as GCM AAD, and transparent,
atomic v1-to-v2 migration.
|===

=== Progress

V0.4 is implemented (see `docs/architecture.adoc`'s "Genesis-Bootstrap +
Identity Hardening (V0.4)" section). **The V0.4 milestone is complete.**

== V0.5 — Madli

Target: the fourth and final scoring dimension — Madli, a machine-to-machine
node-reputation system rating nodes as infrastructure (Bitswap/DHT serving
quality), never content or people, with Veritas-weighted, decay-weighted,
weighted-median aggregation resistant to Sybil clusters and selective
service.

[cols="1,3"]
|===
| Wave | Content

| V0.5
| `lapis-net-madli`: `MadliDailyVector` data model (five fixed-point
metrics — Reachability, Bandwidth, Latency, Delivery-Integrity,
Routing-Helpfulness — signed per `(observer, observedPeer, epochDay)`,
no `nonce`, latest-wins per tuple); `MadliVectorIndex` with two
anti-flooding/anti-backdating invariants (one tracked vector per exact
tuple; a capped number of distinct days per `(observer, observedPeer)`
pair); GossipSub propagation with zero clock/network calls in the
validation path (mirroring `KarmaGossip`/`LtrGossip`'s precedent);
`MadliDecayCalculator`'s five independently-configurable half-lives;
`MadliAggregator`'s Veritas-weighted weighted-median aggregation (a
deliberate, documented exception to the Karma/Virtus "no sibling trust
dependency" rule, since Madli has no application-layer consumer this
wave); `MadliRoutingPolicy`/`MadliReplicationPolicy` — pure,
unit-tested Bitswap-modulation hooks, structurally ready but not wired
into a live fetch this wave (honest scope cut, mirroring V0.1.4's own
provider-discovery limitation); and `MadliSybilResistanceSimulationTest`
— the mandatory adversarial harness resolving the vault note's one
explicitly-unresolved item, proving the Veritas-weighting and
weighted-median defenses hold against a real `TrustGraph`/
`TrustPathFinder`, and explicitly documenting the one accepted residual
(a trusted majority that lies still wins the median).
|===

=== Progress

V0.5 is implemented (see `docs/architecture.adoc`'s "Madli: machine-to-
machine node reputation (V0.5)" section). **The V0.5 milestone is
complete.** All four of the fach-spec's scoring dimensions (Veritas,
Virtus, Karma, Madli) are now implemented.

== V0.6 — Lightning proof

Target: close V0.2.1's "Zwei Zahlungswege" gap on the Lightning side — a second, fully
cryptographically verified `LtrProof` implementation alongside `OnChainProof`, wired into the
gossip hot path, plus the first LTR record-authoring HTTP endpoint.

[cols="1,3"]
|===
| Wave | Content

| V0.6
| `lapis-net-virtus`: `LightningProof` data model (`preimage`, `paymentHash`, `signedInvoice` —
structural shape only, mirroring `OnChainProof`'s constructor discipline) and
`LightningProofVerifier`, the sole consumer of `lightning-kmp` in this module, performing the full
verification chain — `sha256(preimage) == paymentHash`, real BOLT-11 parsing + signature
verification via `Bolt11Invoice.read`, mandatory amount binding (`invoice.amount ==
record.initialValueMsat`), mandatory recipient binding (`invoice.nodeId == record.viewId` — a
Lightning node key IS its Lapis viewId, by protocol commitment), and mandatory content binding
(`invoice.description == canonicalMemo(cid, viewId)`, the anti-replay check) — deliberately never
checking invoice expiry. `LtrRecordCodec`'s `proofType = 2` (previously reserved, rejected outright)
is now implemented, with a DoS-guarded, length-validated-before-allocation invoice field.
`LtrGossip.onGossipMessage` calls `LightningProofVerifier.verify` directly in the gossip hot path —
a deliberate divergence from `OnChainProof`'s (and Karma/Madli's) "never call a network service
inside the validator" precedent, safe here because Lightning-proof verification is pure, bounded,
and local, with zero liveness dependency on anything outside the message bytes. `lapis-net-browser`:
`POST /api/ltr/lightning`, the first LTR record-authoring endpoint, accepting an
externally-obtained `(preimage, signedInvoice)` pair (the author paid a real invoice with their own
wallet out-of-band) and verifying it with the same crypto chain before announcing.
|===

=== Progress

V0.6 is implemented (see `docs/architecture.adoc`'s "Lightning proof (V0.6)" section). **The V0.6
milestone is complete**, with one honestly-scoped, deliberate gap carried forward as explicit future
work:

* **No embedded Lightning node.** Nothing in this codebase runs a real `lightning-kmp` node, holds a
  channel, or has access to real funds — `LightningProofVerifier` only ever verifies proofs already
  handed to it, never constructs or sends a payment.
* **No BOLT-12 Offer/DHT publication, no `invoice_request`/auto-respond flow.** V0.6 only covers the
  BOLT-11 "pay first, submit proof after" path from the Virtus spec note's "Zwei Zahlungswege"
  section; the fuller "A. Lightning via BOLT-12 Offer" vision (a view publishing a standing offer
  other nodes can pay against without out-of-band coordination) remains future work.
* **No live payment settlement testing.** Every test substitutes a preimage/invoice generated
  in-process with real `lightning-kmp` calls (fully real cryptography) — only the network settlement
  event itself (an actual Lightning payment over a real channel) is out of reach in this
  sandbox/CI, mirroring `ElectrumTimeAnchorSourceTest`'s and Madli's Bitswap-modulation precedent
  for external payment/network infrastructure. Real embedded-node send/receive testing is future
  work, likely alongside whichever wave eventually builds the embedded node itself.

== V0.7 — Reference browser/client

Originally proposed as its own closing wave (a Timeline pipeline over all four scoring
dimensions, `Karma → Veritas → Virtus`, default-filtering and credibility color-marking). Decided
against as a standalone wave on 2026-07-18: an early pilot test with PdV/Girchi needs a usable
client from the start, not only after every scoring dimension exists, so the browser was built
incrementally alongside V0.2.x (Virtus display), V0.3 (Karma extension), and V0.5 (Madli
extension) instead — see `lapis-net-browser`. **No separate V0.7 milestone exists**; its scope is
already covered by the incremental browser growth documented in V0.2–V0.5 above.

== V0.8 — Direct messages and calls

Target: X3DH/Double Ratchet for 1:1 chats, MLS for groups, WebRTC for voice/video/conferencing —
full spec in the vault concept note "Direktnachrichten und Anrufe" (not yet mirrored into this
repo's `docs/`).

=== Progress

**Not started.** Fully specified at the concept level (layering model, 1:1 call flow,
multi-participant conferencing, addressing/peer-discovery, multi-device support), zero code exists
in this repository — no `lapis-net-*` module implements X3DH, Double Ratchet, MLS, or WebRTC.
Proposed as an Opus-planned wave (cryptographically novel, Double-Ratchet/MLS implementation is
highly security-critical) in the 2026-07-17 gap analysis; not yet started pending explicit
go-ahead.

== V0.9 — Asynchronous messages (email replacement)

Target: envelope/body message format, optional ECIES/MLS-archive encryption, DHT-inbox +
GossipSub-listener discovery, Lightning-HTLC first-contact spam deposit, market-based pinning —
full spec in the vault concept note "Asynchrone Nachrichten (E-Mail-Ersatz)" (not yet mirrored
into this repo's `docs/`).

=== Progress

**Not started.** Fully specified at the concept level (message format, three encryption modes,
dual discovery channels, threading, attachments, spam protection, pinning economy), zero code
exists in this repository. Proposed as a Sonnet-planned wave with an Opus review pass for the
ECIES encryption scheme specifically, in the 2026-07-17 gap analysis; not yet started pending
explicit go-ahead. Functionally independent of V0.8 (separate subsystem, shares only the identity
keypair and protocol core) — could in principle be sequenced before or after V0.8 once approved.
