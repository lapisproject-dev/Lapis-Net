= Lapis Net: Status
:toc:

Every wave through *V0.9* is implemented and merged to `master`, followed by
post-arc maintenance waves (V0.9.8 to V0.9.20, below), a fix release and three feature releases. The current release is
*v0.13.0*, which adds the experimental, incomplete anonymity mode (off by default) (`v0.10.0` was the first with a chronological version number: up to `v0.9.9` the tags
are wave identifiers (V0.7 was never a standalone wave — its scope was folded into the
incremental browser growth of V0.2–V0.5), from `v0.10.0` on they count releases in the
order they ship). See link:roadmap.adoc[roadmap.adoc] for the
explanation and a map of every tag to its content. Full technical
detail for each module is in the link:modules.adoc[module table]; the full wave-by-wave
history — including scope cuts and hardening follow-ups — is in
link:roadmap.adoc[roadmap.adoc] and
link:architecture.adoc[architecture.adoc].

Known, deliberate gaps — not oversights, each documented at the point it was cut:

* *No embedded Lightning node* — proof verification only, no payment sending; no BOLT-12 offer publication.
* *NAT traversal: relay plus TCP hole punching that is only verified on loopback.* Since `v0.12.0` (V0.9.20) `dcutr` hole punching exists (`--hole-punching=auto|on|off`, default `auto` = only for `--reachability=private`): two NAT'd peers connected through a relay try to open a direct TCP connection, and the relayed connection is released after a verified success. It has been tested on Linux loopback only, never behind a real router or CGNAT; there is no UDP/QUIC punching, no AutoNAT, no Windows support (no `SO_REUSEPORT`), symmetric NATs will not work, and macOS is untested. The concurrency pools are per node, not per relay: an attacker with many identities can exhaust them and keep legitimate connections relayed, and a hostile peer can block the role registry for an address (the punch then fails, the connection stays relayed). It needs a relay that answers Identify and uses a transport whose listener port other processes of the same OS user may share. The rest of this item describes the relay part: A node behind NAT can now be reached: it reserves a slot on a Circuit-Relay-v2 relay and publishes the resulting `/p2p-circuit` address, and a peer that holds only that address dials it through the relay with an end-to-end Noise session the relay cannot read. Acting *as* a relay is opt-in and off by default. Without a successful punch a relayed connection stays relayed for its whole life, and relay operators are not compensated: reputation (Madli) is the intended route: a relay-reliability metric exists since `v0.11.0`, but the publisher that writes it is off by default and only the operator option `--publish-relay-reliability=true` switches it on, and the usage-based priority ledger is local and memory-only (a new identity starts at 0). Using a relay is an explicit, programmatic setting (`LapisNode.relayClient.reserve(relay)`). Since `v0.11.0` the library also has an automatic relay selection (`LapisNode.startAutoRelay`, only for a node declared `NodeReachability.PRIVATE`) and a reachability heuristic that merely warns; there is still no AutoNAT, and the browser and `lapis-net-cli node --reachability=private` start it (the publisher stays off unless `--publish-relay-reliability=true`), and `lapis-net-call` refuses relayed media on purpose, so voice calls still need a direct connection. Rollout constraint: a record advertising the new `RELAY` capability bit is rejected outright by older nodes, so readers must be upgraded everywhere before any node advertises it.
* *Browser call remote control (V0.8.7b)* — `/call.html` remote-controls a call whose audio runs in the JVM node process. Since V0.9.15 the acceptance policy is wired in the browser: blocked callers are shown locally and nothing is sent to them. No mute, no persisted call history (the history is held in memory).
* *Traffic anonymisation (anonymity mode, since `v0.13.0`, experimental and incomplete):* `--anonymity=on|off`, default `off`. A node in anonymity mode uses a fresh transport key per run, connects only to its two guards (plus its bootstrap peers at every start and while it lacks relays or a guard connection), does not listen, publishes an address-free directory entry through circuits, and carries direct messages (module `lapis-net-dm-onion`), mail (module `lapis-net-mail-onion`) and call signals over onion circuits, padded to size classes with cover cells (`--anonymity-padding=standard|off`). Both ends must be in anonymity mode, there is no fallback to a direct connection, and the recipient learns the sender. Call media is not anonymised and can not be: calls are off in the mode unless `--anonymity-allow-call-media=true`, with a confirmation before every call, and a call then reveals your IP address. Own posts, votes, trust grants, self-links, LTR records and manual connections are refused in the mode; missing timeline post bodies are looked up through circuits to relays of the role LOOKUP, which see what is asked and when, but not by whom. Known open points (leak inventory in `docs/anonymity.adoc`): the guards see the address, online times and topics; the bootstrap peers see the address at every start; inbox rendezvous and relay provider records are unreachable; no IPNS consumer is wired in the mode (Q18); there is no batch lookup (Q16); a single relay can withhold an answer or serve an older IPNS record; up to 4 timeline lookups on one circuit are linkable for the exit relay; this is no protection against a global passive observer. Everything was verified on loopback with an injected network locator, not on real networks, behind NATs or under real load. *No external cryptographic or anonymity review has taken place*; `docs/external-review.adoc` prepares one.
* *Post bodies in the DHT (wave Q20, since `v0.13.0`):* browser nodes in normal mode announce the newest (at most 256) post bodies they hold and re-announce them hourly (`--provide-post-bodies`, default `true`, off in anonymity mode); verified on loopback only, the numbers are provisional; the decision is confirmed by the user (2026-11-22), its open points F1 to F6 are not. After a restart only newly arriving posts are announced; before fix wave F6 a relay that fetched a body once from a single holder did not get it again (Nabu's Bitswap resend gap); since F6 the holder resends within bounds, through reflection on a private Nabu field. See `roadmap.adoc`, wave Q20.
* *No group calls, video, multi-device messaging, or MLS* — cut from the V0.8 arc's scope entirely on 2026-08-04, not a partial or stubbed implementation.
* *No delivery receipts or typing indicators* for direct messages — deliberately deferred, not built even as stubs.
* *The DHT fallback is wired since V0.9.15 (V0.9.13, V0.9.14).* The browser publishes and looks up peer records, prekey bundles and mail/DM pointers over the DHT (GossipSub stays the primary path); it is on by default and `--dht-fallback=false` turns it off. The CLI's `node` subcommand uses it for the peer directory only. DHT lookups tell the peers that are asked who is looking for whom (docs/architecture.adoc, section 11); a node in the experimental anonymity mode of `v0.13.0` does not query the DHT itself, and starting it with an explicit `--dht-fallback=true` is refused; the rendezvous key of a victim can be eclipsed by throwaway identities; plaintext mail is deliberately never recoverable from the DHT; a lookup needs the owner's Ed25519 peer ID.
* *Attachments in anonymity mode (wave Q21, since `v0.13.0`):* a browser node in anonymity mode fetches an attachment blob it does not hold from the sender's onion service through a rendezvous circuit (new service application `ATTACHMENT`), never directly; only while the sender is online, at most 4,193,984 bytes per blob (a direct-message attachment at most 4,193,946 bytes), answers padded to nine transfer classes, the blob checked against its CID and stored unserved. A sender hands out only attachments it sent itself, with a key. A MAILBOX lookup through LOOKUP relays is the last resort for blobs up to 131,066 bytes and finds practically nothing in a real network. Forwarding a mail with an attachment reference that is not local is refused. The limits are provisional, not measured in a pilot, and the server's limits are global, so a third party that resolves the sender's descriptor can occupy them. Both download routes refuse cross-site requests (`Sec-Fetch-Site`, `Origin`); a browser that sends neither header (for example Safari before 16.4) is not covered by that guard. Verified on loopback only; experimental, default `--anonymity=off`, no external review; the design (Q21-A to Q21-I) is confirmed by the user (2026-11-22); the fetch token uses a key derived by HKDF from the attachment key (wave Q21-Token). See `anonymity.adoc`, section "Attachments over circuits".
