= Lapis Net: Status

Every wave through *V0.9* is implemented and merged to `master`, followed by
post-arc maintenance waves (V0.9.8 to V0.9.20, below), a fix release and two feature releases. The current release is
*v0.12.0* (`v0.10.0` was the first with a chronological version number: up to `v0.9.9` the tags
are wave identifiers (V0.7 was never a standalone wave — its scope was folded into the
incremental browser growth of V0.2–V0.5), from `v0.10.0` on they count releases in the
order they ship). See link:roadmap.adoc[roadmap.adoc] for the
explanation and a map of every tag to its content. Full technical
detail for each module is in the link:modules.adoc[module table]; the full wave-by-wave
history — including scope cuts and hardening follow-ups — is in
link:roadmap.adoc[roadmap.adoc] and
link:architecture.adoc[architecture.adoc].

Known, deliberate gaps — not oversights, each documented at the point it was cut:

* *No embedded Lightning node* — proof verification only, no payment sending; no BOLT-12 offer publication.
* *NAT traversal: relay plus TCP hole punching that is only verified on loopback.* Since `v0.12.0` (V0.9.20) `dcutr` hole punching exists (`--hole-punching=auto|on|off`, default `auto` = only for `--reachability=private`): two NAT'd peers connected through a relay try to open a direct TCP connection, and the relayed connection is released after a verified success. It has been tested on Linux loopback only, never behind a real router or CGNAT; there is no UDP/QUIC punching, no AutoNAT, no Windows support (no `SO_REUSEPORT`), symmetric NATs will not work, and macOS is untested. The concurrency pools are per node, not per relay: an attacker with many identities can exhaust them and keep legitimate connections relayed, and a hostile peer can block the role registry for an address (the punch then fails, the connection stays relayed). It needs a relay that answers Identify and uses a transport whose listener port other processes of the same OS user may share. The rest of this item describes the relay part: A node behind NAT can now be reached: it reserves a slot on a Circuit-Relay-v2 relay and publishes the resulting `/p2p-circuit` address, and a peer that holds only that address dials it through the relay with an end-to-end Noise session the relay cannot read. Acting *as* a relay is opt-in and off by default. Without a successful punch a relayed connection stays relayed for its whole life, and relay operators are not compensated: reputation (Madli) is the intended route: a relay-reliability metric exists since `v0.11.0`, but the publisher that writes it is off by default and only the operator option `--publish-relay-reliability=true` switches it on, and the usage-based priority ledger is local and memory-only (a new identity starts at 0). Using a relay is an explicit, programmatic setting (`LapisNode.relayClient.reserve(relay)`). Since `v0.11.0` the library also has an automatic relay selection (`LapisNode.startAutoRelay`, only for a node declared `NodeReachability.PRIVATE`) and a reachability heuristic that merely warns; there is still no AutoNAT, and the browser and `lapisnet node --reachability=private` start it (the publisher stays off unless `--publish-relay-reliability=true`), and `lapis-net-call` refuses relayed media on purpose, so voice calls still need a direct connection. Rollout constraint: a record advertising the new `RELAY` capability bit is rejected outright by older nodes, so readers must be upgraded everywhere before any node advertises it.
* *Browser call remote control (V0.8.7b)* — `/call.html` remote-controls a call whose audio runs in the JVM node process. Since V0.9.15 the acceptance policy is wired in the browser: blocked callers are shown locally and nothing is sent to them. No mute, no persisted call history (the history is held in memory).
* *Traffic anonymisation: design, cryptographic foundation, wire integration, (unreleased wave V0.10.0-C) the receiver side with introduction points, rendezvous points and onion service descriptors (unreleased wave V0.10.0-D) an address-free directory entry published through circuits and (unreleased wave V0.10.0-E) path selection with persistent guards, a circuit build policy and the experimental option `--anonymity=on|off` exist; nothing is active by default, no user traffic (messages, mail, calls) uses it and no anonymity is offered (the transport key is still the identity key; the network diversity of paths rests on self-declared relay addresses and was verified only with an injected locator).* The hidden-service API is experimental infrastructure with no link to a Lapis identity. IP addresses remain visible to peers and to the directory (`PeerRecord` publishes addresses; mail uses one GossipSub topic per recipient). See `docs/anonymity.adoc` for the threat model, the known leaks and the wave plan. Since (unreleased wave V0.10.0-F1) a browser node in anonymity mode also carries *direct messages* over circuits (rendezvous streams online, sealed mailbox items announced by relays offline; module `lapis-net-dm-onion`); both ends must be in anonymity mode, there are no attachments and no fallback, the recipient learns the sender, and mail, calls, GossipSub and the DHT were unchanged in that wave. Since (unreleased wave V0.10.0-F2) *mail* also travels over circuits (module `lapis-net-mail-onion`): a mail with attachments of up to 1 MiB in total is delivered while sender and recipient are online at the same time, a small mail without attachments is also delivered while the recipient is offline (as a sealed item on the shared topic); the node subscribes to no per-recipient inbox topic, leaves no DHT pointer and fetches nothing over Nabu/Bitswap for mail. Both ends must be in anonymity mode, there is no fallback, the recipient learns the sender, and call media, call signalling, GossipSub in general and the DHT are unchanged (calls to or from a node in anonymity mode do not work).
* *No group calls, video, multi-device messaging, or MLS* — cut from the V0.8 arc's scope entirely on 2026-08-04, not a partial or stubbed implementation.
* *No delivery receipts or typing indicators* for direct messages — deliberately deferred, not built even as stubs.
* *The DHT fallback is wired since V0.9.15 (V0.9.13, V0.9.14).* The browser publishes and looks up peer records, prekey bundles and mail/DM pointers over the DHT (GossipSub stays the primary path); it is on by default and `--dht-fallback=false` turns it off. The CLI's `node` subcommand uses it for the peer directory only. DHT lookups tell the peers that are asked who is looking for whom, until traffic anonymisation exists (docs/architecture.adoc, section 11); the rendezvous key of a victim can be eclipsed by throwaway identities; plaintext mail is deliberately never recoverable from the DHT; a lookup needs the owner's Ed25519 peer ID.
