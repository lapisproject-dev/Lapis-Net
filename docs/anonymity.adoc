= Traffic anonymisation: design, foundation and wire integration (waves V0.10.0-A and V0.10.0-B)
:toc:

== Status

*Wave B (wire integration, unreleased): the infrastructure is wired, no user traffic uses it, nothing is anonymised.* `lapis-net-onion` (wave A) holds the cryptographic foundation; the new module `lapis-net-onion-wire` (wave B) carries cells over a libp2p stream, keeps a relay's onion keys, publishes relay descriptors and, only with `--onion-relay=true`, lets a node act as a relay. There is no path selection, no application (DM, mail, call, browser) sends anything over a circuit, and the browser is not wired at all. IP addresses remain visible to peers and to the directory.

[WARNING]
====
*What this wave does not give you.* It provides no anonymity. It provides audited-by-our-own-pipeline building blocks (cell format, ntor-style handshake, onion layering, a relay state machine with resource limits) and a written threat model. Several leaks listed below must be closed before anyone may claim anonymity for DM, mail or call signalling. No external cryptographic review has taken place.
====

`V0.10.0-A` and `V0.10.0-B` are wave identifiers, not releases: `v0.10.0` is an existing tag and release numbers are chronological since then. The release number is assigned when the arc ships.

Diagram sources are committed as kUML; GitHub does not render the `[kuml]` blocks (the rendering pipeline is not wired, see `architecture.adoc`, section Diagrams).

== Goals and non-goals

*Goal.* No network observer (ISP, local Wi-Fi, a single relay, the receiving peer) can link the IP address of a sender or receiver to a Lapis pseudonym, for direct messages, mail and call signalling. Pseudonymity itself is unchanged: identities stay stable keys.

*Non-goals.*

* Anonymous content. Content confidentiality stays with the existing end-to-end layers (X3DH/Double Ratchet, hybrid ECIES).
* Protection against a global passive observer who sees both ends of a circuit (traffic confirmation). Not defended, see the threat model.
* The media path of calls. WebRTC reveals IP addresses through ICE; signalling can be anonymised, media cannot without a separate design.
* GossipSub, the DHT and content fetches in part 1 (wave J, later).
* Tor equivalence. This is a small, purpose-built onion design for a small network, with a much smaller anonymity set than Tor.

== Threat model

[cols="2,3,3", options="header"]
|===
| Adversary | Defended | Not defended / caveat

| Local observer (ISP, shared network)
| Sees only encrypted 1024-byte cells to a guard (link encryption: wave B). Cannot see destination identity or content.
| Sees that the user runs the protocol and when it is active. No padding schedule yet (wave H), so volume and timing leak.

| A single malicious relay
| Learns at most its two neighbours and its own position (hop index). Cannot read or undetectably alter cell content.
| A guard sees the client IP; an exit sees the next hop. A relay can destroy circuits (DoS) and observe timing.

| Colluding relays or Sybil identities
| Per-hop authentication and per-hop regenerated filler remove the classic tagging channel. Path selection will weigh Madli reputation and enforce diversity (wave E).
| If one adversary controls both guard and exit of a circuit it can correlate by timing and volume. Madli reputation is a weak Sybil defence (identities are free); it is a weight, never a gate.

| Malicious receiver
| Sees a rendezvous or mailbox, never the sender IP (once wave C/F land).
| Can correlate by timing with its own observations.

| Global passive observer
| *Not defended.*
| End-to-end timing and volume correlation is out of scope.
|===

== Known leaks today

These exist in the current release and must be closed before any anonymity claim.

. *`PeerRecord` publishes addresses.* The signed directory record binds an identity to its current network addresses. This is exactly the pseudonym-to-IP link to be hidden. In anonymity mode a node must publish introduction points, not addresses (wave D).
. *Mail uses one GossipSub topic per recipient.* Subscribing to your own topic links your identity and IP for your mesh neighbours. Mail delivery has to move off the per-recipient topic: store and fetch through circuits (wave F). This wave does not change mail.
. *Gossip timing.* Message publication times and mesh membership leak.
. *WebRTC media.* ICE exposes IPs to the peer.
. *DHT provider records of the offline mailbox path* tell DHT peers who looks for whom.
. *Small anonymity set.* Few relays mean weak anonymity regardless of cryptography.
. *Relay position.* A relay learns its hop index from the CREATE; with the default of three hops that equals Tor's exposure of position, stated here deliberately.
. *Correlation by provoked teardown.* Any party on a path can destroy a circuit and correlate the effect elsewhere (DoS-based correlation). Not prevented.

=== Cell format

Every cell is exactly 1024 bytes: `circuitId(4) | command(1) | body(1019)`. Commands: PADDING (circuit id 0 only), CREATE, CREATED, RELAY, DESTROY. Unused body space is filled with random bytes, not zeros, so empty fields reveal nothing. The parser has no length field: the input size is compared to 1024 before anything is copied, so no allocation depends on attacker data. Unknown commands and a circuit id of 0 on a non-PADDING cell are rejected.

=== Circuit length

Default 3 hops, technical maximum 5 (`MAX_HOPS`). The library accepts 1 to 5 (1 and 2 for tests); a policy minimum of 3 for the production path is enforced when the module is wired (waves B and E). A relay message addressed to hop 3 carries up to 963 bytes of data (1019 - 3*17 - 5 header bytes).

=== Handshake (ntor over X25519)

The handshake follows the published ntor construction (Goldberg, Stebila, Ustaoglu) and is reimplemented from that description; no code was copied. Wire shapes and labels are Lapis-specific, so the pinned test vector is a self-generated regression vector (cross-checked once against an independent script), not an external known-answer test.

....
secret_input = X25519(y,X) | X25519(b,X) | ID | B | X | Y | PROTOID      (client: X25519(x,Y) | X25519(x,B))
KEY_SEED     = HMAC-SHA256(PROTOID:key_extract, secret_input)
verify       = HMAC-SHA256(PROTOID:verify,      secret_input)
AUTH         = HMAC-SHA256(PROTOID:mac, verify | ID | B | Y | X | PROTOID | "Server")
Kf | Kb      = HKDF-SHA256(ikm = KEY_SEED, salt = empty, info = PROTOID:expand, L = 64)
....

`ID` is the SHA-256 digest of the relay identity key, `B` the relay's onion key, `PROTOID` is `LapisNet:ntor-x25519-sha256:v1`. The client compares AUTH in constant time. Ephemerals x and y and every intermediate secret are overwritten after use; this gives forward secrecy for the circuit keys against a later compromise of `B`. The relay's *onion key* is separate from the X3DH encryption key and is bound to the identity by a signed `OnionKeyBinding` with its own domain tag and an expiry; it is meant to be rotated.

Deviation from the plain ntor message: CREATE and EXTEND carry a `hopIndex` byte (the relay's 1-based position), set by the client. It selects the layer size and is bound into every AEAD's associated data; a wrong value only breaks the client's own circuit.

=== Onion layers and the anti-tagging rule

Each hop holds two keys. A layer for hop i has size `1019 - (i-1)*17` (16 tag bytes plus one type byte per layer). Layers are sealed with ChaCha20-Poly1305 (RFC 8439) under an *implicit* nonce `directionTag(4) | counter(8)`; the counter is never transmitted. Replay, duplication, drop and reordering all desynchronise the counter, fail the tag and destroy the circuit. There is deliberately no replay window: the transport stream is reliable and ordered, so any deviation is an attack. After one failed open the cipher is poisoned.

*Why ChaCha20-Poly1305 and not AES-256-GCM (which the rest of the project uses).* It is constant-time in software without AES-NI, it comes from the BouncyCastle lightweight API that is already a dependency, and key material can be held in arrays this code zeroises (a JCE `SecretKeySpec` cannot be reliably wiped). If uniformity with AES-GCM is preferred, the change is confined to one class (`HopCipher`).

*Anti-tagging rule.* Every byte that is not covered by the authentication tag of the receiving hop is discarded and regenerated by that hop with fresh random bytes. Unauthenticated filler that an honest hop forwarded unchanged would be a covert channel through which two colluding, non-adjacent relays (guard and exit) could mark a cell. With the rule, every bit that is ever evaluated is authenticated per hop; a flipped bit in an authenticated region is detected at the next honest hop (forward) or at the client (backward). What remains is destroying a circuit on purpose and correlating the teardown, listed above as not defended.

=== Lifetime, rotation, padding

A circuit lives at most 10 minutes (relay-enforced by a sweep) or 2^32 cells per direction, whichever comes first; new destinations get new circuits (policy, wave E). Part 1 has a fixed cell size and a `DROP` relay message. A padding schedule against timing analysis is *open* (wave H).

=== Link encryption

The libp2p Noise session protects the link only: cells travel over a dedicated stream `/lapis/onion/1.0.0` (wave B, see below), hiding circuit ids and commands from an ISP. The onion layers themselves are ntor plus AEAD, independent of Noise.

== Relay selection (design, wave E)

* *Madli* reputation weights selection; it is never a hard gate and the minimum weight is above zero, so new relays can be chosen. Honest assessment: in a Sybil scenario Madli helps against lazy or unreliable relays, but it does not stop an adversary that creates many reputable-looking identities.
* *Diversity:* never twice the same Lapis identity in a circuit, no two hops from the same IPv4 /16 (IPv6 /32), no two hops from the same operator-declared relay family (a signed field to be defined in a later wave). Optionally no two hops with a direct Veritas trust edge between them; this option is not decided.
* *Guards:* a small, long-lived guard set (1 to 2, rotated over weeks) against the predecessor attack.
* Path-level duplicate checks live in the client (`ClientCircuitBuilder`): relays do not know their neighbours' identities. The relay state machine only refuses to extend to itself and bounds chain depth by `MAX_HOPS`.
* A failed or aborted client-side build is not silent for the relays: `BuilderStep.Failed` carries a DESTROY cell (absent only when the peer itself sent DESTROY) and `ClientCircuitBuilder.abort()` returns one; the host must send it to the first hop, otherwise the relays keep the circuit until the lifetime sweep. PADDING and cells of other circuits on the guard link yield `BuilderStep.Ignored`.

== Relationship to Circuit Relay v2 and DCUtR

Circuit Relay v2 and DCUtR serve reachability (NAT). Onion circuits serve unobservability. A Circuit Relay v2 relay sees both endpoints and is therefore not an anonymity hop. DCUtR deliberately creates direct IP connections and must be *off* on anonymous paths (policy for wave E). Onion relays may themselves be reached through Circuit Relay v2.

== Receiver side and rendezvous (decision open for part 2)

Options:

. *Introduction points plus rendezvous point* (Tor v3 pattern). Live; good for online DM and call signals; complex.
. *Mailbox pointer over circuits* (existing mailbox path, store and fetch through circuits). Offline-capable, higher latency; the DHT provider-record leak must be solved first.
. *Fixed mailbox relay per receiver.* Simple, but a stable relay learns the receiver's identity.

Recommendation: (a) for live traffic, (b) for offline delivery. *The final decision is open and belongs to wave C.*

== Incentives and operation

Running a relay is opt-in per node and can be switched off. Relay reliability will be a Madli metric analogous to the existing relay-reliability metric. No payment in part 1; Lightning or Virtus incentives remain an open option. Operators need bandwidth and circuit limits; the foundation already bounds circuits, creation rate and cell rate (`OnionRelayLimits`).

== Per-node switch

The feature is meant to be part of the protocol core and switchable off per node: a configuration option such as `--anonymity=on|off`. *The name and the default are open*; the decision falls in wave E. Until then the only switch is `--onion-relay=true|false` (default off), which makes a node serve as an infrastructure relay and nothing else.

== Wire integration (wave V0.10.0-B)

=== Module boundary

* `lapis-net-onion` stays free of network code. It only gained `OnionKeyRing` (the current plus the previous onion key during a rotation overlap, with a read/write lock so a scalar is never zeroised while an X25519 operation uses it), a constructor of `OnionRelay` that takes such a ring (the old single-key constructor remains), and the opt-in marker `ExperimentalOnionApi`.
* `lapis-net-directory` depends on `lapis-net-onion` (no cycle: onion knows only core and identity). The descriptor belongs to the directory data, like `PeerRecord`.
* `lapis-net-onion-wire` (new) depends on onion, networking, directory and identity. It could not live in `lapis-net-networking`: that would make networking depend on onion and directory, and directory already depends on networking. Pattern as in `lapis-net-dm`: the module owns a `StrictProtocolBinding`; the handler is registered on the host only in relay mode.

=== Stream protocol `/lapis/onion/1.0.0`

Every cell is exactly 1024 bytes on the stream. There is *no length field*: the frame decoder cuts at 1024 bytes, so a frame size can never be attacker-chosen (the off-by-length class of bug found in the length-prefixed DM codec in 2026-08 cannot occur). A started frame that does not complete within the handshake window (10 s) closes the link (slowloris); an inbound link must deliver a first cell within the same window; the read-idle timeout is 5 minutes. Each link has a cell rate limit (4000 cells/s) and a write-queue cap (256 cells, about 256 KiB): exceeding either closes the link, nothing is ever buffered without bound. Deliberate simplification: back-pressure does not propagate to the previous hop's link (no coupling of circuits, no deadlock); an overfull link is closed and the circuits on it die.

Links are limited to 64 in total (reserved with a compare-and-set loop before a stream is accepted) and to 2 inbound links per remote peer. A quarter of the slots (`reservedOutboundLinks`, `maxLinks/4`) is reserved for outbound links, so idle inbound links can never prevent a relay from opening the link of its own EXTEND. An inbound link that carries no circuit is closed after 30 s (`inboundIdleWithoutCircuitTimeout`) unless it keeps delivering useful cells: only a cell processed on an existing circuit or an accepted CREATE counts as activity; PADDING and cells (RELAY, DESTROY, CREATED) for unknown circuit ids do not. A link can be reused in either direction (an inbound link carries an extend to the same peer; the remote peer id always comes from the Noise-authenticated connection, never from payload bytes), and concurrent dials to one peer share one dial. Link ids are random 64-bit values; the mapping from peer to link exists only inside the manager and is never logged. A Circuit Relay v2 connection may carry a link, but a CR-v2 relay is not an onion hop.

=== Onion keys: persistence and rotation

A relay's onion key lives 7 days; after 4 days a new key is generated and the old one stays valid as the `previous` key for the remaining 3 days (the overlap), so circuits built against a not-yet-republished descriptor still succeed. Persistence (`<data dir>/onion-relay.onionkeys`) is encrypted with the keystore passphrase: AES-256-GCM, key from Argon2id (64 MiB, 3 iterations), fresh random salt and nonce for every write, the header including the identity public key is the associated data, so the file is bound to its identity. The write is atomic (`0600` temp file, `fsync`, atomic move), the directory `0700`. Loading verifies every key binding; an expired key is dropped, a manipulated or foreign file, a wrong passphrase or out-of-range KDF parameters make the relay mode refuse to start (the message names the path, never any content). Without a keystore passphrase the keys exist only in memory (a warning is logged) and are lost on restart. The last used descriptor sequence number is persisted too; after a data loss the sequence restarts at the current epoch second, so peers do not reject new descriptors as replays.

=== Relay descriptor

`OnionRelayDescriptor` is a relay's signed, publicly enumerable advertisement: identity, its libp2p transport key (`IdentityBinding` plus an Ed25519 possession proof with its own domain tag, so an identity cannot point at a stranger's peer id), the `OnionKeyBinding`, a sequence number and a validity of at most 24 hours (never beyond the onion key). Fixed 379-byte encoding, no length field, exact length checked first, a reserved family byte that must be zero (families are not part of this wave). `PeerCapability` gets no new bit, because v0.12.0 readers reject unknown bits; the descriptor alone signals the relay property.

* *Gossip* topic `LapisNet:onion-relay-descriptor-gossip:v1`: size check, decoding and an index pre-check (duplicates, replays and stale sequence numbers are `IGNORE` and cost no budget), then a per-author (6/min) and a global (60/min) rate limit whose excess is `IGNORE` (an honest forwarder must not be penalised), then full verification; invalid is `REJECT`, duplicates, replays and capacity refusals are `IGNORE`. Logging has counters only: no peer id, no identity, no bytes.
* *Index* (`OnionRelayDescriptorIndex`): one current descriptor per identity, strictly increasing sequence numbers, high-water marks that survive eviction (bounded LRU), equivocation at the same sequence is ignored, capacity 1024; a full index never evicts a valid entry for a stranger.
* *Known limitation (Sybil):* identities are free, so an attacker can sign valid descriptors with fresh keys. About 61 such descriptors per minute exhaust the global budget at every node (honest new or rotated descriptors are then ignored), and about 17 minutes of this fill the index to its capacity of 1024, after which the attacker holds it permanently by refreshing, because a full index never evicts and updates of tracked identities are always accepted. Descriptors with random signatures only exhaust the budget at direct neighbours (REJECT is not forwarded, gossip scoring penalises the sender). Admission is not bound to a cost yet; planned mitigations are a cost per index slot (known peer record or DHT presence, proof of work, or Madli weight) or a fair per-identity or per-mesh-peer budget instead of one global bucket.
* *DHT fallback:* the descriptor is an optional part (flag `0x08`) of the node's existing directory value, because one Ed25519 key has exactly one IPNS name. It is verified with the same function as on the gossip path and must belong to the value's identity and binding. Additionally relays announce themselves as providers under the fixed key `LapisNet:onion-relays:v1` and `discoverOnionRelays` resolves the providers; this key is public, its provider set is eclipse-prone, and a result is a hint only (every descriptor is fully verified). If peer record, prekey bundle and descriptor together exceed the value limit, outbox entries are dropped first, never the descriptor or the peer record.

=== Relay mode

`--onion-relay=true` (default off). Off: no protocol handler is registered (a dial of `/lapis/onion/1.0.0` fails multistream negotiation), no onion key is created, no descriptor is published, no key file exists. The descriptor index and its gossip are attached on every CLI node (bounded, read-mostly) so a node can later choose relays. On: the node answers CREATE/EXTEND, publishes its descriptor immediately, re-announces it every 6 hours (and at once after a rotation) and checks the rotation every hour; the DHT copy is written by the node's single IPNS writer (`HeadlessSelfPublisher`), which receives the descriptor, because a second writer would overwrite the peer record.

An EXTEND is executed only towards a relay that has a verified descriptor in the local index and never with a client-supplied link specifier (a non-empty specifier is refused in this wave), so an extend cannot make a relay connect to an arbitrary host. There is no exit service: DATA delivered to a relay is answered with END. A relay's own link cap, circuit cap (1024), creation rates and cell rates apply; pending extends are bounded and time out after 10 seconds.

The relay quality tracker is local and bounded (1024 identities, day buckets, 7 days). It counts extend attempts, reachable links and early destroys with `PROTOCOL` or `AUTH_FAILED` per target relay. It is never published, there is no MadliGossip connection, and it cannot attribute a failure to a specific hop; turning it into Madli metrics is wave E.

=== Assumptions awaiting confirmation

These values and names were chosen by the implementation and must be confirmed:

* *Assumption, confirmation required:* the per-node switch in this wave is only `--onion-relay` (default off); the name and default of the later `--anonymity=on|off` switch remain open (wave E).
* *Assumption, confirmation required:* at least 3 hops in the production path (not part of this wave; the technical maximum is 5).
* *Assumption, confirmation required:* ChaCha20-Poly1305 stays the hop cipher.
* *Assumption, confirmation required:* time and limit constants: onion key 7 days, rotation after 4 days, descriptor TTL 24 hours, republish every 6 hours, 1024 circuits and 64 links per relay, 10 s handshake and extend timeouts.
* *Assumption, confirmation required:* flag `0x08` in the DHT value. A relay node's DHT value is unreadable for v0.12.0 nodes (they reject the whole value, including the peer record on the DHT path); gossip is unaffected and relay mode is opt-in. Not verified against real v0.12.0 nodes.
* *Assumption, confirmation required:* without a keystore passphrase the relay runs with in-memory keys (alternative: refuse to start).
* *Assumption, confirmation required:* every CLI node attaches the descriptor index and gossip (alternative: relay nodes only).
* *Assumption, confirmation required:* relay discovery through the public provider key `LapisNet:onion-relays:v1` is included in the CLI node (alternative: postpone to wave E).

=== Honest limits of wave B

* A relay's IP address and identity are publicly linked by its descriptor; the descriptor makes the set of relays enumerable. That is inherent to a directory-based design and is not hidden.
* The rendezvous provider key is eclipse-prone; its provider list is capped at 8 per lookup.
* Quality values are local and link-level only.
* Not verified: any real NAT or internet topology, anything against real v0.12.0 nodes, any external cryptographic review. Multi-node tests run on loopback.
* Zeroisation of key material covers the arrays this code owns, not copies the JVM or BouncyCastle may hold.
* No anonymity and no user traffic: the client-side circuit API is marked `ExperimentalOnionApi` (an opt-in at compile time) and is meant for tests and diagnostics.

== What the foundation implements

`lapis-net-onion` (pure crypto and state, zero network dependencies): `OnionConstants`, `Cell`/`CellCodec` and the CREATE/CREATED/DESTROY body codecs, `RelayMessageCodec`/`ExtendPayloadCodec`, `OnionKeyBinding`, `NtorHandshake`, `CircuitHopKeys`, `HopCipher`, `OnionLayerCrypto` (`ClientCircuit`, `RelayHopState`), `OnionRelay` (a pure state machine returning actions) with `OnionRelayLimits`, and `ClientCircuitBuilder`. Resource bounds: CREATE rate limits per link and globally before any X25519 work, hard circuit caps reserved with a compare-and-set loop, no per-circuit queues, a per-circuit cell rate, a lifetime sweep, bounded pending extends. Roughly 1 KiB of memory per circuit.

Honest limits: zeroisation covers the arrays this code owns, not copies the JVM or BouncyCastle may hold; the handshake test vector is self-generated; no external review.

`lapis-net-onion-wire` (wave B, unreleased) adds the network side described above: `OnionLinkProtocol`/`OnionLinkManager`, `OnionRelayService`, `OnionKeyStore`, `OnionRelayQualityTracker`, `OnionWire` and the diagnostic `OnionCircuitClient`.

== Wave plan

[cols="1,5"]
|===
| A | This wave: threat model, design, `lapis-net-onion` foundation.
| B | Done (unreleased): wire integration: libp2p stream `/lapis/onion/1.0.0`, link management, onion key persistence and rotation (encrypted at rest), relay descriptor publication in the directory, opt-in relay mode. No user traffic, no path selection.
| C | Receiver side: decide the rendezvous design, introduction points and rendezvous point.
| D | Directory anonymity: `PeerRecord` without addresses in anonymity mode, introduction points instead of addresses.
| E | Path selection (Madli weighting, diversity, guards) and policy (`--anonymity`, DCUtR off on anonymous paths), wiring into `LapisNode`, the browser and the CLI.
| F | DM online and offline over circuits; mail delivery moved off the per-recipient topic.
| G | Call signals over circuits, with an honest note on the media path.
| H | Padding and timing protection (DROP cell schedule), circuit pre-building.
| I | Multi-node tests, Sybil simulation, external cryptographic review recommended.
| J (later) | GossipSub, DHT and content fetches.
|===
