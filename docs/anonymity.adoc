= Traffic anonymisation: design, foundation, wire integration, receiver side, directory, path policy, direct messages, mail, call signals, padding and timing (waves V0.10.0-A to V0.10.0-J3, Q20, Q21)
:toc:

== Status

*Release `v0.13.0` contains every wave described in this document (V0.10.0-A to V0.10.0-J3, Q20, Q21 and Q21-Token, plus the fixes listed in the roadmap). Anonymity mode (`--anonymity=on|off`) stays experimental, incomplete and off by default. No external cryptographic or anonymity review has taken place; everything was verified on loopback only. The remaining leaks are listed in <<leak-inventory-j3>> and in the leak inventory of <<attachments-over-circuits>>.*

*Wave J1a (transport hygiene in anonymity mode, released in `v0.13.0`; first part of wave J) changes what a node in anonymity mode shows on its direct connections. Its libp2p transport key is fresh per run and never stored, so no connection shows the PeerId bound to the identity; mDNS is off; the node neither serves nor queries the DHT and content (Bitswap and Kademlia are not registered, the DHT fallback, auto-relay and relay-reliability publishing are off and refused when set explicitly); GossipSub only receives and forwards on a fixed topic allowlist and publishes nothing of its own; the tombstone of a switch from normal to anonymity mode goes through a circuit and a relay publishes it; posting, votes, trust grants, self-links, LTR records and manual connections are refused with 409. *Wave J1b (connection confinement and the relay directory snapshot, released in `v0.13.0`; second part of wave J)* confines a node in anonymity mode to its two guards: it does not listen at all, every dial outside {primary, backup} is refused before TCP starts, and its bootstrap peers are allowed and contacted only while it has no usable relay view or no live guard connection. It learns relays (descriptor plus peer record) from the snapshot protocol `/lapis/onion-relay-directory/1.0.0`, which every node in normal mode serves. The guards and bootstrap peers see its address. *Wave J2 (lookups through circuits, released in `v0.13.0`; third part of wave J)* lets the node fetch content blocks and IPNS records it does not hold through circuits to relays of the new role LOOKUP, which see what is asked but not who asks; everything is verified by hash or signature. The consumers followed in wave J3.* No external cryptographic or anonymity review has taken place. See <<gossip-dht-fetches>>.

*Wave I (multi-node tests, Sybil simulation, review package, released in `v0.13.0`) adds no feature for the user. It tests more of what exists on real loopback nodes (a late subscriber behind a node that already holds a service descriptor, failure of the primary guard, a mode switch by restart, mail and call signals after a restart with a new onion address), simulates the real path selection against an adversary that controls part of the relays, and prepares the external review in link:external-review.adoc[external-review.adoc]. It fixed one defect that the new test found: the repeat slots of the early republication sent the service descriptor byte-identically, which a node that already holds it ignores and does not forward; they now send a fresh signed version (see <<early-republication>>). The external review itself has not taken place.* See <<wave-i>>.

*Wave H (padding and timing protection, released in `v0.13.0`) makes the traffic of a node in anonymity mode harder to read for a local observer of its guard connection: message sizes are padded to size classes, cover cells are sent towards the guard on a randomised schedule, outgoing cells leave in time slices, and circuits are built in advance. It makes observation by a local observer or a single relay harder; it is NOT protection against a global passive observer, and it does not hide that and roughly when the node is active.* See <<padding-and-timing>>.

*Wave G (call signals over circuits, released in `v0.13.0`) carries the signalling of a call (INVITE, ACCEPT, REJECT, HANGUP) over circuits for a node in anonymity mode, through the same rendezvous stream and the same Double Ratchet session as direct messages. The media path is NOT anonymised and can not be: WebRTC connects the two parties directly, so every call reveals your IP address to the other party and to network observers. Calls are therefore OFF in anonymity mode by default; `--anonymity-allow-call-media=true` turns them on, with a confirmation before every single call. Call signals are online only (never a mailbox), and both ends must be in anonymity mode.* See <<call-signals-over-circuits>>.

*Wave F2 (mail over circuits, released in `v0.13.0`) carries mail over circuits for a node in anonymity mode. A mail with its attachments travels as one bundle over a rendezvous stream to the recipient's onion service; a small mail without attachments that cannot be delivered online is sealed to the recipient and announced on the same shared topic as offline direct messages. The node no longer subscribes to or publishes on a per-recipient inbox topic, leaves no DHT pointer and fetches nothing over Nabu/Bitswap for mail. Call media, GossipSub in general, the DHT and other content fetches are unchanged: they still show identity and IP address, and the libp2p transport key is still the identity key. Call signalling is not available in anonymity mode. Both ends must be in anonymity mode; there is no fallback to a direct connection.* See <<mail-over-circuits>>.

*Wave F1 (direct messages over circuits, released in `v0.13.0`) carries direct messages, online and offline, over circuits for a node in anonymity mode. The sender reaches the recipient's onion service through a rendezvous point; an undeliverable message is sealed to the recipient and announced by relays on one shared topic. Mail, call media, GossipSub, the DHT and content fetches are unchanged: they still show identity and IP address, and the libp2p transport key is still the identity key. Call signalling is not available in anonymity mode (refused before any ratchet step; superseded by wave G, see <<call-signals-over-circuits>>). The recipient learns the sender's identity. Both sides must be in anonymity mode; there is no fallback to a direct connection and no attachments.* See <<dm-over-circuits>>.

*Wave E (path selection and policy, released in `v0.13.0`) adds the first thing a user can switch on: `--anonymity=on`. A node in that mode chooses relays with persistent guards and network diversity, builds circuits under a build policy, and publishes its directory entry only through those circuits. It does not make the node anonymous: direct messages, mail and call signalling still use direct connections and show the IP address, and the libp2p transport key is still the identity key. The option is experimental, off by default, and every start says so.* See <<path-policy>>.

*Wave D (directory anonymity, released in `v0.13.0`) lets a node in directory anonymity mode publish an address-free directory entry through a circuit, and keeps every address-bearing publication of its own off the network. It does not make the node anonymous: the libp2p transport key is still the identity key, so every direct connection of the node shows identity and IP together. No user traffic is anonymised and no anonymity is offered.* See <<directory-anonymity>>.

*Wave C (receiver side and rendezvous, released in `v0.13.0`) adds introduction points, rendezvous points and onion-service descriptors on top of wave B. Still no user traffic uses any of it, there is no path selection, and nothing is anonymised.* See <<receiver-side>>.

*Wave B (wire integration, released in `v0.13.0`): the infrastructure is wired, no user traffic uses it, nothing is anonymised.* `lapis-net-onion` (wave A) holds the cryptographic foundation; the new module `lapis-net-onion-wire` (wave B) carries cells over a libp2p stream, keeps a relay's onion keys, publishes relay descriptors and, only with `--onion-relay=true`, lets a node act as a relay. There is no path selection, no application (DM, mail, call, browser) sends anything over a circuit, and the browser is not wired at all. IP addresses remain visible to peers and to the directory.

[WARNING]
====
*What this wave does not give you.* It provides no anonymity. It provides audited-by-our-own-pipeline building blocks (cell format, ntor-style handshake, onion layering, a relay state machine with resource limits) and a written threat model. Several leaks listed below must be closed before anyone may claim anonymity for DM, mail or call signalling. No external cryptographic review has taken place.
====

== Goals and non-goals

*Goal.* No network observer (ISP, local Wi-Fi, a single relay, the receiving peer) can link the IP address of a sender or receiver to a Lapis pseudonym, for direct messages, mail and call signalling. Pseudonymity itself is unchanged: identities stay stable keys.

*Non-goals.*

* Anonymous content. Content confidentiality stays with the existing end-to-end layers (X3DH/Double Ratchet, hybrid ECIES).
* Protection against a global passive observer who sees both ends of a circuit (traffic confirmation). Not defended, see the threat model.
* The media path of calls. WebRTC reveals IP addresses through ICE; signalling can be anonymised, media cannot without a separate design.
* Anonymous publication of own gossip (posts, votes, trust grants, LTR records, Madli vectors) and anonymous writes into the DHT. Wave J1a refuses them in anonymity mode; a later wave may add a relay role for them.
* Tor equivalence. This is a small, purpose-built onion design for a small network, with a much smaller anonymity set than Tor.

== Threat model

[cols="2,3,3", options="header"]
|===
| Adversary | Defended | Not defended / caveat

| Local observer (ISP, shared network)
| Sees only encrypted 1024-byte cells to a guard (link encryption: wave B). Cannot see destination identity or content.
| Sees that the user runs the protocol and roughly when it is active. Since wave H (default `--anonymity-padding=standard`) the length of a message is hidden inside its size class, the exact timing of sends is hidden in 50 ms slices with cover cells, and a circuit build is not tied to the first send of a message. The size class, coarse activity periods, the return direction and the number of mailbox items still leak (see <<padding-and-timing>>). With `--anonymity-padding=off` none of this applies.

| A single malicious relay
| Learns at most its two neighbours and its own position (hop index). Cannot read or undetectably alter cell content.
| A guard sees the client IP; an exit sees the next hop. A relay can destroy circuits (DoS) and observe timing.

| Colluding relays or Sybil identities
| Per-hop authentication and per-hop regenerated filler remove the classic tagging channel. Path selection will weigh Madli reputation and enforce diversity (wave E).
| If one adversary controls both guard and exit of a circuit it can correlate by timing and volume. Madli reputation is a weak Sybil defence (identities are free); it is a weight, never a gate.

| Malicious receiver
| Sees a rendezvous or mailbox, never the sender IP (once wave C/F land).
| Can correlate by timing with its own observations.

| Global passive observer
| *Not defended.*
| End-to-end timing and volume correlation is out of scope.
|===

== Known leaks today

These existed before waves D and E; the current leaks are listed in <<leak-inventory-j3>>. All of them must be closed before any anonymity claim.

. *`PeerRecord` publishes addresses.* The signed directory record binds an identity to its current network addresses. This is exactly the pseudonym-to-IP link to be hidden. In anonymity mode a node must publish introduction points, not addresses. Directory side addressed in wave D (see <<directory-anonymity>>); the transport-level link between identity and IP remains until wave E.
. *Mail uses one GossipSub topic per recipient.* Subscribing to your own topic links your identity and IP for your mesh neighbours. Mail delivery has to move off the per-recipient topic: store and fetch through circuits (wave F2). Wave F1 does not change mail; it removes the same leak for direct messages (a node in anonymity mode does not subscribe to its own direct-message mailbox topic). *Closed for a node in anonymity mode by wave F2:* it subscribes to no inbox topic, publishes on none, leaves no DHT pointer and fetches nothing over Nabu/Bitswap for mail (see <<mail-over-circuits>>); still present in the normal mode.
. *Gossip timing.* Message publication times and mesh membership leak.
. *WebRTC media.* ICE exposes IPs to the peer. Not closable by this design: since wave G calls are off in anonymity mode by default, and with `--anonymity-allow-call-media=true` the media connects directly and shows the IP address to the other party and to network observers (see <<call-signals-over-circuits>>).
. *DHT provider records of the offline mailbox path* tell DHT peers who looks for whom. Closed for direct messages in anonymity mode by wave F1 (no pointer, no Nabu blob, no IPNS value); closed for mail in anonymity mode by wave F2 as well; still present for nodes in the normal mode.
. *Small anonymity set.* Few relays mean weak anonymity regardless of cryptography.
. *Relay position.* A relay learns its hop index from the CREATE; with the default of three hops that equals Tor's exposure of position, stated here deliberately.
. *Correlation by provoked teardown.* Any party on a path can destroy a circuit and correlate the effect elsewhere (DoS-based correlation). Not prevented.

=== Cell format

Every cell is exactly 1024 bytes: `circuitId(4) | command(1) | body(1019)`. Commands: PADDING (circuit id 0 only), CREATE, CREATED, RELAY, DESTROY. Unused body space is filled with random bytes, not zeros, so empty fields reveal nothing. The parser has no length field: the input size is compared to 1024 before anything is copied, so no allocation depends on attacker data. Unknown commands and a circuit id of 0 on a non-PADDING cell are rejected.

=== Circuit length

Default 3 hops, technical maximum 5 (`MAX_HOPS`). The library accepts 1 to 5 (1 and 2 for tests); a policy minimum of 3 for the production path is enforced when the module is wired (waves B and E). A relay message addressed to hop 3 carries up to 963 bytes of data (1019 - 3*17 - 5 header bytes).

=== Handshake (ntor over X25519)

The handshake follows the published ntor construction (Goldberg, Stebila, Ustaoglu) and is reimplemented from that description; no code was copied. Wire shapes and labels are Lapis-specific, so the pinned test vector is a self-generated regression vector (cross-checked once against an independent script), not an external known-answer test.

....
secret_input = X25519(y,X) | X25519(b,X) | ID | B | X | Y | PROTOID      (client: X25519(x,Y) | X25519(x,B))
KEY_SEED     = HMAC-SHA256(PROTOID:key_extract, secret_input)
verify       = HMAC-SHA256(PROTOID:verify,      secret_input)
AUTH         = HMAC-SHA256(PROTOID:mac, verify | ID | B | Y | X | PROTOID | "Server")
Kf | Kb      = HKDF-SHA256(ikm = KEY_SEED, salt = empty, info = PROTOID:expand, L = 64)
....

`ID` is the SHA-256 digest of the relay identity key, `B` the relay's onion key, `PROTOID` is `LapisNet:ntor-x25519-sha256:v1`. The client compares AUTH in constant time. Ephemerals x and y and every intermediate secret are overwritten after use; this gives forward secrecy for the circuit keys against a later compromise of `B`. The relay's *onion key* is separate from the X3DH encryption key and is bound to the identity by a signed `OnionKeyBinding` with its own domain tag and an expiry; it is meant to be rotated.

Deviation from the plain ntor message: CREATE and EXTEND carry a `hopIndex` byte (the relay's 1-based position), set by the client. It selects the layer size and is bound into every AEAD's associated data; a wrong value only breaks the client's own circuit.

=== Onion layers and the anti-tagging rule

Each hop holds two keys. A layer for hop i has size `1019 - (i-1)*17` (16 tag bytes plus one type byte per layer). Layers are sealed with ChaCha20-Poly1305 (RFC 8439) under an *implicit* nonce `directionTag(4) | counter(8)`; the counter is never transmitted. Replay, duplication, drop and reordering all desynchronise the counter, fail the tag and destroy the circuit. There is deliberately no replay window: the transport stream is reliable and ordered, so any deviation is an attack. After one failed open the cipher is poisoned.

*Why ChaCha20-Poly1305 and not AES-256-GCM (which the rest of the project uses).* It is constant-time in software without AES-NI, it comes from the BouncyCastle lightweight API that is already a dependency, and key material can be held in arrays this code zeroises (a JCE `SecretKeySpec` cannot be reliably wiped). If uniformity with AES-GCM is preferred, the change is confined to one class (`HopCipher`).

*Anti-tagging rule.* Every byte that is not covered by the authentication tag of the receiving hop is discarded and regenerated by that hop with fresh random bytes. Unauthenticated filler that an honest hop forwarded unchanged would be a covert channel through which two colluding, non-adjacent relays (guard and exit) could mark a cell. With the rule, every bit that is ever evaluated is authenticated per hop; a flipped bit in an authenticated region is detected at the next honest hop (forward) or at the client (backward). What remains is destroying a circuit on purpose and correlating the teardown, listed above as not defended.

=== Lifetime, rotation, padding

A circuit lives at most 10 minutes (relay-enforced by a sweep) or 2^32 cells per direction, whichever comes first; new destinations get new circuits (policy, wave E). Part 1 has a fixed cell size and a `DROP` relay message. Padding and timing protection against a local observer is wave H (<<padding-and-timing>>); an observer who sees both ends of a circuit is not defended. A warm circuit (pre-built, wave H) serves exactly one use; there is still no circuit reuse anywhere.

=== Link encryption

The libp2p Noise session protects the link only: cells travel over a dedicated stream `/lapis/onion/1.0.0` (wave B, see below), hiding circuit ids and commands from an ISP. The onion layers themselves are ntor plus AEAD, independent of Noise.

    transition(source = building, target = building) { trigger = "EXTENDED"; guard = "[hops < path length]" }
    transition(source = building, target = open) { trigger = "EXTENDED"; guard = "[all hops done]" }
    transition(source = building, target = closed) { trigger = "AUTH failure"; effect = "zeroise keys" }
    transition(source = open, target = closed) { trigger = "tag failure, DESTROY, lifetime, cell limit"; effect = "zeroise keys" }
}

== Relay selection (design, wave E)

* *Madli* reputation weights selection; it is never a hard gate and the minimum weight is above zero, so new relays can be chosen. Honest assessment: in a Sybil scenario Madli helps against lazy or unreliable relays, but it does not stop an adversary that creates many reputable-looking identities.
* *Diversity:* never twice the same Lapis identity in a circuit, no two hops from the same IPv4 /16 (IPv6 /48), no two hops from the same operator-declared relay family (a signed field to be defined in a later wave). Optionally no two hops with a direct Veritas trust edge between them; this option is not decided.
* *Guards:* a small, long-lived guard set (1 to 2, rotated over weeks) against the predecessor attack.
* Path-level duplicate checks live in the client (`ClientCircuitBuilder`): relays do not know their neighbours' identities. The relay state machine only refuses to extend to itself and bounds chain depth by `MAX_HOPS`.
* *Status after wave E:* implemented as described in <<path-policy>>. The relay family check exists but is inactive (the descriptor has no family field; the count byte must be zero), IPv6 diversity uses the /48 (changed from /32 on 2026-10-24), and the Veritas edge check exists as an internal switch with no option. Madli weights apply only to the middle hops and the endpoints; the guard is drawn once with the same weights and then persists.
* A failed or aborted client-side build is not silent for the relays: `BuilderStep.Failed` carries a DESTROY cell (absent only when the peer itself sent DESTROY) and `ClientCircuitBuilder.abort()` returns one; the host must send it to the first hop, otherwise the relays keep the circuit until the lifetime sweep. PADDING and cells of other circuits on the guard link yield `BuilderStep.Ignored`.

== Relationship to Circuit Relay v2 and DCUtR

Circuit Relay v2 and DCUtR serve reachability (NAT). Onion circuits serve unobservability. A Circuit Relay v2 relay sees both endpoints and is therefore not an anonymity hop. DCUtR deliberately creates direct IP connections and must be *off* on anonymous paths (policy for wave E). Onion relays may themselves be reached through Circuit Relay v2.

== Receiver side and rendezvous (wave V0.10.0-C, released in `v0.13.0`)

*Decision (2026-10-22): option (a), introduction points plus a rendezvous point (the Tor v3 pattern), for live traffic.* The mailbox variant (b) for offline delivery stays wave F; option (c), a fixed mailbox relay per receiver, is rejected because a stable relay learns the receiver's identity. This wave builds the receiver side as infrastructure. It is not wired into `LapisNode`, the CLI, DM, mail, call or the browser, and an onion address is not yet linked to a Lapis identity: that mapping and its distribution to contacts belong to waves D and F. Tests pass the address explicitly.

=== Onion address and why there is no blinding

An onion service has its own Ed25519 *service key*, deliberately neither the Lapis identity (secp256k1) nor the libp2p transport key. The address is `base32(serviceKey(32) | checksum(2) | version(1))`, 56 lowercase characters, with `checksum = SHA-256(domainSeparatedDigest("LapisNet:onion-address-checksum:v1", key, version))[0..2]`. The id used in the end-to-end handshake is `domainSeparatedDigest("LapisNet:onion-service-id:v1", key)`.

*Blinding as in Tor v3 was evaluated and rejected.* Ed25519 key blinding needs point arithmetic on the curve that BouncyCastle does not expose as an API; implementing it ourselves would be home-made cryptography, which this project does not do. The consequence is stated plainly: the descriptor is signed in the clear with the service key, so *onion addresses and their introduction points are enumerable by anyone who reads the public descriptor index, and descriptors of one service are linkable over time*. The descriptor contains no Lapis identity, no peer id and no network address.

=== Protocol

Ten relay commands (codes 6 to 15) travel inside ordinary onion cells; every body has a fixed length and no length field, and the exact length is checked first.

[cols="1,1,2,1"]
|===
| Command | Direction | Body | Bytes

| `ESTABLISH_INTRO` | receiver to introduction point | `version \| authKey(32) \| notValidAfter(8) \| establishSeq(8) \| signature(64)` | 113
| `INTRO_ESTABLISHED` | introduction point to receiver | `status(1)` | 1
| `INTRODUCE1` / `INTRODUCE2` | sender to introduction point / introduction point to receiver (same bytes) | `version \| authKey(32) \| hpkeEnc(32) \| hpkeCiphertext(192+16)` | 273
| `INTRODUCE_ACK` | introduction point to sender | `status(1)`: 0 forwarded, 1 unknown or replay, 2 rate limited, 3 malformed | 1
| `ESTABLISH_RENDEZVOUS` | sender to rendezvous point | `cookie(20)` | 20
| `RENDEZVOUS_ESTABLISHED` | rendezvous point to sender | `status(1)` | 1
| `RENDEZVOUS1` | receiver to rendezvous point | `cookie(20) \| Y(32) \| AUTH(32)` | 84
| `RENDEZVOUS2` | rendezvous point to sender | `Y(32) \| AUTH(32)` | 64
| `RENDEZVOUS_DATA` | both ways over the splice | end-to-end blob | 929
|===

The HPKE plaintext of an introduction is `rendezvousRelayId(32) | rendezvousOnionKeyFingerprint(32) | cookie(20) | X(32) | random padding(76)`, 192 bytes.

. The receiver builds a circuit to each chosen introduction point (default 3) and sends `ESTABLISH_INTRO`. It signs with a fresh *auth key per introduction point*; the signature covers the introduction point's relay-id digest, the auth key, a validity time and an `establishSeq`. The introduction point checks its own digest (no cross-relay replay), the validity (at most one hour ahead) and that `establishSeq` is larger than any earlier registration of the same auth key (no rollback). A larger `establishSeq` replaces the old registration and closes the old circuit, which is how the receiver refreshes a circuit make-before-break. Only after all introduction points answered does the receiver sign and publish its descriptor.
. The sender fetches the descriptor (local gossip index, or the DHT), verifies it completely, builds a circuit to a rendezvous point of its own choosing and sends a random 160-bit cookie. It then builds a circuit to one introduction point and sends `INTRODUCE1`; the introduction point checks role, rate and a replay cache, forwards the body as `INTRODUCE2`, and acknowledges. The sender then closes that circuit.
. The receiver rate-limits, opens the HPKE ciphertext, checks its own replay cache, resolves the rendezvous point *only* through its local relay index (an unknown relay or a fingerprint mismatch is dropped silently, so there is no oracle), answers the end-to-end handshake, builds a circuit to the rendezvous point and sends `RENDEZVOUS1`.
. The rendezvous point finds the cookie (single use), joins the two circuits and sends `RENDEZVOUS2` to the sender, who completes the handshake and checks `AUTH`. From then on only `RENDEZVOUS_DATA` flows.

A relay accepts a role message only at the *last hop* of a circuit that has no role yet; `EXTEND`, `DATA` and `END` on a role circuit, a second role, a second `INTRODUCE1`, a self-splice and every reply-type command arriving as a request are protocol errors that destroy the circuit.

=== Cryptography (established building blocks only)

* *End-to-end handshake:* the existing ntor construction with its own protocol id `LapisNet:hs-ntor-x25519-sha256:v1`. The receiver plays the server with `ID = serviceId` and `B = ` the X25519 encryption key from the signed descriptor; `AUTH` therefore proves to the sender that the party that read the introduction holds the key listed in the descriptor the service key signed. Forward secrecy comes from the two ephemerals. `NtorHandshake` was parametrised by labels; the relay labels and the pinned regression vector are unchanged.
* *Introduction:* HPKE (RFC 9180), base mode, `DHKEM(X25519, HKDF-SHA256)`, `HKDF-SHA256`, ChaCha20-Poly1305, over BouncyCastle; `info` binds the service id and the auth key, `aad` the version and the auth key. There is *no forward secrecy of the introduction against compromise of the encryption key during its lifetime* (the same holds in Tor); the key rotates every 24 hours and the previous one stays accepted until the old descriptor expires. The same X25519 key serves both HPKE and the ntor handshake, separated by distinct labels.
* *End-to-end layer:* two `HopCipher`s (ChaCha20-Poly1305, implicit counter nonce, no replay window, poisoned after one failure) with their own AAD label `LapisNet:hs-e2e:v1`. Every blob is exactly 929 bytes (plaintext `type | length | data | random padding`, so at most *910 bytes* of application data); the rendezvous point only ever sees equal-sized ciphertext and cannot alter a bit without the session dying.

=== Descriptor

`ver(1) | serviceKey(32) | seq(8) | notValidAfter(8) | encKey(32) | count(1) | count x [relay onion key binding(137) | authKey(32)] | signature(64)`: exactly `146 + 169 * count` bytes, at most 653, one to three introduction points. Verification checks the window (`now <= notValidAfter <= now + 6 h + 5 min`), that the descriptor never outlives an introduction relay's onion key binding, every binding signature, pairwise distinct relays and auth keys, and the Ed25519 signature. Three places handle it: `OnionServiceDescriptorIndex` (strictly increasing sequence, high-water marks that survive eviction, equivocation ignored, capacity 4096, never evicts a valid entry for a stranger), `OnionServiceDescriptorGossip` (topic `LapisNet:onion-service-descriptor-gossip:v1`; size, decode, index pre-check without spending budget, then per-author, per-peer and global rate limits whose excess is `IGNORE`, then verification) and `OnionServiceDht` (an IPNS record under the *service key's own name*, never in the node's directory value, so there is no flag and no link to a peer id; the validator requires publisher = service key = address). The DHT path is an API only and is not wired into the node.

=== Limits and timers

Relay side (`OnionRelayLimits`, validated): 256 introduction points in total and 32 per previous link, 10 `INTRODUCE1` per second per introduction point (checked before any other work), replay cache of 8192 body digests, 512 waiting cookies in total and 64 per link, wait timeout 60 s (shorter than the circuit lifetime), 512 spliced pairs. Receiver side (`OnionServiceConfig`): 3 introduction points, descriptor TTL 3 h (at most 6 h) republished hourly (plus, when published through a circuit, the early retry schedule of the descriptor republisher, see "Early republication"), intro refresh after 8 minutes (relays sweep circuits after 10), build timeout 30 s, establish timeout 15 s, exponential backoff 1 s to 60 s with jitter and a replacement relay after 5 failures, 16 concurrent pending rendezvous builds (before acceptance) and at most 256 open accepted sessions (`maxOpenSessions`; further accepted rendezvous are closed at once), 5 `INTRODUCE2` per second, replay cache of 8192 entries per encryption key which *fails closed* when full (and so can be filled by anyone who can encrypt to the public key: an acknowledged denial-of-service limit, bounded by the rate limits). A full cache forces an early encryption key rotation and republication at the next tick, so the service recovers without waiting for the regular rotation every 24 hours; clients holding an older descriptor are rejected until they have fetched the new one. Sender side (`RendezvousClientConfig`): 30 s to build, 15 s to establish, 15 s for the acknowledgement, 30 s for `RENDEZVOUS2`, 60 s overall; the next introduction point is tried at once (no backoff between introduction attempts). *A rendezvous session lives at most as long as the relays' circuit lifetime (10 minutes); reconnecting is the caller's job (waves E and F).*

[[rendezvous-retry]]
*Client-side rendezvous retry (fix wave "rendezvous after guard failover", released in `v0.13.0`).* `AnonymityRuntime.connectToService` retries a rendezvous *once* with a different rendezvous point, after a random wait of 2 to 6 seconds (`SecureRandom`), and only after `TIMEOUT` in `AWAIT_RENDEZVOUS2` or a `RENDEZVOUS_POINT` failure (`RendezvousFailedException` carries reason, state and the number of introduction attempts, with the unchanged message). Reason: a service whose effective guard equals the client's rendezvous point can not build its rendezvous circuit while no other persisted guard is usable, and drops the rendezvous silently (see the guard-conflict oracle under <<path-policy>>); the client only sees the timeout. The second attempt excludes the first rendezvous point and never uses a warm circuit, so the same relay can not be chosen twice in a row. There is no retry after a clear answer of the service (`NO_INTRODUCTION`, `AUTHENTICATION`, `INVALID_DESCRIPTOR`), after a timeout in an earlier state, or after a refusal of the circuit governor (`RATE_LIMITED`, `POOL_FULL`, `LOCKED`; a refused rendezvous circuit ends in `RENDEZVOUS_POINT` like a failed build, but the exception carries the refusal as its `cause` and `refusedByGovernor` is `true`, which the retry checks), and every retry goes through the same governor, so the protection against build storms is unchanged. The `timeout` argument applies to each attempt: the call completes after at most `2 × timeout + 6 s` (`AnonymityRuntime.connectWaitBound`; the DM and mail ports report it through `connectWaitBound`, the DM transport never waits beyond the send deadline). The circuits of the first attempt are destroyed before the retry. Fingerprint trade-off: per failed rendezvous the client's guard sees at most two additional builds and an introduction point at most two `INTRODUCE1` about 30 to 50 seconds apart; the pattern (fixed bound of one, random jitter) is the same for every client and every target, so it is not a per-user trait. An adversary that delays introduction acknowledgements at most doubles the client's waiting time. The count of retries is in `AnonymityDiagnostics.rendezvousRetries` (a number, no target).

=== Assumptions awaiting confirmation (wave C)

* *Assumption, confirmation required:* a dedicated service key per onion service and no link to the Lapis identity in this wave.
* *Assumption, confirmation required:* no Tor-style key blinding (see above).
* *Assumption, confirmation required:* HPKE for the introduction rather than a hs-ntor-style composition.
* *Assumption, confirmation required:* the descriptor index and gossip topic are attached on every node, like the relay descriptor index. Consequence: the Sybil limit described below applies on every node.
* *Assumption, confirmation required:* `ESTABLISH_INTRO` is signed by a per-introduction-point auth key (the Tor pattern), not directly by the service key.
* *Assumption, confirmation required:* all constants in the previous section.
* *Assumption, confirmation required:* sessions of at most 10 minutes; the alternative is a longer lifetime for spliced circuits on every hop.
* *Assumption, confirmation required:* no proof of work against introduction floods.

=== Honest limits of wave C

* *No user traffic is anonymised and no anonymity is offered.* The hidden-service API is `ExperimentalOnionApi`, takes its paths from an injected provider and chooses nothing itself.
* Sybil relays, free choice of introduction relays by the receiver (no path selection yet), the predecessor attack without guards, a small anonymity set and a global passive observer are as described in the threat model; wave C changes none of them.
* Onion addresses and their introduction points are enumerable; descriptors are linkable over time (no blinding).
* Publishing from the service's own node (gossip, DHT) shows that node's IP to its gossip neighbours and to the DHT peers that store or serve the record, together with the onion address. Wave D adds publication through circuits, see <<directory-anonymity>>; it is opt-in and not used by default.
* Teardown correlation still applies: an adversary that provokes a teardown on one half can watch the other half end.
* No forward secrecy for the introduction content against the encryption key within its lifetime.
* An introduction flood is only slowed by rates, not by a cost; the receiver's replay cache can be filled. A full cache forces an early key rotation and republication (at 5 `INTRODUCE2` per second at most about every 27 minutes), during which clients with an older descriptor fail until they have fetched a new one.
* *Known limitation (Sybil, service descriptor index):* a valid service descriptor costs nothing (a fresh Ed25519 service key plus one to three publicly gossiped relay onion key bindings, reusable, and a fresh auth key per entry). About 61 such descriptors per minute exhaust the single global budget (60/min) at every node, so honest new or updated service descriptors are ignored and stop spreading. After about 68 minutes the index is full (capacity 4096) and every new honest service is refused with `CAPACITY`; the attacker keeps the slots by republishing its own keys with a higher sequence number, because a full index never evicts a valid entry and updates of tracked keys are always accepted. The per-author bucket does not help against fresh keys. Gossip discovery of new onion services can thus be stopped network-wide; the DHT path is an API only and not yet wired up. Same class of limit as for the relay descriptor index above. Planned mitigations: a cost per index slot (proof of work, known peer record or Madli weight) or a fair per-mesh-peer budget instead of one global bucket. Not mitigated in wave C.
* Not verified: real NATs, interoperability with v0.12.0, an external cryptographic review, behaviour under real load, interoperability of the HPKE path with other implementations. Multi-node tests run on loopback.

[[directory-anonymity]]
== Directory anonymity (wave V0.10.0-D, released in `v0.13.0`)

Wave D closes the *directory* side of the pseudonym-to-IP link: what a node publishes about itself. It does not close the *transport* side (see the leak inventory, rows 8 to 14). Nothing here anonymises user traffic; nothing is wired into DM, mail or call. The mode is `DirectoryAnonymityMode` (`OFF` by default everywhere; wave E maps `--anonymity` onto it).

[WARNING]
====
*Wave D offers no anonymity.* A node in directory anonymity mode still opens direct libp2p connections whose peer ID is its identity key (`DualKeyIdentity.deriveLibp2pPrivKey`), so every peer it connects to sees identity and IP together. Only the *directory entries* stop carrying addresses, peer ID and binding. Decoupling the transport key is wave E.
====

=== The entry: `AnonymousPeerRecord`

A fixed 248-byte record, no length fields and no free-form field, therefore no tagging or covert channel:

[source]
----
"LNAP"(4) | version(1)=1 | flags(1) [bit0 REVOKED, rest 0] | identity(33, secp256k1)
| serviceKey(32, Ed25519) | servicePossessionProof(64, Ed25519) | capabilities(1) [DM, MAIL, CALL_SIGNAL, rest 0]
| prekeyBundleDigest(32, all zero = none) | sequenceNumber(8) | notValidAfter(8) | signature(64, secp256k1)
----

It contains *no network address, no libp2p peer ID and no `IdentityBinding`*. Two signatures: the outer secp256k1 signature of the identity (domain tag `LapisNet:anonymous-peer-record:v1`) and an Ed25519 possession proof of the *service key* over `identity || sequenceNumber` (tag `LapisNet:anonymous-peer-record-service-possession:v1`). The proof is the mutual binding: nobody can claim a foreign onion service for their identity, and because it is bound to the sequence number an old proof does not transplant into a newer entry. Unknown flag or capability bits are rejected, all-zero and all-ones keys and signatures are rejected, the validity window is `now <= notValidAfter <= now + 6 h + 300 s`. There is no `RELAY` capability: a relay is public by design. A *revocation* (flag bit 0) has no service key, proof, capabilities or digest and is the way back to normal mode.

*Why no transport peer ID in the entry.* The peer ID is the identity's Ed25519 key, publicly bound to the secp256k1 identity by every `PeerRecord`, `OnionRelayDescriptor` and DHT name published so far, and every direct connection shows peer ID and IP together. Putting it into the entry would create the link exactly where it is to be hidden. A rotating, identity-independent key would not help either, because in anonymity mode a sender never dials the recipient but goes through its introduction points. Decoupling the host key itself is wave E.

=== Index, topic and rates

`AnonymousPeerRecordIndex` follows `OnionServiceDescriptorIndex`: one record per identity, strictly rising sequence numbers, high-water marks (65,536) that survive eviction, equivocation ignored, capacity 16,384 identities, a full index refuses new identities and never evicts a valid entry (updates of known identities always pass: the same Sybil boundary as in wave C, documented and not solved). The gossip topic is `LapisNet:anonymous-peer-record-gossip:v1`, a topic of its own that v0.12.0 nodes never subscribe to; every node attaches it so senders can resolve. Validator order: exact size, decode, cheap index pre-check (no rate budget spent), rate limits per author identity (6/min), per forwarding peer (12/min) and global (60/min), whose excess is IGNORE, then full verification. Log lines carry a reason class only.

=== Downgrade protection between the two record types

Both record types use epoch milliseconds as sequence numbers, so they are comparable. `IdentitySupersession` (shared between `PeerRecordIndex` and `AnonymousPeerRecordIndex`, LRU-bounded, in memory) records the highest accepted sequence number of each type per identity:

* an accepted anonymous record removes the identity's address record (`seq <=`) and later address records with `seq <=` are refused, through gossip *and* through the DHT ingest (both go through `PeerRecordIndex.canAccept` and `add`);
* an accepted address record newer than the anonymous one hides the anonymous record (the way back); on a tie the anonymous record wins.

Identities without an anonymous record behave exactly as before. *Remaining window:* a node that saw neither the anonymous record nor the tombstone accepts an old address record until its TTL ends, at most 24 hours; an address that was published once stays visible to archives forever. Persisted address records are restored from local storage on restart before the floor is known again, until the anonymous record is seen again.

| outbox entries stay queued

| `DirectoryDht.publishTombstone`
| the only permitted DHT write: an address-free `PeerRecord` replaces the node's value once.
| sent from the own node

| `SelfRecordRepublisher`, `HeadlessSelfPublisher`
| new parameter `directoryMode` (default `OFF`, unchanged behaviour). With `ON` they publish nothing themselves and call an injected tick instead.
| wiring in wave E

| `OnionWire`
| `experimentalServiceHost` demands a publication channel that does not expose the origin; relay mode and anonymity mode are mutually exclusive.
| a relay descriptor publicly binds identity, peer ID and dialability
|===

=== Switching the mode

`DirectoryModeTransition` with a `DirectoryModeStore` (a small state file, `FileDirectoryModeStore`, written atomically; a missing or corrupt file means "no state": nothing is retired, so a normal node never publishes a revocation and a brand-new identity (or a damaged file) that starts directly in anonymity mode never publishes an identity-bound tombstone). *OFF to ON:* only after a persisted `OFF` state (the node demonstrably ran in normal mode), an address-free tombstone `PeerRecord` with a higher sequence number goes out once from the own node (gossip and `publishTombstone`), then the first anonymous record. A normal-mode start must therefore record `OFF` in the store (`nextSequence(OFF)`) for a later switch to retire its address entry. *Resolved in wave E:* every normal-mode start now persists `OFF` through the sequence source of the own record republisher (CLI and browser), so a later switch to anonymity mode sends the tombstone. A node upgraded from v0.12.0 has no state file; by the rule above it sends no tombstone on its first switch, and its address entries stay until their TTL ends (at most 24 hours). *ON to OFF:* an `AnonymousPeerRecord` revocation with a validity that covers every still-valid anonymous record (6 h), then a newer address record. Wave E wires this: `DirectoryModeRetirement.onNormalStart` builds the revocation at the first normal-mode start after an anonymity run and sends it from the own node through the anonymous-record gossip (the node is about to publish identity and address anyway, so the revocation links nothing new; in the browser the topic is attached only for this one send). OFF is persisted only after the revocation went out; if it could not be sent, the old state stays and the next start retries with a higher sequence number. Sequence numbers are `max(last + 1, nowMillis)` and persisted.

=== Publication through circuits

A node that gossips an entry itself shows its IP and peer ID to its mesh neighbours (the envelope of every GossipSub message is signed with the host key). Therefore the objects go through a circuit: relay command `DIRECTORY_PUBLISH` (client to last hop) with a body of exactly 720 bytes, `type(1) | length(2) | object(<= 717) | random padding`, and the acknowledgement `DIRECTORY_PUBLISHED` with a status byte (0 accepted, 1 invalid, 2 rate limited, 3 malformed, 4 unknown type). Types: anonymous record, onion service descriptor, prekey bundle (a bundle with up to 11 one-time prekeys fits). 720 bytes fit the relay message capacity at the maximum of five hops (929 bytes). The role is accepted only at the last hop of a circuit without another role; at most 4 publishes per circuit, 30 per minute per link and 120 per minute in total (`OnionRelayLimits`), checked before the body is looked at. A wrong body length or an overflowing length field destroys the circuit. The relay validates the object completely with the same functions as the gossip validators and then announces it, so the mesh sees the *relay* as publisher. A valid but already known or superseded object is acknowledged with the same status as a new one, so the status is no oracle on the relay's index.

`OnionDirectoryPublisher` builds the circuit over a path from the injected `OnionPathProvider`, sends one message, waits up to 15 s for the acknowledgement and closes the circuit. A failing relay is put on an exponential backoff and another relay is tried; there is *no fallback to publishing from the own node*. `AnonymousDirectoryPublisher` publishes the anonymous record and the reduced prekey bundle every 60 minutes (record TTL 3 h) and detects the mode switch. `AnonymousDirectory.resolve` answers `Hidden`, `HiddenDescriptorMissing`, `Direct`, `Revoked` or `Unknown`; no DM, mail or call code calls it yet. Resolving the descriptor from the DHT shows the DHT the sender's interest.

[[early-republication]]
=== Early republication

GossipSub hands no history to late subscribers, and there is no catch-up path for anonymous records, prekey bundles or service descriptors (in anonymity mode the lookup deliberately goes without the DHT). A directory object that is published before a receiver subscribed to its topic is therefore invisible to that receiver until the next republication, which used to be an hour away. Seen in practice: node A published, node B started afterwards, and B resolved A as `HiddenDescriptorMissing` (record known, service descriptor missing) for minutes.

After the *first successful* publication the objects are therefore republished on a short, bounded schedule (`DirectoryRepublishSchedule`): 5 s, 15 s, 45 s, 2 min and 5 min after the first success, each slot moved by a random fraction of up to 20 %, consecutive slots at least 3 s apart. The schedule is planned once per process lifetime; neither the hourly republication nor a change of the introduction points restarts it (a later descriptor is sent once, and the slots still open continue with it), so no recurring burst appears. Slots that fell due while the process was suspended are merged into one publication. A failed publication is retried after 5 s, 15 s and 45 s and then every minute (`AnonymousDirectoryPublisher`); a failed service descriptor send is retried after 5 s, 15 s, 45 s, 2 min and 5 min and then given up on (`ServiceDescriptorRepublisher`, the next descriptor of the host heals it).

* *Why not a "mesh ready" signal:* a readiness signal measures only the publisher's own neighbourhood (the relays, which are subscribed at once), never the receivers two hops away, and those are the ones that may subscribe late.
* *Record and prekey bundle go out as new versions* (new sequence numbers). A byte-identical bundle is declined by receivers (`DECLINED` becomes `Invalid`, a score penalty for the relaying peer), so a bundle is never repeated; because the record carries the bundle digest, it is a new version too. The publisher keeps at most 4 versions per minute, below the receivers' per-author rate of 6 per minute (`PublicationRateGuard`; a conformance test drives the real validators along the worst-case timeline).
* *The service descriptor goes out as a fresh version at the repeat slots (wave I):* a byte-identical repetition is free for receivers (the validator's pre-check ignores it before any rate budget is touched), but for the same reason it is not forwarded: a node that already holds the descriptor answers `Ignore`, and GossipSub forwards neither an ignored message nor puts it into its message cache. A repeat therefore reached only direct gossip neighbours of the announcing relay; a late subscriber that is meshed only with nodes that already hold the descriptor never received it and kept resolving `HiddenDescriptorMissing` until the host's next new descriptor (up to one hour). This was found by `MultiNodeDescriptorMultiHopVisibilityTest` (six relays, a holder `M`, a late node `L` meshed only with `M`; on the code before wave I `L` did not see the descriptor within two minutes). At each slot the host now signs the same content again with a higher sequence number (`OnionServiceStateMachine.refreshDescriptor`: same introduction points, authentication keys and encryption key; sequence number, `notValidAfter` and signature are new). Such a version passes every receiver's pre-check, is `Valid` and is forwarded over several hops. The senders limit the refresh versions of one service to 4 per minute (`PublicationRateGuard`, the token is taken only for a version that was really produced), below the receivers' per-author rate of 6 per minute; genuine descriptors are always sent and count against the same budget, so many genuine changes within one minute can exceed 6 (refreshes are skipped meanwhile, a receiver may drop the surplus version); the receiver limits and the acceptance policy are unchanged, and `ServiceDescriptorRefreshConformanceTest` drives the real validator with its default limits along the worst timeline (lowest and highest jitter, failed first attempts, a change of the introduction points in the first minute). If the guard is empty, the host has nothing to refresh (an introduction point is not established) or no refresh is configured, the same descriptor is repeated as before. A genuine new descriptor (change, hourly) is always sent. At most 12 retries and repeats per hour, of which 4 are reserved for retries of a failed first send; an expired descriptor is never sent. The host's session lock is taken before the republisher's monitor; the republisher never calls the host while holding its own monitor (`ServiceDescriptorRepublisherTest`, 1000 rounds against a simulated host lock).
* *What the fresh versions show:* up to six signed versions of one service descriptor in the first five minutes after a start instead of one version plus identical repetitions. They carry no new field and are linkable through the service key anyway; the pattern marks a freshly started host, as the record, the prekey bundle and the millisecond sequence numbers already do. This is one of the questions in link:external-review.adoc[external-review.adoc].
* *Circuit budget:* each publication builds its own circuit under the existing circuit-build governor, which is not bypassed; at most about three objects times six publications plus retries within the first six minutes after a start; later descriptors of the same run add one send each plus failure retries, without a new burst.
* *Honest limit:* a node that subscribes later than about 5 minutes after the publisher's start still sees the entry only at the hourly republication. A catch-up (index sync or relay-side replay) would be a separate wave.

=== Honest limits of wave D

* *No user traffic is anonymised and no anonymity is offered.* There is no path selection (the provider is injected), and the transport key is still identity-bound: the largest remaining leak.

* The publish relay sees the object, and a relay is an amplifier, bounded by the limits above. The entry is public and enumerable: identity, onion address and introduction points are linkable over time.
* The sequence number and validity reveal publication time and clock offset.
* The Sybil boundary of the index is the same as in wave C; a small anonymity set and a global passive observer are as in the threat model.
* Not verified: real NATs, interoperability with v0.12.0 over the network (only the unchanged old topics are tested), an external cryptographic review, behaviour under load, and the decoupling of the transport key.

[[path-policy]]
== Path selection and policy (wave V0.10.0-E, released in `v0.13.0`)

*What it is.* `--anonymity=on` starts the `AnonymityRuntime` (`lapis-net-onion-wire`, package `anonymity`): persistent guards, diverse weighted paths of three relays, a build policy for client circuits, the circuit-based directory publication of wave D and the hosting of the node's onion service (introduction points chosen the same way). The headless CLI node and the browser both wire it; with `off` nothing of this is built, and the browser does not even create an `OnionWire` in normal mode.

*What it is not (state of wave E; wave F1 changed the first point).* Direct messages, mail and call signalling are not routed over circuits, the libp2p transport key is the identity key, and every connection of the node (mesh, DHT, Bitswap) still shows identity and IP. At every start the node warns (log, CLI stderr, a notice in the browser that can not be dismissed). The text of wave E was: _Anonymity mode is incomplete: direct messages, mail and call signalling still use direct connections and reveal your IP address; only the directory publication and path selection are active._ (historical; wave F1 replaced it, see <<dm-over-circuits>> for the current text, which `ANONYMITY_INCOMPLETE_WARNING` and `app.js` carry character for character).

=== Path selection

`OnionPathSelector` is network-free and deterministic for a given `SecureRandom` sequence. Hop 1 is the persistent primary guard; the last hop is prescribed by the caller (publish relay, introduction point, rendezvous point) or drawn; the middle hops are drawn with weights.

* *Never shorter:* a path has at least three relays (`PathPolicy.PRODUCTION_PATH_LENGTH`, equal to the default hop count, not configurable). With too few diverse relays the answer is `Insufficient` (an `InsufficientRelaysException` with the text `insufficient relays`, no identity or address in it), never a shorter path. The circuit factory refuses a shorter path too when the policy is installed (second line against a caller that bypasses the selector).
* *Hard diversity:* no relay twice, not the own identity, no two relays with an overlapping IPv4 /16 or IPv6 /48 bucket, at most one relay of unknown network, no two relays of the same non-null family, optionally no Veritas edge (internal switch, no option). If a last hop chosen by the caller itself collides with the guard the selector throws `PathConflictException` and the caller picks another endpoint. A last hop named by a remote party (the rendezvous point of an INTRODUCE, i.e. `RENDEZVOUS_RECEIVER`, and `INTRODUCE` towards a service-chosen introduction point) is never refused because of the guard: success must not depend on the guard, or a remote party could probe for the guard's identity and network. The diversity rule then applies to the middle hops only (strictly towards the guard, towards the remote last hop as far as possible).
* *Weights:* the Madli reliability (clamped to 0..1) with a floor of 0.02; 0.05 without history (NaN and infinity count as no history). Relays without history together are capped at 15 % of the weight when others exist. A single network bucket (and a single family) is capped at `max(0.10, 1/buckets)` by water filling, recomputed for every hop on the remaining candidates. Madli is never a gate. A relay with several addresses counts for the cap in its smallest bucket only; for diversity all its buckets count. All relays new or all in one bucket: no scaling, the draw still happens.
* *Interaction of the two caps:* the new-relay cap is applied first, the bucket cap second. With only a few networks the bucket cap forces weight over to the other relays, which can lift the share of relays without history above 15 %; this is accepted (a feasible distribution has to sum to one).
* *Randomness:* `SecureRandom` only; `nextDouble()` for the weighted draw, `nextLong(bound)` for the guard lifetime (both without modulo bias).

*Circuit build budgets.* `CircuitBuildGovernor` keeps the attacker-triggerable service rendezvous circuits (`RENDEZVOUS_RECEIVER`) in a separate budget (default 60 per minute, burst 10; over it they are dropped, not delayed) without any backoff, so an INTRODUCE flood or failing rendezvous points can neither starve nor back off the node's own introduction, publication and client circuits.

*Where the network buckets come from.* A relay descriptor carries no address (the family field is a count byte that must be zero). `PeerDirectoryRelayNetworkLocator` reads the relay's `PeerRecord`: only public `ip4`/`ip6` addresses count, `/p2p-circuit`, `dns*`, loopback, private, link-local, CGNAT, unique-local, `0.0.0.0/8`, documentation, benchmarking (`198.18.0.0/15`), reserved (`240.0.0.0/4`) and `2001:db8::/32` addresses are ignored, and a name is never resolved (a resolution would be a network call). A relay without a usable address is in the bucket `Unknown`. *These addresses are self-declared and unverified:* an adversary can declare addresses in networks it does not control and so slip past the diversity check, or declare an honest network to crowd it out. This is a Sybil limit that this wave does not close.

=== Guards

Two guards (primary and backup), each with a lifetime drawn uniformly from 30 to 60 days. The first hop of every circuit is the primary. A guard is replaced when it expires (not rate limited), after at least three consecutive *first-hop* failures spanning at least 24 hours, or when its descriptor has been missing or invalid for at least 72 hours; a replacement because of a failure happens at most once per 24 hours, the backup takes over and a new backup is chosen. Only failures at the first hop count (a dial or link failure, a CREATE that times out or is answered invalidly): a failure while extending to the second or third hop must not be usable to force a guard rotation.

The state lives in `onion/guards.bin` in the data directory: `"LNGS" | version | nonce(12) | AES-256-GCM(state) + tag`, key `HKDF-SHA256(identity secp256k1 private key, salt empty, info "LapisNet:guard-state:v1")`, associated data `"LNGS" | version | SHA-256(own identity public key)`, a fresh nonce for every write, atomic write (temp file `0600`, fsync, atomic move), directory `0700`. A damaged, foreign or implausible file (times in the future, lifetime outside 30 to 60 days, negative counters) is `Invalid` and always leads to new guards; a missing file leads to new guards only if the previous run was in anonymity mode (so a first start is silent). A reset logs `guard state invalid, reselected guards` (no content), counts, and shows as the status code `guard-state-reset`, which later routine errors do not hide for an hour. Deleting the file can not be prevented (an attacker with file access can force a new guard choice); it is made visible, and the rate limit of failure rotations deliberately does not apply to it.

[[guard-reachability]]
*Primary guard reachability fallback (fix wave "rendezvous after guard failover", released in `v0.13.0`).* A first-hop failure at the primary (the node's own dial, link or CREATE result; a failure further along the path counts as a first-hop success) marks the primary *unreachable in memory*. While it is marked and the backup's descriptor is known, builds enter through the persisted backup; after a retry delay of 30 seconds, doubling per failed probe up to 10 minutes, with ±20 % jitter (`SecureRandom`), exactly one build probes the primary again, every parallel build keeps the backup. A success at the primary clears the mark; a probe that fails, or whose build never reports a first-hop result within 60 seconds, extends the delay. A probe whose build is not started at all is handed back unused and counts neither way: a path that conflicts or enters through the other guard (`OnionPathSelector.select`), a refusal of the circuit governor (`CircuitPolicy.unbuiltPath`) and a warm-pool build the governor does not admit right now (`OnionPathSelector.releaseUnusedPath`); otherwise governor pressure alone could keep a recovered primary out for up to 10 minutes per refusal. Failures of builds that were already under way when the mark was set do not extend it. Checks without a build (endpoint choice, the rendezvous point's conflict check) never take the probe. The mark is never persisted (the guard file format and its version stay unchanged; a restart starts with the primary) and it rotates nothing: the persisted primary, its failure counter and the 3-failures-over-24-hours, 72-hour and once-per-24-hours rules are untouched, and no new guard is ever chosen, so the exposure stays the fixed set {primary, backup}. Without a usable backup the marked primary stays the first hop (never "no guard" only because of the mark). Endpoints (`selectEndpoint`) exclude a marked primary in addition to the effective guard and must be diverse (network, family, Veritas edge) to both, so that a later probe build over the primary does not conflict with an endpoint chosen meanwhile (stricter diversity, not looser). Trade-off: whoever disturbs the link to the primary moves the node's circuits to the backup, but not to any new relay; the probes to a dead primary are visible locally and spaced by the jittered retry plan. Tor's primary-guard retry schedule behaves the same way. Before this fix a node whose primary died kept building over it for as long as the primary's relay descriptor was valid (up to 24 hours in production, 18 to 24 hours of remaining TTL after the last republication) and, once the failures had pushed the governor's backoff beyond the 30-second deferral limit, only had a build attempt every few minutes, again over the dead primary (`GuardFailoverScenarioTest` models both).

=== Circuit policy

`CircuitBuildGovernor`: a token bucket of 6 builds per minute with a burst of 3; after a failed build an exponential backoff from 5 seconds to 5 minutes; at most 4 open or in-flight outgoing client circuits (directory publication, rendezvous client); circuits older than 10 minutes are closed by a sweeper every 30 seconds; after `lockdown` (stop) nothing new is admitted. The long-lived introduction circuits of the hosted service do not count against the pool of four (they would starve the publisher) but pay the rate. Every build goes to a new circuit; there is no circuit reuse anywhere. A build that would wait longer than 30 seconds fails with a `rate-limited` status instead of waiting. Every failed or aborted build sends a DESTROY to the first hop.

=== Status and errors

The CLI start line shows `anonymity=on|off`; the browser status carries `anonymityMode`, `anonymityIncomplete`, `guards`, `activeCircuits` and `lastAnonymityError` (+ age) and shows them in the node status panel. The error code is one of `none`, `insufficient-relays`, `build-failed`, `build-timeout`, `rate-limited`, `guard-state-reset`, `publish-failed`: enums and numbers only, never an address or identity. A successful publication clears the code. On loopback every relay is in the unknown bucket, so a real node there reports `insufficient-relays` and publishes nothing; there is no fallback to publishing from the own node.

=== Conflicts and wiring

* `--anonymity=on` with an explicit `--hole-punching=auto|on` aborts the start (`hole-punching cannot be enabled while anonymity=on`); a missing key resolves to off. DCUtR and Identify are off node-wide in this mode.
* `--anonymity=on` with `--onion-relay=true` aborts the start (`onion-relay cannot be combined with anonymity=on`). The design text of waves A to D says "`--onion-relay` stays independent"; wave D already enforces the exclusion at `OnionWire.attach` because a relay descriptor binds identity, peer ID and dialability publicly, so the option layer now matches the code.
* The onion service key of the node is generated freshly at every start (the onion address changes with it); the CLI node publishes no prekey bundle and no DM capability, the browser both.
* Auto-relay reservations (leak 11) and Madli gossip (12) stay available in this mode and are documented, not forbidden. The Madli gossip topic is subscribed to read the relay reliability.

* *Assumption, confirmation required:* DCUtR node-wide off while the mode is on; the mode changes only by restarting the node.
* *Assumption, confirmation required (F1):* `--onion-relay=true` with `--anonymity=on` aborts the start; lifting the exclusion would need a separate relay identity.
* *Assumption, confirmation required (F2):* an explicit `--hole-punching=auto` or `on` together with `--anonymity=on` aborts the start; only a missing key resolves to off.
* *Assumption, confirmation required (F3):* the revocation of an ON to OFF switch is sent from the own node through the anonymous-record gossip; going through a circuit would need path selection (and an `OnionWire`) in normal mode.
* *Assumption, confirmation required (F4):* the pool of 4 counts outgoing client circuits only; introduction circuits are bounded by the host and only pay the rate.
* *Assumption, confirmation required (F5):* the transport-key decoupling (leaks 8 and 14) is not part of this wave; it remains the largest leak.
* *Assumption, confirmation required (F6):* auto-relay reservations, Madli gossip and the DHT fallback are allowed in anonymity mode and documented as leaks. The node's own code sends no Identify request (code review, not a wire test); the Identify responder is off.

=== Honest limits of wave E

* *No user traffic is anonymised.* Only the directory publication and the path selection are active; the transport key is the identity key, so any peer that connects to the node learns identity and IP.
* The network diversity rests on self-declared, unverified addresses; with the real locator it is only as good as those declarations. *It was verified only with an injected locator that gives each relay a synthetic distinct /16*, because on loopback every relay has the same address and no diverse path exists.
* The relay family check is inactive (no field in the descriptor). The Veritas edge check exists only as an internal switch.
* While the primary guard's descriptor is missing from the directory (relay offline, descriptor expired), or while the primary is marked unreachable after a first-hop failure (see <<guard-reachability>>), the backup guard serves as first hop; the primary is only replaced after 72 hours without a descriptor, or by the failure rule.
* *Known limitation (guard-conflict oracle):* a remotely chosen last hop (rendezvous point, introduction point) that equals the effective guard is entered through the other persisted guard. When that one is not usable (only one guard has a known descriptor, for example after the primary's descriptor expired), no circuit can be built to that relay. A client can therefore try rendezvous points one by one: the one over which no `RENDEZVOUS2` ever arrives is the service's guard. The probe costs the client one rendezvous attempt (and its timeout) per candidate and works only while the service has a single usable guard; it existed before the fix wave "rendezvous after guard failover" and is not closed by it (the client-side rendezvous retry hides it from honest clients, it does not stop a prober). Closing it needs a third persisted guard (three primary guards, as Tor has), i.e. a change of the guard file format and more exposure; deliberately not part of that wave (open point in the roadmap).
* A revocation of the anonymous record (switch to normal mode) is only counted as sent after at least one mesh peer received it; otherwise `OFF` is not persisted and the revocation is repeated at the next start.
* A deleted or replaced guard file forces a new guard choice and can not be prevented; it is only made visible.
* A guard that is also operated by the adversary sees the node's IP for every circuit; guards reduce the predecessor attack, they do not remove it. A small anonymity set and a global passive observer are as in the threat model.
* A node upgraded from v0.12.0 sends no tombstone on its first switch to anonymity mode (no persisted `OFF`); its address entries stay until their TTL ends.
* Not verified: real networks and NATs, behaviour under load, interoperability with v0.12.0 over the network (only local), and no external cryptographic review has taken place.

[[dm-over-circuits]]
== Direct messages over circuits (wave V0.10.0-F1, released in `v0.13.0`)

NOTE: This section describes the state of wave F1. Wave F2 changed three things in it: mail now also travels over circuits (see <<mail-over-circuits>>, so every remark below that mail "is unchanged" or "uses direct connections" describes wave F1 only); the sealed item carries a kind byte inside its encrypted plaintext, which lowers the capacity of a direct-message item by one byte (5,668 bytes instead of 5,669); and the warning text below is historical, replaced by the text in <<mail-over-circuits>>.

*What it is.* A node in anonymity mode sends and receives direct messages only through circuits. The ratchet (X3DH and Double Ratchet) is unchanged and keeps protecting the content; what changes is the transport. A new module `lapis-net-dm-onion` is the adapter between `lapis-net-dm` (which knows only the `AnonymousDmTransport` interface and the sealed item format and does not depend on any onion code) and `lapis-net-onion-wire` (which knows nothing about direct messages). `DmSessionManager` is attached with `anonymous = true`: it then registers no `/lapis/dm/1.1.0` protocol, starts no mailbox poller, publishes no pointer on any per-recipient topic and offers nothing to the DHT outbox. There is one inbound pipeline for both entrances (circuit stream and sealed item): `processInboundDmEnvelope`, with duplicate check, X3DH replay register, prekey rate limiter, ratchet decryption and acceptance policy. The sender of an incoming message is known only after decryption.

*What it is not.* Mail and call media still use direct connections; call signalling is not available in anonymity mode (a call attempt is refused up front; superseded by wave G, see <<call-signals-over-circuits>>). GossipSub, the DHT and content fetches still show identity and IP. The recipient learns the sender's identity (it is in the envelope; the point is that the network does not learn who talks to whom, not that the peer is anonymous to the peer). Both sides must be in anonymity mode: a recipient in the normal mode, an unknown identity, a recipient without the DM service and a recipient without a prekey bundle all give the same refusal. There is no fallback to a direct connection, ever. A call invitation over this path is rejected (calls follow in wave G).

At every start the node warned in wave F1 (log, CLI stderr, a notice in the browser that can not be dismissed; historical text, replaced in wave F2): _Anonymity mode is incomplete: direct messages travel over circuits, but mail and call media still use direct connections and reveal your IP address, call signalling is not available, and the network mesh, DHT lookups and fetches still show your identity and address._ The browser's status panel shows seven fixed lines (directory entries, direct messages, mail, call signalling, call media, mesh/DHT/fetches, and the guard and circuit counts) and the DM page shows a fixed notice above the input field and a disabled attachment button.

=== Online path

The sender looks the recipient up in the local directory only (`AnonymousDirectory`, built without a DHT: a DHT lookup would show the DHT neighbours the sender's interest together with its IP). With a service descriptor it opens a rendezvous stream (`AnonymityRuntime.connectToService`): the rendezvous point is a path-selector endpoint, the first frame is a HELLO naming the application (`"LNSV" | version | appId`, DM = 1), the service side dispatches by HELLO (`OnionServiceStreamRouter`; MAIL joined in wave F2, CALL is reserved for a later wave) and closes a stream without a valid HELLO after 10 seconds.

The stream carries `type(1) | len(4) | bytes` frames split into messages of at most 910 bytes. The receiver checks the length against the envelope maximum before it allocates, accepts at most 16 envelopes per stream, 120 per minute over all streams, waits at most 10 seconds between the pieces of one frame and keeps a stream at most 10 minutes. The acknowledgement is sent as soon as a frame is complete and was queued, never after the envelope was processed: its timing says nothing about decryption, the acceptance policy or duplicates (no oracle). A full work queue closes the stream without an acknowledgement; the sender then deposits offline and the duplicate suppression absorbs the possible double. A reply does not use the incoming stream: the answering node resolves the sender and builds its own circuit, so no stream is ever tied to an identity. The sender keeps at most 2 streams (one per onion address, 60 seconds idle) and a new onion address always gets a new circuit.

=== Offline path (design M: sealed mailbox items)

Before wave F1 the sender gossiped a signed pointer on the recipient's own topic (subscribing to it links the recipient's identity and IP for every mesh neighbour), the recipient fetched the blob directly from the sender over Bitswap, and the DHT outbox carried provider records and IPNS values with addresses. None of that is acceptable in anonymity mode. The design keeps no address anywhere on the offline path:

. The sender seals the already encrypted envelope to the recipient's X25519 identity key (the one bound into the prekey bundle). An item is always exactly 5,728 bytes: `version(1) | ephemeralX25519(32) | AEAD(notValidAfter(8) | envLen(2) | envelope | zero padding) | tag(16)`; the key is `HKDF-SHA256(X25519(ephemeral, recipient), salt = ephemeral || recipient, info = "LapisNet:anonymous-mailbox-item:v1")`, used once, ChaCha20-Poly1305 with a zero nonce. The item has no sender signature: the ratchet decryption inside is the only proof of who sent it. There is no forward secrecy for this sealing layer (the long-term identity key is the recipient key); the content stays ratchet-protected.
. The sender sends the item through a circuit to a relay (new relay role `MAILBOX_PUBLISH`, see below). The relay checks only the size and announces the item on the one shared GossipSub topic `LapisNet:anonymous-mailbox:v1`.
. Every node in anonymity mode subscribes to that topic and tries to open every item that passes the validator. An item for someone else does not open and is dropped without a trace. Items are tried on a small bounded executor; the topic's global budget (120 per minute) bounds the work.
. The sender announces the item again every 10 minutes (plus or minus 2 minutes), sealed afresh each time, until its lifetime (48 hours) ends: a recipient that is offline now can only receive an item announced after it comes back. This is the honest limit: *offline delivery works only while the sender keeps announcing*. The queue is in memory (lost on restart, as the pointer queue was), at most 256 entries and 32 per recipient, oldest dropped first.

*Why not the alternatives.* IPNS over circuits would need pre-signed records and a new name space (see assumption D of wave D) and would put values with addresses into the DHT. Relays chosen by the recipient as mailboxes (option c of wave C) would need a new field in the service descriptor and make the recipient's relays targets. The chosen design reveals to a subscriber only "this node is in anonymity mode", which its public record shows anyway, and no third party sees sender or recipient.

*The relay role.* `MAILBOX_PUBLISH` and `MAILBOX_PUBLISHED` are accepted only at the last hop of a circuit without another role. The body is exactly 720 bytes: `itemIndex(1) | fragIndex(1) | fragCount(1) = 8 | reserved(1) = 0 | data(716)`. At most 4 items per circuit, 10 items per minute per link and 60 per minute in total (counted when an item starts, before any payload byte is copied); a wrong length, a broken header, a wrong order or an item not completed within 15 seconds destroys the circuit. Only a rate limit is answered with a status; a circuit that continues after it is destroyed. The relay validator on the topic accepts only items of the exact size from an author that is a relay with a current descriptor (otherwise ignore, so a forwarder that is not yet synced is not penalised), ignores duplicates by SHA-256 and a budget of 10 per minute per author and 120 per minute in total.

=== Refusals the user sees

|===
| Code | HTTP | Meaning
| `recipient-not-reachable-anonymously` | 503 | Unknown, not in anonymity mode, no DM service or no prekey bundle: one answer for all of them. No session is created.
| `anonymity-not-ready` | 503 | No guards yet or the service host is not started (also before the runtime exists at start). No fallback.
| `rate-limited` | 503 | Reserved: circuit builds are being throttled. Today an undeliverable online attempt is queued for the offline path instead, so the browser does not currently produce it.

The refusal for the recipient happens before any session work, so a refused first contact leaves no session on the sender's side that the recipient never bootstrapped. A message that could not be delivered online is not re-encrypted for the offline path: the same envelope bytes are sealed, because a second encryption would turn the first message into a `TEXT` envelope that the recipient cannot open.

*One-time-prekey collisions (fix, released in `v0.13.0`).* When a first-contact `X3DH_INITIAL` arrives over a circuit and its
one-time prekey is already consumed, the responder resolves the initiator and sends an authenticated
`X3DH_REJECTED` over a circuit of its own (see "One-time-prekey collisions and authenticated handshake rejection" in
`architecture.adoc`). That is a reflection: an unauthenticated `X3DH_INITIAL` with a valid public binding makes the
responder build a circuit to the claimed sender. It is bounded: one rejection per claimed sender per 300 s, at most
10 per minute in total, a queue of 16, only towards a sender that is online. Reusing the inbound rendezvous circuit
for the answer would avoid it but needs an extension of `AnonymousDmTransport` (a later wave). Republishing the
bundle after every consumption (the alternative that only narrows the window) was rejected because it would show
directory observers the time of every first contact. Log lines on this path name no peer (`who()` prints
`<peer>`).

=== Honest limits of wave F1

* The recipient learns the sender's identity; only the network is blinded. Both ends must be in anonymity mode.
* A small anonymity set, Sybil relays and a global passive observer are as in the threat model. Timing correlation is possible, including the pattern of the re-announcement; padding to the cell size is wave H. The fixed 5,728 bytes of the offline items are already uniform.
* Spam on the shared topic can starve its budget (a denial of service limit, not a confidentiality problem). The relay sees that one circuit carried several items, but neither sender, recipient nor content. A relay that is also a subscriber sees every item that passes it, like everybody.
* No per-peer limit exists on the receiving side (the peer is anonymous); the global and per-stream limits are what protects the node.
* Offline delivery needs the sender to keep announcing; the queue is lost on a restart. The sender cannot tell whether an item was delivered, so it announces until the lifetime ends.
* An item is sealed to the long-term X25519 identity key: no forward secrecy for the sender and recipient metadata of the sealing layer.
* A call invitation over this path was rejected in wave F1; wave G accepts it over the circuit door only (the sealed mailbox door still rejects it).
* One selector fix belongs to this wave: a remotely chosen last hop (an introduction point named by a descriptor) that equals the node's primary guard used to produce a path with the guard twice, which the circuit builder refuses. The circuit now enters through the *other persisted guard* in that case (since the fix wave "rendezvous after guard failover": while the backup is the effective guard, the other one is the primary; a dead primary then fails the build like any guard outage); if the other guard is not usable the selector answers `GuardConflict` (`GuardConflictException`, a subclass of `InsufficientRelaysException`, counted separately in the host diagnostics) and the build is retried later. See the known limitation "guard-conflict oracle" under <<path-policy>>.
* Not verified: real NATs and real networks (all tests use loopback nodes with an injected locator that gives each relay a synthetic /16), behaviour under load, an external cryptographic review of the sealing construction, and interoperability with v0.12.0 over the network.

=== Assumptions awaiting confirmation (wave F1)

* *Assumption, confirmation required:* the wave is one unit with ordered commits on one branch (not split into F1a online and F1b offline).
* *Assumption, confirmation required:* the offline design is M (sealed items announced by relays on one shared topic), not IPNS over circuits and not recipient-chosen mailbox relays.
* *Assumption, confirmation required:* the content size in anonymity mode is limited to what fits one sealed item (about 5.4 KB), online and offline alike, and `message-too-large-anonymous` is a fourth refusal code (the design team had fixed three).
* *Assumption, confirmation required:* the sealing key is the X25519 identity key of the prekey bundle, not the (rotating) signed prekey.
* *Assumption, confirmation required:* constants: re-announcement every 10 minutes plus or minus 2 minutes, offline lifetime 48 hours (not 7 days), at most 4 items per circuit, at most 256 pending items and 32 per recipient, topic budgets 120 per minute in total and 10 per relay author, at most 2 cached streams with 60 seconds idle, 30 seconds for one online delivery attempt, relay limits 10 items per minute per link and 60 in total, 15 seconds to assemble an item.
* *Assumption, confirmation required:* attachments are refused in anonymity mode in this wave; whether they travel over circuits later (waves F2 or J) is open. _Superseded by wave Q21 (released in `v0.13.0`): see <<attachments-over-circuits>>._
* *Assumption, confirmation required:* call signalling is refused in anonymity mode until wave G, so a call from or to a node in anonymity mode fails. (Superseded by wave G.)
* *Assumption, confirmation required:* the browser banner text (current text of `ANONYMITY_INCOMPLETE_WARNING`) and the seven fixed lines of the status panel were written for this wave from the facts above; the design team's wording was not available to the implementation and should replace them if it differs.
* *Assumption, confirmation required:* the digest of the prekey bundle in the anonymous record is not compared with the bundle found in the directory (a legitimate bundle refresh would make such a comparison fail spuriously).

[[mail-over-circuits]]
== Mail over circuits (wave V0.10.0-F2, released in `v0.13.0`)

*What it is.* A node in anonymity mode sends and receives mail only through circuits. The mail itself is unchanged: a signed `MessageEnvelope` and a body that is hybrid-ECIES sealed (or, if the user chooses `NONE`, plain), exactly as on the direct path. What changes is the transport and the places a mail may touch. A new module `lapis-net-mail-onion` is the adapter between `lapis-net-mail` (which knows only the `AnonymousMailTransport` and `AnonymousMailInboundSink` interfaces and does not depend on onion code) and `lapis-net-onion-wire`. The browser attaches `MailSender` with `anonymous = true` and `InboxGossip` through `attachAnonymous`; both are built before the anonymity runtime exists, so the transport is installed afterwards and every send fails with `anonymity-not-ready` until then. There is no fallback to the direct path, ever.

In anonymity mode, mail and its attachments no longer use:

* the per-recipient inbox topic (`InboxTopics`): not subscribed, not published on (`attachAnonymous` registers no subscription, `MailSender` never calls `publish`);
* the DHT outbox: `MailSender` is refused a `DhtOutbox` at construction (fail closed), so there are no pointers, no provider records (`MessagingRendezvous`) and no IPNS values for mail;
* the DHT fetcher (`InboxDhtFetcher`): not attached; it would fetch envelope and body from the sender over Nabu/Bitswap, which dials the sender;
* Nabu/Bitswap for attachments: `GET /api/mail/attachment/{cid}` reads the local blockstore only (`getLocal`; the ordinary `get` falls back to provider lookup and Bitswap on a miss), and the sender builds a bundle only from blobs it holds locally.

*What it is not.* Call media still uses direct connections (WebRTC reveals IP addresses to the peer) and call signalling is not available; GossipSub in general, the DHT and other content fetches still show identity and IP address. The recipient learns the sender's identity (it is in the signed envelope). Both ends must be in anonymity mode: a recipient in the normal mode, an unknown identity, a revoked one, one without the MAIL service and one without a prekey bundle all give the same refusal.

At every start the node warns (log, CLI stderr, a notice in the browser that can not be dismissed): _Anonymity mode is incomplete: direct messages and mail travel over circuits, but call media still uses direct connections and reveals your IP address, call signalling is not available, and the network mesh, DHT lookups and fetches still show your identity and address._ The text is the same character for character in `ANONYMITY_INCOMPLETE_WARNING`, in `app.js` and here (a test compares the first two). The browser's status panel keeps its seven fixed lines; the mail line reads _Mail: over circuits (small mail also offline; up to 1 MiB with attachments only while both are online)_. The mail page shows a fixed notice above the compose form.

=== Delivery: two size classes and a hard limit

The class applies to the transport bundle: the signed mail frame plus all attachment blobs.

| `INLINE` | frame at most 5,668 bytes (the capacity of a sealed item), no attachments | rendezvous stream `MAIL`, constant acknowledgement | a sealed item on the shared topic, announced again every 10 minutes (plus or minus 2) until 48 hours, by the same queue as offline direct messages | the infrastructure of wave F1 serves it unchanged; every item is exactly 5,728 bytes
| `CIRCUIT` | bundle at most 1 MiB, at most 16 attachments | rendezvous stream `MAIL`, one bundle frame, attachments in band, constant acknowledgement | *no item.* The sender keeps the bundle in a bounded in-memory queue and tries the stream again every 10 minutes (plus or minus 2) for 48 hours | no relay stores content, no one dials the sender, integrity comes from self-certifying CIDs
| too large | more than 1 MiB or more than 16 attachments | -- | -- | refused with `mail-too-large-anonymous` (413) before any network step; nothing is stored, built or sent

*Why not the alternatives.*

. _Blob storage at relays, reached over circuits._ This would be a new relay role that stores content. Relays would become storage targets and abuse magnets, and quota, deletion and liability would be open questions. It belongs, if anywhere, to a later wave (I or J).
. _Chunking a bundle over many items._ A 44 KB bundle needs eight items from the topic's global budget (120 per minute for the whole network, shared with direct messages); a few mails would starve everybody else.
. _Pulling from a hidden service of the sender._ The sender would have to run a service and a descriptor of its own for this; it offers nothing that pushing to the recipient's service does not.

=== Keys and one item format for two kinds

The sender looks the recipient up in the local anonymous directory only (no DHT). It needs the `MAIL` capability in the recipient's anonymous record and the recipient's prekey bundle; the sealing key is the X25519 identity key of the bundle, like for direct messages. The mail body stays hybrid-ECIES sealed to the recipient's secp256k1 key as before.

Direct messages and mail share one sealed item format and one topic. The kind is inside the encrypted plaintext, not in a header, because any cleartext header field would tell every observer of the topic which items are mail:

----
version(1) | ephemeralX25519(32) | AEAD( notValidAfter(8) | kind(1) | len(2) | payload | zero padding ) | tag(16)
----

Always exactly 5,728 bytes; `kind` is 1 (DM) or 2 (MAIL); the payload capacity is 5,668 bytes (`SealedMailboxBox`, in `lapis-net-directory`; `SealedMailboxItemCodec` of `lapis-net-dm` is now a thin wrapper). The wire format of wave F1 (unreleased at that time) was changed in place; there is nothing to migrate. Two consumers (the direct-message subscriber and the mail subscriber) now listen on the shared topic (`AnonymousMailboxGossip.addConsumer`, at most 4); each opens an item with the same key, which is two key agreements per item at no more than 120 items per minute. An item of the other kind simply does not open.

=== Bundle and stream

A bundle is `version(1) = 1 | frameLen(4) | mailFrame | count(1) | { blobLen(4) | blob }*`. Every length is checked against the remaining bytes and the limits before anything is allocated; the sum is at most 1 MiB and `count` at most 16. CIDs are not transmitted: the receiver computes them from the blob bytes. The stream carries `type(1) | len(4) | bytes` frames as for direct messages, with a new type 3 (bundle) accepted by the receiver; the acknowledgement is the same constant frame (type 2).

The sender opens a *new circuit for every delivery*; there is no stream cache, because mail is rare and this keeps deliveries unlinkable. A delivery runs on a small bounded executor (2 threads, queue 16; if that is full the online attempt is skipped and the mail is queued at once) so that the HTTP thread never waits for a circuit. Every failure path closes the circuit.

The receiver (`OnionMailInboundHandler`) serves at most 4 mail streams at once (a fifth is closed immediately), one bundle per stream, 30 bundles and 8 MiB per minute over all streams, 10 seconds between the pieces of one frame, the complete 5-byte frame header within 15 seconds of the stream's creation, a body rate of at least 1 KiB/s on average (measured from the end of the header, after a 10-second grace period) and 120 seconds per stream. A body must also be able to finish within the stream's lifetime at the rate it has shown so far, so a stream that keeps its slot to the end of its lifetime has to complete its frame and thereby consume budget. The byte budget for the minute is reserved from the declared frame length in the header *before* the body buffer is allocated. A full work queue (8) closes the stream without an acknowledgement; the sender then keeps the mail and retries. The acknowledgement is sent as soon as the frame is complete and queued, never after the acceptance check, and a refused bundle does not end the stream early.

* *Known limitation (slot exhaustion):* peers are anonymous and there is no per-peer limit. An attacker that sends a header declaring a large frame and then a body at just above the minimum rate (roughly 4 KiB/s of upstream for all four streams) keeps all 4 mail stream slots busy until the sweeper cuts them, and the budget reserved for the declared length (up to 4 MiB of the 8 MiB per minute) is held meanwhile. The reservation is returned when such a stream is cut, so the attack costs the attacker no budget, and honest senders retry (every 10 minutes, for 48 hours). The minimum rate and the completion projection make the attack far more expensive than a byte-per-interval trickle, but do not remove it. Planned mitigation: not returning the reservation of a stream cut for being slow, or a cost per stream (proof of work).

=== One entrance, one policy

Both anonymous paths (the stream and the sealed item) end in `InboxGossip.anonymousIngest`, which runs the very stages of the gossip validator: frame decode, `checkEnvelope` (addressing, signature, content binding, the live acceptance policy including the contact bypass, read per message) and `ingestChecked` with the `InboxIndex` duplicate suppression. A test feeds the same frames and gate configurations (Veritas path, Karma, contact bypass, none) through both entrances and compares the decisions. `updateAcceptanceCheck` changes both. Attachment blobs are looked at only *after* a mail was accepted, and only blobs whose own CID is referenced by the decrypted body are stored (everything else is discarded and counted); a refused mail stores nothing. Accepted mail (envelope, body and attachment blobs) is written with `NabuStorage.putUnserved` into a separate local blockstore (`<blockstore>-private`) that Bitswap and the DHT engine never see: a remote peer cannot probe acceptance or presence with WANT_HAVE or GET_PROVIDERS, so storage is no side channel. `get` and `getLocal` still read it locally. Mail that additionally arrives through the public gossip or DHT paths is stored in the served blockstore like any public mail.

=== Signal path

* `DmSessionManager.sendCallSignal` in anonymity mode encrypts with the existing ratchet session (a call never begins a first contact: without a session the send fails as before) and hands the envelope to the rendezvous stream with a delivery deadline of 15 seconds.
* *Online only.* A call signal is never deposited as a sealed mailbox item: if the recipient is not reachable (no service descriptor) the send fails before any ratchet step is consumed, with the fixed error `call-signal-path-lost`. The sealed mailbox door of the inbound sink still rejects `CALL_SIGNAL` before any decryption, exactly as the offline poller does on the direct path; only the circuit door accepts it.
* A signal arriving through the circuit door goes through the same inbound pipeline as every other message: session requirement, authenticated decryption, replay suppression and the acceptance rules (`classifyQuarantinedSender`). There is no bypass and no new policy path. `marksAcceptance` is passed through unchanged.
* *No reply route.* The V0.9.19 reply route (answering over the INVITE's open connection) is a direct-connection concept. In anonymity mode inbound signals carry no route and `sendCallSignal` refuses one.
* *Size.* A call signal is capped well below the envelope limit of the circuit stream. It is NOT subject to the 5,668-byte limit of a sealed mailbox item, because it never uses one.
* *Timing.* The 15 second signal deadline is at most the call dial timeout, so the 20 second media shutdown wait of `CallManager.stop()` stays valid. A lost path ends the call locally as `CIRCUIT_LOST`; this reason is local only: it is never encoded (`CallSignalCodec.encode` refuses it) and a wire value of 10 is rejected as malformed. There is no wire format change; older nodes are not affected.

=== The media path and the default

Calls are *off* in anonymity mode by default (`CallMediaPolicy.DISABLED`): `placeCall` throws before any hand-off, the HTTP API answers `409` with the code `CALL_MEDIA_DISABLED_IN_ANONYMITY_MODE` (no network traffic, no history entry), and an inbound INVITE is dropped silently (see below). `--anonymity-allow-call-media=true` (environment `LAPISNET_ANONYMITY_ALLOW_CALL_MEDIA`, browser file key `anonymityAllowCallMedia`, only valid with `--anonymity=on`, restart required) selects `CallMediaPolicy.EXPOSED`.

With the option, a call reveals your IP address to the other party *and to network observers*. Therefore the node enforces a confirmation for every call, both in the HTTP API (`409` with `MEDIA_EXPOSURE_CONFIRMATION_REQUIRED` unless the body says `confirmMediaExposure: true`) and in `CallManager` itself (`placeCall` and `acceptCall` throw without it). The browser asks with an alertdialog before each outgoing call and before accepting each incoming one; the confirmation is never stored, Enter and Escape never accept or reject a ringing call in this mode, and the desktop notification carries no peer information. A missing `callMedia` field in the status is treated like `exposed` (fail safe).

*Reduced SDP, not anonymity.* With the option the SDP is reduced before it leaves the node and again when it arrives, as text only (the PeerConnection is untouched): only `typ host` UDP candidates with a public unicast address survive, at most one per component (IPv4 preferred); private (RFC 1918), loopback, link-local, CGNAT, ULA, multicast, IPv4-mapped and `.local` candidates are dropped, and the connection, RTCP and origin addresses are replaced with the placeholder `0.0.0.0`. No STUN, no TURN and no TCP is used. This keeps your LAN topology out of the signal and limits the exposure to one address per component; it does not hide that address.

=== Refusals the user sees

* `409 CALL_MEDIA_DISABLED_IN_ANONYMITY_MODE` (calls off) and `409 MEDIA_EXPOSURE_CONFIRMATION_REQUIRED`; the page shows fixed German texts and never the server's wording.
* `CIRCUIT_LOST` ("Verbindung abgebrochen") when the signal path failed during setup. "Recipient not reachable anonymously" is deliberately shown the same way: the same answer can not be told apart.

=== What the caller observes

The transport acknowledgement of the circuit stream is constant and is sent before any processing. A recipient that blocks the caller (acceptance rule), has calls off, or simply does not answer produces the same observation at the caller: no reply at all, then `RING_TIMEOUT`. In particular an INVITE to a node with calls off is dropped *before* the BUSY check: no REJECT and no BUSY is sent. The capability bits published in the anonymous directory entry are unchanged (`DM`, `MAIL`), so the option is not fingerprintable there.

[[padding-and-timing]]
== Padding and timing protection (wave V0.10.0-H, released in `v0.13.0`)

*What it is.* Four measures against a LOCAL observer of the connection between a node in anonymity mode and its guard (an ISP, a shared network, the guard itself), controlled by `--anonymity-padding=standard|off` (default `standard`, also `LAPISNET_ANONYMITY_PADDING` and `anonymityPadding` in `browser.properties`; valid but without effect while `--anonymity=off`). *It is not protection against a global passive observer* who sees both ends of a circuit: end-to-end correlation of timing and volume stays out of scope. *Compatibility:* both ends of a stream must run wave H. With the default `--anonymity-padding=standard` a sender always uses the padded frame types 4 (`ENVELOPE_PADDED`) and 5 (`MAIL_BUNDLE_PADDED`). A receiver on master or any earlier release (including v0.10.0-G) does not know them and closes the stream on the first header ("unexpected frame type"); the sender gets no acknowledgement, so direct messages, call signals and online mail on the circuit path from a wave H node to such a node fail without a diagnostic (mail then falls back to the mailbox or retry path). Nothing negotiates a capability: there is no version field in the service descriptor or the link handshake. Until both nodes run wave H, a wave H node that talks to older nodes must use `--anonymity-padding=off` (unpadded frames, which every build accepts). A receiver of wave H still accepts the unpadded types.

=== Size classes

On a rendezvous stream every message is one 1024-byte cell (929 byte end-to-end blob, at most 910 bytes of data). The length of a direct message, call signal or mail bundle therefore shows only as the NUMBER of cells. The sender pads the frame with zero bytes, inside the end-to-end encrypted stream, up to the next class: the smallest power of two of cells that holds it, capped at the cell count of the largest legal frame. Padded frames carry their own type (`ENVELOPE_PADDED` = 4, `MAIL_BUNDLE_PADDED` = 5); the receiver still accepts the unpadded types (a sender with padding off).

[cols="2,5", options="header"]
|===
| Kind | Classes (cells)
| Direct message and call signal (frame up to 65,715 bytes)
| 1, 2, 4, 8, 16, 32, 64, 73
| Mail bundle (frame up to 1 MiB + 16)
| 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 1153
|===

A frame of `n` bytes needs `ceil((5 + n) / 910)` cells. A normal text message stays at one cell and costs nothing; the overhead is below a factor of two. The padding is derived deterministically from the authenticated length, so a peer cannot choose it. The receiver counts and discards the padding bytes and never inspects them (no padding oracle). The acknowledgement is sent only after the LAST padding byte, so its timing does not reveal the real length; a sender that stops short of its class is never acknowledged and the idle sweep closes the stream. The memory quota sees the real length; the rate check (`bodyTooSlow`) counts the whole class.

Fixed already before this wave (checked by tests): the directory publish message (one cell, answer one cell), the mailbox item (always 5,728 bytes = 8 fragments), the introduce and rendezvous handshake, and the acknowledgements.

=== Cover cells

A node sends a cover cell on a randomised schedule: the next one follows after `U(0.5, 1.5)` times 4 s. The cover cell is a relay `DROP` addressed to hop 2 (the middle relay) of a randomly chosen own, already built circuit, never to the guard (the guard would recognise it and could drop it). A relay discards a `DROP` without any answer, keeps no state for it and does not tear down a circuit that has a role (introduction, rendezvous, publish); a `DROP` counts against the per-circuit cell limit (2,000 per second) and the per-link limit, like every cell. No relay code was added; tests pin this. Relays never create cover, so cover cannot amplify. A cover cell is skipped when no circuit is open: cover is never a reason to build one. A token bucket caps cover at 1 KiB per second (burst 16 cells); real traffic never draws from it and is never delayed by it. Cover is sent in one direction only (client to relay); the return direction stays unpadded.

=== Time slices

Outgoing cells are not written when they are produced but at the next boundary of a 50 ms slice (per link, in order), at most as many per boundary as the link's write queue holds. A slice with real cells is followed by at least three slices with one cover cell each, so the end of a burst is not visible at slice resolution. A single timer entry exists only while cells or a tail are pending; an idle node runs no steady timer, and no thread is added (the existing timer thread of the link manager is used). Only an anonymity-mode node installs the shaper, and such a node never relays for others (the modes exclude each other), so only its own cells are shaped.

Latency budget: at most one slice (50 ms) per send step at the own guard link. A direct message or call signal with its acknowledgement: up to about 100 ms more (sender and receiver each shape once). Establishing a rendezvous: about six own send steps, up to about 300 ms. A large mail is paced by the write queue (at least about 5 MiB per second) and is not slower than 1153 cells divided by the queue.

=== Warm circuit pool

Up to two circuits (half of the governor pool of four) are built in advance, one at a time, only when the governor admits a build at once (the rate limit and the backoff of failed builds apply; one token is always left for real builds). The 30-second maintenance round starts at most one such build, so there is no dial storm. A warm circuit is handed out once, for a rendezvous (the circuit's last hop becomes the rendezvous point), a mailbox publish or a directory publish; the governor slot moves to the new purpose and the circuit keeps its age. An idle warm circuit older than six minutes is closed (relays sweep at ten minutes). A real build that finds the pool full closes an idle warm circuit first, so the pool never makes a real build fail. Introduction circuits are not pre-built (their last hop is chosen by the service). This replaces the sentence "every build goes to a new circuit" by: a warm circuit serves exactly one use; there is still no reuse.

=== Bandwidth budget

Expected cover: about 0.25 cells per second, i.e. about 256 B/s at the guard link (about 21 MiB per day), plus burst tails (three cells after each active slice). The cap is 1 KiB/s (about 84 MiB per day). The relay side pays about twice that, because the middle relay receives each cover cell too. Real traffic is not capped. There is no mobile or battery mode in the repository; whoever needs one uses `--anonymity-padding=off`.

=== Leak inventory after wave H

Closed or weakened: the length of a message inside its size class; the exact timing of sends at the guard link (hidden in a 50 ms slice, with a cover tail); the build of a circuit at the moment of a rendezvous or publish (warm pool).

Still open:

* the size class itself (a long message against a short one), and coarse periods of activity;
* the return direction (relay to client) has no cover and no slicing;
* the number of mailbox items per circuit (one to four) and the one acknowledgement per item;
* the build of the introduction circuit of a rendezvous (not pre-built);
* GossipSub, DHT lookups and fetches (wave J) and WebRTC media;
* a global passive observer, a small anonymity set, correlation by provoked teardown.

=== Honest limits of wave H

* The measures are verified on loopback and with a manual clock, not on real networks, NATs, under load, or against a real observer on the wire. No external cryptographic or traffic-analysis review has taken place.
* The guard itself sees the cover cells it forwards and can tell cover from payload by the cell count it relays beyond hop 1 only if it colludes with hop 2.
* A node that sends nothing for a long time still shows cover at a low rate; a node with padding off shows its real pattern.

=== Assumptions awaiting confirmation (wave H)

* *Assumption, confirmation required:* cover defaults: mean 4 s with plus or minus 50 % jitter, burst tail of three slices, cap 1 KiB/s with a burst of 16 cells, slice 50 ms (about 21 MiB per day expected, about 84 MiB per day at most at the guard link, twice that in the network).
* *Assumption, confirmation required:* the cover cell is addressed to hop 2, so the guard cannot recognise it. Alternatives: the last hop (more relay cost) or link-level padding (cheap, but visible to the guard).
* *Assumption, confirmation required:* no cover or padding in the return direction; a balance would need negotiated padding through the guard and per-circuit relay state, which contradicts "a DROP keeps no state".
* *Assumption, confirmation required:* mailbox items are not padded to a fixed count; dummy items would use up the relay rate limits (10 per minute per link).
* *Assumption, confirmation required:* the introduction circuit is not pre-built.
* *Assumption, confirmation required:* the warm pool stays on with `--anonymity-padding=off` (it is not padding and its cost is low).
* *Assumption, confirmation required:* size classes are powers of two (overhead below 2x); powers of four would give fewer classes and up to 4x overhead.
* *Assumption, confirmation required:* `--anonymity-padding` offers only `standard` and `off`; the cover budget is fixed in the code.

[[failover-rendezvous]]
*Fix wave "rendezvous after guard failover" (released in `v0.13.0`, measured).* `MultiNodeGuardFailoverTest` occasionally failed its first rendezvous after the failover with `TIMEOUT` (3 of 6 runs in an earlier measurement under load, taken before the failure message carried the state). Measured on the code before the fix, under the load profile of the earlier runs (12 busy loops pinned to two cores, Gradle itself not pinned), with diagnostic counters and a temporary identity probe on a throw-away branch: 12 runs, 2 lost to an external Gradle daemon stop, so 10 valid; in 1 of 10 the first attempt failed, in `AWAIT_RENDEZVOUS2`, with A's `rendezvous[guardConflict]` counter at 1, and B's rendezvous point (a warm circuit) was A's effective guard `K`. In every valid run the first build over `K` came only after `P`'s descriptor had left A's index (A republished 100 to 121 s after `P` went down), and A's governor reached 24 to 32 consecutive failures even with the test's shortened backoff. Cause of the flake: when the client's rendezvous point equals the service's effective guard and no other persisted guard is usable, the service can not build its rendezvous circuit and drops the rendezvous silently (see the guard-conflict oracle under <<path-policy>>). Fix: the client retries once with another rendezvous point (<<rendezvous-retry>>). Second, separate finding (production defect, from the code and `GuardFailoverScenarioTest`, not the cause of the flake): a dead primary with a valid descriptor kept being the first hop for up to 24 hours; fixed by the in-memory reachability fallback (<<guard-reachability>>). Results after the fix: see the roadmap entry of the fix wave.

*Found by the tests, not fixed here.* A restarted node is a late subscriber without catch-up: it does not see the long-running peers until their next publication (hourly). A call that the restarted node has to answer needs the caller's record; `MultiNodeCallSignalsOverCircuitsTest` therefore restarts the caller as well when the restarted node does not see it within 25 seconds, the way the other multi-node tests restart the unseen node. A catch-up path is a separate wave.

[[sybil-simulation]]
=== Sybil simulation

*What it is.* `SybilPathSimulation` (test sources of `lapis-net-onion-wire`) drives the real `OnionPathSelector`, `GuardManager` and path policy, without any network and without a mock, over a synthetic population of 100 relays in which an adversary controls a share `f` of the relays. Per client, a fresh guard manager chooses a guard; the client then builds 20 circuits. Measured: the chance that the guard is adversarial (`P(G)`), that the drawn last hop is adversarial (`P(E)`), that both are (`P(G and E)`), that at least one of the 20 circuits has both, and that the guards of two independent clients (the two ends of a conversation) are both adversarial. Each cell reports the proportion with its 95 % Wilson score interval. `f^2` is shown for comparison only (what a uniform choice without any policy would give).

*Model assumptions (assumptions, not facts).*

* 100 relays; the adversary controls 5, 10, 20 or 33 percent.
* Honest relays: reputation spread evenly over 0.5 to 0.95, every tenth without history; each in its own /16 network (a second variant puts them into 20 shared /16 networks).
* The addresses are self-declared (see <<path-policy>>), so the adversary can claim any network: `DISTINCT_V4_16` (every adversarial relay in its own /16) is the realistic attack; `SAME_V4_16`, `SAME_V6_48` and `NO_ADDRESS` show what the diversity rule alone achieves.
* The adversary's reputation is either none (`NEW`) or the maximum (`MAXIMAL`). Madli is a weight and never a gate.
* Seed `20261027`; the run is deterministic.

*Hard guarantees of the policy (asserted by `SybilPathSimulationTest` in `check`).* If the adversary's relays share one /16, one /48 or have no address, no circuit has an adversarial guard and an adversarial last hop at the same time: two relays of one network never share a path, and at most one relay of unknown network is allowed. With distinct declared addresses there is no such guarantee.

*Not modelled.* A global observer; timing correlation beyond the guard-and-exit pair; circuits with a prescribed last hop (introduction and rendezvous circuits); churn; the guard lifetime over time (the adversary's chance to be chosen at some point in 30 to 60 days); an adversary that also manipulates the honest relays' reputation.

*Honest framing.* The figures are a simulation of this code under these assumptions, not a guarantee and not a measurement of a real network. They are an input for the external review (see link:external-review.adoc[external-review.adoc]), not its result.

*Reading the table.*

=== Stream protocol `/lapis/onion/1.0.0`

Every cell is exactly 1024 bytes on the stream. There is *no length field*: the frame decoder cuts at 1024 bytes, so a frame size can never be attacker-chosen (the off-by-length class of bug found in the length-prefixed DM codec in 2026-08 cannot occur). A started frame that does not complete within the handshake window (10 s) closes the link (slowloris); an inbound link must deliver a first cell within the same window; the read-idle timeout is 5 minutes. Each link has a cell rate limit (4000 cells/s) and a write-queue cap (256 cells, about 256 KiB): exceeding either closes the link, nothing is ever buffered without bound. Deliberate simplification: back-pressure does not propagate to the previous hop's link (no coupling of circuits, no deadlock); an overfull link is closed and the circuits on it die.

Links are limited to 64 in total (reserved with a compare-and-set loop before a stream is accepted) and to 2 inbound links per remote peer. A quarter of the slots (`reservedOutboundLinks`, `maxLinks/4`) is reserved for outbound links, so idle inbound links can never prevent a relay from opening the link of its own EXTEND. An inbound link that carries no circuit is closed after 30 s (`inboundIdleWithoutCircuitTimeout`) unless it keeps delivering useful cells: only a cell processed on an existing circuit or an accepted CREATE counts as activity; PADDING and cells (RELAY, DESTROY, CREATED) for unknown circuit ids do not. A link can be reused in either direction (an inbound link carries an extend to the same peer; the remote peer id always comes from the Noise-authenticated connection, never from payload bytes), and concurrent dials to one peer share one dial. A link that is admitted but not yet ready is reused too (the caller waits for it; if it ends first the request fails, there is no silent re-dial). When two peers dial each other at the same moment, the link opened by the side with the lower peer id (compared as unsigned bytes) is canonical: a loser that was never handed out is closed at once, one that was already in use is retired by the idle check once its circuits are gone, and new requests prefer the canonical link, so the pair converges on one link without cutting live circuits. Link ids are random 64-bit values; the mapping from peer to link exists only inside the manager and is never logged. A Circuit Relay v2 connection may carry a link, but a CR-v2 relay is not an onion hop.

=== Onion keys: persistence and rotation

A relay's onion key lives 7 days; after 4 days a new key is generated and the old one stays valid as the `previous` key for the remaining 3 days (the overlap), so circuits built against a not-yet-republished descriptor still succeed. Persistence (`<data dir>/onion-relay.onionkeys`) is encrypted with the keystore passphrase: AES-256-GCM, key from Argon2id (64 MiB, 3 iterations), fresh random salt and nonce for every write, the header including the identity public key is the associated data, so the file is bound to its identity. The write is atomic (`0600` temp file, `fsync`, atomic move), the directory `0700`. Loading verifies every key binding; an expired key is dropped, a manipulated or foreign file, a wrong passphrase or out-of-range KDF parameters make the relay mode refuse to start (the message names the path, never any content). Without a keystore passphrase the keys exist only in memory (a warning is logged) and are lost on restart. The last used descriptor sequence number is persisted too; after a data loss the sequence restarts at the current epoch second, so peers do not reject new descriptors as replays.

=== Relay descriptor

`OnionRelayDescriptor` is a relay's signed, publicly enumerable advertisement: identity, its libp2p transport key (`IdentityBinding` plus an Ed25519 possession proof with its own domain tag, so an identity cannot point at a stranger's peer id), the `OnionKeyBinding`, a sequence number and a validity of at most 24 hours (never beyond the onion key). Fixed 379-byte encoding, no length field, exact length checked first, a reserved family byte that must be zero (families are not part of this wave). `PeerCapability` gets no new bit, because v0.12.0 readers reject unknown bits; the descriptor alone signals the relay property.

* *Gossip* topic `LapisNet:onion-relay-descriptor-gossip:v1`: size check, decoding and an index pre-check (duplicates, replays and stale sequence numbers are `IGNORE` and cost no budget), then a per-author (6/min) and a global (60/min) rate limit whose excess is `IGNORE` (an honest forwarder must not be penalised), then full verification; invalid is `REJECT`, duplicates, replays and capacity refusals are `IGNORE`. Logging has counters only: no peer id, no identity, no bytes.
* *Index* (`OnionRelayDescriptorIndex`): one current descriptor per identity, strictly increasing sequence numbers, high-water marks that survive eviction (bounded LRU), equivocation at the same sequence is ignored, capacity 1024; a full index never evicts a valid entry for a stranger.
* *Known limitation (Sybil):* identities are free, so an attacker can sign valid descriptors with fresh keys. About 61 such descriptors per minute exhaust the global budget at every node (honest new or rotated descriptors are then ignored), and about 17 minutes of this fill the index to its capacity of 1024, after which the attacker holds it permanently by refreshing, because a full index never evicts and updates of tracked identities are always accepted. Descriptors with random signatures only exhaust the budget at direct neighbours (REJECT is not forwarded, gossip scoring penalises the sender). Admission is not bound to a cost yet; planned mitigations are a cost per index slot (known peer record or DHT presence, proof of work, or Madli weight) or a fair per-identity or per-mesh-peer budget instead of one global bucket.
* *DHT fallback:* the descriptor is an optional part (flag `0x08`) of the node's existing directory value, because one Ed25519 key has exactly one IPNS name. It is verified with the same function as on the gossip path and must belong to the value's identity and binding. Additionally relays announce themselves as providers under the fixed key `LapisNet:onion-relays:v1` and `discoverOnionRelays` resolves the providers; this key is public, its provider set is eclipse-prone, and a result is a hint only (every descriptor is fully verified). If peer record, prekey bundle and descriptor together exceed the value limit, outbox entries are dropped first, never the descriptor or the peer record.

=== Relay mode

`--onion-relay=true` (default off). Off: no protocol handler is registered (a dial of `/lapis/onion/1.0.0` fails multistream negotiation), no onion key is created, no descriptor is published, no key file exists. The descriptor index and its gossip are attached on every CLI node (bounded, read-mostly) so a node can later choose relays. On: the node answers CREATE/EXTEND, publishes its descriptor immediately, re-announces it every 6 hours (and at once after a rotation) and checks the rotation every hour; the DHT copy is written by the node's single IPNS writer (`HeadlessSelfPublisher`), which receives the descriptor, because a second writer would overwrite the peer record.

An EXTEND is executed only towards a relay that has a verified descriptor in the local index and never with a client-supplied link specifier (a non-empty specifier is refused in this wave), so an extend cannot make a relay connect to an arbitrary host. There is no exit service: DATA delivered to a relay is answered with END. A relay's own link cap, circuit cap (1024), creation rates and cell rates apply; pending extends are bounded and time out after 10 seconds.

The relay quality tracker is local and bounded (1024 identities, day buckets, 7 days). It counts extend attempts, reachable links and early destroys with `PROTOCOL` or `AUTH_FAILED` per target relay. It is never published, there is no MadliGossip connection, and it cannot attribute a failure to a specific hop; turning it into Madli metrics is wave E.

=== Transport key

`LapisNode.create` takes a `TransportKeyPolicy`. `IdentityDerived` (the default, normal mode) keeps the key derived from the identity. `EphemeralPerRun` (anonymity mode, chosen by `NodeWiringOptions.transportKeyPolicy()`) generates a fresh Ed25519 key per process run from `SecureRandom`; it is never written and never logged, and the seed bytes the policy generated are overwritten once the libp2p key object exists (copies inside the libp2p and BouncyCastle objects are not under our control). `PeerRecord` and `IdentityBinding` are built from the identity, never from the host's PeerId, so no published object ties the identity to the PeerId of the run. The Noise handshake, the GossipSub message signature (`from` field) and the onion links use the per-run key. Relays still see a new PeerId per run; the onion layer works with identities, not PeerIds.

=== Connection confinement

Since J1b a node in anonymity mode is created with a `ConnectionConfinement` (`NodeWiringOptions.connectionConfinement()`). The allowed set is the transport peer ids of the two guards (from their current descriptors), plus the peer ids named in the `/p2p/<id>` of the bootstrap addresses while the controller allows them. It starts empty and with bootstrap peers not allowed (fail-closed).

* *No listener.* The host is built without any listen address; `LAPISNET_LISTEN_ADDR` is ignored with a warning (the address is not logged). Verified: a jvm-libp2p 1.3.5 host without a listen address starts and dials out (`LapisNodeConfinementTest`).
* *Dials.* TCP and the relay transport are wrapped in `ConfiningTransport`. jvm-libp2p 1.3.5 (`NetworkImpl.connect`, checked with `javap`) appends `/p2p/<peer id>` to every address before `Transport.dial`, so every dial path of the host (`LapisNode.connect`, `host.newStream` of DM and storage, GossipSub, bootstrap) passes the check with its target. A dial outside the set, without `/p2p` or to `/p2p-circuit` fails with `ConnectionConfinedException` before the delegate is touched: no SYN, no Noise handshake (unit test `ConnectionConfinementTest`; on a real host `LapisNodeConfinementTest`: 0 accepts at a counting listener). `LapisNode.connect` refuses such a peer before it even looks for an existing connection.
* *Existing connections.* `ConnectionConfinementHandler` runs first on both handler paths (direct and relayed inbound), before the connection cap; every handler registered through `LapisNode.addConnectionHandler` (GossipSub among them) is gated by it, so a refused connection takes no slot in the cap and is never announced. When the allowed set shrinks (bootstrap peers no longer allowed, a guard replaced) `LapisNode.closeConnectionsOutside` closes the connections outside it. A relayed inbound connection can not reach a confined node, which holds no relay reservation; the handler is the backstop.
* *Peer exchange.* jvm-libp2p 1.3.5 and 1.4.0 (checked with `javap`) have no `doPX` switch: PX peers of a PRUNE go to `GossipParams.connectCallback` (a no-op by default) after truncation to `maxPeersAcceptedInPruneMsg`. Under the anonymity policy both `maxPeersAcceptedInPruneMsg` and `maxPeersSentInPruneMsg` are 0 and the callback is an explicit no-op; the transport check is the second barrier. Tested at the parameter level; a PRUNE with PX between real nodes is not constructed in a test.
* *Bootstrap addresses.* In anonymity mode every bootstrap address must contain `/p2p/<peer id>` and must not be relayed; otherwise the start is refused with `bootstrap peer address must include /p2p/<peer id> while anonymity=on` (never silently skipped). `LapisNode.start` refuses bootstrap peers for a confined node: the controller dials them. Without any bootstrap peer the start is not refused, but such a node (no listener, no mDNS, no persisted descriptors) can reach no relay and stays `bootstrapping`: the controller logs `no-bootstrap-peers` once, the status carries `noBootstrapPeers`, the CLI prints a warning on stderr and the browser panel shows it.

`AnonymousConnectionController` (onion wire, every 30 s +/- 3 s from the supervisor and after every snapshot) keeps the state `bootstrapping` or `guards-only`:

. the guards' peer ids become the allowed guard set, and each guard is dialled when not connected (addresses from its verified peer record);
. `ready` = a full path can be selected (a check without a build), `guardLink` = a live guard connection;
. in `bootstrapping` the bootstrap peers are allowed, dialled with backoff (5 s, 15 s, 45 s, then 60 s, at most 4 per step) and asked for a snapshot (at most 4 random ones, one request per source and 10 minutes, at most 6 requests per hour in total; a source that does not speak the protocol is not asked again);
. each guard is asked once after it is connected and then every 3 h +/- 20 %;
. with `ready && guardLink` the state becomes `guards-only`: bootstrap peers are no longer allowed and every connection outside {primary, backup} is closed (a bootstrap peer that is also a guard stays). Losing that for two consecutive steps returns to `bootstrapping` (no close-and-reconnect loop).

Status (CLI start line, browser panel): `connectionState` (`bootstrapping`, `guards-only`; `unconfined` for a runtime without confinement in tests), `guardConnections`, `snapshotFetches`, `snapshotRejectedEntries`, `singleDirectorySource`, `noBootstrapPeers`, `gossipOnlyRelayView`; no address, no id. Measured on loopback (`MultiNodeRelayDirectorySnapshotTest`, six relays, one bootstrap): the client was `guards-only` 91 ms after the start of the runtime, and its first directory publication through a 3-hop circuit followed after 5.5 s; afterwards every connection of the client went to {primary, backup}.

=== Relay directory snapshot

Protocol `/lapis/onion-relay-directory/1.0.0`, one request per stream:

* Request: exactly 5 bytes, `"LNRD" | version(1)`. No parameter: the request does not tell the serving node what the asker already knows (no "since" field as a fingerprint).
* Response: `"LNRS" | version(1) | count(u16) | count x ( descriptor[379] | recordLen(u16) | record[recordLen] )`; `recordLen = 0` means no record. Limits: at most 256 entries, a record at most 1024 bytes, the response at most 512 KiB, 15 s in total. The reader checks the header fields before it allocates, decides completion from the length fields (no dependence on close semantics), rejects trailing bytes and rejects the whole response on any structural fault.
* Why the record: the first hop's dial addresses come from the guard's peer record (`OnionClientCircuit` looks them up in the peer directory) and the network-diversity locator reads peer records too. A snapshot of descriptors alone would leave the node unable to dial its guard.

*Serving side* (`OnionRelayDirectoryServer`, Q10): registered by `OnionWire.attach` on every node in normal mode, never in anonymity mode. It answers from a cached, fully encoded snapshot rebuilt at most every 30 s, with a `SecureRandom` choice of 256 when there are more. A record is attached only when the node's peer directory holds a valid one with the descriptor's identity and peer id, at least one direct address and at most 1024 bytes. Limits: 2 requests per remote peer id per 10 minutes (an LRU of 1024 buckets; weak on its own, since anonymous nodes have a fresh peer id per run), 30 per minute in total, 4 streams at once and at most 2 of them from one remote address (the IPv4 address or the IPv6 /64, because peer ids cost nothing), one request per stream, the request complete within 5 s; anything over the limits, a malformed or late request or more bytes than one request closes the stream without an answer. A refused request takes no token from any bucket (both buckets are checked before either is taken). The concurrency slot is given back as soon as the answer has been flushed, not when the reader closes the stream: the server still never closes the stream itself (an early close can drop the queued answer on some muxers), so a stream that lingers after its answer holds no slot; such streams are bounded by the global rate times the 15 s total timeout. Only counters are logged.

*Asking side* (`OnionRelayDirectoryClient`): opens the stream with `connection.muxerSession().createStream(binding)` on the existing connection, so the protocol is not registered on the asking host and the protocol set of a node in anonymity mode does not grow. Results: `Ok`, `Unsupported` (the peer does not speak the protocol, e.g. a v0.12.0 node: the controller moves to the next source; when every configured bootstrap peer answered `Unsupported` before any snapshot arrived, the gate opens 120 s later on the gossip view, see below), `Malformed`, `Timeout`, `Failed`. Implementation note: the request is written on the stream's event loop after the controller completes, because the multistream negotiation handlers (with their varint length prepender) are still in the pipeline inside `onStartInitiator` (observed as a stray `05` before the request).

*Validation* (`RelayDirectorySnapshotIngest`, "as for gossip"): each descriptor passes `OnionRelayDescriptorIndex.precheck` (duplicates, replays, stale versions cost nothing), then the budget for new identities, then `OnionRelayDescriptorIndex.add` (outer signature, identity binding, possession proof, onion key binding, validity window, strictly increasing sequence number). A record is used only when its descriptor is the current one afterwards, and only after `PeerRecord.verify`, `verifyBinding`, `verifyPossession`, expiry, at least one address `MultiaddrHygiene` allows (wildcard and multicast are blocked; loopback and private ranges stay allowed, as everywhere in this project), and identity AND peer id equal to the descriptor's; a validly signed record of another relay or peer id counts as invalid. Verified records enter the peer directory through `PeerDirectoryGossip.ingestFromSnapshot` and are never re-published (as with the DHT path). Budgets: at most 64 new identities per snapshot and 512 from snapshots in total (half the index), so the gossip path keeps at least 512 slots; more than a quarter of the entries cryptographically invalid discards the rest and blocks the source for an hour. The gossip validator and its limits (6 per author and minute, 60 in total) are unchanged; the snapshot path has its own budget, bounded by the fetch rate times 256.

*Provenance and the guard choice.* The ingest counts, per identity, the distinct sources (peer ids of the connections the snapshots came over, at most 4 per identity, an LRU of 4096 identities) that delivered a validly signed current descriptor, also when the entry was not taken for the budget. Gossip is NOT a provenance source: its `from` field is not authenticated in this codebase (NOP router validator), and a source could gossip its own entries to confirm them (deviation from the plan, which named a gossip source). A NEW guard is chosen only when the relay view is ready: answers from at least `min(2, configured sources)` distinct sources, or 120 s after the first answer once every configured source is _settled_. A source is settled when it delivered a snapshot, answered `Unsupported`, was blocked by the ingest, or could not be dialled four times in a row (backoff 5 s, 15 s, 45 s, so about 65 s). A source that is reachable but whose fetch failed (`Failed`, `Malformed`, `Timeout`, for example because its server refused the stream over its limits) keeps the gate closed; until it delivers its first snapshot it is asked again after 5 s, 15 s, 45 s and then every 60 s (within the hourly budget of 6 fetches) instead of after 10 minutes. Without this rule (security audit of wave J1b) one hostile source that answers at once, plus an honest second source whose server is kept busy for two minutes, decided the guard choice alone: every relay had one source, the preference for confirmed candidates was off, and the guards chosen from the hostile view stay for 30 to 60 days. A gate that has opened stays open. When at least 3 of all candidates are confirmed by two or more sources, only confirmed ones are offered, for the primary and for the backup (counted over all candidates, not over the pool without the primary; the J1b load series found that a threshold on the smaller pool let an unconfirmed Sybil become the backup); otherwise all. An older, validly signed version of a descriptor and a validly signed entry that was not taken for the budget also count as provenance (sources cache their snapshot for 30 s, so versions differ). This gate and preference sit in `OnionPathSelector` (`GuardChoiceGate`), so they cover both places that choose a guard: the first-hop choice of a build and the backup in `GuardManager.maintain` (which a confined node calls with `OnionPathSelector.pickNewGuard`). No diversity rule is relaxed. With a single configured source the first guard choice trusts it (Q14): logged once as `single-directory-source` and shown in the status.

*Gossip fallback.* When every configured bootstrap peer answered `Unsupported` (old v0.12.0 nodes serve no snapshots) and no snapshot has arrived, the gate opens 120 s after the last of them did, and the guard choice uses the relay view that gossip from the bootstrap peers built meanwhile, as in J1a: no provenance (gossip is not a source), so the preference for confirmed candidates does not apply. Logged once as `gossip-only-relay-view` and shown in the status (`gossipOnlyRelayView`). A bootstrap peer that is never reached does not count as unsupported: with one such peer the gate stays closed and the node stays `bootstrapping` (fail-closed). Tested in `AnonymousConnectionControllerTest`.

[[eclipse-analysis]]
=== Eclipse and partitioning analysis

There is no signed consensus as in Tor; the relay view of a confined node is the union of what its sources and guards deliver.

* *(a) A source omits honest relays.* The union over several sources and the two guards fills the gap (tested: two sources, one omits a relay, the union is complete). If all sources, or both guards, are hostile, they control the view completely.
* *(b) Sybil flood.* A source can deliver validly signed descriptors of identities it minted. At most 64 new identities per snapshot and 512 from snapshots in total enter the index, so honest relays arriving later through gossip are still accepted (tested with 1000 descriptors from one source). Over-budget entries still count as provenance after a signature check, so a flood from the first source can not keep the honest relays it also served from being confirmed by a second source.
* *(c) Targeted fake view* (relays only the victim learns about, an epistemic attack). Mitigated only for the guard choice by the gate and the preference for confirmed candidates; for middle hops it stays open.
* *(d) Replays and older versions.* The high-water marks of the index refuse them (tested: a guard snapshot with older versions changes nothing).
* *(e) A hostile guard* can not forge descriptors; it can omit relays or deliver real Sybils. The share caps of the path selection stay.
* Tested on loopback: a hostile bootstrap with 200 Sybil descriptors in diverse synthetic networks plus an honest bootstrap; no guard came from the Sybil set.

=== Why the node does not listen (Q9)

The alternative considered was: keep the listen socket and close connections from outside the allowed set after the handshake. That reveals more than not listening: with Noise XX the responder sends its static key in message 2, before it can check the initiator, so anyone who knows the address learns the PeerId of the run and that a Lapis node runs there; "handshake completes, then immediate close" is a fingerprint of anonymity mode of its own, while a closed port answers with RST and looks like no node at all; and between the connection and `ConnectionHandler.handleConnection` a prober could already negotiate streams. A node in anonymity mode never needs inbound connections: guards never dial the client, every hop is built from the client, and rendezvous runs over circuits. Hence no listener.

=== Gossip in anonymity mode

`GossipPubSub.attach(node, GossipAnonymityPolicy())`: `subscribe` refuses every topic outside `ANONYMITY_GOSSIP_ALLOWLIST` with `GossipAnonymityRefusedException` (the message names no topic), and `publish` and `publishReporting` refuse every own publication before anything is handed to the router (the leak scanner's tap sees nothing). Forwarding of other nodes' messages is the router's job and continues. The allowlist holds the shared, global topics only (anonymous peer records, service and relay descriptors, the anonymous mailbox topic, Madli vectors, peer records, prekey bundles, Veritas, Virtus LTR, Karma, post announcements); no identity-scoped topic. A test compares it with the real topic constants.

=== DHT and storage in anonymity mode

`NabuStorage.attach(..., networkMode = StorageNetworkMode.LOCAL_ONLY)` registers neither Bitswap nor Kademlia on the host and does not put the node's own addresses into its address book. `provide`, `findProviders`, `publishIpnsValue`, `registerPeerAddress`, `connectToDhtPeer` and `get` with explicit peers throw `AnonymousStorageRefusedException`. `get` without peers answers from the local and the unserved store, and otherwise from a `RemoteContentSource` if one is attached; a remotely supplied block is used only when its SHA-256 matches a raw-codec CID and is stored unserved, and a remotely supplied IPNS record is validated like a DHT answer (signature by the requested name's key, expiry). In J1a no `RemoteContentSource` exists in production, so content the node does not hold is unavailable. `DirectoryDht`, its maintenance job and the DHT outbox are not attached. `NodeWiringOptions.effective()` switches the DHT fallback, auto-relay and relay-reliability publishing off in anonymity mode even for options built in code; `resolve` refuses an explicit `true` for any of them together with `--anonymity=on`.

=== Tombstone through a circuit

A node that ran in normal mode before used to gossip its address-free tombstone (and write it to the DHT) from itself when it switched to anonymity mode, which tied the identity to the address of that run. Since J1a the `AnonymityRuntime` sends it through a circuit as the new directory object `TOMBSTONE_PEER_RECORD` (type 4) of DIRECTORY_PUBLISH. The relay validates it with the checks of the peer-record gossip validator plus "no address" and "not expired", publishes it once on the peer-record topic and answers a repeat with the same status. A relay without a peer directory (or of an older version) answers `UNKNOWN_TYPE`, and the client tries another relay. There is no DHT tombstone in anonymity mode any more: an old DHT value of the node stays visible until its validity ends (at most 24 hours). A relay that cannot store the tombstone (failing storage) answers `RATE_LIMITED`, never `ACCEPTED`, so the client moves on to another relay. If no relay accepts the tombstone, the transition is retried along the same backoff as a failed record publication (5 s, 15 s, 45 s, then once a minute) and the anonymous record is not published until it succeeds (fail-closed).

=== Lookups through circuits

Wave J2 gives a node in anonymity mode a way to content and IPNS values it does not hold, without a direct connection: its LOCAL_ONLY storage asks a `RemoteContentSource`, and the `CircuitRemoteContentSource` of the `AnonymityRuntime` turns every miss into a lookup through a circuit whose last hop is a relay of the new role LOOKUP. The relay looks the key up with its own storage (normal mode) and answers through the same circuit. The client verifies everything.

*Roles.* Client: `OnionLookupClient` (in wave J2 one request per circuit, purpose `CircuitPurpose.LOOKUP`, circuit closed after the answer, no reuse; wave J3 added reuse for timeline lookups and the NOT_FOUND cross-check, see <<lookup-consumers>>) and `CircuitRemoteContentSource` (blocking `fetchBlock` and `resolveIpnsRecord`, a small LRU cache of verified blocks of at most 64 entries and 8 MiB, `blockIfCached` that never blocks and schedules one background lookup; IPNS records are never cached). Relay: the state machine `OnionRelay` accepts the request only at the last hop of a circuit without another role (role `LOOKUP`), the host's `OnionLookupService` checks and paces, and `NabuLookupSink` asks the relay's storage. The storage of the anonymous node is bound late through `DeferredRemoteContentSource` (it is attached before the onion wire exists); it answers `null` while nothing is bound, and the source is unbound before the runtime stops. The browser has no relay mode, so the role exists only on CLI relays.

*Wire format* (lapis-net-onion, `LookupMessages.kt`, version 1). Relay commands `LOOKUP_REQUEST` (20) and `LOOKUP_RESPONSE` (21). A request body is always 720 bytes: `version(1) = 1 | requestId(1) | op(1) | flags(1) = 0 | keyLength(2) | key (at most 256) | random padding`. Operations: `GET_BLOCK` (1, key = the 36 bytes of a CIDv1 with raw codec and SHA-256) and `GET_IPNS_RECORD` (2, key = the routing key `/ipns/<Ed25519 identity multihash>`). An answer is a series of 720-byte fragments `version(1) | requestId(1) | fragIndex(2) | fragCount(2) | data(714)`; the data of all fragments is the payload `status(1) | classIndex(1) | length(4) | content | random padding`, padded to the smallest of four size classes of 2, 8, 32 and 128 KiB (header included, so the largest content is 131,066 bytes), which take 3, 12, 46 and 184 cells. Statuses: `FOUND`, `NOT_FOUND`, `RATE_LIMITED`, `MALFORMED`, `UNSUPPORTED_OPERATION`, `UNSUPPORTED_VERSION`, `TOO_LARGE`, `DISABLED`, `TIMEOUT`; every status except `FOUND` travels in class 0, so an observer can not tell an error from a small hit by its size. A wrong body length, flags other than 0 or a key length of 0, above 256 or beyond the body destroy the circuit; an unknown version or operation is answered with its status. 720 bytes fit the relay-message capacity at the maximum of five hops (929 bytes), as the two publish bodies do. There is no capability flag in the signed relay descriptor (that would be a format change, Q4).

*Verification.* The relay validates what its storage returned before it answers (a block must hash to its CID, a record must validate completely and be signed by the key its name names); content that does not verify is answered `NOT_FOUND` and its bytes are never sent. The client checks the same with `RemoteContentVerifier` (the checks `NabuStorage` uses), and the storage checks once more before it stores a block unserved. The client's reassembly is strict: request id, ascending fragment index, a fragment count that matches the class in the first fragment, a length within the class and a known status; the buffer is allocated only after the first header was checked and is at most one class large. A relay whose answer does not verify, or whose fragments are broken, gets a backoff of 24 hours, and the next relay is asked (at most two relays per lookup). Only raw/SHA-256 CIDs (the only CIDs this codebase creates) and canonical Ed25519 IPNS names are accepted at both ends, checked by hand before any parser runs: Nabu's `Cid.cast` allocates from a declared length before it checks a bound, so an untrusted key never reaches it unchecked, and no other DHT key or codec is ever looked up on a client's behalf.

*Abuse protection at the relay* (operator liability, resources). The state machine allows 4 requests per circuit, one outstanding at a time (a second one while the first is open destroys the circuit), 60 per link and 240 in total per minute; a rate limit, an unknown version or operation and a disabled role are answered by the state machine itself in class 0, without a lookup. `OnionLookupService` then applies, in this order: the key shape check; a negative cache (4096 entries, 5 minutes; it holds `NOT_FOUND` and `TOO_LARGE`); an attempt limit of 2 lookups per key and 10 minutes over all clients that ended *without content* (`NOT_FOUND`, `TIMEOUT`, content that does not verify; beyond it `NOT_FOUND` without a lookup and without a new negative entry), while a lookup that found the key clears its count and sets a _found mark_ for 30 minutes (4096 entries): during the mark a lookup of that key without content is answered `TIMEOUT`, counts as no miss, writes no negative entry and extends the mark; a spent byte budget (beyond it `RATE_LIMITED` without a lookup); at most 8 lookups at once, on a pool of its own (it never takes the dial pool that extends need); the lookup itself with a deadline of 20 s; the validation; a byte budget of 8 MiB per minute counted by size class for answers and by the bytes actually received for an oversized block or content that does not verify (Bitswap delivers the whole block before its size is known, so such a download is charged even beyond the budget and refuses further lookups until the minute turns). Answers leave at 8 fragments per 50 ms (a 184-cell answer would otherwise overflow the 256-cell queue of the link to the middle relay, and the link manager would close that link with other parties' circuits on it) and never earlier than 1.5 s plus up to 1 s of jitter after the request, cache hits and errors included. Caches and limits are keyed by SHA-256 of operation and key, never by the key; the logs carry counters and coarse reasons only, never a CID, name, link or circuit.

*The relay keeps nothing it fetched for a client.* `NabuStorage.fetchTransient` registers the Bitswap want with `addToBlockstore = false`, so Nabu writes the received block nowhere (checked in the bytecode of Nabu 0.8.0: a received block is written to the served blockstore only for a want registered with `true`); it never calls `provide`, and it never answers from the unserved store that holds what the relay itself received over anonymous paths. Exception: when the relay's own code had already registered a want for the same block, that want keeps its own setting (and an own `get` that starts while a transient want for the same block is pending receives the block without storing it).

*Trade-offs.* No positive cache: the relay keeps no content of anonymous clients, and a cache would make the answer time an oracle for what others asked. The negative cache and the attempt limit protect the relay and the DHT against repeated lookups of missing keys, at the price of a timing oracle (row 27) that the minimum delay only narrows. A relay that does not want the role answers `DISABLED` instead of destroying the circuit, so that the reliability counters of middle relays (`recordDestroyedByTarget`) do not penalise it; a relay of an older version destroys the circuit (row 28), which the client can recognise only by time and state (the destroy reason is not passed up), and backs off. Found in the tests and confirmed in the bytecode of Nabu 0.8.0: Nabu's Bitswap responder does not resend a block to a peer it already sent it to (`BitswapEngine.recentBlocksSent`, an LRU of 1000 blocks per peer for 100 peers, without expiry), so before fix wave F6 a second lookup of the same block from the same holder missed although the block existed. Since F6 the holder resends within bounds (`BitswapResendLimits`: one re-send per relay and block per 5 s, a bucket per peer and a global one), and a relay lookup inside the storage's repeat window waits for the running request or, if that one already completed, asks the holder again; see `docs/architecture.adoc`, "Bitswap resend". A second lookup can still miss without the block being gone - its only holder went offline or is at its re-send limit - and that is what the found mark keeps answering `TIMEOUT` instead of `NOT_FOUND`. The security audit of wave J2 found two ways to turn that into censorship. Round 1: the attempt limit counted found lookups too, so three requests per LOOKUP relay every five minutes made every anonymous client get `NOT_FOUND` for existing content (and cache it for 10 minutes); now only lookups without content count. Round 2: even then, a block held by one holder could be asked three times (`FOUND`, then a timeout because the holder does not resend, then an immediate miss because the storage skipped the holder it just asked - both causes are fixed since F6, but a holder at its re-send limit or offline produces the same pattern), and the two misses put `NOT_FOUND` into the negative cache. The found mark closes this: after a verified `FOUND` a miss of the same key is answered `TIMEOUT` (the client moves on to its next relay and caches nothing) and never feeds the attempt limit or the negative cache, as long as the key is asked at least every 30 minutes. Only a verified `FOUND` sets the mark, so a key that never existed gets none; content deleted after it was found is answered `TIMEOUT` instead of `NOT_FOUND` by this relay while the mark lasts. The marks share the bound of the other maps (4096 keys, least recently used first out): an attacker who gets 4096 other existing keys FOUND at the same relay (at least about 17 minutes at the limit of 240 requests per minute) pushes a mark out and can then repeat the two-miss pattern for that key; the attempt limit and the negative cache bound the damage to that relay and 5 to 10 minutes. A key that was not asked for 30 minutes loses the mark, and from then on its misses count again (the relay can then no longer tell an absent block from a holder that does not answer).

*Fail closed.* The client uses no path other than `OnionCircuitFactory.build` with the circuit policy of anonymity mode installed (governor, minimum path length, guards); without the policy, without a usable relay or in lockdown the result is `Unavailable`. A LOCAL_ONLY storage has no Bitswap and no Kademlia, so there is nothing to fall back to. Blocking calls never run on an event loop: answers are reassembled in the circuit callback, verification and the completion of futures run on the link manager's pool.

*Governor.* `CircuitPurpose.LOOKUP` is a pool purpose (part of the four client circuits) with a bucket of its own on top of the general one: at most one lookup circuit open or being built and two builds per minute (over it the build is delayed, not refused). The general bucket of six per minute is shared, so lookups use at most two of its six tokens per minute and can not starve the publications (tested). A warm circuit is handed to a lookup only if the limit of one allows it; otherwise it stays warm.

*Existing callers that now cause circuit lookups in anonymity mode* (state of wave J2, found with grep; wave J3 replaced the timeline path, see <<lookup-consumers>>): the browser timeline (`BrowserApi`, `storage.get(entry.cid)` for post bodies it does not hold) now schedules a background lookup per missing body through `blockIfCached`; the body appears on a later request. The IPNS resolution of `DirectoryDht` is not attached in anonymity mode (DHT fallback off). The DM attachment fetcher, the mailbox poller and the inbox fetcher pass explicit peers and stay refused in LOCAL_ONLY; the mail API reads only the local blockstore in anonymity mode. _Wave Q21: both attachment routes now fetch a blob that is not local from the sender's onion service, and as a last resort through one MAILBOX lookup (<<attachments-over-circuits>>)._ `NabuStorage.getThroughRemote` is the explicit blocking call for the consumers of J3 and the multi-node test.

*Throughput (wave J2).* One lookup at a time and two lookup circuits per minute mean about two lookups per minute per client. That is tight for the timeline consumers of J3 (many blocks) and noted in the roadmap.

[[lookup-consumers]]
=== Lookup consumers and circuit reuse (wave J3)

Wave J3 connects the lookups of J2 to their consumers, raises the throughput for timeline posts by reusing circuits, cross-checks a `NOT_FOUND` at a second relay, shows lookup counters in the status and replaces the start warning. The wire format (LOOKUP version 1), the relay limits, the governor (one open LOOKUP circuit, two builds per minute) and every persisted format are unchanged; there is no batch operation (Q16). _Superseded by wave Q16: LOOKUP version 2 adds a batch operation for timeline block lookups, see <<lookup-batch>>._

*What the code showed before J3 started* (these findings changed the premises of the design draft):

. *Post bodies are not announced in the DHT* (Q20). `PostAnnouncementGossip` carries the body in the gossip message; `NabuStorage.put` does not call `provide`, and the only `provide` calls in production code are the rendezvous keys of `DirectoryDht`. The relay side (`fetchTransient`) finds content only through `lookupProviders`, so without a provider record a lookup ends `NOT_FOUND`. A timeline lookup through circuits therefore finds a body in the real network only where a node `provide`s it; the multi-node tests call `provide` explicitly. J3 builds the consumer and adds no `provide` (that would mean DHT load and visible holder sets, a separate wave). _Superseded by wave Q20 (released in `v0.13.0`): nodes in normal mode now announce the newest post bodies they hold; see <<post-body-provides>>._
. *The mailbox poller does not run in anonymity mode* (Q21). `DmSessionManager` returns without `DmProtocol` and without a poller when the mode is on; mailbox blobs, DM and mail bodies travel in-band over circuits. The only content consumers left are the attachment paths (`MailApi`, `DmApi`), which answer `attachments-unavailable-anonymous`; attachments can be larger than the largest lookup answer (131,066 bytes) and are not provided either. J3 wires no MAILBOX consumer; the context exists in the client and is tested. _Superseded by wave Q21 (released in `v0.13.0`): attachments are fetched from the sender's onion service; the MAILBOX lookup is wired only as a last resort, see <<attachments-over-circuits>>._
. *No IPNS consumer runs in anonymity mode* (Q18). `NabuStorage.resolveIpnsValue` in LOCAL_ONLY already goes through the circuit source (J2), but `DirectoryDht` is attached only with the DHT fallback, which is off in this mode, and no `OnionServiceDht` is published. Wiring directory reads (prekey bundles, peer records) through `GET_IPNS_RECORD` would tell the exit relay "someone wants to reach node X" (not who asks); that needs a decision and is not built.
. *Rendezvous records are provider keys* (`MessagingRendezvous`, `OnionRelayRendezvous`, FIND_PROVIDERS) and can not be reached with LOOKUP version 1. They stay unreachable (Q18).

*Contexts.* `OnionLookupClient` knows three contexts (`LookupContext`): `TIMELINE`, `MAILBOX` and `IPNS`. A circuit only ever carries lookups of one context. Identical keys are merged only within a context, and the negative cache is kept per context, so two consumers never share a circuit or an answer. A blocking `CircuitRemoteContentSource.fetchBlock` is a `MAILBOX` lookup (no production caller in J3; since wave Q21 the last-resort attachment fallback), an IPNS record always an `IPNS` one, the background lookups of the timeline are `TIMELINE` lookups.

*Circuit reuse* (Q15). A `TIMELINE` circuit is kept after a verified answer (`FOUND` or `NOT_FOUND`) for the next lookup only if all of these hold: the next queued lookup is a `TIMELINE` lookup whose deadline has not passed and which this exit has not answered `NOT_FOUND`; the exit is not on backoff; the circuit carried fewer than 4 requests (`requestsPerCircuitTimeline`, never more than the relay's limit of 4, checked once more right before sending); the circuit is younger than 10 minutes minus the answer timeout (45 s) and the build timeout (20 s), so an answer always arrives before the relays close the circuit at 10 minutes. Otherwise the circuit is closed at once. There is no idle hold: a held circuit would block the single lookup slot of the governor for every other context. `MAILBOX` and `IPNS` lookups use one circuit per request. Every answer on a reused circuit is verified like the first one, with a fresh request id and a fresh reassembly; a manipulated answer closes the circuit and puts the relay on the 24-hour backoff, and the next lookup builds a new circuit to another exit. A destroy of a reused circuit is a plain failure, never the "older relay" verdict (its relay has answered a lookup already). With all four requests of each circuit answered, two builds per minute give up to 8 timeline lookups per minute; cross-checks and failures lower that.

*Cross-check of NOT_FOUND* (Q17). A `NOT_FOUND` from one relay is asked again at a second relay (a different exit, a new circuit) while an attempt is left (at most two relays per lookup for all kinds of error together). Two `NOT_FOUND` give a confirmed result, cached for 10 minutes; a cross-check that is impossible (no other usable relay) or ends without an answer (timeout, refusal, manipulation, admission) gives an unconfirmed `NOT_FOUND`, cached for 2 minutes only, and an unconfirmed result never overwrites a confirmed one that is still valid. A second relay that delivers what the first answered `NOT_FOUND` for is believed; the first relay is not penalised (a `NOT_FOUND` is not provably a lie: the Bitswap gap, a provider walk that ends early), only a counter records it.

*Queue.* At most 32 lookups wait behind the running one, of them at most 24 timeline lookups; a full timeline share drops the oldest waiting timeline lookup, never a lookup of another context. *Governor refusals.* When the governor answers `POOL_FULL` (right after the start the node's own circuits, introduction points, publications and the warm pool, can fill the four client circuits for a moment) or `RATE_LIMITED` (the build budget, or the backoff of up to 5 minutes after failed builds, would delay the build beyond 30 s), the lookup pauses for 500 ms and tries again until its deadline; this uses no attempt and gives no verdict about a relay. In J2 both ended the lookup `Unavailable` at once; the load series of J3 showed this as failures of the first lookups after a start (`RATE_LIMITED` 276 times in one run, `POOL_FULL` or `RATE_LIMITED` in another). A refusal by lockdown, a path that is too short or a missing circuit policy still ends the lookup at once (fail closed).

*Timeline consumer.* `GET /api/timeline` in anonymity mode reads each post body through `NabuStorage.localOrRemoteState`, which never blocks on the network: the local stores first, then the view of the circuit source (`RemoteContentSource.blockState`: a verified block in its cache, a running lookup, or the memo of recent outcomes, at most 1024 entries: a confirmed `NOT_FOUND` for 10 minutes, an unconfirmed one or a failed lookup for 2 minutes; a lookup that reached no relay, was dropped by the queue or ended by a close is not remembered, so the next request asks again; the memo holds states, never content). A miss starts a background `TIMELINE` lookup, newest posts first, at most 8 new lookups per request; the next request starts the next ones. The response keeps its order. A post without its body carries the fixed marker as text and one of four states in `contentState`: `local`, `fetching`, `not-found` (only when two relays agreed) and `unavailable` (an unconfirmed `NOT_FOUND`, a failure, or no lookup started yet). The browser shows _Fetching through circuits; reload to see it._ or _Not found through two relays._ (fixed texts, `textContent`, no animation, no automatic reload, no re-sorting) and the marker otherwise. In mode off the timeline uses `storage.get` exactly as before (`contentState` `local` or `unavailable`).

*Status counters.* `OnionLookupClient.statusCounters()` gives `requested`, `found`, `notFound` (confirmed), `notFoundUnconfirmed`, `failed` and `rejected` (answers that did not verify), plus the number of lookup relays known, available and on backoff, numbers only. `requested` counts every caller request including negative-cache hits and merged duplicates; every lookup that ends counts once in `found`, `notFound`, `notFoundUnconfirmed` or `failed`. The browser status shows them as one line: _Lookups: {requested} asked, {found} found, {notFound} not found ({unconfirmed} unconfirmed), {failed} failed, {rejected} rejected; {available} of {known} lookup relay(s) available, {backoff} on backoff_. The static line about the mesh now reads _Network mesh: guards only (they see your address); missing posts are looked up through circuits_ (the old line "direct, identity and address are visible" had been wrong since J1a). All lookup numbers are 0 in mode off.

*The found mark and an attacker who asked first* (tested in `OnionLookupClientReuseTest`, T-C5). A relay that once fetched a block from its only holder can not fetch it from that holder again (Bitswap gap, see J2). While the relay's found mark lasts (30 minutes, renewed by every miss) it answers such a lookup `TIMEOUT`: the client puts that relay on the 30-second failure backoff and asks another relay; if no other relay is usable the result is `Unavailable` (denied, nothing cached), never `NOT_FOUND`. Only after the mark has expired, or at a relay that never found the block, can a miss end `NOT_FOUND`; with the cross-check, a block held by a single holder is then reported `NOT_FOUND` only if both chosen relays miss it, and confirmed only then.

At every start, and while it lacks relays or a guard connection, it also connects to its bootstrap peers, which see your address. Missing posts are looked up through circuits: the last relay of a circuit sees what is asked and when, but not by whom, and up to four post lookups on one circuit are linked to each other; such lookups find a post only if a node in normal mode announces it in the DHT, which nodes do for the newest posts they hold. Attachments are fetched from the sender's onion service while the sender is online (up to 4 MiB each); inbox rendezvous records are not reachable in this mode. Posting, votes and trust grants are unavailable._ The text no longer claims that mail or names are fetched through circuits (no such consumer is wired in this mode); Q15 was confirmed as up to four requests per circuit, so the sub-clause about four linked lookups stays. Wave Q21 replaced the sentence _Attachments and inbox rendezvous records are not reachable in this mode._ by the attachment sentence above (decision Q21-F, *confirmed by the user (2026-11-22)*).

=== Batch lookups (wave Q16, LOOKUP version 2)

Wave Q16 lets a client ask one LOOKUP relay for up to 8 keys of one operation in a single request (the client sends up to 4). It exists for the timeline consumers of J3: until then they asked their exit one key at a time on a reused circuit, each round trip costing the relay's minimum answer time of 1.5 s plus jitter, and the lookup slot of the governor (one open LOOKUP circuit, two builds per minute) stayed busy for all of them. A batch costs one such round trip plus the slowest lookup. *The throughput bound does not change with the defaults:* with 4 keys per circuit and two builds per minute the client still reaches at most 8 lookups per minute; the gain is latency and an earlier free lookup slot. More throughput would need a larger key budget per circuit and therefore more linkability for the exit relay (see the decisions below). All limits in this section are *provisional and were not measured in a pilot*; nothing here is a claim of anonymity, and no external review has taken place.

[kuml, lookup-v2-batch-sequence, svg]
----
import dev.kuml.core.dsl.sequenceDiagram

sequenceDiagram(name = "LOOKUP version 2 batch with version 1 fallback") {
    val client = lifeline(name = "Client")
    val guard = lifeline(name = "Guard")
    val middle = lifeline(name = "Middle")
    val exit = lifeline(name = "Exit (LOOKUP relay)")

    message(from = client, to = guard, label = "RELAY LOOKUP_REQUEST v2 (op, up to 4 keys)")
    message(from = guard, to = middle, label = "forwarded unchanged (720 bytes)")
    message(from = middle, to = exit, label = "forwarded unchanged (720 bytes)")
    reply(from = exit, to = client, label = "LOOKUP_RESPONSE v2: item 0, item 1, ... in order, after the slowest item")
    reply(from = exit, to = client, label = "relay of 0.13.0 instead: UNSUPPORTED_VERSION (v1 framing), circuit stays open")
    message(from = client, to = guard, label = "fallback: LOOKUP_REQUEST v1 (one key), no penalty")
}
----

*Wire format.* The relay commands stay `LOOKUP_REQUEST` and `LOOKUP_RESPONSE`; the first byte is the version.

* Request, always 720 bytes: `version(1) = 2 | requestId(1) | op(1) | flags(1) = 0 | itemCount(2) | items: [keyLength(1) | key] x itemCount | random padding`. One operation per batch. `itemCount` is 1 to 8, a key is 1 to 64 bytes (a CID is 36 bytes, an IPNS routing key about 44), duplicate keys in one batch are refused. A broken batch destroys the circuit, as a broken version-1 request does.
* Answer: per item the unchanged payload `status(1) | classIndex(1) | length(4) | content | random padding`, padded to the smallest class (2, 8, 32, 128 KiB), in fragments `version(1) = 2 | requestId(1) | itemIndex(1) | fragIndex(2) | fragCount(2) | data(713)`. The fragment counts per class stay 3, 12, 46 and 184, so there are no new size classes and the largest content stays 131,066 bytes. Items come strictly in request order, the fragments of one item contiguously. A status other than `FOUND` is always class 0.
* The `itemCount` field sits where version 1 carries its key length (bytes 4 and 5) and byte 3 is zero on purpose: a relay of 0.13.0 checks the length, `flags` and a key length of 1 to 256 *before* it looks at the version, so it answers a version-2 request with `UNSUPPORTED_VERSION` (three fragments, version-1 framing) and keeps the circuit instead of destroying it. A unit test runs the unchanged version-1 decoder over batches. A relay of 0.12.0 destroys the circuit as before (leak row 28).
* A refusal of the whole batch by the relay (rate limit, lookup role off, unknown operation) is answered per item, in class 0, in version-2 framing, so it costs as many cells as the same number of misses.

*Compatibility.* There is no version negotiation round trip and no descriptor flag: a client sends version 2 only when two or more timeline block lookups are waiting, and only to an exit it does not know to be version-1 only. If the exit answers `UNSUPPORTED_VERSION` (or, as an older relay does before it looks at the version, `RATE_LIMITED`) in the version-1 framing as the first answer, the client accepts exactly these two and no other version-1 answer to a version-2 request; it remembers the exit as version-1 only for 6 hours (memory only, 1024 entries, never persisted) and sends the group on as version-1 requests over the same circuit, without any penalty for the relay. Every other deviation is a manipulation.

*Relay side.* `OnionRelay` counts the batch as one request against `lookupRequestsPerCircuit` (4) and its items against the new `lookupItemsPerCircuit` (16, provisional); beyond it the circuit is closed with `RESOURCE_LIMIT`. The per-link and global counters are charged *per item*, all or nothing, so batching does not loosen the abuse limits. The item count is read before the full decode; nothing is allocated from declared lengths. `OnionLookupService.onBatch` runs every item through the same admission as a single lookup, in the same order (shape check, negative cache, attempt limit, byte budget), the in-flight limit applies per item (the excess of a batch gets `RATE_LIMITED` for those items), content is verified at the relay as before, and nothing unverified is sent. The whole answer leaves no earlier than the minimum answer time plus jitter after the batch arrived and only when the slowest item is done, paced at 8 fragments per 50 ms over all items. Worst case about 32 s for 8 largest-class items, below the client's 45 s answer deadline (plus an allowance per extra item).

*Client side.* Only `TIMELINE` block lookups are batched; `MAILBOX` and `IPNS` keep one circuit and one request each. A group is formed when the request is sent: the lead lookup plus waiting timeline lookups for which this exit is neither one that answered `NOT_FOUND` nor one that refused them (at most `batchItemsTimeline = 4` and never more distinct keys than `itemsPerCircuitTimeline = 4` over the life of the circuit; a circuit therefore shows its exit at most the 4 keys Q15 allowed). Each item is verified on its own against its CID (the IPNS rule is the same). If any item is manipulated (a block that does not hash to its CID, `MALFORMED` for a key the client had checked) the relay gets the 24-hour backoff once and the circuit is closed; items verified by their hash are still taken, the others go on at another relay. Without manipulation each item follows the J3 rules: `FOUND` ends it, `NOT_FOUND` is cross-checked as a group at a second exit (Q17), a refused item is asked elsewhere without penalising the relay unless the relay refused every item, in which case it gets the usual failure backoff once. Counters in the status are unchanged: every key still counts exactly once as found, not found, unconfirmed or failed.

*Anonymity assessment (no claim of anonymity).*

* *Linked sets.* The exit relay links the keys of one batch. With the default budget that is no more than before (4 keys on a reused circuit were already linked by the circuit); the batch only shows them as one simultaneous set instead of one after another, and the order "newest first" shows a slice of the timeline as before. The retried items of a cross-check go together to the second exit and are linked there as well.
* *Version fingerprint (new, leak row 30).* A version-2 request tells the exit that the client runs wave Q16 or later and splits the set of clients by version. Single lookups stay version 1 and show nothing.
* *Downgrade.* A relay can force version 1 with `UNSUPPORTED_VERSION`. Version 1 links the same or fewer keys; the cost is latency only. The client does not penalise it, so a relay cannot use the penalty to play clients against other relays.
* *Selective censorship of single items* stays possible as in version 1 and is caught by the per-item cross-check.
* *No dummy items.* Random keys would make the relay run DHT walks for a stranger and the exit knows the item count anyway.
* *Network observer.* The request is always 720 bytes and hides the item count. The answer is one burst whose length is the sum of the items' fragment counts; some sums point to one composition (for example 187 = 184 + 3). That is not worse than separate bursts in version 1 and gives no new guarantee.
* *Rejections* come per item in class 0 and look like that many misses.
* *Timing oracle.* See leak row 27: narrowed in batches, not closed.
* *Load.* The per-item counters, the per-item in-flight limit and the byte budget keep an anonymous client from getting more work out of a batch than out of the same number of single requests; one batch can fill the relay's lookup pool, and the excess is refused per item (a fairness cap per batch is open, decision Q16-C).

*What does not change.* Version 1 is byte-identical (golden test). The governor (one open LOOKUP circuit, two builds per minute), the circuit lifetime, the 4-request limit per circuit, the start warning, the browser texts and every persisted format are unchanged. There is no new option and no descriptor field.

*Honest limits.*

* Verified on loopback only (unit tests, multi-node tests with a relay of 0.13.0 behaviour and a relay without the lookup role); no real network, no pilot measurement of the limits.
* The throughput stays at 8 lookups per minute with the defaults; a higher key budget per circuit would raise it and the linkability together.
* Single lookups stay version 1, so the fingerprint only appears for groups; two code paths have to be kept.
* IPNS batches are supported by the wire format and the relay but not used by any client (the IPNS consumer is open, Q18).
* No external cryptographic or anonymity review has taken place.

*Decisions (Q16-A to Q16-F), each implemented with the conservative variant and open for the user to change:*

* *Q16-A, key budget per timeline circuit:* 4 (as Q15). 8 would double the throughput bound and the number of linked keys and would change the start warning in three files.
* *Q16-B, sizes:* 4 items per request from the client, 8 on the wire, 16 items per circuit at the relay.
* *Q16-C, fairness:* a batch may use all 8 in-flight places of the relay; the excess gets `RATE_LIMITED` per item. A cap of half could be added.
* *Q16-D, answer strategy:* all items together after the slowest (narrows the timing oracle, costs latency); streaming item by item is the alternative.
* *Q16-E, partly manipulated batch:* items verified by hash are kept; the alternative is to discard all.
* *Q16-F, memory of version-1-only exits:* 6 hours, memory only; release assignment: with the next release after `v0.13.0`.

=== Post body provides (wave Q20, released in `v0.13.0`)

A browser node in normal mode now announces (DHT `provide`) the bodies of the newest posts it holds, so that a node that missed the gossip, and the LOOKUP relay of an anonymous client, can find a holder. `NabuStorage.put` still does not provide anything; `BlockProvideScheduler` in `lapis-net-storage` does, fed by `PostAnnouncementGossip` after a body was stored. Version, wire format and persisted formats are unchanged.

* *Scope:* own and received posts alike, on the same code path; at most 256 tracked bodies per node (the oldest-tracked one drops out), each re-announced every hour +/- 10 %, a newly tracked body after a random delay of 0 to 2 minutes. At most 2 announcements per 15-second cycle, fanout 10. Nothing is announced in anonymity mode (no scheduler is created; `--provide-post-bodies=true` together with `--anonymity=on` refuses the start).
* *Only served blocks:* before each announcement the scheduler checks the served (public) blockstore; blocks received over anonymous paths live in the unserved store and are never announced.
* *Metadata:* see leak 29. The DHT peers near a post learn that this node holds it; holders form a visible set per post.
* *After a restart* only posts that arrive or are created again are announced: the tracked set lives in memory, and the post index is not reloaded.
* *Measured on loopback (wave Q20 tests):* a body that the holder only tracked reached an anonymous client through a circuit. In the same run a body the holder did NOT track was found as well, because on loopback the relays have the holder in their routing table and Nabu's responder names itself for blocks it holds; in a real network that happens only when a lookup's walk reaches a holder. With two holders and the same exit relay, the second lookup of the same body was `Unavailable` (12 of 12 runs of the Q20 load series; the Bitswap gap at the relay, see below). The untracked control body was found in 12 of 12 runs. Since fix wave F6 the tests assert `Found` for that second lookup, and for a second lookup through the same exit with a single holder (measured values in the roadmap, fix wave F6).
* *Bitswap gap, addressed in fix wave F6:* Nabu's `BitswapEngine.recentBlocksSent` (a private map without expiry) kept a holder from sending the same block to the same relay again, also with a single holder. Since F6 `RefreshableBitswapEngine` reads that map through reflection and lets a re-send through within `BitswapResendLimits` (see `docs/architecture.adoc`, "Bitswap resend"). Remaining: the workaround depends on a private Nabu field (fail-safe, guarded by a test), and a holder at its re-send limit stays silent like before.
* *Open, not confirmed by the user:* F1 whether the switch should follow `--dht-fallback` (today independent, default `true`); F2 pressure on other nodes' provider stores (body keys share the LRU of 1,024 keys per node with the rendezvous records of offline mail, DM and onion relays, so many distinct posts can displace rendezvous records; a separate partition would be a follow-up wave); F3 the numbers (fanout 10, 256, 1 h, 2 per 15 s) are provisional, not measured in a pilot; F4 own posts are not held longer than received ones (that would point at the author); F5 the wording of the start warning; F6 the Bitswap gap (addressed in fix wave F6, released in `v0.13.0`).
* *Rollback:* an older version refuses the unknown key `provide-post-bodies` in arguments, environment or `browser.properties` and does not start; remove the key before downgrading.

=== Honest limits of wave J2

* The exit relay of a lookup learns the CID or IPNS name and the time of the query (not the client's address); the relay's own DHT and Bitswap queries show the relay, with its address, as the asker to providers and DHT peers.
* A single relay can deny an answer (`NOT_FOUND`) or serve an older but valid IPNS record; the client can not tell. `NOT_FOUND` is not cross-checked with a second relay (the budget of two builds per minute); freshness of IPNS records is not provable.
* The negative cache and the attempt limit are a timing oracle for "someone asked this key recently" (row 27); the minimum answer delay narrows it only.
* About two lookups per minute per client. Before fix wave F6 a holder never resent a block to a relay it already sent it to (Nabu's responder keeps no expiry for that), so a relay could serve a block held by a single holder about once. Since F6 the holder resends within bounds (one re-send per relay and block per 5 s, a per-peer and a global bucket); a relay whose holder is at that limit, or offline, still misses: such lookups end `TIMEOUT` while the found mark lasts, and the client asks its next relay. Once the mark has expired without lookups, such a miss counts again and can end `NOT_FOUND` (negatively cached for 5 minutes). The global re-send bucket of a holder can be emptied by about 20 identities; re-sends of that holder are then denied for every relay until it refills (first sends are not affected). A positive cache is ruled out above.
* Older relays destroy a lookup circuit; middle relays then count that against them (row 28). There is no capability flag in the descriptor. The client recognises such a relay only by time and state (the destroy reason is not passed up): a DESTROY from the network within 1.5 s of the request and before the first answer fragment puts the exit relay on the 30-minute backoff, so a middle relay that goes down in that window is still misread as an older exit relay. A later DESTROY counts as a plain failure (30-second backoff); a broken guard link, a local close and the end of the caller's deadline give no verdict about the exit relay. The client believes a `NOT_FOUND` of the first relay and caches it for 10 minutes; a lying exit relay can therefore still hide one key from one client for that time (cross-checking a `NOT_FOUND` at a second relay is left to wave J3). It can no longer end a lookup with other answers: `MALFORMED` for a key the client checked itself is a provable lie (24-hour manipulation backoff, the next relay is asked), and `TOO_LARGE` moves on to the next relay with the 30-second failure backoff.
* The timeline schedules lookups for the post bodies it is missing: the LOOKUP relays learn which posts the user views (bounded by the queue of 32 and the build rate).
* Provider lists are never returned to the client: providers are resolved inside the relay as part of `GET_BLOCK` (the client could not use a list without a direct dial).
* Verified on loopback only, with unit and multi-node tests and a load series (details in the roadmap); no real network, no NAT.
* Known, unchanged: `DmSessionManager.send` holds its per-peer lock while it dials (up to 15 s of queueing).
* No external cryptographic or anonymity review has taken place.

More configured bootstrap peers raise the cost: the attacker then has to make every other source undialable, not only one. An explicit `--onion-relay-lookup=true` with `--anonymity=on` refuses the start (as Q6); without `--onion-relay` it is a warning without effect. Older relays destroy the circuit and the client backs off (row 28).
* *Q5, own publications:* refused with 409 (`anonymity-publish-unavailable`) in this wave; a relay role `GOSSIP_PUBLISH` later. Implemented in J1a.
* *Q6, option conflicts:* an explicit `--auto-relay=true`, `--publish-relay-reliability=true` or `--dht-fallback=true` with `--anonymity=on` refuses the start; a missing key resolves to off. This tightens the earlier behaviour (D-rows 11 and 12 were allowed). Implemented in J1a.
* *Q7, tombstone:* through a circuit as directory object type 4; no DHT tombstone in anonymity mode (an old DHT value stays visible up to 24 hours); no IPNS write through a relay. Implemented in J1a.
* *Q8, LOOKUP constants:* largest answer 128 KiB, size classes 2, 8, 32 and 128 KiB, 4 requests per circuit at the relay and 1 by the client, at most 1 open LOOKUP circuit and 2 builds per minute within the existing pool. Confirmed by the user on 2026-11-17, implemented in J2 with these precisions and additions: (a) 128 KiB is the padded answer including a 6-byte header, so the largest content is 131,066 bytes, with 3, 12, 46 and 184 cells per class; (b) at the relay at most one outstanding request per circuit (sequential within the 4); (c) Q8 names no values for the following, which operator liability and resources need: 60 requests per link and minute, 240 in total per minute, 8 lookups at once, a byte budget of 8 MiB per minute, a negative cache of 4096 entries for 5 minutes, an attempt limit of 2 per key and 10 minutes (since the J2 security audit: lookups without content only), a relay lookup deadline of 20 s, pacing of 8 fragments per 50 ms, a minimum answer time of 1.5 s plus up to 1 s of jitter; (d) the result is about two lookups per minute per client, tight for J3.
* *Q9, listen socket:* the review of the proposal (keep listening, close foreign connections after the handshake) found that it reveals the PeerId of the run and a fingerprint of its own (see the section above); proposed, confirmed by the user on 2026-11-17: no listener in anonymity mode, a backstop handler for any connection from outside the allowed set, an explicit `LAPISNET_LISTEN_ADDR` ignored with a warning. Implemented in J1b.
* *Q10, who serves snapshots:* every node in normal mode with the onion wire registers the server; the only change in normal mode is one more protocol id (alternative: relays only, which would leave bootstrap peers that are no relays without an answer). Confirmed by the user on 2026-11-17, implemented in J1b.
* *Q11, topic coverage:* documented and measured only; relays do not change their subscriptions (that would change normal mode). Alternative: relays subscribe to the whole allowlist with real validators. Confirmed by the user on 2026-11-17 for J1b.
* *Q12, constants:* 256 entries, record at most 1024 bytes, response at most 512 KiB, 15 s; server 2 per peer and 10 minutes, 30 per minute, 4 at once and 2 per address, request within 5 s, cache 30 s; client one request per source and 10 minutes (retry of a source without a snapshot yet after 5 s, 15 s, 45 s, then 60 s), at most 6 per hour, guard refresh 3 h +/- 20 %; ingest 64 new identities per snapshot, at most 512 from snapshots, block for an hour above 25 % invalid; gate 2 sources or 120 s once every source is settled (a source counts as unreachable after 4 failed dials), preference with at least 3 confirmed candidates; hysteresis 2 steps. Confirmed by the user on 2026-11-17, implemented in J1b.
* *Q13, persistence:* descriptors and records are not persisted, so every start contacts the bootstrap peers (row 23); persisting the guards' descriptor and record is a later format change. Confirmed by the user on 2026-11-17 for J1b.
* *Q14, a single source:* the first guard choice trusts it, with the status flag and the log line `single-directory-source` (alternative: refuse the guard choice until two sources answered, which would leave a node with one bootstrap peer without guards). Confirmed by the user on 2026-11-17, implemented in J1b.


[[attachments-over-circuits]]
== Attachments over circuits (wave Q21, released in `v0.13.0`)

*Status:* released in `v0.13.0`; the detailed design (decisions Q21-A to Q21-I below) is *confirmed by the user (2026-11-22)*; the fetch token was changed to a derived key in wave Q21-Token. Anonymity mode stays experimental and off by default (`--anonymity=off`). No external cryptographic or anonymity review has taken place. Verified on loopback only.

*What the code showed first.* Mail attachments already arrived in band with the mail (the `CIRCUIT` bundle, at most 1 MiB and 16 attachments). Direct-message attachments were refused entirely in anonymity mode (409). No node announces attachments in the DHT, and an anonymous sender can not (`LOCAL_ONLY`, no listener), so a MAILBOX lookup through LOOKUP relays finds nothing between two anonymous nodes in a real network; on loopback it does, because the responder names itself. LOOKUP version 1 carries at most 131,066 bytes per block, and the circuit governor allows one open lookup circuit and two builds per minute. Every anonymous DM or mail node already runs an onion service (`OnionServiceStreamRouter`, applications `DM` and `MAIL`). This is why the recipient now fetches the blob *from the sender's onion service* (Q21-A) instead of through LOOKUP relays.

=== Flow

. B (recipient, anonymity mode) opens `GET /api/dm/attachment/{peer}/{cid}` or `GET /api/mail/attachment/{cid}`.
. A blob held locally (served or unserved store) is served as before.
. Otherwise `AnonymousAttachmentFetcher` (browser) asks `OnionAttachmentClient` (`lapis-net-dm-onion`): it resolves the sender (DM: the inbound peer; mail: `envelope.sender`) in the local anonymous directory only (never the DHT), opens one rendezvous stream to the sender's onion service with the new application `ATTACHMENT(3)` (`AnonymityRuntime.connectToService`; never a direct connection) and sends one fetch request.
. A (sender) answers with `OnionAttachmentServer`: it checks the request, looks the CID up among the attachments it *sent itself* (`BrowserOutboundAttachmentSource`, Q21-G), compares the fetch token in constant time, loads the blob locally and sends the answer after the minimum delay, paced.
. B checks every chunk header before anything is allocated for its data, the index sequence, the class against the length, the length against what it accepts, and finally the SHA-256 of the blob against the CID. A verified blob is stored *unserved* (`putUnserved`), so a second download is local and the blob is never served or announced, not even after a switch to normal mode. Then the DM blob is decrypted and its length checked (`DmAttachmentFetcher.decryptVerified`), a mail blob decrypted as before.
. Only if the sender's service was not reachable (or the stream closed) and the blob fits one lookup (at most 131,066 bytes), one MAILBOX lookup through a circuit is tried as the last resort (Q21-B): best effort, it finds only what a node in normal mode happens to announce.

=== Formats (new, additive)

All new formats are version 1; nothing existing changes (LOOKUP version 1, `DmContentCodec`, `AttachmentRef`/`DmAttachmentRef`, sealed items, the mail bundle, every persisted format, every cryptographic primitive). The signed `AnonymousPeerRecord` gets no capability flag (that would be a format change): an older node does not know the application id, closes the stream after its HELLO timeout, and the fetching side reports `NOT_REACHABLE`.

* *Request* (`AttachmentFetchCodec`, frame type 6 in `DmCircuitFraming`), always 720 bytes: `version(1) = 1 | flags(1) = 0 | cidLen(2) = 36 | cid(36, CIDv1 raw SHA-256) | token(32) | random padding`. The CID bytes are checked by hand before `Cid.cast` (that one allocates from a declared length first).
* *Answer chunks* (frame type 7), each payload exactly the size of its lookup class: `status(1) | classIndex(1) | chunkIndex(2) | chunkCount(2) | totalLength(4) | data | zero padding`. The header is 10 bytes, so a 128 KiB chunk carries 131,062 data bytes. Zero padding is enough because the stream is end-to-end encrypted (same reasoning as `FrameSizeClasses`); the frames have fixed sizes, so `--anonymity-padding=off` changes nothing here.
* *Status values:* `FOUND(0)`, `NOT_FOUND(1)`, `RATE_LIMITED(2)`, `MALFORMED(3)`, `TOO_LARGE(6)`. Every status other than `FOUND` is one class-0 chunk with `totalLength = 0`, as small as the smallest hit.
* *Fetch token* (Q21-D, changed in wave Q21-Token): first a token key `K_t = HKDF-SHA256(ikm = attachment key, salt = empty, info = "LapisNet:attachment-fetch-token-key:v1" || cid bytes, L = 32)`, then `token = HMAC-SHA256(key = K_t, msg = "LapisNet:attachment-fetch:v1" || cid bytes)`; compared with `MessageDigest.isEqual`, a new `HKDFBytesGenerator` and `HMac` (BouncyCastle) per call, the derived key is zeroed after use. The attachment key is used for AES-GCM and as HKDF input only; the HMAC key is a separate HKDF output bound to the CID (wave Q21-Token). A new construction from existing primitives, not externally reviewed. The wire format is unchanged (720-byte request, 32-byte token). A mail attachment without a key (encryption `NONE`) has no token and is not fetchable.

.Transfer classes (observable size of an answer)
|===
| Blob length (bytes) | Chunks | Class of each chunk | Bytes of chunk payload on the stream

| 1 to 2,038 | 1 | 2 KiB | 2,048
| 2,039 to 8,182 | 1 | 8 KiB | 8,192
| 8,183 to 32,758 | 1 | 32 KiB | 32,768
| 32,759 to 131,062 | 1 | 128 KiB | 131,072
| 131,063 to 262,124 | 2 | 128 KiB | 262,144
| 262,125 to 524,248 | 4 | 128 KiB | 524,288
| 524,249 to 1,048,496 | 8 | 128 KiB | 1,048,576
| 1,048,497 to 2,096,992 | 16 | 128 KiB | 2,097,152

| above 4,193,984 | -- | -- | refused (`TOO_LARGE`)

Chunks past the data carry padding only. The client refuses (`MANIPULATED`: stream closed, nothing stored) a chunk count that does not fit the length, a class other than 128 KiB for a multi-chunk answer, a gap or repetition in the indices, a frame whose length is not a class size, bytes after the last chunk, or a blob that does not hash to its CID. A manipulated answer and a not-found answer reach the browser under the same code (no oracle).

=== Limits (Q21-C, provisional, not measured in a pilot)

* *Size:* at most 32 chunks, 4,193,984 bytes of blob. For a direct message that is 4,193,946 bytes of plaintext per attachment (`MAX_ANONYMOUS_DM_ATTACHMENT_BYTES`, blob header and GCM tag subtracted), instead of 16 MiB in normal mode; at most 4 attachments as before. A larger one is refused with `attachment-too-large-anonymous` (413) before the base64 decoding and again after it, before storage, cipher or session are touched.
* *Server:* 2 streams at once (a third is closed without an answer), 12 requests per minute (more: `RATE_LIMITED`), 16 MiB per minute reserved from the transfer class *before* the blob is loaded (not enough left: `RATE_LIMITED`), a request within 10 s, a stream at most 180 s, answer no earlier than 1.5 s plus 0 to 1 s jitter after the request, pacing 8 stream messages per 50 ms (the rendezvous stream has no backpressure; a refused send ends the transfer and gives the slot and the reservation back). With two streams at most two blobs of 4 MiB are in memory.
* *Client:* 2 downloads at once (more: `rate-limited`, 503), connect 30 s, overall deadline 180 s, at most 15 s of silence between two answer messages.
* *Outbound source:* at most the newest 10,000 history entries (direct messages, then the sent folder) are examined per request; an older attachment is not found. The scan cost is bounded by the request rate.
* *One fetch per stream* (Q21-H): two attachments of one message cost two circuits from the general build budget (6 per minute), which can lead to `rate-limited`.

=== Refusal codes of the download routes

|===
| Code | Status | Meaning

| `attachments-unavailable-anonymous` | 404 | The fetch found nothing: the sender's service is not reachable, it does not hold the blob, the token did not match, the answer was manipulated, or (mail) the attachment has no key. Deliberately one code.
| `attachment-too-large-anonymous` | 413 | The blob is larger than one fetch can carry (and, on send, a DM attachment above 4,193,946 bytes).
| `attachment-fetch-timeout-anonymous` | 504 | The fetch did not complete within its deadline.
| `rate-limited` | 503 | Two downloads already run, or the sender's service refused for its rate or byte budget.
| `anonymity-not-ready` | 503 | The anonymity runtime is not ready (no guards yet).
|===

The browser pages fetch an attachment with `fetch()` in anonymity mode and show one fixed text per code (never the server's text). Forwarding a mail with an attachment reference that is not local stays refused with `attachments-unavailable-anonymous` (409, Q21-I; "fetch first, then bundle" would be a later wave). The mailbox poller still does not run in anonymity mode.

=== Anonymity properties

* The rendezvous point and the relays see only end-to-end encrypted cells; the guards of both sides see the number of cells, i.e. only the transfer class.
* The sender learns that a holder of the attachment key fetches at time T; with a mail to several recipients it does not learn which one, and it never learns the recipient's address.
* The recipient learns that the sender is online, which it can learn with a direct message anyway.
* An unknown CID and a wrong token give byte-identical answers after the same delay, so the service is no oracle for "does identity A hold CID X". The minimum delay hides the cost of the lookup only while that cost stays below it.
* The server hands out only attachments its node sent itself, never received or foreign blobs, so a node never becomes a holder of other people's content. Since wave Q21 every attachment sent in anonymity mode (direct message and mail, encrypted or not) is stored unserved, so it is never served over Bitswap or announced, not even after a switch to normal mode; the onion service still loads it, because it reads both local stores.
* *Honest limit:* a global observer who sees both ends can correlate the send of a message with the later fetch; that is inherent.
* *LOOKUP fallback (Q21-B):* the exit relay learns the CID of the encrypted blob and the time, not who asks; the fallback occupies the single lookup slot for up to 60 s.
* *Key separation (wave Q21-Token):* the attachment key is never used directly as an HMAC key; the token is an HMAC under a key derived by HKDF from the attachment key and the CID, so a token for one CID says nothing about the token key of another, and the AES-GCM key and the HMAC key are different values.
* Nothing logged names a CID, an identity, a descriptor, a token or a derived key; only counters and coarse reasons.
* *Only the node's own pages can start a fetch.* Both download routes (`GET /api/dm/attachment/{peer}/{cid}`, `GET /api/mail/attachment/{cid}`) check `Sec-Fetch-Site` (same-origin or none) and `Origin` (a loopback origin) before any lookup (`requireLoopbackRequest`), in every mode. Otherwise a foreign web page could embed `<img src="http://127.0.0.1:<port>/api/dm/attachment/...">` and learn from its own onion service that its visitor is the anonymous identity it sent the attachment to. A refused request answers 403 and touches neither the store nor the network.

=== Leak inventory (wave Q21)

. Sender's service: fetch time and transfer class of each fetch of its own attachments (not the fetcher's identity or address).
. Guards of both sides: cell count of each transfer (one of nine classes) and its timing.
. Exit relay of a MAILBOX fallback: CID of the encrypted blob and time.
. A recipient can tell whether the sender is online (as with direct messages).

=== Honest limits of wave Q21

* The sender must be online when the recipient fetches; there is no relay storage.
* At most 4,193,984 bytes per blob; DM attachments above that can not be sent in anonymity mode.
* A mail attachment without encryption key can not be fetched; forwarding a reference that is not local is refused.
* The LOOKUP fallback is practically without effect in a real network: nobody announces attachments, so it finds something only if a node in normal mode happens to hold and announce it.
* Verified on loopback only (unit tests, a multi-node test with six relays and two anonymous nodes, and a load series); no real network, no NAT.
* The limits are provisional; the outbound scan is bounded at 10,000 entries.
* *The server's limits are global, not per requester* (an onion service can not tell requesters apart). Anyone who can resolve the sender's descriptor can keep both stream slots busy (open a stream, send nothing for 10 s, reopen) or use up the 12 requests per minute with random CIDs. Legitimate recipients then get `rate-limited` or no answer, and a stream that closes without an answer leads to the MAILBOX fallback (Q21-B), which shows the exit relay the CID and the time. An attacker can therefore push a recipient onto the fallback path; it learns nothing itself, but the exit relay does. Accepted for this wave; a later wave may skip the fallback when the stream closed without any answer bytes.
* The server looks the CID up and loads the blob (up to about 4 MiB from disk) on its single scheduler thread. A slow load delays the pacing and timers of the other stream, and the minimum answer delay is then only a lower bound. This happens only after a valid token, so it is no oracle for outsiders.
* No external cryptographic or anonymity review has taken place.

=== Decisions (Q21-A to Q21-I), confirmed by the user (2026-11-22)

* *Q21-A, source of the blob:* the sender's onion service; MAILBOX only as last resort (implemented). Alternatives: push DM attachments in band like the mail bundle (both online at send time, a retry queue, bytes for attachments never opened); manifest chunking plus provides in normal mode (changes the normal mode, new DHT metadata).
* *Q21-B, LOOKUP MAILBOX as last resort:* wired, documented as best effort; can be removed.
* *Q21-C, limits:* the numbers above (4 MiB), provisional, not measured in a pilot.
* *Q21-D, fetch token:* HKDF-derived token key (changed in wave Q21-Token), the construction above.
* *Q21-E, codes:* as in the table above; manipulation and not-found under one code.
* *Q21-F, warning text:* the attachment sentence of the start warning (all four variants, character-identical in `AnonymityStatus.kt`, `app.js` and this document).
* *Q21-G, what the server hands out:* only outbound attachments with a key.
* *Q21-H, one fetch per stream.*
* *Q21-I, forwarding of references that are not local:* still refused; "fetch first, then bundle" is a later wave.
