= Traffic anonymisation: design, foundation, wire integration, receiver side, directory, path policy, direct messages, mail, call signals, padding and timing (waves V0.10.0-A to V0.10.0-I)
:toc:

== Status

*Wave I (multi-node tests, Sybil simulation, review package, unreleased) adds no feature for the user. It tests more of what exists on real loopback nodes (a late subscriber behind a node that already holds a service descriptor, failure of the primary guard, a mode switch by restart, mail and call signals after a restart with a new onion address), simulates the real path selection against an adversary that controls part of the relays, and prepares the external review in link:external-review.adoc[external-review.adoc]. It fixed one defect that the new test found: the repeat slots of the early republication sent the service descriptor byte-identically, which a node that already holds it ignores and does not forward; they now send a fresh signed version (see <<early-republication>>). The external review itself has not taken place.* See <<wave-i>>.

*Wave H (padding and timing protection, unreleased) makes the traffic of a node in anonymity mode harder to read for a local observer of its guard connection: message sizes are padded to size classes, cover cells are sent towards the guard on a randomised schedule, outgoing cells leave in time slices, and circuits are built in advance. It makes observation by a local observer or a single relay harder; it is NOT protection against a global passive observer, and it does not hide that and roughly when the node is active.* See <<padding-and-timing>>.

*Wave G (call signals over circuits, unreleased) carries the signalling of a call (INVITE, ACCEPT, REJECT, HANGUP) over circuits for a node in anonymity mode, through the same rendezvous stream and the same Double Ratchet session as direct messages. The media path is NOT anonymised and can not be: WebRTC connects the two parties directly, so every call reveals your IP address to the other party and to network observers. Calls are therefore OFF in anonymity mode by default; `--anonymity-allow-call-media=true` turns them on, with a confirmation before every single call. Call signals are online only (never a mailbox), and both ends must be in anonymity mode.* See <<call-signals-over-circuits>>.

*Wave F2 (mail over circuits, unreleased) carries mail over circuits for a node in anonymity mode. A mail with its attachments travels as one bundle over a rendezvous stream to the recipient's onion service; a small mail without attachments that cannot be delivered online is sealed to the recipient and announced on the same shared topic as offline direct messages. The node no longer subscribes to or publishes on a per-recipient inbox topic, leaves no DHT pointer and fetches nothing over Nabu/Bitswap for mail. Call media, GossipSub in general, the DHT and other content fetches are unchanged: they still show identity and IP address, and the libp2p transport key is still the identity key. Call signalling is not available in anonymity mode. Both ends must be in anonymity mode; there is no fallback to a direct connection.* See <<mail-over-circuits>>.

*Wave F1 (direct messages over circuits, unreleased) carries direct messages, online and offline, over circuits for a node in anonymity mode. The sender reaches the recipient's onion service through a rendezvous point; an undeliverable message is sealed to the recipient and announced by relays on one shared topic. Mail, call media, GossipSub, the DHT and content fetches are unchanged: they still show identity and IP address, and the libp2p transport key is still the identity key. Call signalling is not available in anonymity mode (refused before any ratchet step; superseded by wave G, see <<call-signals-over-circuits>>). The recipient learns the sender's identity. Both sides must be in anonymity mode; there is no fallback to a direct connection and no attachments.* See <<dm-over-circuits>>.

*Wave E (path selection and policy, unreleased) adds the first thing a user can switch on: `--anonymity=on`. A node in that mode chooses relays with persistent guards and network diversity, builds circuits under a build policy, and publishes its directory entry only through those circuits. It does not make the node anonymous: direct messages, mail and call signalling still use direct connections and show the IP address, and the libp2p transport key is still the identity key. The option is experimental, off by default, and every start says so.* See <<path-policy>>.

*Wave D (directory anonymity, unreleased) lets a node in directory anonymity mode publish an address-free directory entry through a circuit, and keeps every address-bearing publication of its own off the network. It does not make the node anonymous: the libp2p transport key is still the identity key, so every direct connection of the node shows identity and IP together. No user traffic is anonymised and no anonymity is offered.* See <<directory-anonymity>>.

*Wave C (receiver side and rendezvous, unreleased) adds introduction points, rendezvous points and onion-service descriptors on top of wave B. Still no user traffic uses any of it, there is no path selection, and nothing is anonymised.* See <<receiver-side>>.

*Wave B (wire integration, unreleased): the infrastructure is wired, no user traffic uses it, nothing is anonymised.* `lapis-net-onion` (wave A) holds the cryptographic foundation; the new module `lapis-net-onion-wire` (wave B) carries cells over a libp2p stream, keeps a relay's onion keys, publishes relay descriptors and, only with `--onion-relay=true`, lets a node act as a relay. There is no path selection, no application (DM, mail, call, browser) sends anything over a circuit, and the browser is not wired at all. IP addresses remain visible to peers and to the directory.

[WARNING]
====
*What this wave does not give you.* It provides no anonymity. It provides audited-by-our-own-pipeline building blocks (cell format, ntor-style handshake, onion layering, a relay state machine with resource limits) and a written threat model. Several leaks listed below must be closed before anyone may claim anonymity for DM, mail or call signalling. No external cryptographic review has taken place.

== Goals and non-goals

*Goal.* No network observer (ISP, local Wi-Fi, a single relay, the receiving peer) can link the IP address of a sender or receiver to a Lapis pseudonym, for direct messages, mail and call signalling. Pseudonymity itself is unchanged: identities stay stable keys.

*Non-goals.*

* Anonymous content. Content confidentiality stays with the existing end-to-end layers (X3DH/Double Ratchet, hybrid ECIES).
* Protection against a global passive observer who sees both ends of a circuit (traffic confirmation). Not defended, see the threat model.
* The media path of calls. WebRTC reveals IP addresses through ICE; signalling can be anonymised, media cannot without a separate design.
* GossipSub, the DHT and content fetches in part 1 (wave J, later).
* Tor equivalence. This is a small, purpose-built onion design for a small network, with a much smaller anonymity set than Tor.

[[threat-model]]
== Threat model

[cols="2,3,3", options="header"]
|===
| Adversary | Defended | Not defended / caveat

| Local observer (ISP, shared network)
| Sees only encrypted 1024-byte cells to a guard (link encryption: wave B). Cannot see destination identity or content.
| Sees that the user runs the protocol and roughly when it is active. Since wave H (default `--anonymity-padding=standard`) the length of a message is hidden inside its size class, the exact timing of sends is hidden in 50 ms slices with cover cells, and a circuit build is not tied to the first send of a message. The size class, coarse activity periods, the return direction and the number of mailbox items still leak (see <<padding-and-timing>>). With `--anonymity-padding=off` none of this applies.

| A single malicious relay
| Learns at most its two neighbours and its own position (hop index). Cannot read or undetectably alter cell content.
| A guard sees the client IP; an exit sees the next hop. A relay can destroy circuits (DoS) and observe timing.

| Colluding relays or Sybil identities
| Per-hop authentication and per-hop regenerated filler remove the classic tagging channel. Path selection will weigh Madli reputation and enforce diversity (wave E).
| If one adversary controls both guard and exit of a circuit it can correlate by timing and volume. Madli reputation is a weak Sybil defence (identities are free); it is a weight, never a gate.

| Malicious receiver
| Sees a rendezvous or mailbox, never the sender IP (once wave C/F land).
| Can correlate by timing with its own observations.

| Global passive observer
| *Not defended.*
| End-to-end timing and volume correlation is out of scope.
|===

[[known-leaks]]
== Known leaks today

These exist in the current release and must be closed before any anonymity claim.

. *`PeerRecord` publishes addresses.* The signed directory record binds an identity to its current network addresses. This is exactly the pseudonym-to-IP link to be hidden. In anonymity mode a node must publish introduction points, not addresses. Directory side addressed in wave D (see <<directory-anonymity>>); the transport-level link between identity and IP remains until wave E.
. *Mail uses one GossipSub topic per recipient.* Subscribing to your own topic links your identity and IP for your mesh neighbours. Mail delivery has to move off the per-recipient topic: store and fetch through circuits (wave F2). Wave F1 does not change mail; it removes the same leak for direct messages (a node in anonymity mode does not subscribe to its own direct-message mailbox topic). *Closed for a node in anonymity mode by wave F2:* it subscribes to no inbox topic, publishes on none, leaves no DHT pointer and fetches nothing over Nabu/Bitswap for mail (see <<mail-over-circuits>>); still present in the normal mode.
. *Gossip timing.* Message publication times and mesh membership leak.
. *WebRTC media.* ICE exposes IPs to the peer. Not closable by this design: since wave G calls are off in anonymity mode by default, and with `--anonymity-allow-call-media=true` the media connects directly and shows the IP address to the other party and to network observers (see <<call-signals-over-circuits>>).
. *DHT provider records of the offline mailbox path* tell DHT peers who looks for whom. Closed for direct messages in anonymity mode by wave F1 (no pointer, no Nabu blob, no IPNS value); closed for mail in anonymity mode by wave F2 as well; still present for nodes in the normal mode.
. *Small anonymity set.* Few relays mean weak anonymity regardless of cryptography.
. *Relay position.* A relay learns its hop index from the CREATE; with the default of three hops that equals Tor's exposure of position, stated here deliberately.
. *Correlation by provoked teardown.* Any party on a path can destroy a circuit and correlate the effect elsewhere (DoS-based correlation). Not prevented.

=== Cell format

Every cell is exactly 1024 bytes: `circuitId(4) | command(1) | body(1019)`. Commands: PADDING (circuit id 0 only), CREATE, CREATED, RELAY, DESTROY. Unused body space is filled with random bytes, not zeros, so empty fields reveal nothing. The parser has no length field: the input size is compared to 1024 before anything is copied, so no allocation depends on attacker data. Unknown commands and a circuit id of 0 on a non-PADDING cell are rejected.

=== Circuit length

Default 3 hops, technical maximum 5 (`MAX_HOPS`). The library accepts 1 to 5 (1 and 2 for tests); a policy minimum of 3 for the production path is enforced when the module is wired (waves B and E). A relay message addressed to hop 3 carries up to 963 bytes of data (1019 - 3*17 - 5 header bytes).

=== Handshake (ntor over X25519)

The handshake follows the published ntor construction (Goldberg, Stebila, Ustaoglu) and is reimplemented from that description; no code was copied. Wire shapes and labels are Lapis-specific, so the pinned test vector is a self-generated regression vector (cross-checked once against an independent script), not an external known-answer test.

....
secret_input = X25519(y,X) | X25519(b,X) | ID | B | X | Y | PROTOID      (client: X25519(x,Y) | X25519(x,B))
KEY_SEED     = HMAC-SHA256(PROTOID:key_extract, secret_input)
verify       = HMAC-SHA256(PROTOID:verify,      secret_input)
AUTH         = HMAC-SHA256(PROTOID:mac, verify | ID | B | Y | X | PROTOID | "Server")
Kf | Kb      = HKDF-SHA256(ikm = KEY_SEED, salt = empty, info = PROTOID:expand, L = 64)
....

`ID` is the SHA-256 digest of the relay identity key, `B` the relay's onion key, `PROTOID` is `LapisNet:ntor-x25519-sha256:v1`. The client compares AUTH in constant time. Ephemerals x and y and every intermediate secret are overwritten after use; this gives forward secrecy for the circuit keys against a later compromise of `B`. The relay's *onion key* is separate from the X3DH encryption key and is bound to the identity by a signed `OnionKeyBinding` with its own domain tag and an expiry; it is meant to be rotated.

Deviation from the plain ntor message: CREATE and EXTEND carry a `hopIndex` byte (the relay's 1-based position), set by the client. It selects the layer size and is bound into every AEAD's associated data; a wrong value only breaks the client's own circuit.

=== Onion layers and the anti-tagging rule

Each hop holds two keys. A layer for hop i has size `1019 - (i-1)*17` (16 tag bytes plus one type byte per layer). Layers are sealed with ChaCha20-Poly1305 (RFC 8439) under an *implicit* nonce `directionTag(4) | counter(8)`; the counter is never transmitted. Replay, duplication, drop and reordering all desynchronise the counter, fail the tag and destroy the circuit. There is deliberately no replay window: the transport stream is reliable and ordered, so any deviation is an attack. After one failed open the cipher is poisoned.

*Why ChaCha20-Poly1305 and not AES-256-GCM (which the rest of the project uses).* It is constant-time in software without AES-NI, it comes from the BouncyCastle lightweight API that is already a dependency, and key material can be held in arrays this code zeroises (a JCE `SecretKeySpec` cannot be reliably wiped). If uniformity with AES-GCM is preferred, the change is confined to one class (`HopCipher`).

*Anti-tagging rule.* Every byte that is not covered by the authentication tag of the receiving hop is discarded and regenerated by that hop with fresh random bytes. Unauthenticated filler that an honest hop forwarded unchanged would be a covert channel through which two colluding, non-adjacent relays (guard and exit) could mark a cell. With the rule, every bit that is ever evaluated is authenticated per hop; a flipped bit in an authenticated region is detected at the next honest hop (forward) or at the client (backward). What remains is destroying a circuit on purpose and correlating the teardown, listed above as not defended.

=== Lifetime, rotation, padding

A circuit lives at most 10 minutes (relay-enforced by a sweep) or 2^32 cells per direction, whichever comes first; new destinations get new circuits (policy, wave E). Part 1 has a fixed cell size and a `DROP` relay message. Padding and timing protection against a local observer is wave H (<<padding-and-timing>>); an observer who sees both ends of a circuit is not defended. A warm circuit (pre-built, wave H) serves exactly one use; there is still no circuit reuse anywhere.

=== Link encryption

The libp2p Noise session protects the link only: cells travel over a dedicated stream `/lapis/onion/1.0.0` (wave B, see below), hiding circuit ids and commands from an ISP. The onion layers themselves are ntor plus AEAD, independent of Noise.

== Relay selection (design, wave E)

* *Madli* reputation weights selection; it is never a hard gate and the minimum weight is above zero, so new relays can be chosen. Honest assessment: in a Sybil scenario Madli helps against lazy or unreliable relays, but it does not stop an adversary that creates many reputable-looking identities.
* *Diversity:* never twice the same Lapis identity in a circuit, no two hops from the same IPv4 /16 (IPv6 /48), no two hops from the same operator-declared relay family (a signed field to be defined in a later wave). Optionally no two hops with a direct Veritas trust edge between them; this option is not decided.
* *Guards:* a small, long-lived guard set (1 to 2, rotated over weeks) against the predecessor attack.
* Path-level duplicate checks live in the client (`ClientCircuitBuilder`): relays do not know their neighbours' identities. The relay state machine only refuses to extend to itself and bounds chain depth by `MAX_HOPS`.
* *Status after wave E:* implemented as described in <<path-policy>>. The relay family check exists but is inactive (the descriptor has no family field; the count byte must be zero), IPv6 diversity uses the /48 (changed from /32 on 2026-10-24), and the Veritas edge check exists as an internal switch with no option. Madli weights apply only to the middle hops and the endpoints; the guard is drawn once with the same weights and then persists.
* A failed or aborted client-side build is not silent for the relays: `BuilderStep.Failed` carries a DESTROY cell (absent only when the peer itself sent DESTROY) and `ClientCircuitBuilder.abort()` returns one; the host must send it to the first hop, otherwise the relays keep the circuit until the lifetime sweep. PADDING and cells of other circuits on the guard link yield `BuilderStep.Ignored`.

== Relationship to Circuit Relay v2 and DCUtR

Circuit Relay v2 and DCUtR serve reachability (NAT). Onion circuits serve unobservability. A Circuit Relay v2 relay sees both endpoints and is therefore not an anonymity hop. DCUtR deliberately creates direct IP connections and must be *off* on anonymous paths (policy for wave E). Onion relays may themselves be reached through Circuit Relay v2.

[[receiver-side]]
== Receiver side and rendezvous (wave V0.10.0-C, unreleased)

*Decision (2026-10-22): option (a), introduction points plus a rendezvous point (the Tor v3 pattern), for live traffic.* The mailbox variant (b) for offline delivery stays wave F; option (c), a fixed mailbox relay per receiver, is rejected because a stable relay learns the receiver's identity. This wave builds the receiver side as infrastructure. It is not wired into `LapisNode`, the CLI, DM, mail, call or the browser, and an onion address is not yet linked to a Lapis identity: that mapping and its distribution to contacts belong to waves D and F. Tests pass the address explicitly.

=== Onion address and why there is no blinding

An onion service has its own Ed25519 *service key*, deliberately neither the Lapis identity (secp256k1) nor the libp2p transport key. The address is `base32(serviceKey(32) | checksum(2) | version(1))`, 56 lowercase characters, with `checksum = SHA-256(domainSeparatedDigest("LapisNet:onion-address-checksum:v1", key, version))[0..2]`. The id used in the end-to-end handshake is `domainSeparatedDigest("LapisNet:onion-service-id:v1", key)`.

*Blinding as in Tor v3 was evaluated and rejected.* Ed25519 key blinding needs point arithmetic on the curve that BouncyCastle does not expose as an API; implementing it ourselves would be home-made cryptography, which this project does not do. The consequence is stated plainly: the descriptor is signed in the clear with the service key, so *onion addresses and their introduction points are enumerable by anyone who reads the public descriptor index, and descriptors of one service are linkable over time*. The descriptor contains no Lapis identity, no peer id and no network address.

=== Protocol

Ten relay commands (codes 6 to 15) travel inside ordinary onion cells; every body has a fixed length and no length field, and the exact length is checked first.

[cols="1,1,2,1"]
|===
| Command | Direction | Body | Bytes

| `ESTABLISH_INTRO` | receiver to introduction point | `version \| authKey(32) \| notValidAfter(8) \| establishSeq(8) \| signature(64)` | 113
| `INTRO_ESTABLISHED` | introduction point to receiver | `status(1)` | 1
| `INTRODUCE1` / `INTRODUCE2` | sender to introduction point / introduction point to receiver (same bytes) | `version \| authKey(32) \| hpkeEnc(32) \| hpkeCiphertext(192+16)` | 273
| `INTRODUCE_ACK` | introduction point to sender | `status(1)`: 0 forwarded, 1 unknown or replay, 2 rate limited, 3 malformed | 1
| `ESTABLISH_RENDEZVOUS` | sender to rendezvous point | `cookie(20)` | 20
| `RENDEZVOUS_ESTABLISHED` | rendezvous point to sender | `status(1)` | 1
| `RENDEZVOUS1` | receiver to rendezvous point | `cookie(20) \| Y(32) \| AUTH(32)` | 84
| `RENDEZVOUS2` | rendezvous point to sender | `Y(32) \| AUTH(32)` | 64
| `RENDEZVOUS_DATA` | both ways over the splice | end-to-end blob | 929
|===

The HPKE plaintext of an introduction is `rendezvousRelayId(32) | rendezvousOnionKeyFingerprint(32) | cookie(20) | X(32) | random padding(76)`, 192 bytes.

[kuml, onion-rendezvous-sequence, svg]
----
import dev.kuml.core.dsl.sequenceDiagram

    val receiver = lifeline(name = "Receiver")
    val intro = lifeline(name = "Introduction point")
    val sender = lifeline(name = "Sender")
    val rdv = lifeline(name = "Rendezvous point")

    message(from = receiver, to = intro, label = "ESTABLISH_INTRO (auth key, signed)")
    reply(from = intro, to = receiver, label = "INTRO_ESTABLISHED")
    message(from = sender, to = rdv, label = "ESTABLISH_RENDEZVOUS (cookie)")
    reply(from = rdv, to = sender, label = "RENDEZVOUS_ESTABLISHED")
    message(from = sender, to = intro, label = "INTRODUCE1 (HPKE to the service key)")
    reply(from = intro, to = sender, label = "INTRODUCE_ACK")
    message(from = intro, to = receiver, label = "INTRODUCE2")
    message(from = receiver, to = rdv, label = "RENDEZVOUS1 (cookie, Y, AUTH)")
    message(from = rdv, to = sender, label = "RENDEZVOUS2 (Y, AUTH)")
    message(from = sender, to = rdv, label = "RENDEZVOUS_DATA (end-to-end blob)")
    message(from = rdv, to = receiver, label = "RENDEZVOUS_DATA (same blob)")
}
----

. The receiver builds a circuit to each chosen introduction point (default 3) and sends `ESTABLISH_INTRO`. It signs with a fresh *auth key per introduction point*; the signature covers the introduction point's relay-id digest, the auth key, a validity time and an `establishSeq`. The introduction point checks its own digest (no cross-relay replay), the validity (at most one hour ahead) and that `establishSeq` is larger than any earlier registration of the same auth key (no rollback). A larger `establishSeq` replaces the old registration and closes the old circuit, which is how the receiver refreshes a circuit make-before-break. Only after all introduction points answered does the receiver sign and publish its descriptor.
. The sender fetches the descriptor (local gossip index, or the DHT), verifies it completely, builds a circuit to a rendezvous point of its own choosing and sends a random 160-bit cookie. It then builds a circuit to one introduction point and sends `INTRODUCE1`; the introduction point checks role, rate and a replay cache, forwards the body as `INTRODUCE2`, and acknowledges. The sender then closes that circuit.
. The receiver rate-limits, opens the HPKE ciphertext, checks its own replay cache, resolves the rendezvous point *only* through its local relay index (an unknown relay or a fingerprint mismatch is dropped silently, so there is no oracle), answers the end-to-end handshake, builds a circuit to the rendezvous point and sends `RENDEZVOUS1`.
. The rendezvous point finds the cookie (single use), joins the two circuits and sends `RENDEZVOUS2` to the sender, who completes the handshake and checks `AUTH`. From then on only `RENDEZVOUS_DATA` flows.

A relay accepts a role message only at the *last hop* of a circuit that has no role yet; `EXTEND`, `DATA` and `END` on a role circuit, a second role, a second `INTRODUCE1`, a self-splice and every reply-type command arriving as a request are protocol errors that destroy the circuit.

=== Cryptography (established building blocks only)

* *End-to-end handshake:* the existing ntor construction with its own protocol id `LapisNet:hs-ntor-x25519-sha256:v1`. The receiver plays the server with `ID = serviceId` and `B = ` the X25519 encryption key from the signed descriptor; `AUTH` therefore proves to the sender that the party that read the introduction holds the key listed in the descriptor the service key signed. Forward secrecy comes from the two ephemerals. `NtorHandshake` was parametrised by labels; the relay labels and the pinned regression vector are unchanged.
* *Introduction:* HPKE (RFC 9180), base mode, `DHKEM(X25519, HKDF-SHA256)`, `HKDF-SHA256`, ChaCha20-Poly1305, over BouncyCastle; `info` binds the service id and the auth key, `aad` the version and the auth key. There is *no forward secrecy of the introduction against compromise of the encryption key during its lifetime* (the same holds in Tor); the key rotates every 24 hours and the previous one stays accepted until the old descriptor expires. The same X25519 key serves both HPKE and the ntor handshake, separated by distinct labels.
* *End-to-end layer:* two `HopCipher`s (ChaCha20-Poly1305, implicit counter nonce, no replay window, poisoned after one failure) with their own AAD label `LapisNet:hs-e2e:v1`. Every blob is exactly 929 bytes (plaintext `type | length | data | random padding`, so at most *910 bytes* of application data); the rendezvous point only ever sees equal-sized ciphertext and cannot alter a bit without the session dying.

=== Descriptor

`ver(1) | serviceKey(32) | seq(8) | notValidAfter(8) | encKey(32) | count(1) | count x [relay onion key binding(137) | authKey(32)] | signature(64)`: exactly `146 + 169 * count` bytes, at most 653, one to three introduction points. Verification checks the window (`now <= notValidAfter <= now + 6 h + 5 min`), that the descriptor never outlives an introduction relay's onion key binding, every binding signature, pairwise distinct relays and auth keys, and the Ed25519 signature. Three places handle it: `OnionServiceDescriptorIndex` (strictly increasing sequence, high-water marks that survive eviction, equivocation ignored, capacity 4096, never evicts a valid entry for a stranger), `OnionServiceDescriptorGossip` (topic `LapisNet:onion-service-descriptor-gossip:v1`; size, decode, index pre-check without spending budget, then per-author, per-peer and global rate limits whose excess is `IGNORE`, then verification) and `OnionServiceDht` (an IPNS record under the *service key's own name*, never in the node's directory value, so there is no flag and no link to a peer id; the validator requires publisher = service key = address). The DHT path is an API only and is not wired into the node.

=== Limits and timers

Relay side (`OnionRelayLimits`, validated): 256 introduction points in total and 32 per previous link, 10 `INTRODUCE1` per second per introduction point (checked before any other work), replay cache of 8192 body digests, 512 waiting cookies in total and 64 per link, wait timeout 60 s (shorter than the circuit lifetime), 512 spliced pairs. Receiver side (`OnionServiceConfig`): 3 introduction points, descriptor TTL 3 h (at most 6 h) republished hourly (plus, when published through a circuit, the early retry schedule of the descriptor republisher, see "Early republication"), intro refresh after 8 minutes (relays sweep circuits after 10), build timeout 30 s, establish timeout 15 s, exponential backoff 1 s to 60 s with jitter and a replacement relay after 5 failures, 16 concurrent pending rendezvous builds (before acceptance) and at most 256 open accepted sessions (`maxOpenSessions`; further accepted rendezvous are closed at once), 5 `INTRODUCE2` per second, replay cache of 8192 entries per encryption key which *fails closed* when full (and so can be filled by anyone who can encrypt to the public key: an acknowledged denial-of-service limit, bounded by the rate limits). A full cache forces an early encryption key rotation and republication at the next tick, so the service recovers without waiting for the regular rotation every 24 hours; clients holding an older descriptor are rejected until they have fetched the new one. Sender side (`RendezvousClientConfig`): 30 s to build, 15 s to establish, 15 s for the acknowledgement, 30 s for `RENDEZVOUS2`, 60 s overall; the next introduction point is tried at once (no backoff between introduction attempts). *A rendezvous session lives at most as long as the relays' circuit lifetime (10 minutes); reconnecting is the caller's job (waves E and F).*

=== Assumptions awaiting confirmation (wave C)

* *Assumption, confirmation required:* a dedicated service key per onion service and no link to the Lapis identity in this wave.
* *Assumption, confirmation required:* no Tor-style key blinding (see above).
* *Assumption, confirmation required:* HPKE for the introduction rather than a hs-ntor-style composition.
* *Assumption, confirmation required:* the descriptor index and gossip topic are attached on every node, like the relay descriptor index. Consequence: the Sybil limit described below applies on every node.
* *Assumption, confirmation required:* `ESTABLISH_INTRO` is signed by a per-introduction-point auth key (the Tor pattern), not directly by the service key.
* *Assumption, confirmation required:* all constants in the previous section.
* *Assumption, confirmation required:* sessions of at most 10 minutes; the alternative is a longer lifetime for spliced circuits on every hop.
* *Assumption, confirmation required:* no proof of work against introduction floods.

=== Honest limits of wave C

* *No user traffic is anonymised and no anonymity is offered.* The hidden-service API is `ExperimentalOnionApi`, takes its paths from an injected provider and chooses nothing itself.
* Sybil relays, free choice of introduction relays by the receiver (no path selection yet), the predecessor attack without guards, a small anonymity set and a global passive observer are as described in the threat model; wave C changes none of them.
* Onion addresses and their introduction points are enumerable; descriptors are linkable over time (no blinding).
* Publishing from the service's own node (gossip, DHT) shows that node's IP to its gossip neighbours and to the DHT peers that store or serve the record, together with the onion address. Wave D adds publication through circuits, see <<directory-anonymity>>; it is opt-in and not used by default.
* Teardown correlation still applies: an adversary that provokes a teardown on one half can watch the other half end.
* No forward secrecy for the introduction content against the encryption key within its lifetime.
* An introduction flood is only slowed by rates, not by a cost; the receiver's replay cache can be filled. A full cache forces an early key rotation and republication (at 5 `INTRODUCE2` per second at most about every 27 minutes), during which clients with an older descriptor fail until they have fetched a new one.
* *Known limitation (Sybil, service descriptor index):* a valid service descriptor costs nothing (a fresh Ed25519 service key plus one to three publicly gossiped relay onion key bindings, reusable, and a fresh auth key per entry). About 61 such descriptors per minute exhaust the single global budget (60/min) at every node, so honest new or updated service descriptors are ignored and stop spreading. After about 68 minutes the index is full (capacity 4096) and every new honest service is refused with `CAPACITY`; the attacker keeps the slots by republishing its own keys with a higher sequence number, because a full index never evicts a valid entry and updates of tracked keys are always accepted. The per-author bucket does not help against fresh keys. Gossip discovery of new onion services can thus be stopped network-wide; the DHT path is an API only and not yet wired up. Same class of limit as for the relay descriptor index above. Planned mitigations: a cost per index slot (proof of work, known peer record or Madli weight) or a fair per-mesh-peer budget instead of one global bucket. Not mitigated in wave C.
* Not verified: real NATs, interoperability with v0.12.0, an external cryptographic review, behaviour under real load, interoperability of the HPKE path with other implementations. Multi-node tests run on loopback.

[[directory-anonymity]]
== Directory anonymity (wave V0.10.0-D, unreleased)

Wave D closes the *directory* side of the pseudonym-to-IP link: what a node publishes about itself. It does not close the *transport* side (see the leak inventory, rows 8 to 14). Nothing here anonymises user traffic; nothing is wired into DM, mail or call. The mode is `DirectoryAnonymityMode` (`OFF` by default everywhere; wave E maps `--anonymity` onto it).

[WARNING]
====
*Wave D offers no anonymity.* A node in directory anonymity mode still opens direct libp2p connections whose peer ID is its identity key (`DualKeyIdentity.deriveLibp2pPrivKey`), so every peer it connects to sees identity and IP together. Only the *directory entries* stop carrying addresses, peer ID and binding. Decoupling the transport key is wave E.
====

=== The entry: `AnonymousPeerRecord`

A fixed 248-byte record, no length fields and no free-form field, therefore no tagging or covert channel:

[source]
----
"LNAP"(4) | version(1)=1 | flags(1) [bit0 REVOKED, rest 0] | identity(33, secp256k1)
| serviceKey(32, Ed25519) | servicePossessionProof(64, Ed25519) | capabilities(1) [DM, MAIL, CALL_SIGNAL, rest 0]
| prekeyBundleDigest(32, all zero = none) | sequenceNumber(8) | notValidAfter(8) | signature(64, secp256k1)
----

It contains *no network address, no libp2p peer ID and no `IdentityBinding`*. Two signatures: the outer secp256k1 signature of the identity (domain tag `LapisNet:anonymous-peer-record:v1`) and an Ed25519 possession proof of the *service key* over `identity || sequenceNumber` (tag `LapisNet:anonymous-peer-record-service-possession:v1`). The proof is the mutual binding: nobody can claim a foreign onion service for their identity, and because it is bound to the sequence number an old proof does not transplant into a newer entry. Unknown flag or capability bits are rejected, all-zero and all-ones keys and signatures are rejected, the validity window is `now <= notValidAfter <= now + 6 h + 300 s`. There is no `RELAY` capability: a relay is public by design. A *revocation* (flag bit 0) has no service key, proof, capabilities or digest and is the way back to normal mode.

*Why no transport peer ID in the entry.* The peer ID is the identity's Ed25519 key, publicly bound to the secp256k1 identity by every `PeerRecord`, `OnionRelayDescriptor` and DHT name published so far, and every direct connection shows peer ID and IP together. Putting it into the entry would create the link exactly where it is to be hidden. A rotating, identity-independent key would not help either, because in anonymity mode a sender never dials the recipient but goes through its introduction points. Decoupling the host key itself is wave E.

=== Index, topic and rates

`AnonymousPeerRecordIndex` follows `OnionServiceDescriptorIndex`: one record per identity, strictly rising sequence numbers, high-water marks (65,536) that survive eviction, equivocation ignored, capacity 16,384 identities, a full index refuses new identities and never evicts a valid entry (updates of known identities always pass: the same Sybil boundary as in wave C, documented and not solved). The gossip topic is `LapisNet:anonymous-peer-record-gossip:v1`, a topic of its own that v0.12.0 nodes never subscribe to; every node attaches it so senders can resolve. Validator order: exact size, decode, cheap index pre-check (no rate budget spent), rate limits per author identity (6/min), per forwarding peer (12/min) and global (60/min), whose excess is IGNORE, then full verification. Log lines carry a reason class only.

=== Downgrade protection between the two record types

Both record types use epoch milliseconds as sequence numbers, so they are comparable. `IdentitySupersession` (shared between `PeerRecordIndex` and `AnonymousPeerRecordIndex`, LRU-bounded, in memory) records the highest accepted sequence number of each type per identity:

* an accepted anonymous record removes the identity's address record (`seq <=`) and later address records with `seq <=` are refused, through gossip *and* through the DHT ingest (both go through `PeerRecordIndex.canAccept` and `add`);
* an accepted address record newer than the anonymous one hides the anonymous record (the way back); on a tie the anonymous record wins.

Identities without an anonymous record behave exactly as before. *Remaining window:* a node that saw neither the anonymous record nor the tombstone accepts an old address record until its TTL ends, at most 24 hours; an address that was published once stays visible to archives forever. Persisted address records are restored from local storage on restart before the floor is known again, until the anonymous record is seen again.

=== Switching the mode

`DirectoryModeTransition` with a `DirectoryModeStore` (a small state file, `FileDirectoryModeStore`, written atomically; a missing or corrupt file means "no state": nothing is retired, so a normal node never publishes a revocation and a brand-new identity (or a damaged file) that starts directly in anonymity mode never publishes an identity-bound tombstone). *OFF to ON:* only after a persisted `OFF` state (the node demonstrably ran in normal mode), an address-free tombstone `PeerRecord` with a higher sequence number goes out once from the own node (gossip and `publishTombstone`), then the first anonymous record. A normal-mode start must therefore record `OFF` in the store (`nextSequence(OFF)`) for a later switch to retire its address entry. *Resolved in wave E:* every normal-mode start now persists `OFF` through the sequence source of the own record republisher (CLI and browser), so a later switch to anonymity mode sends the tombstone. A node upgraded from v0.12.0 has no state file; by the rule above it sends no tombstone on its first switch, and its address entries stay until their TTL ends (at most 24 hours). *ON to OFF:* an `AnonymousPeerRecord` revocation with a validity that covers every still-valid anonymous record (6 h), then a newer address record. Wave E wires this: `DirectoryModeRetirement.onNormalStart` builds the revocation at the first normal-mode start after an anonymity run and sends it from the own node through the anonymous-record gossip (the node is about to publish identity and address anyway, so the revocation links nothing new; in the browser the topic is attached only for this one send). OFF is persisted only after the revocation went out; if it could not be sent, the old state stays and the next start retries with a higher sequence number. Sequence numbers are `max(last + 1, nowMillis)` and persisted.

=== Publication through circuits

A node that gossips an entry itself shows its IP and peer ID to its mesh neighbours (the envelope of every GossipSub message is signed with the host key). Therefore the objects go through a circuit: relay command `DIRECTORY_PUBLISH` (client to last hop) with a body of exactly 720 bytes, `type(1) | length(2) | object(<= 717) | random padding`, and the acknowledgement `DIRECTORY_PUBLISHED` with a status byte (0 accepted, 1 invalid, 2 rate limited, 3 malformed, 4 unknown type). Types: anonymous record, onion service descriptor, prekey bundle (a bundle with up to 11 one-time prekeys fits). 720 bytes fit the relay message capacity at the maximum of five hops (929 bytes). The role is accepted only at the last hop of a circuit without another role; at most 4 publishes per circuit, 30 per minute per link and 120 per minute in total (`OnionRelayLimits`), checked before the body is looked at. A wrong body length or an overflowing length field destroys the circuit. The relay validates the object completely with the same functions as the gossip validators and then announces it, so the mesh sees the *relay* as publisher. A valid but already known or superseded object is acknowledged with the same status as a new one, so the status is no oracle on the relay's index.

`OnionDirectoryPublisher` builds the circuit over a path from the injected `OnionPathProvider`, sends one message, waits up to 15 s for the acknowledgement and closes the circuit. A failing relay is put on an exponential backoff and another relay is tried; there is *no fallback to publishing from the own node*. `AnonymousDirectoryPublisher` publishes the anonymous record and the reduced prekey bundle every 60 minutes (record TTL 3 h) and detects the mode switch. `AnonymousDirectory.resolve` answers `Hidden`, `HiddenDescriptorMissing`, `Direct`, `Revoked` or `Unknown`; no DM, mail or call code calls it yet. Resolving the descriptor from the DHT shows the DHT the sender's interest.

[[early-republication]]
=== Early republication

GossipSub hands no history to late subscribers, and there is no catch-up path for anonymous records, prekey bundles or service descriptors (in anonymity mode the lookup deliberately goes without the DHT). A directory object that is published before a receiver subscribed to its topic is therefore invisible to that receiver until the next republication, which used to be an hour away. Seen in practice: node A published, node B started afterwards, and B resolved A as `HiddenDescriptorMissing` (record known, service descriptor missing) for minutes.

After the *first successful* publication the objects are therefore republished on a short, bounded schedule (`DirectoryRepublishSchedule`): 5 s, 15 s, 45 s, 2 min and 5 min after the first success, each slot moved by a random fraction of up to 20 %, consecutive slots at least 3 s apart. The schedule is planned once per process lifetime; neither the hourly republication nor a change of the introduction points restarts it (a later descriptor is sent once, and the slots still open continue with it), so no recurring burst appears. Slots that fell due while the process was suspended are merged into one publication. A failed publication is retried after 5 s, 15 s and 45 s and then every minute (`AnonymousDirectoryPublisher`); a failed service descriptor send is retried after 5 s, 15 s, 45 s, 2 min and 5 min and then given up on (`ServiceDescriptorRepublisher`, the next descriptor of the host heals it).

* *Why not a "mesh ready" signal:* a readiness signal measures only the publisher's own neighbourhood (the relays, which are subscribed at once), never the receivers two hops away, and those are the ones that may subscribe late.
* *Record and prekey bundle go out as new versions* (new sequence numbers). A byte-identical bundle is declined by receivers (`DECLINED` becomes `Invalid`, a score penalty for the relaying peer), so a bundle is never repeated; because the record carries the bundle digest, it is a new version too. The publisher keeps at most 4 versions per minute, below the receivers' per-author rate of 6 per minute (`PublicationRateGuard`; a conformance test drives the real validators along the worst-case timeline).
* *The service descriptor goes out as a fresh version at the repeat slots (wave I):* a byte-identical repetition is free for receivers (the validator's pre-check ignores it before any rate budget is touched), but for the same reason it is not forwarded: a node that already holds the descriptor answers `Ignore`, and GossipSub forwards neither an ignored message nor puts it into its message cache. A repeat therefore reached only direct gossip neighbours of the announcing relay; a late subscriber that is meshed only with nodes that already hold the descriptor never received it and kept resolving `HiddenDescriptorMissing` until the host's next new descriptor (up to one hour). This was found by `MultiNodeDescriptorMultiHopVisibilityTest` (six relays, a holder `M`, a late node `L` meshed only with `M`; on the code before wave I `L` did not see the descriptor within two minutes). At each slot the host now signs the same content again with a higher sequence number (`OnionServiceStateMachine.refreshDescriptor`: same introduction points, authentication keys and encryption key; sequence number, `notValidAfter` and signature are new). Such a version passes every receiver's pre-check, is `Valid` and is forwarded over several hops. The senders limit the refresh versions of one service to 4 per minute (`PublicationRateGuard`, the token is taken only for a version that was really produced), below the receivers' per-author rate of 6 per minute; genuine descriptors are always sent and count against the same budget, so many genuine changes within one minute can exceed 6 (refreshes are skipped meanwhile, a receiver may drop the surplus version); the receiver limits and the acceptance policy are unchanged, and `ServiceDescriptorRefreshConformanceTest` drives the real validator with its default limits along the worst timeline (lowest and highest jitter, failed first attempts, a change of the introduction points in the first minute). If the guard is empty, the host has nothing to refresh (an introduction point is not established) or no refresh is configured, the same descriptor is repeated as before. A genuine new descriptor (change, hourly) is always sent. At most 12 retries and repeats per hour, of which 4 are reserved for retries of a failed first send; an expired descriptor is never sent. The host's session lock is taken before the republisher's monitor; the republisher never calls the host while holding its own monitor (`ServiceDescriptorRepublisherTest`, 1000 rounds against a simulated host lock).
* *What the fresh versions show:* up to six signed versions of one service descriptor in the first five minutes after a start instead of one version plus identical repetitions. They carry no new field and are linkable through the service key anyway; the pattern marks a freshly started host, as the record, the prekey bundle and the millisecond sequence numbers already do. This is one of the questions in link:external-review.adoc[external-review.adoc].
* *Circuit budget:* each publication builds its own circuit under the existing circuit-build governor, which is not bypassed; at most about three objects times six publications plus retries within the first six minutes after a start; later descriptors of the same run add one send each plus failure retries, without a new burst.
* *Honest limit:* a node that subscribes later than about 5 minutes after the publisher's start still sees the entry only at the hourly republication. A catch-up (index sync or relay-side replay) would be a separate wave.

[[path-policy]]
== Path selection and policy (wave V0.10.0-E, unreleased)

*What it is.* `--anonymity=on` starts the `AnonymityRuntime` (`lapis-net-onion-wire`, package `anonymity`): persistent guards, diverse weighted paths of three relays, a build policy for client circuits, the circuit-based directory publication of wave D and the hosting of the node's onion service (introduction points chosen the same way). The headless CLI node and the browser both wire it; with `off` nothing of this is built, and the browser does not even create an `OnionWire` in normal mode.

*What it is not (state of wave E; wave F1 changed the first point).* Direct messages, mail and call signalling are not routed over circuits, the libp2p transport key is the identity key, and every connection of the node (mesh, DHT, Bitswap) still shows identity and IP. At every start the node warns (log, CLI stderr, a notice in the browser that can not be dismissed). The text of wave E was: _Anonymity mode is incomplete: direct messages, mail and call signalling still use direct connections and reveal your IP address; only the directory publication and path selection are active._ (historical; wave F1 replaced it, see <<dm-over-circuits>> for the current text, which `ANONYMITY_INCOMPLETE_WARNING` and `app.js` carry character for character).

=== Path selection

`OnionPathSelector` is network-free and deterministic for a given `SecureRandom` sequence. Hop 1 is the persistent primary guard; the last hop is prescribed by the caller (publish relay, introduction point, rendezvous point) or drawn; the middle hops are drawn with weights.

* *Never shorter:* a path has at least three relays (`PathPolicy.PRODUCTION_PATH_LENGTH`, equal to the default hop count, not configurable). With too few diverse relays the answer is `Insufficient` (an `InsufficientRelaysException` with the text `insufficient relays`, no identity or address in it), never a shorter path. The circuit factory refuses a shorter path too when the policy is installed (second line against a caller that bypasses the selector).
* *Hard diversity:* no relay twice, not the own identity, no two relays with an overlapping IPv4 /16 or IPv6 /48 bucket, at most one relay of unknown network, no two relays of the same non-null family, optionally no Veritas edge (internal switch, no option). If a last hop chosen by the caller itself collides with the guard the selector throws `PathConflictException` and the caller picks another endpoint. A last hop named by a remote party (the rendezvous point of an INTRODUCE, i.e. `RENDEZVOUS_RECEIVER`, and `INTRODUCE` towards a service-chosen introduction point) is never refused because of the guard: success must not depend on the guard, or a remote party could probe for the guard's identity and network. The diversity rule then applies to the middle hops only (strictly towards the guard, towards the remote last hop as far as possible).
* *Weights:* the Madli reliability (clamped to 0..1) with a floor of 0.02; 0.05 without history (NaN and infinity count as no history). Relays without history together are capped at 15 % of the weight when others exist. A single network bucket (and a single family) is capped at `max(0.10, 1/buckets)` by water filling, recomputed for every hop on the remaining candidates. Madli is never a gate. A relay with several addresses counts for the cap in its smallest bucket only; for diversity all its buckets count. All relays new or all in one bucket: no scaling, the draw still happens.
* *Interaction of the two caps:* the new-relay cap is applied first, the bucket cap second. With only a few networks the bucket cap forces weight over to the other relays, which can lift the share of relays without history above 15 %; this is accepted (a feasible distribution has to sum to one).
* *Randomness:* `SecureRandom` only; `nextDouble()` for the weighted draw, `nextLong(bound)` for the guard lifetime (both without modulo bias).

*Circuit build budgets.* `CircuitBuildGovernor` keeps the attacker-triggerable service rendezvous circuits (`RENDEZVOUS_RECEIVER`) in a separate budget (default 60 per minute, burst 10; over it they are dropped, not delayed) without any backoff, so an INTRODUCE flood or failing rendezvous points can neither starve nor back off the node's own introduction, publication and client circuits.

*Where the network buckets come from.* A relay descriptor carries no address (the family field is a count byte that must be zero). `PeerDirectoryRelayNetworkLocator` reads the relay's `PeerRecord`: only public `ip4`/`ip6` addresses count, `/p2p-circuit`, `dns*`, loopback, private, link-local, CGNAT, unique-local, `0.0.0.0/8`, documentation, benchmarking (`198.18.0.0/15`), reserved (`240.0.0.0/4`) and `2001:db8::/32` addresses are ignored, and a name is never resolved (a resolution would be a network call). A relay without a usable address is in the bucket `Unknown`. *These addresses are self-declared and unverified:* an adversary can declare addresses in networks it does not control and so slip past the diversity check, or declare an honest network to crowd it out. This is a Sybil limit that this wave does not close.

=== Guards

Two guards (primary and backup), each with a lifetime drawn uniformly from 30 to 60 days. The first hop of every circuit is the primary. A guard is replaced when it expires (not rate limited), after at least three consecutive *first-hop* failures spanning at least 24 hours, or when its descriptor has been missing or invalid for at least 72 hours; a replacement because of a failure happens at most once per 24 hours, the backup takes over and a new backup is chosen. Only failures at the first hop count (a dial or link failure, a CREATE that times out or is answered invalidly): a failure while extending to the second or third hop must not be usable to force a guard rotation.

The state lives in `onion/guards.bin` in the data directory: `"LNGS" | version | nonce(12) | AES-256-GCM(state) + tag`, key `HKDF-SHA256(identity secp256k1 private key, salt empty, info "LapisNet:guard-state:v1")`, associated data `"LNGS" | version | SHA-256(own identity public key)`, a fresh nonce for every write, atomic write (temp file `0600`, fsync, atomic move), directory `0700`. A damaged, foreign or implausible file (times in the future, lifetime outside 30 to 60 days, negative counters) is `Invalid` and always leads to new guards; a missing file leads to new guards only if the previous run was in anonymity mode (so a first start is silent). A reset logs `guard state invalid, reselected guards` (no content), counts, and shows as the status code `guard-state-reset`, which later routine errors do not hide for an hour. Deleting the file can not be prevented (an attacker with file access can force a new guard choice); it is made visible, and the rate limit of failure rotations deliberately does not apply to it.

=== Circuit policy

`CircuitBuildGovernor`: a token bucket of 6 builds per minute with a burst of 3; after a failed build an exponential backoff from 5 seconds to 5 minutes; at most 4 open or in-flight outgoing client circuits (directory publication, rendezvous client); circuits older than 10 minutes are closed by a sweeper every 30 seconds; after `lockdown` (stop) nothing new is admitted. The long-lived introduction circuits of the hosted service do not count against the pool of four (they would starve the publisher) but pay the rate. Every build goes to a new circuit; there is no circuit reuse anywhere. A build that would wait longer than 30 seconds fails with a `rate-limited` status instead of waiting. Every failed or aborted build sends a DESTROY to the first hop.

=== Status and errors

The CLI start line shows `anonymity=on|off`; the browser status carries `anonymityMode`, `anonymityIncomplete`, `guards`, `activeCircuits` and `lastAnonymityError` (+ age) and shows them in the node status panel. The error code is one of `none`, `insufficient-relays`, `build-failed`, `build-timeout`, `rate-limited`, `guard-state-reset`, `publish-failed`: enums and numbers only, never an address or identity. A successful publication clears the code. On loopback every relay is in the unknown bucket, so a real node there reports `insufficient-relays` and publishes nothing; there is no fallback to publishing from the own node.

=== Conflicts and wiring

* `--anonymity=on` with an explicit `--hole-punching=auto|on` aborts the start (`hole-punching cannot be enabled while anonymity=on`); a missing key resolves to off. DCUtR and Identify are off node-wide in this mode.
* `--anonymity=on` with `--onion-relay=true` aborts the start (`onion-relay cannot be combined with anonymity=on`). The design text of waves A to D says "`--onion-relay` stays independent"; wave D already enforces the exclusion at `OnionWire.attach` because a relay descriptor binds identity, peer ID and dialability publicly, so the option layer now matches the code.
* The onion service key of the node is generated freshly at every start (the onion address changes with it); the CLI node publishes no prekey bundle and no DM capability, the browser both.
* Auto-relay reservations (leak 11) and Madli gossip (12) stay available in this mode and are documented, not forbidden. The Madli gossip topic is subscribed to read the relay reliability.

=== Assumptions awaiting confirmation (wave E)

* *Assumption, confirmation required:* three hops in production, not configurable.
* *Assumption, confirmation required:* two guards (primary and backup), a lifetime of 30 to 60 days, replacement after three first-hop failures over 24 hours or 72 hours of a missing descriptor, at most one failure replacement per 24 hours.
* *Confirmed (2026-10-24, changed from /32 to /48):* IPv6 diversity on the /48 and IPv4 on the /16; at most one relay of unknown network per path. A /48 is finer than a /32: relays of one provider in different /48 blocks count as different networks, which eases "insufficient relays" in a small network but weakens the protection against an attacker who runs many relays from one large provider block.
* *Assumption, confirmation required:* the weights (0.02 floor, 0.05 without history) and the caps (`max(0.10, 1/buckets)`, 15 % for relays without history, new-relay cap first).
* *Assumption, confirmation required:* the circuit policy constants (6 per minute, burst 3, pool 4, 10 minutes, backoff 5 seconds to 5 minutes, 30 seconds maximum wait).
* *Assumption, confirmation required:* DCUtR node-wide off while the mode is on; the mode changes only by restarting the node.
* *Assumption, confirmation required (F1):* `--onion-relay=true` with `--anonymity=on` aborts the start; lifting the exclusion would need a separate relay identity.
* *Assumption, confirmation required (F2):* an explicit `--hole-punching=auto` or `on` together with `--anonymity=on` aborts the start; only a missing key resolves to off.
* *Assumption, confirmation required (F3):* the revocation of an ON to OFF switch is sent from the own node through the anonymous-record gossip; going through a circuit would need path selection (and an `OnionWire`) in normal mode.
* *Assumption, confirmation required (F4):* the pool of 4 counts outgoing client circuits only; introduction circuits are bounded by the host and only pay the rate.
* *Assumption, confirmation required (F5):* the transport-key decoupling (leaks 8 and 14) is not part of this wave; it remains the largest leak.
* *Assumption, confirmation required (F6):* auto-relay reservations, Madli gossip and the DHT fallback are allowed in anonymity mode and documented as leaks. The node's own code sends no Identify request (code review, not a wire test); the Identify responder is off.

=== Honest limits of wave E

* *No user traffic is anonymised.* Only the directory publication and the path selection are active; the transport key is the identity key, so any peer that connects to the node learns identity and IP.
* The network diversity rests on self-declared, unverified addresses; with the real locator it is only as good as those declarations. *It was verified only with an injected locator that gives each relay a synthetic distinct /16*, because on loopback every relay has the same address and no diverse path exists.
* The relay family check is inactive (no field in the descriptor). The Veritas edge check exists only as an internal switch.
* While the primary guard's descriptor is missing from the directory (relay offline, descriptor expired), the backup guard serves as first hop; the primary is only replaced after 72 hours without a descriptor, or by the failure rule.
* A revocation of the anonymous record (switch to normal mode) is only counted as sent after at least one mesh peer received it; otherwise `OFF` is not persisted and the revocation is repeated at the next start.
* A deleted or replaced guard file forces a new guard choice and can not be prevented; it is only made visible.
* A guard that is also operated by the adversary sees the node's IP for every circuit; guards reduce the predecessor attack, they do not remove it. A small anonymity set and a global passive observer are as in the threat model.
* A node upgraded from v0.12.0 sends no tombstone on its first switch to anonymity mode (no persisted `OFF`); its address entries stay until their TTL ends.
* Not verified: real networks and NATs, behaviour under load, interoperability with v0.12.0 over the network (only local), and no external cryptographic review has taken place.

[[dm-over-circuits]]
== Direct messages over circuits (wave V0.10.0-F1, unreleased)

NOTE: This section describes the state of wave F1. Wave F2 changed three things in it: mail now also travels over circuits (see <<mail-over-circuits>>, so every remark below that mail "is unchanged" or "uses direct connections" describes wave F1 only); the sealed item carries a kind byte inside its encrypted plaintext, which lowers the capacity of a direct-message item by one byte (5,668 bytes instead of 5,669); and the warning text below is historical, replaced by the text in <<mail-over-circuits>>.

*What it is.* A node in anonymity mode sends and receives direct messages only through circuits. The ratchet (X3DH and Double Ratchet) is unchanged and keeps protecting the content; what changes is the transport. A new module `lapis-net-dm-onion` is the adapter between `lapis-net-dm` (which knows only the `AnonymousDmTransport` interface and the sealed item format and does not depend on any onion code) and `lapis-net-onion-wire` (which knows nothing about direct messages). `DmSessionManager` is attached with `anonymous = true`: it then registers no `/lapis/dm/1.1.0` protocol, starts no mailbox poller, publishes no pointer on any per-recipient topic and offers nothing to the DHT outbox. There is one inbound pipeline for both entrances (circuit stream and sealed item): `processInboundDmEnvelope`, with duplicate check, X3DH replay register, prekey rate limiter, ratchet decryption and acceptance policy. The sender of an incoming message is known only after decryption.

*What it is not.* Mail and call media still use direct connections; call signalling is not available in anonymity mode (a call attempt is refused up front; superseded by wave G, see <<call-signals-over-circuits>>). GossipSub, the DHT and content fetches still show identity and IP. The recipient learns the sender's identity (it is in the envelope; the point is that the network does not learn who talks to whom, not that the peer is anonymous to the peer). Both sides must be in anonymity mode: a recipient in the normal mode, an unknown identity, a recipient without the DM service and a recipient without a prekey bundle all give the same refusal. There is no fallback to a direct connection, ever. A call invitation over this path is rejected (calls follow in wave G).

At every start the node warned in wave F1 (log, CLI stderr, a notice in the browser that can not be dismissed; historical text, replaced in wave F2): _Anonymity mode is incomplete: direct messages travel over circuits, but mail and call media still use direct connections and reveal your IP address, call signalling is not available, and the network mesh, DHT lookups and fetches still show your identity and address._ The browser's status panel shows seven fixed lines (directory entries, direct messages, mail, call signalling, call media, mesh/DHT/fetches, and the guard and circuit counts) and the DM page shows a fixed notice above the input field and a disabled attachment button.

=== Online path

The sender looks the recipient up in the local directory only (`AnonymousDirectory`, built without a DHT: a DHT lookup would show the DHT neighbours the sender's interest together with its IP). With a service descriptor it opens a rendezvous stream (`AnonymityRuntime.connectToService`): the rendezvous point is a path-selector endpoint, the first frame is a HELLO naming the application (`"LNSV" | version | appId`, DM = 1), the service side dispatches by HELLO (`OnionServiceStreamRouter`; MAIL joined in wave F2, CALL is reserved for a later wave) and closes a stream without a valid HELLO after 10 seconds.

The stream carries `type(1) | len(4) | bytes` frames split into messages of at most 910 bytes. The receiver checks the length against the envelope maximum before it allocates, accepts at most 16 envelopes per stream, 120 per minute over all streams, waits at most 10 seconds between the pieces of one frame and keeps a stream at most 10 minutes. The acknowledgement is sent as soon as a frame is complete and was queued, never after the envelope was processed: its timing says nothing about decryption, the acceptance policy or duplicates (no oracle). A full work queue closes the stream without an acknowledgement; the sender then deposits offline and the duplicate suppression absorbs the possible double. A reply does not use the incoming stream: the answering node resolves the sender and builds its own circuit, so no stream is ever tied to an identity. The sender keeps at most 2 streams (one per onion address, 60 seconds idle) and a new onion address always gets a new circuit.

=== Offline path (design M: sealed mailbox items)

Before wave F1 the sender gossiped a signed pointer on the recipient's own topic (subscribing to it links the recipient's identity and IP for every mesh neighbour), the recipient fetched the blob directly from the sender over Bitswap, and the DHT outbox carried provider records and IPNS values with addresses. None of that is acceptable in anonymity mode. The design keeps no address anywhere on the offline path:

. The sender seals the already encrypted envelope to the recipient's X25519 identity key (the one bound into the prekey bundle). An item is always exactly 5,728 bytes: `version(1) | ephemeralX25519(32) | AEAD(notValidAfter(8) | envLen(2) | envelope | zero padding) | tag(16)`; the key is `HKDF-SHA256(X25519(ephemeral, recipient), salt = ephemeral || recipient, info = "LapisNet:anonymous-mailbox-item:v1")`, used once, ChaCha20-Poly1305 with a zero nonce. The item has no sender signature: the ratchet decryption inside is the only proof of who sent it. There is no forward secrecy for this sealing layer (the long-term identity key is the recipient key); the content stays ratchet-protected.
. The sender sends the item through a circuit to a relay (new relay role `MAILBOX_PUBLISH`, see below). The relay checks only the size and announces the item on the one shared GossipSub topic `LapisNet:anonymous-mailbox:v1`.
. Every node in anonymity mode subscribes to that topic and tries to open every item that passes the validator. An item for someone else does not open and is dropped without a trace. Items are tried on a small bounded executor; the topic's global budget (120 per minute) bounds the work.
. The sender announces the item again every 10 minutes (plus or minus 2 minutes), sealed afresh each time, until its lifetime (48 hours) ends: a recipient that is offline now can only receive an item announced after it comes back. This is the honest limit: *offline delivery works only while the sender keeps announcing*. The queue is in memory (lost on restart, as the pointer queue was), at most 256 entries and 32 per recipient, oldest dropped first.

*Why not the alternatives.* IPNS over circuits would need pre-signed records and a new name space (see assumption D of wave D) and would put values with addresses into the DHT. Relays chosen by the recipient as mailboxes (option c of wave C) would need a new field in the service descriptor and make the recipient's relays targets. The chosen design reveals to a subscriber only "this node is in anonymity mode", which its public record shows anyway, and no third party sees sender or recipient.

*The relay role.* `MAILBOX_PUBLISH` and `MAILBOX_PUBLISHED` are accepted only at the last hop of a circuit without another role. The body is exactly 720 bytes: `itemIndex(1) | fragIndex(1) | fragCount(1) = 8 | reserved(1) = 0 | data(716)`. At most 4 items per circuit, 10 items per minute per link and 60 per minute in total (counted when an item starts, before any payload byte is copied); a wrong length, a broken header, a wrong order or an item not completed within 15 seconds destroys the circuit. Only a rate limit is answered with a status; a circuit that continues after it is destroyed. The relay validator on the topic accepts only items of the exact size from an author that is a relay with a current descriptor (otherwise ignore, so a forwarder that is not yet synced is not penalised), ignores duplicates by SHA-256 and a budget of 10 per minute per author and 120 per minute in total.

=== Refusals the user sees

[cols="2,1,3", options="header"]
|===
| Code | HTTP | Meaning
| `recipient-not-reachable-anonymously` | 503 | Unknown, not in anonymity mode, no DM service or no prekey bundle: one answer for all of them. No session is created.
| `anonymity-not-ready` | 503 | No guards yet or the service host is not started (also before the runtime exists at start). No fallback.
| `rate-limited` | 503 | Reserved: circuit builds are being throttled. Today an undeliverable online attempt is queued for the offline path instead, so the browser does not currently produce it.
| `message-too-large-anonymous` | 413 | The content is larger than a sealed item (about 5.4 KB). Checked before anything is encrypted, so no half-sent state or phantom session exists.
| `attachments-unavailable-anonymous` | 409 | Attachments are fetched from the sender's node, which would be a direct connection; refused before storage, cipher or session are touched, and a download of a blob that is not local is refused too.
| `dm-send-failed` | 502 | Any other send failure, in both modes. The exception message (which names peers) is never passed on or logged.
|===

The refusal for the recipient happens before any session work, so a refused first contact leaves no session on the sender's side that the recipient never bootstrapped. A message that could not be delivered online is not re-encrypted for the offline path: the same envelope bytes are sealed, because a second encryption would turn the first message into a `TEXT` envelope that the recipient cannot open.

| 8, 14, 15 | GossipSub envelope, direct connections in general, DHT lookups | *largest remaining leaks*, unchanged (transport key, wave J)

=== Honest limits of wave F1

* The recipient learns the sender's identity; only the network is blinded. Both ends must be in anonymity mode.
* A small anonymity set, Sybil relays and a global passive observer are as in the threat model. Timing correlation is possible, including the pattern of the re-announcement; padding to the cell size is wave H. The fixed 5,728 bytes of the offline items are already uniform.
* Spam on the shared topic can starve its budget (a denial of service limit, not a confidentiality problem). The relay sees that one circuit carried several items, but neither sender, recipient nor content. A relay that is also a subscriber sees every item that passes it, like everybody.
* No per-peer limit exists on the receiving side (the peer is anonymous); the global and per-stream limits are what protects the node.
* Offline delivery needs the sender to keep announcing; the queue is lost on a restart. The sender cannot tell whether an item was delivered, so it announces until the lifetime ends.
* An item is sealed to the long-term X25519 identity key: no forward secrecy for the sender and recipient metadata of the sealing layer.
* A call invitation over this path was rejected in wave F1; wave G accepts it over the circuit door only (the sealed mailbox door still rejects it).
* One selector fix belongs to this wave: a remotely chosen last hop (an introduction point named by a descriptor) that equals the node's primary guard used to produce a path with the guard twice, which the circuit builder refuses. The circuit now enters through the backup guard in that case; without a backup the build reports "insufficient relays" and is retried later.
* Not verified: real NATs and real networks (all tests use loopback nodes with an injected locator that gives each relay a synthetic /16), behaviour under load, an external cryptographic review of the sealing construction, and interoperability with v0.12.0 over the network.

=== Assumptions awaiting confirmation (wave F1)

* *Assumption, confirmation required:* the wave is one unit with ordered commits on one branch (not split into F1a online and F1b offline).
* *Assumption, confirmation required:* the offline design is M (sealed items announced by relays on one shared topic), not IPNS over circuits and not recipient-chosen mailbox relays.
* *Assumption, confirmation required:* the content size in anonymity mode is limited to what fits one sealed item (about 5.4 KB), online and offline alike, and `message-too-large-anonymous` is a fourth refusal code (the design team had fixed three).
* *Assumption, confirmation required:* the sealing key is the X25519 identity key of the prekey bundle, not the (rotating) signed prekey.
* *Assumption, confirmation required:* constants: re-announcement every 10 minutes plus or minus 2 minutes, offline lifetime 48 hours (not 7 days), at most 4 items per circuit, at most 256 pending items and 32 per recipient, topic budgets 120 per minute in total and 10 per relay author, at most 2 cached streams with 60 seconds idle, 30 seconds for one online delivery attempt, relay limits 10 items per minute per link and 60 in total, 15 seconds to assemble an item.
* *Assumption, confirmation required:* attachments are refused in anonymity mode in this wave; whether they travel over circuits later (waves F2 or J) is open.
* *Assumption, confirmation required:* call signalling is refused in anonymity mode until wave G, so a call from or to a node in anonymity mode fails. (Superseded by wave G.)
* *Assumption, confirmation required:* the browser banner text (current text of `ANONYMITY_INCOMPLETE_WARNING`) and the seven fixed lines of the status panel were written for this wave from the facts above; the design team's wording was not available to the implementation and should replace them if it differs.
* *Assumption, confirmation required:* the digest of the prekey bundle in the anonymous record is not compared with the bundle found in the directory (a legitimate bundle refresh would make such a comparison fail spuriously).

[[mail-over-circuits]]
== Mail over circuits (wave V0.10.0-F2, unreleased)

*What it is.* A node in anonymity mode sends and receives mail only through circuits. The mail itself is unchanged: a signed `MessageEnvelope` and a body that is hybrid-ECIES sealed (or, if the user chooses `NONE`, plain), exactly as on the direct path. What changes is the transport and the places a mail may touch. A new module `lapis-net-mail-onion` is the adapter between `lapis-net-mail` (which knows only the `AnonymousMailTransport` and `AnonymousMailInboundSink` interfaces and does not depend on onion code) and `lapis-net-onion-wire`. The browser attaches `MailSender` with `anonymous = true` and `InboxGossip` through `attachAnonymous`; both are built before the anonymity runtime exists, so the transport is installed afterwards and every send fails with `anonymity-not-ready` until then. There is no fallback to the direct path, ever.

In anonymity mode, mail and its attachments no longer use:

* the per-recipient inbox topic (`InboxTopics`): not subscribed, not published on (`attachAnonymous` registers no subscription, `MailSender` never calls `publish`);
* the DHT outbox: `MailSender` is refused a `DhtOutbox` at construction (fail closed), so there are no pointers, no provider records (`MessagingRendezvous`) and no IPNS values for mail;
* the DHT fetcher (`InboxDhtFetcher`): not attached; it would fetch envelope and body from the sender over Nabu/Bitswap, which dials the sender;
* Nabu/Bitswap for attachments: `GET /api/mail/attachment/{cid}` reads the local blockstore only (`getLocal`; the ordinary `get` falls back to provider lookup and Bitswap on a miss), and the sender builds a bundle only from blobs it holds locally.

*What it is not.* Call media still uses direct connections (WebRTC reveals IP addresses to the peer) and call signalling is not available; GossipSub in general, the DHT and other content fetches still show identity and IP address. The recipient learns the sender's identity (it is in the signed envelope). Both ends must be in anonymity mode: a recipient in the normal mode, an unknown identity, a revoked one, one without the MAIL service and one without a prekey bundle all give the same refusal.

At every start the node warns (log, CLI stderr, a notice in the browser that can not be dismissed): _Anonymity mode is incomplete: direct messages and mail travel over circuits, but call media still uses direct connections and reveals your IP address, call signalling is not available, and the network mesh, DHT lookups and fetches still show your identity and address._ The text is the same character for character in `ANONYMITY_INCOMPLETE_WARNING`, in `app.js` and here (a test compares the first two). The browser's status panel keeps its seven fixed lines; the mail line reads _Mail: over circuits (small mail also offline; up to 1 MiB with attachments only while both are online)_. The mail page shows a fixed notice above the compose form.

=== Delivery: two size classes and a hard limit

The class applies to the transport bundle: the signed mail frame plus all attachment blobs.

*Why not the alternatives.*

. _Blob storage at relays, reached over circuits._ This would be a new relay role that stores content. Relays would become storage targets and abuse magnets, and quota, deletion and liability would be open questions. It belongs, if anywhere, to a later wave (I or J).
. _Chunking a bundle over many items._ A 44 KB bundle needs eight items from the topic's global budget (120 per minute for the whole network, shared with direct messages); a few mails would starve everybody else.
. _Pulling from a hidden service of the sender._ The sender would have to run a service and a descriptor of its own for this; it offers nothing that pushing to the recipient's service does not.

=== Keys and one item format for two kinds

The sender looks the recipient up in the local anonymous directory only (no DHT). It needs the `MAIL` capability in the recipient's anonymous record and the recipient's prekey bundle; the sealing key is the X25519 identity key of the bundle, like for direct messages. The mail body stays hybrid-ECIES sealed to the recipient's secp256k1 key as before.

Direct messages and mail share one sealed item format and one topic. The kind is inside the encrypted plaintext, not in a header, because any cleartext header field would tell every observer of the topic which items are mail:

----
version(1) | ephemeralX25519(32) | AEAD( notValidAfter(8) | kind(1) | len(2) | payload | zero padding ) | tag(16)
----

Always exactly 5,728 bytes; `kind` is 1 (DM) or 2 (MAIL); the payload capacity is 5,668 bytes (`SealedMailboxBox`, in `lapis-net-directory`; `SealedMailboxItemCodec` of `lapis-net-dm` is now a thin wrapper). The wire format of the unreleased wave F1 was changed in place; there is nothing to migrate. Two consumers (the direct-message subscriber and the mail subscriber) now listen on the shared topic (`AnonymousMailboxGossip.addConsumer`, at most 4); each opens an item with the same key, which is two key agreements per item at no more than 120 items per minute. An item of the other kind simply does not open.

=== Bundle and stream

A bundle is `version(1) = 1 | frameLen(4) | mailFrame | count(1) | { blobLen(4) | blob }*`. Every length is checked against the remaining bytes and the limits before anything is allocated; the sum is at most 1 MiB and `count` at most 16. CIDs are not transmitted: the receiver computes them from the blob bytes. The stream carries `type(1) | len(4) | bytes` frames as for direct messages, with a new type 3 (bundle) accepted by the receiver; the acknowledgement is the same constant frame (type 2).

The sender opens a *new circuit for every delivery*; there is no stream cache, because mail is rare and this keeps deliveries unlinkable. A delivery runs on a small bounded executor (2 threads, queue 16; if that is full the online attempt is skipped and the mail is queued at once) so that the HTTP thread never waits for a circuit. Every failure path closes the circuit.

The receiver (`OnionMailInboundHandler`) serves at most 4 mail streams at once (a fifth is closed immediately), one bundle per stream, 30 bundles and 8 MiB per minute over all streams, 10 seconds between the pieces of one frame, the complete 5-byte frame header within 15 seconds of the stream's creation, a body rate of at least 1 KiB/s on average (measured from the end of the header, after a 10-second grace period) and 120 seconds per stream. A body must also be able to finish within the stream's lifetime at the rate it has shown so far, so a stream that keeps its slot to the end of its lifetime has to complete its frame and thereby consume budget. The byte budget for the minute is reserved from the declared frame length in the header *before* the body buffer is allocated. A full work queue (8) closes the stream without an acknowledgement; the sender then keeps the mail and retries. The acknowledgement is sent as soon as the frame is complete and queued, never after the acceptance check, and a refused bundle does not end the stream early.

* *Known limitation (slot exhaustion):* peers are anonymous and there is no per-peer limit. An attacker that sends a header declaring a large frame and then a body at just above the minimum rate (roughly 4 KiB/s of upstream for all four streams) keeps all 4 mail stream slots busy until the sweeper cuts them, and the budget reserved for the declared length (up to 4 MiB of the 8 MiB per minute) is held meanwhile. The reservation is returned when such a stream is cut, so the attack costs the attacker no budget, and honest senders retry (every 10 minutes, for 48 hours). The minimum rate and the completion projection make the attack far more expensive than a byte-per-interval trickle, but do not remove it. Planned mitigation: not returning the reservation of a stream cut for being slow, or a cost per stream (proof of work).

=== One entrance, one policy

Both anonymous paths (the stream and the sealed item) end in `InboxGossip.anonymousIngest`, which runs the very stages of the gossip validator: frame decode, `checkEnvelope` (addressing, signature, content binding, the live acceptance policy including the contact bypass, read per message) and `ingestChecked` with the `InboxIndex` duplicate suppression. A test feeds the same frames and gate configurations (Veritas path, Karma, contact bypass, none) through both entrances and compares the decisions. `updateAcceptanceCheck` changes both. Attachment blobs are looked at only *after* a mail was accepted, and only blobs whose own CID is referenced by the decrypted body are stored (everything else is discarded and counted); a refused mail stores nothing. Accepted mail (envelope, body and attachment blobs) is written with `NabuStorage.putUnserved` into a separate local blockstore (`<blockstore>-private`) that Bitswap and the DHT engine never see: a remote peer cannot probe acceptance or presence with WANT_HAVE or GET_PROVIDERS, so storage is no side channel. `get` and `getLocal` still read it locally. Mail that additionally arrives through the public gossip or DHT paths is stored in the served blockstore like any public mail.

=== Refusals the user sees

[cols="2,1,3", options="header"]
|===
| Code | HTTP | Meaning
| `recipient-not-reachable-anonymously` | 503 | Unknown, not in anonymity mode, revoked, no MAIL service or no prekey bundle: one answer for all of them, checked for every recipient before anything is sent (all or nothing; it does not say which recipient).
| `anonymity-not-ready` | 503 | No guards yet or the runtime is not up (also before the transport is installed at start). No fallback.
| `mail-too-large-anonymous` | 413 | More than 1 MiB in total or more than 16 attachments. Checked before the base64 decoding in the API and again in the pre-flight, before any circuit is built.
| `attachments-unavailable-anonymous` | 409 on send, 404 on download | An attachment blob is not held locally (for example a forwarded reference). Anonymity mode never fetches blobs from the network.

The API answers an accepted send the same way whether the bundle was delivered at once or queued. The exception messages of other failures (which may name peers) are never passed on. An attachment is stored in the local blockstore before the pre-flight (that is a local operation); a refused send can therefore leave an orphan blob locally, which is as inert as any unreferenced blob.

[[call-signals-over-circuits]]
== Call signals over circuits (wave V0.10.0-G, unreleased)

*What it is.* A call has two paths. The *signals* (INVITE, ACCEPT, REJECT, HANGUP; they carry the SDP) now travel over circuits for a node in anonymity mode. The *media* (the audio itself) is a direct WebRTC connection and can not be moved onto circuits: the two parties must learn each other's address to connect. This wave therefore moves the signals and is honest about the media. There is no second cryptographic layer: the Double Ratchet session between the two identities stays the only end-to-end layer, and the route is chosen inside `DmSessionManager` exactly like for direct messages. `CallManager` stays transport-independent and `lapis-net-call` still depends on `lapis-net-dm` only (the module graph is unchanged; the multi-node test uses the test fixtures of `lapis-net-dm-onion`).

At every start in anonymity mode the node warns (log, CLI stderr, a notice in the browser that can not be dismissed). Since wave H there are four fixed texts, chosen by the call-media option and by `--anonymity-padding`. Calls off, padding standard (the default): _Anonymity mode is incomplete: direct messages, mail and call signals travel over circuits, padded to size classes with cover cells towards the guard; this does not hide traffic from an observer who sees both ends; calls are off because call media would reveal your IP address; the network mesh, DHT lookups and fetches still show your identity and address._ Calls allowed with `--anonymity-allow-call-media=true`, padding standard: _Anonymity mode is incomplete: direct messages, mail and call signals travel over circuits, padded to size classes with cover cells towards the guard; this does not hide traffic from an observer who sees both ends; but calls are allowed (--anonymity-allow-call-media=true) and call media connects directly: every call reveals your IP address to the other party and to network observers; the network mesh, DHT lookups and fetches still show your identity and address._ Calls off, `--anonymity-padding=off`: _Anonymity mode is incomplete: direct messages, mail and call signals travel over circuits; padding is off (--anonymity-padding=off), so message sizes and timing are visible to an observer of your connection; calls are off because call media would reveal your IP address; the network mesh, DHT lookups and fetches still show your identity and address._ Calls allowed, padding off: _Anonymity mode is incomplete: direct messages, mail and call signals travel over circuits; padding is off (--anonymity-padding=off), so message sizes and timing are visible to an observer of your connection; but calls are allowed (--anonymity-allow-call-media=true) and call media connects directly: every call reveals your IP address to the other party and to network observers; the network mesh, DHT lookups and fetches still show your identity and address._ The four texts are the same character for character in `ANONYMITY_INCOMPLETE_WARNING`, `ANONYMITY_INCOMPLETE_WARNING_CALL_MEDIA_EXPOSED`, `ANONYMITY_INCOMPLETE_WARNING_PADDING_OFF`, `ANONYMITY_INCOMPLETE_WARNING_PADDING_OFF_CALL_MEDIA_EXPOSED` (selected by `anonymityIncompleteWarning`), in `app.js` and here (a test compares them). The browser status panel says _Call signals: through circuits_ and, depending on the option, _Call media: off (would reveal your IP address)_ or _Call media: direct connection, your IP address is visible to the other party and to network observers_, and, since wave H, an eighth line about padding.

=== Signal path

* `DmSessionManager.sendCallSignal` in anonymity mode encrypts with the existing ratchet session (a call never begins a first contact: without a session the send fails as before) and hands the envelope to the rendezvous stream with a delivery deadline of 15 seconds.
* *Online only.* A call signal is never deposited as a sealed mailbox item: if the recipient is not reachable (no service descriptor) the send fails before any ratchet step is consumed, with the fixed error `call-signal-path-lost`. The sealed mailbox door of the inbound sink still rejects `CALL_SIGNAL` before any decryption, exactly as the offline poller does on the direct path; only the circuit door accepts it.
* A signal arriving through the circuit door goes through the same inbound pipeline as every other message: session requirement, authenticated decryption, replay suppression and the acceptance rules (`classifyQuarantinedSender`). There is no bypass and no new policy path. `marksAcceptance` is passed through unchanged.
* *No reply route.* The V0.9.19 reply route (answering over the INVITE's open connection) is a direct-connection concept. In anonymity mode inbound signals carry no route and `sendCallSignal` refuses one.
* *Size.* A call signal is capped well below the envelope limit of the circuit stream. It is NOT subject to the 5,668-byte limit of a sealed mailbox item, because it never uses one.
* *Timing.* The 15 second signal deadline is at most the call dial timeout, so the 20 second media shutdown wait of `CallManager.stop()` stays valid. A lost path ends the call locally as `CIRCUIT_LOST`; this reason is local only: it is never encoded (`CallSignalCodec.encode` refuses it) and a wire value of 10 is rejected as malformed. There is no wire format change; older nodes are not affected.

=== The media path and the default

Calls are *off* in anonymity mode by default (`CallMediaPolicy.DISABLED`): `placeCall` throws before any hand-off, the HTTP API answers `409` with the code `CALL_MEDIA_DISABLED_IN_ANONYMITY_MODE` (no network traffic, no history entry), and an inbound INVITE is dropped silently (see below). `--anonymity-allow-call-media=true` (environment `LAPISNET_ANONYMITY_ALLOW_CALL_MEDIA`, browser file key `anonymityAllowCallMedia`, only valid with `--anonymity=on`, restart required) selects `CallMediaPolicy.EXPOSED`.

With the option, a call reveals your IP address to the other party *and to network observers*. Therefore the node enforces a confirmation for every call, both in the HTTP API (`409` with `MEDIA_EXPOSURE_CONFIRMATION_REQUIRED` unless the body says `confirmMediaExposure: true`) and in `CallManager` itself (`placeCall` and `acceptCall` throw without it). The browser asks with an alertdialog before each outgoing call and before accepting each incoming one; the confirmation is never stored, Enter and Escape never accept or reject a ringing call in this mode, and the desktop notification carries no peer information. A missing `callMedia` field in the status is treated like `exposed` (fail safe).

*Reduced SDP, not anonymity.* With the option the SDP is reduced before it leaves the node and again when it arrives, as text only (the PeerConnection is untouched): only `typ host` UDP candidates with a public unicast address survive, at most one per component (IPv4 preferred); private (RFC 1918), loopback, link-local, CGNAT, ULA, multicast, IPv4-mapped and `.local` candidates are dropped, and the connection, RTCP and origin addresses are replaced with the placeholder `0.0.0.0`. No STUN, no TURN and no TCP is used. This keeps your LAN topology out of the signal and limits the exposure to one address per component; it does not hide that address.

=== Refusals the user sees

* `409 CALL_MEDIA_DISABLED_IN_ANONYMITY_MODE` (calls off) and `409 MEDIA_EXPOSURE_CONFIRMATION_REQUIRED`; the page shows fixed German texts and never the server's wording.
* `CIRCUIT_LOST` ("Verbindung abgebrochen") when the signal path failed during setup. "Recipient not reachable anonymously" is deliberately shown the same way: the same answer can not be told apart.

=== What the caller observes

The transport acknowledgement of the circuit stream is constant and is sent before any processing. A recipient that blocks the caller (acceptance rule), has calls off, or simply does not answer produces the same observation at the caller: no reply at all, then `RING_TIMEOUT`. In particular an INVITE to a node with calls off is dropped *before* the BUSY check: no REJECT and no BUSY is sent. The capability bits published in the anonymous directory entry are unchanged (`DM`, `MAIL`), so the option is not fingerprintable there.

=== Honest limits of wave G

* A call is *not anonymous*: the media reveals the IP address. Only the signalling is hidden. If you need anonymity, do not turn the option on.
* A small anonymity set, Sybil relays and a global passive observer are as in the threat model. Timing correlation between the signals and the start of the media is possible until wave H.
* Without a public address on at least one side the call fails (no STUN, no TURN, no relayed media; on the same LAN it may fail as well, because private candidates are dropped).
* The caller learns nothing about why a call was not answered; the callee learns the caller's identity. Both ends must be in anonymity mode, there is no fallback.
* One global limit of 30 INVITEs per minute applies in anonymity mode in addition to the per-sender limit, because senders are cheap over circuits.
* Calls share the rendezvous stream limits (per-minute envelope cap and receive queue) with direct messages; a call produces at most about four signals.
* *Not verified:* real NATs and networks, real WebRTC media in anonymity mode (the filter drops loopback candidates, so this can not be tested on one host), behaviour under load, interoperability with v0.12.0 over the network, an external cryptographic review. The multi-node test runs on loopback with six relays, an injected locator with synthetic networks and a fake media engine.

=== Assumptions awaiting confirmation (wave G)

* *Assumption, confirmation required:* ICE candidates are reduced to public host candidates, not server-reflexive ones. The design paper asked for srflx only, but the code deliberately has no STUN ("no third party") and the SDP policy rejects srflx; a STUN server would be an additional observer. Alternative for a later wave: an operator-configured STUN server. The temporary-IPv6 rule can not be applied reliably on SDP text; the mitigation is "IPv6 only when no IPv4 candidate exists".
* *Assumption, confirmation required:* the constants: signal delivery deadline 15 seconds, global limit 30 INVITEs per 60 seconds, connect timeout 45 seconds with the option.
* *Assumption, confirmation required:* the capability bit for calls is not published, so the option is not visible in the directory and the "calls off" and "blocked" cases stay indistinguishable. A call to a node without the option simply rings out.
* *Assumption, confirmation required:* the reason "recipient not reachable anonymously" is shown as `CIRCUIT_LOST` to the caller, because the answer must not differ.
* *Assumption, confirmation required:* "at least four nodes and three relays" was read as four user nodes plus relays; the path policy needs more than three relays to build rendezvous paths, so the test uses six, as the F1 and F2 tests do.
* *Assumption, confirmation required:* the observer test checks that each node is connected to relays only (not to the other party); a dedicated test hook for the guard identities was not added, so "only guards" is checked as "only relays".
* *Assumption, confirmation required:* the browser wording (band, confirmation, labels) was written from the facts above; the design team's wording should replace it if it differs.

[[padding-and-timing]]
== Padding and timing protection (wave V0.10.0-H, unreleased)

*What it is.* Four measures against a LOCAL observer of the connection between a node in anonymity mode and its guard (an ISP, a shared network, the guard itself), controlled by `--anonymity-padding=standard|off` (default `standard`, also `LAPISNET_ANONYMITY_PADDING` and `anonymityPadding` in `browser.properties`; valid but without effect while `--anonymity=off`). *It is not protection against a global passive observer* who sees both ends of a circuit: end-to-end correlation of timing and volume stays out of scope. *Compatibility:* both ends of a stream must run wave H. With the default `--anonymity-padding=standard` a sender always uses the padded frame types 4 (`ENVELOPE_PADDED`) and 5 (`MAIL_BUNDLE_PADDED`). A receiver on master or any earlier release (including v0.10.0-G) does not know them and closes the stream on the first header ("unexpected frame type"); the sender gets no acknowledgement, so direct messages, call signals and online mail on the circuit path from a wave H node to such a node fail without a diagnostic (mail then falls back to the mailbox or retry path). Nothing negotiates a capability: there is no version field in the service descriptor or the link handshake. Until both nodes run wave H, a wave H node that talks to older nodes must use `--anonymity-padding=off` (unpadded frames, which every build accepts). A receiver of wave H still accepts the unpadded types.

=== Size classes

On a rendezvous stream every message is one 1024-byte cell (929 byte end-to-end blob, at most 910 bytes of data). The length of a direct message, call signal or mail bundle therefore shows only as the NUMBER of cells. The sender pads the frame with zero bytes, inside the end-to-end encrypted stream, up to the next class: the smallest power of two of cells that holds it, capped at the cell count of the largest legal frame. Padded frames carry their own type (`ENVELOPE_PADDED` = 4, `MAIL_BUNDLE_PADDED` = 5); the receiver still accepts the unpadded types (a sender with padding off).

[cols="2,5", options="header"]
|===
| Kind | Classes (cells)
| Direct message and call signal (frame up to 65,715 bytes)
| 1, 2, 4, 8, 16, 32, 64, 73
| Mail bundle (frame up to 1 MiB + 16)
| 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 1153
|===

A frame of `n` bytes needs `ceil((5 + n) / 910)` cells. A normal text message stays at one cell and costs nothing; the overhead is below a factor of two. The padding is derived deterministically from the authenticated length, so a peer cannot choose it. The receiver counts and discards the padding bytes and never inspects them (no padding oracle). The acknowledgement is sent only after the LAST padding byte, so its timing does not reveal the real length; a sender that stops short of its class is never acknowledged and the idle sweep closes the stream. The memory quota sees the real length; the rate check (`bodyTooSlow`) counts the whole class.

Fixed already before this wave (checked by tests): the directory publish message (one cell, answer one cell), the mailbox item (always 5,728 bytes = 8 fragments), the introduce and rendezvous handshake, and the acknowledgements.

=== Cover cells

A node sends a cover cell on a randomised schedule: the next one follows after `U(0.5, 1.5)` times 4 s. The cover cell is a relay `DROP` addressed to hop 2 (the middle relay) of a randomly chosen own, already built circuit, never to the guard (the guard would recognise it and could drop it). A relay discards a `DROP` without any answer, keeps no state for it and does not tear down a circuit that has a role (introduction, rendezvous, publish); a `DROP` counts against the per-circuit cell limit (2,000 per second) and the per-link limit, like every cell. No relay code was added; tests pin this. Relays never create cover, so cover cannot amplify. A cover cell is skipped when no circuit is open: cover is never a reason to build one. A token bucket caps cover at 1 KiB per second (burst 16 cells); real traffic never draws from it and is never delayed by it. Cover is sent in one direction only (client to relay); the return direction stays unpadded.

=== Time slices

Outgoing cells are not written when they are produced but at the next boundary of a 50 ms slice (per link, in order), at most as many per boundary as the link's write queue holds. A slice with real cells is followed by at least three slices with one cover cell each, so the end of a burst is not visible at slice resolution. A single timer entry exists only while cells or a tail are pending; an idle node runs no steady timer, and no thread is added (the existing timer thread of the link manager is used). Only an anonymity-mode node installs the shaper, and such a node never relays for others (the modes exclude each other), so only its own cells are shaped.

Latency budget: at most one slice (50 ms) per send step at the own guard link. A direct message or call signal with its acknowledgement: up to about 100 ms more (sender and receiver each shape once). Establishing a rendezvous: about six own send steps, up to about 300 ms. A large mail is paced by the write queue (at least about 5 MiB per second) and is not slower than 1153 cells divided by the queue.

=== Warm circuit pool

Up to two circuits (half of the governor pool of four) are built in advance, one at a time, only when the governor admits a build at once (the rate limit and the backoff of failed builds apply; one token is always left for real builds). The 30-second maintenance round starts at most one such build, so there is no dial storm. A warm circuit is handed out once, for a rendezvous (the circuit's last hop becomes the rendezvous point), a mailbox publish or a directory publish; the governor slot moves to the new purpose and the circuit keeps its age. An idle warm circuit older than six minutes is closed (relays sweep at ten minutes). A real build that finds the pool full closes an idle warm circuit first, so the pool never makes a real build fail. Introduction circuits are not pre-built (their last hop is chosen by the service). This replaces the sentence "every build goes to a new circuit" by: a warm circuit serves exactly one use; there is still no reuse.

=== Bandwidth budget

Expected cover: about 0.25 cells per second, i.e. about 256 B/s at the guard link (about 21 MiB per day), plus burst tails (three cells after each active slice). The cap is 1 KiB/s (about 84 MiB per day). The relay side pays about twice that, because the middle relay receives each cover cell too. Real traffic is not capped. There is no mobile or battery mode in the repository; whoever needs one uses `--anonymity-padding=off`.

=== Leak inventory after wave H

Closed or weakened: the length of a message inside its size class; the exact timing of sends at the guard link (hidden in a 50 ms slice, with a cover tail); the build of a circuit at the moment of a rendezvous or publish (warm pool).

Still open:

* the size class itself (a long message against a short one), and coarse periods of activity;
* the return direction (relay to client) has no cover and no slicing;
* the number of mailbox items per circuit (one to four) and the one acknowledgement per item;
* the build of the introduction circuit of a rendezvous (not pre-built);
* GossipSub, DHT lookups and fetches (wave J) and WebRTC media;
* a global passive observer, a small anonymity set, correlation by provoked teardown.

=== Honest limits of wave H

* The measures are verified on loopback and with a manual clock, not on real networks, NATs, under load, or against a real observer on the wire. No external cryptographic or traffic-analysis review has taken place.
* The guard itself sees the cover cells it forwards and can tell cover from payload by the cell count it relays beyond hop 1 only if it colludes with hop 2.
* A node that sends nothing for a long time still shows cover at a low rate; a node with padding off shows its real pattern.

=== Assumptions awaiting confirmation (wave H)

* *Assumption, confirmation required:* cover defaults: mean 4 s with plus or minus 50 % jitter, burst tail of three slices, cap 1 KiB/s with a burst of 16 cells, slice 50 ms (about 21 MiB per day expected, about 84 MiB per day at most at the guard link, twice that in the network).
* *Assumption, confirmation required:* the cover cell is addressed to hop 2, so the guard cannot recognise it. Alternatives: the last hop (more relay cost) or link-level padding (cheap, but visible to the guard).
* *Assumption, confirmation required:* no cover or padding in the return direction; a balance would need negotiated padding through the guard and per-circuit relay state, which contradicts "a DROP keeps no state".
* *Assumption, confirmation required:* mailbox items are not padded to a fixed count; dummy items would use up the relay rate limits (10 per minute per link).
* *Assumption, confirmation required:* the introduction circuit is not pre-built.
* *Assumption, confirmation required:* the warm pool stays on with `--anonymity-padding=off` (it is not padding and its cost is low).
* *Assumption, confirmation required:* size classes are powers of two (overhead below 2x); powers of four would give fewer classes and up to 4x overhead.
* *Assumption, confirmation required:* `--anonymity-padding` offers only `standard` and `off`; the cover budget is fixed in the code.
* *Assumption, confirmation required:* the eighth status line of the browser panel and its wording were written by the implementation; the design team's review of the wording is outstanding.

[[sybil-simulation]]
=== Sybil simulation

*What it is.* `SybilPathSimulation` (test sources of `lapis-net-onion-wire`) drives the real `OnionPathSelector`, `GuardManager` and path policy, without any network and without a mock, over a synthetic population of 100 relays in which an adversary controls a share `f` of the relays. Per client, a fresh guard manager chooses a guard; the client then builds 20 circuits. Measured: the chance that the guard is adversarial (`P(G)`), that the drawn last hop is adversarial (`P(E)`), that both are (`P(G and E)`), that at least one of the 20 circuits has both, and that the guards of two independent clients (the two ends of a conversation) are both adversarial. Each cell reports the proportion with its 95 % Wilson score interval. `f^2` is shown for comparison only (what a uniform choice without any policy would give).

*Model assumptions (assumptions, not facts).*

* 100 relays; the adversary controls 5, 10, 20 or 33 percent.
* Honest relays: reputation spread evenly over 0.5 to 0.95, every tenth without history; each in its own /16 network (a second variant puts them into 20 shared /16 networks).
* The addresses are self-declared (see <<path-policy>>), so the adversary can claim any network: `DISTINCT_V4_16` (every adversarial relay in its own /16) is the realistic attack; `SAME_V4_16`, `SAME_V6_48` and `NO_ADDRESS` show what the diversity rule alone achieves.
* The adversary's reputation is either none (`NEW`) or the maximum (`MAXIMAL`). Madli is a weight and never a gate.
* Seed `20261027`; the run is deterministic.

*Hard guarantees of the policy (asserted by `SybilPathSimulationTest` in `check`).* If the adversary's relays share one /16, one /48 or have no address, no circuit has an adversarial guard and an adversarial last hop at the same time: two relays of one network never share a path, and at most one relay of unknown network is allowed. With distinct declared addresses there is no such guarantee.

*Not modelled.* A global observer; timing correlation beyond the guard-and-exit pair; circuits with a prescribed last hop (introduction and rendezvous circuits); churn; the guard lifetime over time (the adversary's chance to be chosen at some point in 30 to 60 days); an adversary that also manipulates the honest relays' reputation.

*Honest framing.* The figures are a simulation of this code under these assumptions, not a guarantee and not a measurement of a real network. They are an input for the external review (see link:external-review.adoc[external-review.adoc]), not its result.

*Reading the table.*

* With every adversarial relay in one /16, one /48 or without an address, `P(G and E)` is zero in all cells: the diversity rule works as designed. But the adversary does not have to cooperate with it: addresses are self-declared, so the realistic row is `DISTINCT_V4_16`.
* With distinct declared addresses and no history (`NEW`), the adversary stays far below `f`: the cap for relays without history holds (at 33 % of the relays, `P(G)` is 3.65 %).
* With distinct declared addresses and the maximal reputation, the adversary is chosen far more often than its share: at 33 % of the relays `P(G)` is 43 % and `P(G and E)` 18 %, against 10.9 % for a uniform choice; at 20 % it is 27 % and 7 %. Madli is a weight, so a Sybil adversary that obtains a high reputation turns the weighting to its advantage. The simulation takes the reputation as given; how expensive it is to obtain, and whether the reputation of honest relays can be inflated or deflated, is not modelled.
* The guard is chosen once and kept for 30 to 60 days, so `P(any G and E ...)` is close to `P(G)` in the rows with a maximal reputation: once the guard is adversarial, an adversarial last hop appears within 20 circuits almost surely (43.09 % against 43.09 % at 33 %). The longer a guard is kept, the more this applies.
* Spreading the honest relays over only 20 /16 networks changes the figures little.
* No circuit ended as "insufficient relays".

=== Stream protocol `/lapis/onion/1.0.0`

Every cell is exactly 1024 bytes on the stream. There is *no length field*: the frame decoder cuts at 1024 bytes, so a frame size can never be attacker-chosen (the off-by-length class of bug found in the length-prefixed DM codec in 2026-08 cannot occur). A started frame that does not complete within the handshake window (10 s) closes the link (slowloris); an inbound link must deliver a first cell within the same window; the read-idle timeout is 5 minutes. Each link has a cell rate limit (4000 cells/s) and a write-queue cap (256 cells, about 256 KiB): exceeding either closes the link, nothing is ever buffered without bound. Deliberate simplification: back-pressure does not propagate to the previous hop's link (no coupling of circuits, no deadlock); an overfull link is closed and the circuits on it die.

Links are limited to 64 in total (reserved with a compare-and-set loop before a stream is accepted) and to 2 inbound links per remote peer. A quarter of the slots (`reservedOutboundLinks`, `maxLinks/4`) is reserved for outbound links, so idle inbound links can never prevent a relay from opening the link of its own EXTEND. An inbound link that carries no circuit is closed after 30 s (`inboundIdleWithoutCircuitTimeout`) unless it keeps delivering useful cells: only a cell processed on an existing circuit or an accepted CREATE counts as activity; PADDING and cells (RELAY, DESTROY, CREATED) for unknown circuit ids do not. A link can be reused in either direction (an inbound link carries an extend to the same peer; the remote peer id always comes from the Noise-authenticated connection, never from payload bytes), and concurrent dials to one peer share one dial. A link that is admitted but not yet ready is reused too (the caller waits for it; if it ends first the request fails, there is no silent re-dial). When two peers dial each other at the same moment, the link opened by the side with the lower peer id (compared as unsigned bytes) is canonical: a loser that was never handed out is closed at once, one that was already in use is retired by the idle check once its circuits are gone, and new requests prefer the canonical link, so the pair converges on one link without cutting live circuits. Link ids are random 64-bit values; the mapping from peer to link exists only inside the manager and is never logged. A Circuit Relay v2 connection may carry a link, but a CR-v2 relay is not an onion hop.

=== Onion keys: persistence and rotation

A relay's onion key lives 7 days; after 4 days a new key is generated and the old one stays valid as the `previous` key for the remaining 3 days (the overlap), so circuits built against a not-yet-republished descriptor still succeed. Persistence (`<data dir>/onion-relay.onionkeys`) is encrypted with the keystore passphrase: AES-256-GCM, key from Argon2id (64 MiB, 3 iterations), fresh random salt and nonce for every write, the header including the identity public key is the associated data, so the file is bound to its identity. The write is atomic (`0600` temp file, `fsync`, atomic move), the directory `0700`. Loading verifies every key binding; an expired key is dropped, a manipulated or foreign file, a wrong passphrase or out-of-range KDF parameters make the relay mode refuse to start (the message names the path, never any content). Without a keystore passphrase the keys exist only in memory (a warning is logged) and are lost on restart. The last used descriptor sequence number is persisted too; after a data loss the sequence restarts at the current epoch second, so peers do not reject new descriptors as replays.

=== Relay descriptor

`OnionRelayDescriptor` is a relay's signed, publicly enumerable advertisement: identity, its libp2p transport key (`IdentityBinding` plus an Ed25519 possession proof with its own domain tag, so an identity cannot point at a stranger's peer id), the `OnionKeyBinding`, a sequence number and a validity of at most 24 hours (never beyond the onion key). Fixed 379-byte encoding, no length field, exact length checked first, a reserved family byte that must be zero (families are not part of this wave). `PeerCapability` gets no new bit, because v0.12.0 readers reject unknown bits; the descriptor alone signals the relay property.

* *Gossip* topic `LapisNet:onion-relay-descriptor-gossip:v1`: size check, decoding and an index pre-check (duplicates, replays and stale sequence numbers are `IGNORE` and cost no budget), then a per-author (6/min) and a global (60/min) rate limit whose excess is `IGNORE` (an honest forwarder must not be penalised), then full verification; invalid is `REJECT`, duplicates, replays and capacity refusals are `IGNORE`. Logging has counters only: no peer id, no identity, no bytes.
* *Index* (`OnionRelayDescriptorIndex`): one current descriptor per identity, strictly increasing sequence numbers, high-water marks that survive eviction (bounded LRU), equivocation at the same sequence is ignored, capacity 1024; a full index never evicts a valid entry for a stranger.
* *Known limitation (Sybil):* identities are free, so an attacker can sign valid descriptors with fresh keys. About 61 such descriptors per minute exhaust the global budget at every node (honest new or rotated descriptors are then ignored), and about 17 minutes of this fill the index to its capacity of 1024, after which the attacker holds it permanently by refreshing, because a full index never evicts and updates of tracked identities are always accepted. Descriptors with random signatures only exhaust the budget at direct neighbours (REJECT is not forwarded, gossip scoring penalises the sender). Admission is not bound to a cost yet; planned mitigations are a cost per index slot (known peer record or DHT presence, proof of work, or Madli weight) or a fair per-identity or per-mesh-peer budget instead of one global bucket.
* *DHT fallback:* the descriptor is an optional part (flag `0x08`) of the node's existing directory value, because one Ed25519 key has exactly one IPNS name. It is verified with the same function as on the gossip path and must belong to the value's identity and binding. Additionally relays announce themselves as providers under the fixed key `LapisNet:onion-relays:v1` and `discoverOnionRelays` resolves the providers; this key is public, its provider set is eclipse-prone, and a result is a hint only (every descriptor is fully verified). If peer record, prekey bundle and descriptor together exceed the value limit, outbox entries are dropped first, never the descriptor or the peer record.

=== Relay mode

`--onion-relay=true` (default off). Off: no protocol handler is registered (a dial of `/lapis/onion/1.0.0` fails multistream negotiation), no onion key is created, no descriptor is published, no key file exists. The descriptor index and its gossip are attached on every CLI node (bounded, read-mostly) so a node can later choose relays. On: the node answers CREATE/EXTEND, publishes its descriptor immediately, re-announces it every 6 hours (and at once after a rotation) and checks the rotation every hour; the DHT copy is written by the node's single IPNS writer (`HeadlessSelfPublisher`), which receives the descriptor, because a second writer would overwrite the peer record.

An EXTEND is executed only towards a relay that has a verified descriptor in the local index and never with a client-supplied link specifier (a non-empty specifier is refused in this wave), so an extend cannot make a relay connect to an arbitrary host. There is no exit service: DATA delivered to a relay is answered with END. A relay's own link cap, circuit cap (1024), creation rates and cell rates apply; pending extends are bounded and time out after 10 seconds.

The relay quality tracker is local and bounded (1024 identities, day buckets, 7 days). It counts extend attempts, reachable links and early destroys with `PROTOCOL` or `AUTH_FAILED` per target relay. It is never published, there is no MadliGossip connection, and it cannot attribute a failure to a specific hop; turning it into Madli metrics is wave E.
